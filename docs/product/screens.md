# 화면 명세

사용자 화면과 관리자 화면을 만들기 전에, 무엇이 필요한지를 한곳에 정리하는 문서다.
디자인 도구에 시안을 맡기기 전에 이 문서의 칸을 채우는 것이 목적이다. 화면별 명세는 A1~A12, B1~B10 을 채웠다(아래 [화면별 명세](#화면별-명세)).

- 기준: `main` `f29bfd9` (2026-10-18). A 는 `auth-server`, `billing-server`, `notification-server`, B 는 `game-server` 를 이 시점에 읽었다
- 서버의 API 가 **있는지**를 화면마다 적는다. "있음"은 지금 서버가 그 기능을 갖췄다는 뜻이고, 화면의 완성 여부와는 별개다.
- 서비스 구조는 [서비스 구조 명세](../architecture/services.md), 제품 방향은 [플랫폼과 제품 방향](platform.md).

## 쓰는 순서

1. 서비스와 핵심 경험, 첫 출시 범위
2. 사용자 흐름(가입에서 플레이, 중단, 이어하기까지)
3. 화면 목록과 목적
4. 핵심 화면의 칸 채우기(아래 [화면마다 채울 칸](#화면마다-채울-칸))
5. PC 와 모바일 초안
6. 실제 서버에 붙여 보며 검증. 스마트폰으로 한 판을 끝까지 해 본다.
7. 앱으로 감쌌을 때의 검증(로그인 유지, 앱 복귀, 재접속, 가상 키보드, 뒤로 가기)

페이지, 탭, 팝업, 패널을 나눠서 센다. 화면 수는 이 구분 없이 세지 않는다.

## 서비스와 핵심 경험

| 서비스 | 핵심 경험 | 상태 |
| --- | --- | --- |
| TRPG | AI 가 진행하고 서버가 규칙과 상태를 관리하는 텍스트 TRPG. 상태, 소지품, 퀘스트, 주사위가 플레이에 실제로 영향을 주고 화면에서 분명히 보인다 | 서버 대부분 구현 |
| chat | 캐릭터 하나와 1:1 로 대화한다. 내가 누구인지(페르소나)와 상대가 나를 기억하는지가 중심이다 | 계획 |
| story | 세계관 안에서 여러 인물을 만나며 이야기를 즐긴다. 인물마다 호감도가 있고, 장소를 옮기고, 소지품을 직접 보고, 엔딩이 있다 | 계획 |

- 세 서비스는 로그인, 잔액, 충전을 공유한다. 공통 껍데기를 한 번 만든다.
- 화면에 보이는 상태(HP, 소지품, 호감도, 장소)는 서버의 값이다. 모델에게 묻지 않고 화면이 서버에서 읽는다.

## 사용자 흐름

각 흐름을 단계와 화면으로 풀어 쓴다. 지금은 뼈대만 적는다.

| 흐름 | 단계 |
| --- | --- |
| 가입에서 첫 플레이 | 가입(이메일 인증) → 로그인 → 본인인증(환영 크레딧, 성인 확인) → 탐색 → 선택 → 플레이 |
| 충전 | 잔액 확인 → 충전 → 결제창(토스) → 완료 → 내역 → (7일 안) 청약철회 |
| TRPG 한 판 | 시나리오 탐색 → 소개 → 테이블 만들기 또는 참가 → 캐릭터 → 라운드(선언, 판정, 서술) → 중단 → 이어하기 |
| chat 한 번의 대화 | 캐릭터 탐색 → 소개 → 시작 상황과 페르소나 고르기 → 대화(스트리밍) → 다시 생성 → 중단 → 이어하기 |
| story 한 번의 이야기 | 세계관 소개 → 시작 → 장소와 인물 → 대화와 이동 → 호감도와 이벤트 → 엔딩 |
| 신고 | 글, 캐릭터, 시나리오 보기 → 신고 → 접수 확인 |
| 보호자 동의(미성년 결제) | 본인인증에서 나이 확인 → 결제 시 보호자 안내 → 보호자 인증과 동의 → 결제 알림 |

## 화면마다 채울 칸

핵심 화면은 아래 칸을 모두 채운다.

1. 목적과 그 화면에 오는 경로
2. 보여 주는 정보와 그 출처(어느 서버의 어느 값)
3. 할 수 있는 행동과 버튼의 동작
4. 버튼이 비활성인 조건(권한, 크레딧, 인원, 상태)
5. 로딩, 빈 화면, 오류, 연결 끊김, 크레딧 부족
6. PC 와 모바일에서의 배치 차이
7. 첫 출시에 들어가는지, 이후인지

## 화면별 명세

"화면마다 채울 칸"의 일곱 칸을 화면마다 채운다. 서버 쪽 값은 `game-server` 의 응답 모양에서 읽은 것이다. 코드로 확인하지 못한 것은 각 화면 끝의 "확인할 것"에 모았다.

### A1 첫 화면·탐색

**1. 목적과 경로**

서비스(TRPG, chat, story)를 고르고, 공개된 것을 둘러본다. 로그인 전의 첫인상이기도 하다.

- 오는 경로: 앱 첫 실행, 주소. 로그인한 사람은 마지막으로 쓴 서비스로 곧바로 가게 할 수 있다.
- 나가는 길: TRPG 는 B1(시나리오 탐색), 가입·로그인은 A2.

**2. 보여 주는 정보와 출처**

| 영역 | 내용 | 출처 |
| --- | --- | --- |
| 서비스 고르기 | TRPG, chat, story | chat 과 story 는 계획이다. 첫 출시에는 TRPG 하나를 앞에 두고 나머지는 "준비 중"이거나 숨긴다 |
| 이어하기 | 내가 앉아 있는 테이블 | `GET /tables`(B3) |
| 공개된 시나리오 | 최근 공개한 것 몇 개 | `GET /listings?limit=` (B1) |
| 헤더 | 잔액, 알림 배지, 내 정보 | A6, A10, A5 |

**3. 할 수 있는 행동 / 4. 비활성**

서비스 카드를 눌러 들어가기, 이어하기, 로그인. 로그인 전에는 위의 서버 값을 읽지 못한다(**공개 목록도 401**).

**5. 상태**

로그인 전(소개와 가입 유도), 로그인 후 테이블이 없음("첫 테이블 만들기" 또는 B1), 이어할 테이블이 있음.

**6. PC 와 모바일, 7. 첫 출시**

초안이다. 들어간다(필수 공통 묶음). 서버에 있는 것으로 만들 수 있는 최소가 위 표다.

**확인할 것**

- **로그인 전에 보여 줄 공개 시나리오 목록은 서버가 막고 있다**(401). 로그인 전 화면에서 목록을 보이려면 서버에 열 경로가 필요하거나, 첫 화면을 소개문과 가입 유도로만 둔다. (이슈 #428)
- chat 과 story 가 첫 출시에 없다면 카드를 숨길지 "준비 중"으로 보일지 정한다.
- 서비스마다 토큰의 `aud` 가 다르다([서비스 구조 명세](../architecture/services.md)). 서비스 사이를 오갈 때 다시 로그인하지 않게 하려면 토큰 발급이 `aud` 를 어떻게 싣는지 인증 세션과 확인한다.

### A2 가입, 로그인

**1. 목적과 경로**

가입하고, 로그인하고, 비밀번호를 잊거나 바꾼다. 모두 인증 서버(`/api/v1/auth/`)가 맡는다.

- 오는 경로: A1 첫 화면, 로그인이 필요한 화면에서 401 을 받았을 때. 로그인이 끝나면 오던 화면으로 돌아간다.
- 나가는 길: 가입 직후와 로그인 직후는 A3 본인인증(안 했으면 안내), 아니면 A1.

**2. 입력과 출처**

가입은 세 단계, 로그인은 두 단계다. 둘 다 이메일 인증 코드(6 자리)를 거친다.

| 단계 | 호출 | 보내는 것 | 오는 것 |
| --- | --- | --- | --- |
| 가입 1 | `POST /signup` | `email` | 202. 새 이메일이든 이미 가입된 이메일이든 같은 응답이다. 코드는 5분 유효, 1분에 1통·1시간에 5통까지 |
| 가입 2 | `POST /signup/verify` | `email`, `code` | 200 과 `signup_ticket`(30분 유효). 코드가 틀리면 400, 다섯 번 틀리면 그 코드는 버려진다 |
| 가입 3 | `POST /signup/complete` | `signup_ticket`, `username`, `nickname`, `password`, `age_over_14`(`true`) | 201. 로그인할 수 있다 |
| 로그인 1 | `POST /login` | `username`, `password` | 202 와 `login_ticket`(10분 유효). 가입한 이메일로 코드가 간다 |
| 로그인 2 | `POST /login/verify` | `login_ticket`, `code` | 200 과 `access_token`, `token_type`, `expires_in`. refresh 쿠키가 설정된다 |
| 코드 다시 받기 | `POST /login/resend` | `login_ticket` | 코드 재발송 |
| 비밀번호 잊음 | `POST /password/reset` → 메일 링크 → `POST /password/reset/confirm` | `email` → `email`, `token`, `new_password` | 요청은 가입된 주소든 아니든 같은 202. 링크는 30분, 한 번만 쓴다. 끝나면 모든 기기가 로그아웃된다 |

입력의 규칙:

- 아이디: 영문 소문자, 숫자, 밑줄 4~20 자. `admin`, `root` 같은 예약어는 안 된다.
- 닉네임: 한글, 영문, 숫자, 밑줄 2~20 자. 공백 불가. 예약어 불가.
- 비밀번호: 128 자까지. 앞뒤 공백도 비밀번호의 일부다. 서버가 아이디·이메일·닉네임과 비슷한지, 너무 짧은지(Django 기본 최소 길이), 흔한 비밀번호인지, 숫자만인지를 본다. 구체적 최소 길이는 서버 설정을 확인한다(아래).
- `age_over_14` 는 "만 14세 이상입니다" 체크다. 거짓이면 400 이다. 자기 신고라 실제 나이는 A3 에서 다시 본다.

**3. 할 수 있는 행동**

위 표의 호출이 곧 행동이다. 이어서:

- 로그인 상태 유지: access 토큰(15분)은 **메모리에만** 둔다. 만료되면 `POST /refresh`(쿠키, 14일)로 새로 받는다. 화면이 `/refresh` 를 **한 번에 하나만** 부른다. 같은 쿠키로 동시에 두 번 가면 폐기된 토큰의 재사용으로 처리되어 모든 세션이 끊긴다.
- 비밀번호 바꾸기(로그인한 상태): `POST /password/change` `{current_password, new_password}`. 다른 기기는 로그아웃되고 이 기기는 새 토큰을 받는다.

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 가입 3: 아이디·닉네임·비밀번호 규칙 위반, 중복 | 400, 어느 값인지 | 그 칸에 이유를 보인다. 티켓은 그대로 다시 쓸 수 있다 |
| 가입 3: 티켓이 틀리거나 만료 | 400 `signup_ticket_invalid` | 1단계부터 다시 |
| 가입 3: 이미 가입을 마침 | 409 `email_registered` | 로그인으로 보낸다 |
| 가입 3: 방금 다른 가입이 같은 값을 가져감 | 409 | 다른 값을 고르게 한다 |
| 로그인 1: 아이디 없음 또는 비밀번호 틀림 | 401 | 둘을 구분하지 않는다. 같은 문구로 보인다 |
| 로그인 1: 가입 이메일 인증을 끝내지 않음 | 403 `email_not_verified` | 가입 1단계로 안내한다 |
| 로그인 1: 코드를 지금 보낼 수 없음 | 429 `login_code_unavailable`, `retry_after`(초) | 남은 시간을 세어 버튼을 막는다 |
| 로그인 2: 티켓이 쓸 수 없음 | 401 `login_ticket_invalid` | 로그인 1단계부터 다시 |
| 시도 횟수 초과 | 429 `too_many_attempts`, `retry_after`, `Retry-After` 헤더 | 기다릴 시간을 보인다. 무엇을 기준으로 셌는지는 알려 주지 않는다 |
| 정지된 계정 | 401 | 아이디·비밀번호가 틀린 것과 같은 응답이다. 정지 이유를 알리지 않으므로 같은 문구로 보이고, 문의 안내를 둔다 |

시도 횟수의 한도: 로그인은 IP 당 10분에 30번, 계정과 IP 당 틀린 시도 15분에 5번. 가입은 IP 당 1시간에 10번. 비밀번호 재설정은 IP 당 1시간에 5번. 비밀번호 변경은 틀린 시도 15분에 5번. 예약어 아이디로 1시간 안에 3번 시도한 IP 는 평소와 같은 401 로 막힌다.

**5. 상태**

| 상황 | 화면의 처리 |
| --- | --- |
| 코드 입력 중 | 남은 유효 시간(가입 5분, 로그인 10분 티켓)과 다시 받기를 보인다. 다시 받기는 1분 대기, 1시간 5통 |
| 메일이 오지 않음 | 발송은 메일 발송함에 적힌 뒤 워커가 보낸다. 지연될 수 있다. "스팸함을 확인하세요", 다시 받기를 안내한다 |
| 토큰 만료 | 화면이 `/refresh` 로 조용히 갱신한다. 401 이면 로그인으로 보낸다 |
| 다른 기기에서 세션이 끊김 | 비밀번호 변경·재설정, 모든 기기 로그아웃, 계정 정지로 끊긴 세션의 토큰은 서버들이 거부한다. 401 이면 로그인으로 보낸다 |
| `/refresh`, `/logout` 이 403 `origin_not_allowed` | 허용한 출처가 아니다. 개발 설정의 문제다. 사용자에게는 일반 오류로 보인다 |
| 오류 | 서버가 `X-Request-ID` 를 돌려준다. 문의 화면에 그 값을 보이게 한다 |

**6. PC 와 모바일**

초안이다.

- PC: 가운데 카드 하나. 가입은 단계 표시줄(1/3), 로그인은 아이디·비밀번호 다음 코드 입력.
- 모바일: 같은 단계를 한 화면에 하나씩. 코드 입력은 숫자 키패드와 자동완성(메일의 코드 붙여넣기)을 켠다.

**7. 첫 출시**

들어간다(필수 공통 묶음).

**확인할 것**

- 비밀번호의 최소 길이와 그 밖의 강도 규칙은 Django 의 기본 검사기를 쓴다. 화면이 미리 안내하려면 서버 설정의 값을 확인한다. 서버가 말해 주는 오류 문구를 그대로 보이는 것을 첫 출시의 기본으로 한다.
- 정지된 계정은 로그인 때 "비밀번호가 틀림"과 같은 401 을 받는다. 정지됐다는 사실을 사용자가 알 길이 없어서 문의 안내를 어디에 둘지 정한다.
- 로그인이 항상 이메일 코드를 거치므로 로그인 한 번에 메일이 한 통 나간다. 이 방식을 첫 출시에서도 유지할지(신뢰하는 기기 기억 같은 것이 없다) 정한다.
- 비밀번호 재설정 링크의 화면 주소(`PASSWORD_RESET_URL`)는 프런트가 정한다. 링크의 `#` 뒤 값(`email`, `token`)을 읽어 `confirm` 으로 보내는 화면이 필요하다.
- 소셜 로그인은 서버에 없다.

### A3 본인인증

**1. 목적과 경로**

휴대폰 본인인증으로 나이(성인 여부)를 확인하고, 환영 크레딧(실버)을 한 번 받는다. 성인용 시나리오와 미성년자의 결제 가능 여부가 여기서 갈린다.

- 오는 경로: 가입·로그인 직후의 안내, 성인용 시나리오에서 403 `adult_content_required` 를 받았을 때, 마이페이지(A5).
- 나가는 길: 완료 후 오던 화면. 지갑(A6)에서 환영 크레딧을 확인한다.

**2. 입력과 출처**

본인인증은 본인확인 업체(NICE, KCB 같은 곳)의 화면에서 하고, 업체에서 받은 글자(`token`)를 `POST /identity/verify` 로 낸다. 지금은 실제 업체가 없고 가짜 업체(개발용)뿐이다. 운영에서는 가짜 업체를 쓸 수 없고, 업체를 설정하지 않으면 503 이다.

내 상태는 `GET /me` 의 `identity` 에 있다.

| 칸 | 뜻 | 기준 |
| --- | --- | --- |
| `verified` | 본인인증을 마쳤다 | |
| `legal_adult` | 민법의 성년이다. 결제가 본다 | 만 19세 생일부터 |
| `adult_content` | 성인용 내용을 볼 수 있다 | 만 19세가 되는 해의 1월 1일부터 |

본인인증을 하지 않은 계정은 셋 다 `false` 다. 나이를 모르면 성인으로 보지 않는다. 날짜는 한국 날짜로 매일 다시 센다. 미성년자도 그날이 지나면 다시 인증하지 않아도 저절로 바뀐다.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 본인인증 | `POST /identity/verify` `{token}` | 201 과 `identity` 상태. 토큰은 다시 주지 않는다. 성인 내용을 보려면 `/refresh` 를 한 번 불러 `adult_content` 가 실린 새 토큰을 받는다(늦어도 15분 뒤에는 저절로) |

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 업체가 그 `token` 을 모름 | 400 `identity_token_invalid` | 업체 화면부터 다시 |
| 만 14세 미만 | 403 `identity_under_age` | 계정이 막히고 가입 때 받은 정보가 지워지며 세션이 끊긴다. 로그인 화면으로 보내고 안내한다 |
| 이미 인증한 계정 | 409 `identity_already_verified` | 이미 인증했다고 알린다 |
| 다른 계정이 이미 그 사람으로 인증 | 409 `identity_in_use` | 한 사람에 한 계정이다. 문의 안내 |
| 본인인증을 받지 않는 서버 | 503 `identity_unavailable` | "지금은 본인인증을 할 수 없습니다" |

**5. 상태**

| 상황 | 화면의 처리 |
| --- | --- |
| 인증 전 | 성인용 시나리오는 목록에서 없는 것처럼 보인다(B1). 환영 크레딧을 받을 수 있다고 안내한다 |
| 인증 직후 | 성인용 보기가 바로 열리지 않으면 토큰 갱신을 한 번 부른다. 환영 크레딧은 결제 서버가 워커로 주므로 지갑에 바로 안 보일 수 있다 |
| 인증 후 미성년자 | 결제는 보호자 동의 뒤에 된다(A4) |

**6. PC 와 모바일**

초안이다. 업체의 인증 화면은 팝업이나 새 창으로 열리며, 앱으로 감쌌을 때(WebView)의 동작은 업체를 정한 뒤 검증한다.

**7. 첫 출시**

들어간다(필수 공통 묶음). 실제 업체는 사업자 계약이 필요해서 가짜 업체로 화면을 먼저 만든다.

**확인할 것**

- 실제 본인확인 업체를 정하고 계약해야 한다. 업체마다 팝업, 리다이렉트, 앱 연동의 방식이 달라 화면이 바뀐다.
- 환영 크레딧의 양과 지급 시점(워커가 결제 서버에 맡기는 일)을 화면이 어떻게 알려 줄지. 지갑(A6)에서 받은 시각이 보이는지 확인한다.
- 만 14세 미만으로 계정이 막혔을 때 사용자에게 보일 안내 문구는 정책으로 정한다.

### A4 보호자 동의

**1. 목적과 경로**

미성년자(성년 전)는 보호자가 동의해야 결제할 수 있다. 보호자는 계정을 만들지 않는다. 결제를 막는 것은 결제 서버다.

- 오는 경로: 결제 시 보호자 안내(A7), 마이페이지(A5)의 "보호자 동의".
- 보호자의 화면은 메일 링크로 열린다(동의 7일 유효).

**2. 입력과 출처**

| 단계 | 호출 | 보내는 것 | 비고 |
| --- | --- | --- | --- |
| 1. 요청(미성년자) | `POST /guardian/request` | `guardian_email` | 202. 보호자 메일로 동의 링크(`GUARDIAN_CONSENT_URL#token=...`)가 간다. 다시 요청하면 앞의 링크는 못 쓴다 |
| 2. 동의(보호자) | `POST /guardian/consent` | `consent_token`(링크의 `token`), `identity_token`(보호자의 본인인증) | 보호자와 미성년자에게 메일이 간다. 보호자의 메일에 철회 링크가 있다 |
| 3. 철회(보호자) | `POST /guardian/revoke` | `revoke_token`(철회 링크의 `token`) | 두 번 보내도 200. `revoked` 가 이번에 철회했는지다 |

내 동의 상태는 `GET /me` 의 `guardian_consent` 다: `none`, `requested`, `consented`, `revoked`.

**3. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| (요청) 본인인증 전 | 403 `identity_verification_required` | A3 으로 |
| (요청) 이미 성년 | 409 `guardian_not_needed` | 동의가 필요 없다고 알린다 |
| (요청) 보호자가 이미 동의함 | 409 `guardian_consent_active` | 보호자를 바꾸려면 지금의 보호자가 먼저 철회한다 |
| (요청) 자기 이메일을 적음 | 400 `guardian_email` | |
| (요청) 너무 자주 | 429 `guardian_request_unavailable`, `retry_after` | 1분에 1통, 하루 5통 |
| (동의·철회) 링크가 틀리거나 만료 | 400 `guardian_link_invalid` | 위조와 만료를 구분하지 않는다. 다시 요청하라고 안내 |
| (동의) 보호자가 성년이 아님 | 403 `guardian_not_adult` | |
| (동의) 미성년자 본인의 휴대폰으로 인증 | 409 `guardian_is_minor` | |

**4. 상태, PC 와 모바일**

- 요청 후 `requested`: "보호자의 동의를 기다리는 중", 링크 재발송.
- `consented`: 결제 가능, 철회는 보호자의 메일 링크로만 한다는 안내.
- `revoked`: 결제 불가, 다시 요청.
- 보호자의 화면은 모바일 메일에서 열린다. 모바일 우선으로 한다.

**5. 첫 출시**

이후다([첫 출시의 범위](#첫-출시의-범위)). 다만 미성년자가 가입할 수 있으므로(만 14세 이상) 첫 출시에서는 미성년자의 결제를 막기만 하고 안내문을 두는 방법이 최소다.

**확인할 것**

- 첫 출시에 A4 가 이후라면 미성년자가 결제하려 할 때의 서버 응답(결제 서버의 거절)과 안내 문구를 A7 에서 확인한다.
- 동의·철회 링크의 화면 주소(`GUARDIAN_CONSENT_URL`, `GUARDIAN_REVOKE_URL`)는 프런트가 정한다. 로그인 없이 열리는 화면이다.

### A5 마이페이지

**1. 목적과 경로**

내 계정을 보고, 로그아웃하고, 비밀번호를 바꾼다. 지갑, 주문 내역, 본인인증, 보호자 동의로 가는 문이다.

- 오는 경로: 모든 화면의 헤더(내 정보).

**2. 보여 주는 정보와 출처**

`GET /me` (access 토큰 필요):

| 정보 | 서버의 칸 |
| --- | --- |
| 내 ID(`sub` 와 같다) | `public_id` |
| 아이디 | `username` |
| 이메일 | `email` |
| 닉네임 | `nickname` |
| 본인인증 상태 | `identity.verified`, `identity.legal_adult`, `identity.adult_content` |
| 보호자 동의 | `guardian_consent` |

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 로그아웃(이 기기) | `POST /logout` | refresh 쿠키 폐기 |
| 모든 기기 로그아웃 | `POST /logout-all` | 모든 세션 종료. 다른 서버의 토큰도 끊긴 세션으로 거부된다 |
| 비밀번호 변경 | `POST /password/change` | A2 와 같다 |
| 본인인증 | A3 으로 | |
| 보호자 동의 | A4 로 | 미성년자에게만 보인다 |
| 닉네임 바꾸기, 탈퇴 | 없음 | 서버에 아직 없다(계획) |

**4. 상태, PC 와 모바일, 첫 출시**

- 401 이면 로그인으로 보낸다. 로그아웃 후에는 메모리의 access 토큰을 지우고 첫 화면으로 간다.
- PC: 왼쪽 메뉴(계정, 지갑, 주문 내역, 보안), 오른쪽 내용. 모바일: 목록형.
- 첫 출시에 들어간다(필수 공통 묶음). 닉네임 바꾸기와 탈퇴는 서버가 생기면 더한다.

**확인할 것**

- 닉네임 바꾸기, 이메일 바꾸기, 탈퇴는 서버에 없다. 개인정보보호법상 탈퇴(삭제) 경로가 출시 전에 필요한지 정한다.
- 활성 세션 목록(어느 기기에 로그인했는지) 보기는 서버에 없다. 모든 기기 로그아웃만 있다.

### A6 지갑

**1. 목적과 경로**

내 크레딧(골드와 실버)을 보고, 어떻게 들어오고 나갔는지 원장을 읽는다. 충전(A7), 출석(A9)으로 가는 문이다.

- 오는 경로: 모든 화면 헤더의 잔액, 마이페이지(A5), 크레딧이 모자라다는 알림(B6).
- 화면에서는 산 크레딧을 **골드**, 무료 크레딧을 **실버**라고 부른다. 1개가 1크레딧으로 같다. API 의 이름은 `paid`, `free` 그대로다.

**2. 보여 주는 정보와 출처**

`GET /api/v1/billing/wallet`:

| 정보 | 서버의 칸 | 비고 |
| --- | --- | --- |
| 골드 | `paid` | 산 크레딧. 사라지지 않는다 |
| 실버 | `free` | 무료 크레딧. 지급된 뒤 30일(`FREE_CREDIT_TTL`)이 지나면 사라진다 |
| 합 | `total` | |
| 곧 사라질 실버 | `next_expiry` | 실버 중 가장 먼저 사라지는 것. `{"amount": "10", "expires_at": "2026-10-22T15:00:00Z"}`. 실버가 없으면 `null` |

- 양은 숫자가 아니라 **글자**다(`"80"`). 화면이 더하거나 빼지 않고 서버가 준 값을 그대로 보인다.
- 지갑이 없는 사용자도 200 이고 모두 `"0"`, `next_expiry` 는 `null` 이다.
- `next_expiry` 의 `amount` 는 그 시각에 사라지는 양이다(같은 시각의 지급이 여럿이면 더한 것). 그 뒤에 사라질 실버는 싣지 않는다. `expires_at` 은 UTC 고, 그 시각부터 쓸 수 없다. "10 실버가 3일 뒤에 사라진다"처럼 보인다.

원장 `GET /api/v1/billing/wallet/entries?limit=&before=`: 최근 것부터. 한 줄은 `id`, `operation_id`(한 번의 변경이 남긴 줄을 묶는다), `kind`(`paid`/`free`), `reason`, `amount`(늘면 양수, 줄면 음수), `order_id`, `hold_id`, `created_at` 이다. `limit` 은 1~100(기본 20), 다음 쪽은 응답의 `next_before` 를 `before` 로 넣는다. `next_before` 가 `null` 이면 끝이다.

`reason` 의 뜻과 화면의 말(제안):

| `reason` | 뜻 | 화면의 말 |
| --- | --- | --- |
| `deposit` | 산 크레딧이 들어옴 | 충전 |
| `grant` | 무료 크레딧 지급 | 지급(환영, 출석, 상자) |
| `spend` | 씀 | 사용 |
| `hold` / `release` | 서술 값을 먼저 빼 둠 / 돌아옴 | 서술 값 대기 / 반환 |
| `expire` | 실버가 기한이 지나 사라짐 | 만료 |
| `refund` / `unrefund` | 청약철회로 빠짐 / 철회가 거절되어 돌아옴 | 환불 / 환불 취소 |
| `regroup` | 내부 정리. 같은 작업의 줄을 더하면 0 | 보이지 않거나 접는다 |

쓰는 순서: 스탠다드 모델은 실버를 먼저 쓰고 모자라면 골드를 쓴다(`SPEND_FREE_FIRST` 기본). 프리미엄 모델은 골드만 쓴다.

**6. PC 와 모바일**

초안이다. PC: 위에 잔액 두 칸(골드, 실버), 아래에 원장 표. 모바일: 잔액 카드 둘, 원장은 줄 목록.

**7. 첫 출시**

들어간다(필수 공통 묶음).

**확인할 것**

- 지갑은 가장 먼저 사라지는 실버 하나(`next_expiry`)만 준다. 사라질 날마다의 목록은 없다. 7일 안에 사라질 양의 합은 알림함의 `credit.expiring` 으로도 온다(A10). 두 값은 다를 수 있다(지갑은 가장 이른 시각의 양만, 알림은 7일 안의 합).
- 홀드로 빠진 크레딧(`hold`)이 서술 뒤에 확정되는 줄(`spend`)과 어떻게 이어지는지 사용자에게 어떻게 보일지. `hold_id` 로 묶을 수 있다.
- 헤더의 잔액을 읽는 시점. 서술이 끝날 때마다 읽으면 요청이 많아진다. 스트림 이벤트 `narration_credits_short` 같은 것으로 다시 읽을지 정한다.

### A7 충전과 결제

**1. 목적과 경로**

골드를 충전한다. 지금은 **실제 돈이 나가지 않는 테스트 모드**다.

- 오는 경로: 지갑(A6), 크레딧 부족 안내(B6).
- 나가는 길: 결제가 끝나면 지갑(A6)에 잔액이 늘어난 것을 보인다.

**2. 입력과 출처**

상품 `GET /api/v1/billing/products`: 번호, 이름, 값(원), 크레딧. 지금은 4 개이고 1원이 1크레딧이다. 많이 산다고 더 주지 않는다.

| 번호 | 값 | 크레딧 |
| --- | --- | --- |
| `credits-1000` | 1,000원 | 1,000 |
| `credits-5000` | 5,000원 | 5,000 |
| `credits-10000` | 10,000원 | 10,000 |
| `credits-30000` | 30,000원 | 30,000 |

흐름은 여섯 걸음이다.

1. `GET /products` 로 상품을 본다.
2. `POST /orders` `{product_id}` 에 `Idempotency-Key` 머리말(UUID 등, 8~128 자)을 **요청마다 새로** 붙여 주문을 만든다(`pending`). 응답을 받지 못해 다시 보낼 때는 **같은 키**를 쓴다. 값과 크레딧은 서버가 상품에서 찾는다. 클라이언트가 보낸 금액은 쓰지 않는다.
3. 결제창(토스페이먼츠 결제위젯)에서 결제한다. 끝나면 토스페이먼츠가 브라우저를 화면으로 돌려보내며 `paymentKey` 를 주소에 붙인다.
4. `POST /orders/{id}/confirm` `{payment_key}` 로 승인을 요청한다(`paid` 또는 `failed`).
5. 결과를 모르는 채로 끝나면(202 `confirming`) 같은 결제 번호로 다시 부르거나 `GET /orders/{id}` 로 나중에 본다.
6. 7 일 안이고 그 주문의 크레딧이 하나도 줄지 않았으면 청약철회(A8).

주문의 상태: `pending`, `confirming`, `paid`, `failed`, `refunding`, `refunded`, `expired`.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 주문 만들기 | `POST /orders` | 201(새로) 또는 200(같은 키로 이미 만든 것) |
| 승인 요청 | `POST /orders/{id}/confirm` | 같은 결제 번호로 몇 번 불러도 크레딧은 한 번만 들어간다 |
| 주문 읽기 | `GET /orders/{id}` | `status`, `failure_code`, `refundable`, `refundable_until` |

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 본인인증 전 | 403 `payment.verification_required` | A3 으로 보낸다 |
| 미성년자, 보호자 동의 전·철회 | 403 `payment.guardian_consent_required` | A4 로 보낸다 |
| 같은 키로 다른 상품 | 409 | 새 키로 새 주문을 만든다 |
| 주문이 만료됨(24시간) | 409 | 새 키로 새 주문 |
| 이미 다른 결제 번호로 진행됨, 결제 번호가 다른 주문에 쓰임 | 409 | 처음부터 다시 |
| 결제 거절 | 200 `status: failed`, `failure_code` | 이유를 보이고 다시 시도하게 한다. 돈은 나가지 않았다 |
| 승인 결과를 모름 | 202 `status: confirming` | **실패로 보이지 않는다.** "결제 확인 중"을 보이고 같은 결제 번호로 다시 부르거나 나중에 `GET /orders/{id}` 로 읽는다 |
| 서버가 바쁨 | 503 | 결제 실패가 아니다. 같은 결제 번호로 다시 보낸다 |

**5. 상태**

| 상황 | 화면의 처리 |
| --- | --- |
| 결제창을 연 채 떠남 | 주문은 24시간 뒤 `expired`. 돈이 오간 적이 없다 |
| `confirming` 이 오래 감 | 서버가 하루 한 번 도는 대사로 결제 대행사에 결과를 물어 끝낸다. 화면은 "확인 중, 잠시 뒤 지갑에서 확인하세요"를 보인다 |
| 가상계좌(입금 대기) | 받지 않는다. 입금 대기로 오면 서버가 곧바로 취소하고 `failed` 다 |
| 결제 직후 | 지갑을 다시 읽어 잔액을 보인다. 두 번 충전되지 않게 승인 요청을 한 번만 보낸다 |

**6. PC 와 모바일**

초안이다. 상품 카드 넷, 결제위젯은 같은 화면 아래에 그린다. 모바일은 결제창이 새 창이나 리다이렉트로 열리고, 돌아올 때 `paymentKey` 를 읽어 승인을 요청하는 화면이 필요하다. 앱으로 감쌌을 때의 복귀를 검증한다.

**7. 첫 출시**

들어간다(필수 공통 묶음). 다만 실제 결제 전에 사업자 등록과 전자결제 신청이 필요하고, 그때까지는 테스트 모드다.

**확인할 것**

- **구글 플레이 앱 안에서는 구글 결제를 써야 한다.** 서버의 결제 경로(`channel`)는 `web` 하나뿐이다. 앱으로 낼 때의 결제는 별도 단계다. (이슈 #431)
- 결제위젯이 돌려보내는 주소(`successUrl`, `failUrl`)를 프런트가 정해야 한다. 서버의 개발용 결제 화면(`/dev/checkout`)이 참고용이다.
- 거절 사유(`failure_code`)의 목록과 화면의 문구. 카드사 사유를 그대로 보이지 않는다.
- 환불이 아닌 취소, 영수증, 현금영수증 같은 것은 서버에 없다.

### A8 주문 내역·청약철회

**1. 목적과 경로**

산 주문을 보고, 조건이 맞으면 7 일 안에 전액을 청약철회한다.

- 오는 경로: 지갑(A6)의 원장 줄(`order_id`), 마이페이지(A5).

**2. 보여 주는 정보와 출처**

`GET /orders/{id}` 의 주문: `id`, `product_id`, `price`(원, 숫자), `credits`(글자), `status`, `failure_code`, `created_at`, `expires_at`, `paid_at`, `refundable`(지금 철회할 수 있는가), `refundable_until`(치른 시각 + 7일), `refunded_at`.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 주문 읽기 | `GET /orders/{id}` | |
| 청약철회 | `POST /orders/{id}/refund` | 본문 없음. 금액과 이유는 서버가 정한다(전액, 청약철회). 수수료 없음 |

**4. 버튼이 비활성인 조건**

환불 버튼은 `refundable` 이 참일 때만 연다. 서버가 거절하는 경우는 모두 409 다: 치른 주문이 아님, 7 일이 지남, **그 주문의 크레딧을 일부라도 썼음**(홀드로 묶인 것도 준 것으로 센다), 결제 대행사가 취소를 거절함(크레딧은 돌아오고 주문은 `paid`), 같은 주문의 다른 요청과 엇갈림(다시 보낸다). 무료 크레딧은 상관없다.

**5. 상태**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 취소됨 | 200 `refunded` | 돈이 돌아갔다고 알린다 |
| 크레딧은 뺐고 결과를 모름 | 202 `refunding` | "환불 처리 중". 같은 주소를 다시 부르면 같은 취소를 다시 보낸다 |
| 남의 주문, 없는 주문 | 404 | 같은 답이다 |
| 서버가 바쁨 | 503 | 주문은 적어 둔 상태에 남는다. 다시 보낸다 |

**6. PC 와 모바일, 7. 첫 출시**

초안이다. 표(PC)와 카드(모바일). 첫 출시 범위안에서는 **이후**다([첫 출시의 범위](#첫-출시의-범위)). 다만 전자상거래법의 청약철회를 첫 결제부터 보장해야 하는지 확인한다(아래).

**확인할 것**

- **주문 목록 경로가 없다.** `GET /orders/{id}` 하나뿐이어서 "내 주문 내역"은 원장(`wallet/entries`)에서 `reason` 이 `deposit`, `refund` 이고 `order_id` 가 있는 줄로 이어야 한다. 주문 목록을 서버가 주는 것이 낫다. 결제 세션과 정한다. (이슈 #430)
- 철회가 안 되는 이유(크레딧을 썼음, 7 일이 지남)를 화면이 구분해 보이려면 서버가 이유를 줘야 한다. 지금은 `refundable` 참/거짓과 409 뿐이다. (이슈 #430)
- 법적으로 7 일 철회와 이미 쓴 크레딧의 환불 규정이 맞는지는 약관과 함께 확인한다. 이 문서는 서버의 동작만 적는다.

### A9 출석·보물 상자

**1. 목적과 경로**

본인인증을 마친 사용자가 하루에 한 번 출석해서 실버를 받는다. 7 일 주기의 마지막 날에는 보물 상자를 연다.

- 오는 경로: 지갑(A6), 홈(A1)의 출석 알림.

**2. 보여 주는 정보와 출처**

`GET /attendance`: 오늘 받았는지, 주기의 며칠째인지, 오늘의 하루 양, 상자를 여는 날인지. 본인인증 전이면 `verified: false`.

- 하루 양은 기본 7 일 동안 140, 160, 180, 200, 220, 240, 260 실버(설정 `ATTENDANCE_SILVER`). 한 주 1,400 실버.
- **하루라도 빠지면 1일째부터 다시 센다.** 마지막 날 다음 날도 1일째다. 날짜는 한국 날짜이고 자정에 바뀐다.
- 받은 실버는 다른 무료 크레딧처럼 30일 뒤에 사라지고 스탠다드 모델에만 쓴다.

`GET /attendance/rewards`는 **로그인 없이** 누구나 읽는다. 하루 양과 보물 상자의 확률표(표 버전 `v1`)를 준다. 상자의 결과: 미믹 — 물렸다(0, 10%), 미믹 — 이빨 사이의 동전(100, 20%), 고블린의 주머니(300, 30%), 모험가의 배낭(600, 22%), 보물 더미(1,500, 15%), 용의 보물(5,000, 3%). 평균 617 실버. 확률을 공개하는 것은 서비스의 약속이므로 화면에 표를 보인다.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 출석 | `POST /attendance` | 201 `{day, cycle_day, silver, chest?, expires_at}`. `chest` 는 마지막 날에만 있고 `{table, outcome, name, silver}` 다 |

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 본인인증 전 | 403 `attendance.verification_required` | A3 으로 |
| 오늘 이미 받음 | 409 `attendance.already_claimed` | 버튼을 막고 "내일 다시"를 보인다 |

**5. 상태, 6. PC 와 모바일**

- 주기 진행을 7 개의 칸으로 보이고 오늘 칸을 강조한다. 마지막 칸은 상자 그림.
- 상자를 열 때의 연출은 화면이 정하고, 결과는 `chest.outcome` 과 `silver` 만 믿는다.
- 서버가 확률을 바꾸지 않고 표 버전을 올려 공지한다. 화면이 `table` 버전을 같이 보인다.

**7. 첫 출시**

이후다([첫 출시의 범위](#첫-출시의-범위)). 서버는 이미 있고, 환영 크레딧과 출석이 무료 이용의 중심이므로 앞당길지 정한다.

**확인할 것**

- 연속 출석이 끊겼을 때 사용자에게 "1일째로 돌아갔다"는 것을 미리 알릴 값이 응답에 있는지(`cycle_day`가 1로 오는지) 확인한다.
- 출석 보상표의 하루 양이 설정값이라 바뀔 수 있다. 화면이 숫자를 하드코딩하지 않고 `rewards` 에서 읽는다.

### A10 알림

**1. 목적과 경로**

사람에게 보내는 알림함. 다른 서버가 서명한 요청으로 알림을 넣고, 사용자는 자기 알림을 읽고 읽음으로 한다.

- 오는 경로: 헤더의 종 모양과 읽지 않은 수.

**2. 보여 주는 정보와 출처**

| 호출 | 뜻 |
| --- | --- |
| `GET /api/v1/notification/me/notifications?before=&limit=` | 내 알림, 최근 것부터. `limit` 은 1~100(기본 20), `next_before` 로 다음 쪽 |
| `GET .../unread-count` | 읽지 않은 수 `{"unread": 3}` |
| `POST .../{id}/read` | 하나를 읽음으로. 처음 읽은 시각이고 다시 해도 바뀌지 않는다 |
| `POST .../read-all` `{"up_to": 57}` | 그 번호까지 읽지 않은 것을 모두 읽음으로. 목록을 받은 뒤 새로 들어온 알림은 읽음이 되지 않는다 |

알림 하나: `{id, source, kind, payload, created_at, read_at}`. `source` 는 보낸 서버(`game`, `billing`, `board`), `kind` 는 점으로 나눈 종류(`scenario.sanctioned` 등), `payload` 는 종류마다 다른 내용이다. **문구는 서버가 주지 않는다.** 화면이 `kind` 별로 문장을 만든다. 보관 기간은 30 일이다(읽었는지와 상관없이).

**3. 할 수 있는 행동, 4. 버튼이 비활성인 조건**

위 표의 호출이 행동이다. 남의 알림 번호는 404(없는 것과 같은 답)이다. 401(토큰), 503(공개키를 구할 수 없음, `Retry-After`)이다. 알림함은 `aud` 에 `ai-trpg-notification` 이 있는 토큰으로 부른다.

**5. 상태, 6. PC 와 모바일**

- 빈 알림함, 읽지 않은 수 배지(99+ 같은 표시는 화면이 정한다).
- PC: 종 모양에서 열리는 패널. 모바일: 전체 화면 목록.
- 읽지 않은 수를 얼마나 자주 읽을지(폴링 간격, 화면에 들어올 때) 정한다. 실시간 스트림은 알림 서버에 없다.

**7. 첫 출시**

들어간다(필수 공통 묶음).

**확인할 것**

- **알림을 넣는 서버는 게임, 결제, 게시판 셋이다.** 게임은 모델 은퇴 셋과 운영자의 제재 셋, 결제는 결제와 크레딧 넷, 게시판은 댓글 둘을 넣는다(아래 표). 원본은 `game-server/README.md` 와 `board-server/README.md` 의 "알림 보내기", `billing-server/README.md` 의 "정리 작업과 대사"(사용자의 알림함), 받는 쪽은 `notification-server/README.md` 의 "알림 넣기(서버끼리)"다.
- 지금 오는 `kind` 는 아래 열두 가지다. 화면이 `kind` 별로 문장을 만든다. 모르는 `kind` 는 일반 문구로 보인다. 화면은 `source` 와 `kind` 를 함께 보고 문장을 고른다. 표에 없는 짝은 일반 문구로 보인다.

  | `kind` | `source` | 받는 사람 | `payload` |
  | --- | --- | --- | --- |
  | `narration_model.retiring` | `game` | 테이블의 방장 | `table_id`, `title`, `narration_model`, `retires_on`, `days_left` |
  | `narration_model.replaced` | `game` | 방장 | `table_id`, `title`, `from`, `narration_model`, `reason`, `round`, `price` |
  | `narration_model.unavailable` | `game` | 방장 | `table_id`, `title`, `narration_model`, `reason` |
  | `scenario.sanctioned` | `game` | 시나리오 제작자 | `scenario_id`, `title`, `version_number`, `publishing_banned` |
  | `publishing.banned` | `game` | 공개가 금지된 사람 | `automatic`(저절로 올랐는지) |
  | `publishing.unbanned` | `game` | 그 사람 | 없음 |
  | `order.paid` | `billing` | 결제한 사람 | `order_id`, `product_id`, `price`(원, 숫자), `credits`(글자) |
  | `order.refunded` | `billing` | 청약철회한 사람 | `order.paid` 와 같다 |
  | `credit.welcome` | `billing` | 환영 크레딧을 받은 사람 | `amount`(글자), `expires_at` |
  | `credit.expiring` | `billing` | 무료 크레딧이 7일 안에 사라지는 사람. 한 사람에게 7일에 한 번 | `amount`(사라질 양의 합, 글자), `first_expires_at`(가장 먼저 사라지는 때) |
  | `post.commented` | `board` | 글쓴이 | `board_slug`, `post_id`, `post_title`, `comment_id` |
  | `comment.replied` | `board` | 그 댓글의 글쓴이 | `board_slug`, `post_id`, `post_title`, `comment_id`, `parent_id` |

  크레딧의 양(`credits`, `amount`)은 정확한 값을 지키려고 글자로 온다(A6 과 같다). `expires_at`, `first_expires_at` 은 UTC 의 ISO 8601 시각이다.
  자기 글에 자기가 단 댓글, 자기 댓글에 자기가 단 답글은 알리지 않는다. 답글은 그 댓글의 글쓴이에게만 가고 글쓴이에게 또 가지 않는다. 댓글의 내용은 싣지 않는다(지운 댓글도 알림함에는 남아서). 눌렀을 때 글로 가서 댓글을 본다.
  크레딧이 모자라다는 것은 알림이 아니다. 테이블 방(B6)이 그 자리에서 보인다.
  제재 알림에는 사유와 운영자를 싣지 않는다(신고한 사람이 드러날 수 있어서). 화면도 사유를 보이지 않는다.
- 알림을 눌렀을 때 어디로 가는지(`payload` 의 ID 로 가는 화면 주소)는 `kind` 마다 정한다.
- 알림을 끄는 설정은 서버에 없다.
- 시나리오 제작자에게 추천 모델의 은퇴를 알릴지, 제재의 까닭을 당사자에게 어떻게 알릴지는 정하지 않았다. (이슈 #385)

### A11 공지·게시판

**1. 목적과 경로**

사이트가 운영하는 커뮤니티. 공지, 이벤트, 자유 게시판, 시나리오 이야기 네 게시판에서 글을 읽고 쓰고, 댓글과 답글을 달고, 검색하고, 신고한다. 시나리오 소개 페이지의 평(B2)은 여기가 아니라 게임 쪽의 일이다.

- 오는 경로: 헤더의 메뉴, 공지 배너, 알림(A10).
- 읽기(목록, 글, 댓글, 검색)는 **로그인 없이** 열려 있다. 쓰기, 신고는 로그인이 필요하다.

**2. 입력과 출처 (`/api/v1/board`)**

| 화면 | 호출 | 담는 것 |
| --- | --- | --- |
| 게시판 고르기 | `GET /boards` | 정해 둔 차례대로 |
| 글 목록 | `GET /boards/{slug}/posts?page=&size=` | `pinned`(고정한 글, 첫 쪽에만), `items`(본문 없음), `page`, `size`(1~50), `total`. 쪽 번호 방식 |
| 글 읽기 | `GET /posts/{id}` | 제목, 본문, `author_nickname`, `comment_count`, 시각 |
| 댓글 | `GET /posts/{id}/comments?after=&size=` | 댓글마다 `replies`. "다음 몇 개" 방식: `next` 가 있으면 더 있다 |
| 검색 | `GET /posts?q=&board=` | 제목과 본문. 낱말 2자 이상, 5개까지, 전체 50자. 모든 낱말이 들어 있는 글 |
| 글 쓰기·고치기 | `POST /boards/{slug}/posts`, `PATCH /posts/{id}` | 제목 100자, 본문 20000자 |
| 댓글 쓰기·고치기 | `POST /posts/{id}/comments`, `PATCH /comments/{id}` | 2000자. 답글은 `parent_id`. 답글에는 답글을 달지 못한다 |
| 신고 | `POST /posts/{id}/reports`, `POST /comments/{id}/reports` | `reason`: `spam`, `abuse`, `sexual`, `illegal`, `other`. 설명 500자(`other` 는 필수) |

화면이 알아야 할 모양:

- 글쓴이는 `author_nickname`. 서버가 이름을 모르면 `null` 이니 "알 수 없음"으로 그린다.
- 지운 댓글에 답글이 달려 있으면 자리가 남고 `deleted: true`, `content` 와 글쓴이가 `null` 이다. "삭제된 댓글입니다"로 그린다. `comment_count` 는 이 자리를 세지 않는다.
- 고정한 글은 기간이 있다(`pinned_until`). 끝나면 저절로 제 자리로 돌아온다.
- 공지사항과 이벤트 게시판은 운영자만 쓴다. 누가 운영자인지는 토큰에 없고 서버가 안다(`operators`). 그래서 화면이 쓰기 버튼을 미리 숨길 값은 없다(아래).

**3. 할 수 있는 행동**

글 쓰기, 고치기, 지우기(글쓴이, 운영자는 남의 글도), 댓글과 답글, 검색, 신고. 운영자는 여기에 고정과 풀기가 있고, 신고 처리는 관리자 화면(E)에서 한다.

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 로그인 전 | 401 | 읽기만 보이고 쓰기는 로그인으로 보낸다 |
| 운영자 게시판에 씀 | 403 | 이유를 알린다 |
| 남의 글, 댓글을 고치거나 지움 | 403 | 글쓴이에게만 버튼을 보인다 (`author_id` 와 내 ID 를 비교) |
| 자기 글을 신고 | 403 | 내 글에는 신고 버튼을 보이지 않는다 |
| 같은 것을 두 번 신고 | 409 | "이미 신고했습니다" |
| 쓰기 횟수 초과 | 429 `retry_after` | 남은 초를 보인다. 글 10분에 5개, 댓글 1분에 10개, 신고 1시간에 20건. 운영자는 걸리지 않는다 |
| 한 댓글의 답글이 100개, 고정이 5개 | 409 | 이유를 알린다 |

**5. 상태**

| 상황 | 화면의 처리 |
| --- | --- |
| 빈 게시판, 검색 결과 없음 | 첫 글 쓰기, 다른 낱말 안내 |
| 지웠거나 없는 글 | 404. 목록으로 |
| 검색이 3초를 넘김 | 503. 낱말을 줄여 다시 시도하게 한다 |
| 인증 서버 공개키 문제 | 503 `Retry-After`. 로그아웃시키지 않고 잠시 뒤 다시 |
| 입력 오류 | 400 `errors` 의 칸별 문장을 칸 옆에 보인다 |

**6. PC 와 모바일**

초안이다. PC: 게시판 탭, 목록 표, 글은 아래에 댓글 이어붙이기. 모바일: 목록 카드, 글 전체 화면, 댓글은 "더 보기"로 `after` 를 이어 받는다.

**7. 첫 출시**

이후다([첫 출시의 범위](#첫-출시의-범위)). 서버는 있다. 다만 공지(점검, 약관 변경)를 알릴 곳이 첫 출시에 필요하니, 공지 목록과 글 읽기만 앞당길지 정한다.

**확인할 것**

- 게시판의 `slug` 네 개와 이름, 차례는 `GET /boards` 에서 읽는다. 문서에는 적지 않았다.
- 운영자인지는 `GET /me` 의 `is_operator` 로 안다. 운영자만 쓰는 게시판(`write_policy`)에서 쓰기 버튼과 신고 목록을 운영자에게만 보인다. 서버도 막으므로 화면의 숨김은 편의다.
- 내 글에 댓글이, 내 댓글에 답글이 달리면 알림이 간다(A10 의 `post.commented`, `comment.replied`). 알림을 누르면 `board_slug` 와 `post_id` 로 이 화면의 글로 간다.
- 글에 이미지를 붙이는 길이 없다. 본문은 글자뿐이다. 본문을 서식으로 보일지(마크다운 같은 것) 정한다. 서식을 허용하면 화면이 위험한 입력을 걸러야 한다.
- 닉네임이 토큰에 실려 오므로 닉네임을 바꾼 사람의 옛 글에 새 이름이 나오는 때는 그 사람이 다시 로그인해 이 서버를 처음 부른 뒤다.

### B1 시나리오 탐색

**1. 목적과 경로**

공개된 시나리오를 둘러보고 하나를 고른다.

- 오는 경로: A1 첫 화면에서 TRPG 를 고른다. 로그인한 뒤에만 열린다.
- 나가는 길: 카드를 누르면 B2 시나리오 소개로 간다.

**2. 보여 주는 정보와 출처**

`GET /listings` 가 돌려주는 `PublicListing` 의 칸이다. 카드와 B2 의 상세가 같은 모양이다.

| 정보 | 서버의 칸 | 비고 |
| --- | --- | --- |
| 제목 | `title` | |
| 한 줄 소개 | `tagline` | 최대 100 자 |
| 장르 | `genres` | 시나리오마다 최대 3 개. 운영자가 정한 목록에서 고른다(아래) |
| 태그 | `tags` | 제작자가 자유롭게 적는다. 최대 10 개, 하나에 20 자까지 |
| 등급 | `rating` | `all` 또는 `adult` |
| 추천 인원 | `recommended_players.min`, `max` | 추천일 뿐 테이블의 정원을 막지 않는다 |
| 공개한 때 | `published_at` | |
| 만든 사람 | `creator_id` | 인증 서버의 `public_id` 다. 이름은 인증 서버가 안다 |
| 판 | `version`, `version_note` | 공개 중인 판의 번호와 변경 내용 |

목록의 조건과 순서:

- 거르는 조건은 장르 하나(`?genre=`)와 태그 하나(`?tag=`)다. 둘을 함께 걸면 둘 다 맞는 것만 나온다. 태그는 적힌 글자가 정확히 같은 것만 맞는다.
- 순서는 최근에 공개한 것부터로 고정이다. 고를 수 없다.
- 쪽은 `limit` 기본 20 개(최대 100), `offset` 으로 넘긴다. 응답의 `total` 이 조건에 맞는 전체 개수다.
- 장르 값은 `fantasy`, `wuxia`, `urban_fantasy`, `sf`, `apocalypse`, `horror`, `mystery`, `romance`, `slice_of_life`, `alt_history`, `comedy`, `for_men`, `for_women` 이다. 앞의 열한 개는 이야기의 종류이고 뒤의 둘은 누구를 위한 이야기인가다. 화면에 보이는 말은 화면이 정한다.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 목록 보기 | `GET /listings` | 첫 쪽을 읽는다 |
| 장르로 거르기 | `GET /listings?genre=horror` | 한 번에 하나만 걸 수 있다 |
| 태그로 거르기 | `GET /listings?tag=...` | 카드나 B2 의 태그를 눌러 온다 |
| 더 보기 | `GET /listings?offset=...` | `total` 보다 `offset` 이 작으면 다음 쪽이 있다 |
| 시나리오 열기 | B2 로 이동 | |

**4. 버튼이 비활성인 조건**

- 성인용 시나리오는 성인 확인이 안 된 사람에게 목록에도 `total` 에도 나오지 않는다. 403 이 아니라 그냥 없는 것으로 보인다. 그래서 화면은 "숨겨진 것이 있다"고 알릴 수 없다. 성인 확인(A3)으로 가는 안내는 화면이 따로 둔다.
- 거르는 조건에 맞는 것이 없으면 빈 목록이다. 오류가 아니다.

**5. 상태**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 로딩 | | 카드 모양의 자리 표시 |
| 공개된 시나리오가 하나도 없음 | 빈 목록 | "아직 공개된 시나리오가 없습니다" |
| 조건에 맞는 것이 없음 | 빈 목록 | 조건을 푸는 버튼과 함께 안내 |
| 로그인하지 않음, 토큰 만료 | 401 | 로그인(A2)으로 보낸다 |
| 오류 | 5xx, 연결 실패 | 다시 시도 버튼. 이미 읽은 쪽은 남긴다 |

**6. PC 와 모바일**

초안이다.

- PC: 카드 격자, 왼쪽에 장르 줄. 아래로 내리면 이어서 읽는다.
- 모바일: 한 줄에 카드 하나, 장르는 위의 가로 칩. 태그 거르기는 칩을 눌러서 한다.

**7. 첫 출시**

들어간다(필수 TRPG 묶음). 정렬, 글 검색, 인원 거르기는 서버에 없으므로 서버 쪽 일이 먼저다. 이후로 둔다.

**확인할 것**

- **인원으로 찾기는 서버에 없다.** [화면 목록](#b-trpg)의 B1 목적에는 "인원"이 있지만 거르는 조건은 장르와 태그뿐이다. 추천 인원은 카드에 보이기만 한다. 서버에 조건을 더할지, 첫 출시에서 뺄지 정한다. (이슈 #428)
- 제목·소개 글 검색, 정렬 바꾸기, 장르 둘 이상 걸기도 없다.
- **로그인하지 않으면 목록을 못 본다**(401). A1 의 "공개 목록"을 로그인 전에 보여 줄지 정한다. 보여 주려면 서버의 이 두 경로를 열어야 한다. (이슈 #428)
- 만든 사람 이름은 `creator_id` 만 온다. 인증 서버에서 이름을 찾는 길(한꺼번에 여러 명)이 있는지 확인한다.
- 표지 그림, 플레이 횟수, 인기 같은 칸은 서버에 없다.

### B2 시나리오 소개

**1. 목적과 경로**

이 시나리오로 한 판을 할지 정한다. 소개를 읽고 테이블을 만들거나, 이미 열린 테이블을 찾아 간다.

- 오는 경로: B1 의 카드, 시나리오 주소를 받은 사람. 테이블의 응답(`TableSummary`, `TableDetail`)에는 `scenario_id` 가 없어서 B3·B6 에서 이리로 오는 길은 지금 없다(아래 확인할 것).
- 나가는 길: "테이블 만들기"는 B4, "열린 테이블 보기"는 B3 의 이 시나리오 필터.

**2. 보여 주는 정보와 출처**

`GET /listings/{scenario_id}` 의 `PublicListing` 이다. B1 의 카드와 같은 칸에 긴 소개글이 더 있다.

| 정보 | 서버의 칸 | 비고 |
| --- | --- | --- |
| 소개글 | `description` | 최대 5000 자 |
| 위 표의 나머지 | B1 의 표와 같다 | 제목, 한 줄 소개, 장르, 태그, 등급, 추천 인원, 만든 사람, 판, 공개한 때 |

서버가 일부러 보내지 않는 것: 판의 굳힌 내용(GM 전용 글이 들어 있다), 초안, 공개하지 않은 판. `GET /scenarios/{id}` 와 `/versions/{n}` 은 만든 사람 자신만 읽을 수 있다.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 테이블 만들기 | B4 로 이동 | `scenario_id` 를 들고 간다. 판을 비우면 지금 공개 중인 판이 된다 |
| 열린 테이블 보기 | `GET /tables/lobby?scenario_id=...` | 모집 중이고 자리가 남은 공개 테이블이다(B3) |
| 태그 누르기 | B1 로 이동 | 그 태그로 거른다 |
| 신고 | 계획 | E4 에서 받는다. 게임 서버에 신고를 받는 경로는 아직 없다 |

**4. 버튼이 비활성인 조건**

- 성인용이고 성인 확인이 안 된 사람에게는 이 시나리오가 **없는 것**으로 보인다(404). 403 이 아니다.
- 공개가 내려갔거나 지워진 시나리오도 같은 404 다. 서버는 둘을 구분해 알려 주지 않는다.
- 크레딧이 모자란다고 만들기가 막히지는 않는다. 값은 라운드마다 매겨진다(B8).

**5. 상태**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 로딩 | | 소개글 모양의 자리 표시 |
| 없음 | 404 | "볼 수 없는 시나리오입니다". 공개가 끝났는지, 등급 때문인지는 알려 주지 않는다. B1 로 돌아가는 길을 둔다 |
| 로그인하지 않음 | 401 | 로그인(A2)으로 보낸다. 끝난 뒤 이 화면으로 돌아온다 |
| 연결 실패 | | 다시 시도 |

**6. PC 와 모바일**

초안이다.

- PC: 왼쪽에 소개글, 오른쪽에 붙어 있는 패널(등급, 추천 인원, 장르, "테이블 만들기", "열린 테이블 보기").
- 모바일: 소개글을 먼저, "테이블 만들기"는 아래에 고정한다.

**7. 첫 출시**

들어간다(필수 TRPG 묶음). 평가는 이후다.

**확인할 것**

- **스타팅 목록, 허용된 캐릭터 방식, 프리젠, 추천 서술 모델은 테이블을 만들기 전에는 읽을 길이 없다.** `PublicListing` 에 없고, 판을 읽는 길은 만든 사람 전용이다. 테이블이 만들어진 뒤에야 `TableDetail` 이 `opening`, `character_modes`, 프리젠 목록을 준다. 그래서 B4 의 스타팅 고르기(`opening_index`)와 캐릭터 방식 좁히기는 남의 시나리오에서는 값을 보고 고를 수 없다. 서버에 읽는 길을 더하는 일이 필요하다. 스타팅은 최대 5 개이고 하나에 2000 자까지다. (이슈 #428)
- **평가는 서버에 없다.** 별점이든 댓글이든 아직 칸도 경로도 없다. 평가를 게시판 서비스의 댓글로 둘지, 게임 서버에 둘지 정해지지 않았다. 정해질 때까지 화면 목록의 "평가"는 비워 둔다.
- 테이블의 응답에 `scenario_id` 가 없다. 로비의 카드나 테이블 방에서 "이 시나리오 소개"로 가려면 서버가 그 값을 줘야 한다. (이슈 #428)
- 새 판이 공개되면 이미 열린 테이블은 만들 때의 판을 그대로 쓴다. 소개 화면에 "공개 판이 바뀌었다"는 표시가 필요한지는 정하지 않았다.
- 신고의 대상이 시나리오일 때 어느 서비스가 받는지는 E4 에서 정한다.

### B3 테이블 로비

**1. 목적과 경로**

들어갈 테이블을 찾는다. 공개 테이블에 들어가거나, 초대 코드로 들어가거나, 앉아 있는 내 테이블로 돌아간다.

- 오는 경로: A1 탐색, B2 시나리오 소개(그 시나리오의 테이블만 거른다), 마이페이지.
- 나가는 길: 들어가면 테이블 방(B6)의 모집 중 상태로 간다. 테이블을 만들려면 B4 로 간다.

**2. 보여 주는 정보와 출처**

| 영역 | 보이는 것 | 출처(게임 서버) |
| --- | --- | --- |
| 공개 테이블 | 모집 중이고 자리가 남은 것만, 최근에 만든 것부터 | `GET /tables/lobby`(`?scenario_id=` 로 거른다) |
| 한 줄 정보 | 제목, 등급, 인원(`member_count` / `capacity`), 비밀번호 여부(`has_password`), 문체, 라운드 시간 제한, 서술 모델, 크레딧 기다리기, 쪽지 알림, 장부 초안 | `TableSummary` 의 칸. 들어가기 전에 알아야 할 설정이 여기에 모두 있다 |
| 서술 모델의 이름과 값 | 모델 이름과 1인 1라운드의 값 | `TableSummary.narration_model` 의 이름표를 `GET /tables/narration-models` 에서 찾는다(B8) |
| 내 테이블 | 내가 앉아 있는 테이블 | `GET /tables` |

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 공개 테이블에 들어가기 | `POST /tables/{id}/join` `{password?}` | 비밀번호가 걸려 있으면 보낸다 |
| 초대 코드로 들어가기 | `POST /tables/join` `{invite_code}` | 로비에 없는 테이블에도 들어간다 |
| 시나리오로 거르기 | 로비에 `?scenario_id=` | |
| 내 테이블로 돌아가기 | `GET /tables` 에서 고른다 | 이어하기 |
| 테이블 만들기 | B4 | |

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 자리가 없음, 모집 중이 아님, 이미 앉아 있음 | 충돌 오류(`table_full`, `not_recruiting`, `already_seated`) | 목록은 들어가는 순간에 달라졌을 수 있다. 정상 흐름으로 다루고 목록을 다시 읽는다 |
| 비밀번호가 틀림 | 틀렸다는 답. 너무 많이 틀리면 한동안 429 | 틀린 이유를 자세히 말하지 않는다. 429 면 잠시 뒤에 다시 하라고 안내한다 |
| 성인용 테이블 | 로비에는 없는 것으로 보인다. 초대 코드로 알게 된 경우에만 403 | 로비에서 가린다. 403 이면 인증으로 가는 길을 안내한다(#59) |

**5. 상태**

공통 상태(아래)에 더해 이 화면만의 것이다.

| 상태 | 화면의 원칙 |
| --- | --- |
| 로비가 비었음 | 첫 테이블을 만드는 길(B4)을 안내한다 |
| 로비는 실시간이 아니다 | 스트림은 테이블 안에만 있다. 화면을 열 때와 당겨서 새로 고칠 때 읽는다 |
| 들어간 직후 | 테이블 방(B6)으로 보낸다. 캐릭터가 없으면 B5 로 이어진다 |

**6. PC 와 모바일**

- PC: 위에 시나리오 걸러보기, 아래에 카드 목록. 오른쪽에 내 테이블.
- 모바일: 탭으로 "로비"와 "내 테이블"을 나눈다. 한 줄 정보는 접어 두고 눌러서 펼친다.

**7. 첫 출시**

들어간다(필수 TRPG 묶음).

**확인할 것**

- 로비를 거르는 값은 시나리오 하나뿐이다(장르, 태그, 인원은 없다). 필요하면 서버에 더해야 한다
- 비밀번호를 너무 많이 틀렸을 때 429 의 답에 기다릴 시간이 실려 오는지
- 한 번에 읽는 개수와 페이지 넘기는 방식(`Paging` 의 기본값)

### B4 테이블 만들기

**1. 목적과 경로**

시나리오 하나로 테이블을 연다. 만든 사람이 방장이 되어 앉는다.

- 오는 경로: B2 시나리오 소개에서 "테이블 만들기", B3 에서 만들기.
- 나가는 길: 만들면 테이블 방(B6)의 모집 중 상태로 간다. 방장에게는 초대 코드가 온다.

**2. 입력과 출처**

| 설정 | 서버의 칸 | 기본값과 제약 |
| --- | --- | --- |
| 시나리오와 판 | `scenario_id`, `version` | 판을 비우면 공개 중인 판. 번호를 적는 것은 자기 시나리오일 때만 |
| 스타팅 | `opening_index` | 판의 스타팅 중 몇 번째(0 부터) |
| 정원 | `capacity` | 방장을 포함해 1~4 명(`TABLE_MAX_PLAYERS`). 시나리오의 추천 인원(`recommended_players`)은 참고일 뿐 막지 않는다 |
| 로비에 보이기 | `is_public` | 만든 뒤에 바꿀 수 없다 |
| 비밀번호 | `password` | 로비에 보이는 테이블에만 건다. 4~64 자, 앞뒤 공백을 떼지 않는다 |
| 캐릭터 방식 | `character_modes` | 판이 허용한 것 안에서 좁힌다. 만든 뒤에 바꿀 수 없다 |
| 서술 문체 | `narration_style` | 비우면 시나리오의 추천. 방장이 나중에 바꿀 수 있다 |
| 라운드 시간 제한 | `round_time_limit` | 기본 5 분. `null` 이면 제한이 없다 |
| 서술 모델 | `narration_model` | 비우면 시나리오의 추천 모델, 쓸 수 없으면 같은 회사의 대체 모델. 고를 수 있는 것은 `GET /tables/narration-models`(B8) |
| 크레딧 기다리기 | `credit_wait_seconds`, `remove_short_payers` | 모자란 사람을 기다리는 시간, 지나면 빼고 서술하는가(기본 예) |
| 쪽지 알림 | `whisper_notice` | 기본 끔 |
| 장부 초안 | `ledger_drafts` | 기본 끔 |

만든 뒤에 방장이 바꿀 수 있는 것은 문체, 라운드 시간 제한, 서술 모델, 크레딧 기다리기, 쪽지 알림, 장부 초안이다. 로비에 보이기와 캐릭터 방식은 바꿀 수 없다.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 만들기 | `POST /tables` | 201 과 테이블을 돌려준다. 만든 사람이 방장으로 앉는다 |

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 서술 모델이 정해지지 않음 | 422 `narration_model` | 시나리오의 추천도 대체도 없는 경우다. 모델을 고르게 하고 다시 보낸다 |
| 비밀번호가 있는데 비공개 | 422 | 비공개를 고르면 비밀번호 칸을 막는다 |
| 정원이 범위 밖, 스타팅이 없음 | 422 | 범위 안에서만 고르게 한다 |
| 성인용 시나리오인데 인증 전 | 403 | 인증으로 가는 길을 안내한다 |

**5. 상태**

- 모바일: 단계로 나눈다(시나리오와 스타팅, 정원과 공개, 자세한 설정).

### B5 캐릭터 만들기·고르기

**1. 목적과 경로**

내 캐릭터를 정한다. 시작 전에 정하고, 진행 중에 죽으면 새 캐릭터를 들인다.

- 오는 경로: 테이블에 앉은 직후(모집 중), 캐릭터가 죽었을 때(진행 중).
- 나가는 길: 모두가 정하면 방장이 테이블을 시작한다(`POST /tables/{id}/start`).

**2. 보여 주는 정보와 출처**

| 영역 | 보이는 것 | 출처(게임 서버) |
| --- | --- | --- |
| 쓸 수 있는 방식 | 프리젠, 직접 쓰기, 능력치를 직접 적기, 점수 사기, 주사위 | `TableDetail.character_modes` |
| 프리젠 | 이름, 설명, 시트, 가져간 사람, 죽었는가 | `TableDetail.pregens[]`(`taken_by`, `dead`) |
| 기본 시트 | 직접 쓰기에서 받는 숫자 | `TableDetail.default_sheet` |
| 규칙 | 능력치의 이름, 점수 사기의 총점과 값표, 주사위 굴리는 법, 점수의 범위 | `TableDetail.rules` |
| 최대 HP | 능력치를 직접 정하면 규칙으로 구한다(기준값과 상한) | `TableDetail.player_made_hp`, 정한 뒤 `sheet.max_hp` |
| 내 굴림 | 굴린 눈과 점수, 굴린 횟수, 다시 굴리기를 받았는가 | `members[].roll`, `TableDetail.reroll_allowed` |
| 보관함 | 내가 저장한 캐릭터들 | `GET /personas` |

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 캐릭터 정하기 | `PUT /tables/{id}/character` | 모집 중에만. 보낸 것으로 캐릭터를 통째로 바꾼다 |
| 프리젠 | `{mode: pregen, pregen_index}` | 이름과 설명을 함께 보내면 그 칸만 고쳐 쓴다 |
| 직접 쓰기 | `{mode: custom, name, description?}` | 숫자는 시나리오의 기본 시트 |
| 능력치 직접 적기 | `{mode: manual, name, abilities}` | 규칙의 점수 범위 안이면 무엇이든 된다. 최대 HP 는 서버가 구한다 |
| 점수 사기 | `{mode: point_buy, name, abilities}` | 규칙의 총점 안에서 살 수 있어야 한다 |
| 주사위 | 먼저 `POST .../character/roll`, 그다음 `{mode: rolled, name, abilities}` | 굴리는 것은 서버다. 굴린 점수를 남김없이 한 번씩 능력치에 놓는다 |
| 보관함에서 가져오기 | 화면이 `GET /personas` 로 읽어 이름, 설명, 능력치를 위의 요청에 담는다 | `CharacterUpdate` 에 보관함 번호 칸이 없다 |
| 보관함에 저장 | `POST .../character/persona` | 프리젠은 저장하지 못한다. 저장한 것은 사본이다 |
| 보관함 관리 | `POST`, `PUT`, `DELETE /personas` | 가져간 테이블은 바뀌지 않는다 |
| 쓰러진 캐릭터 보내기 | `DELETE .../character` | 진행 중에 쓰러져 있을 때만. 죽고, 되돌릴 수 없다 |
| 새 캐릭터 들이기 | `POST .../character`(201) | 진행 중에 내 캐릭터가 죽었을 때만. 주사위 방식이면 먼저 새로 굴린다. 다음 라운드부터 선언한다 |
| 테이블 시작(방장) | `POST .../start` | 모두가 캐릭터를 정해야 한다 |

**4. 버튼이 비활성인 조건**

| 상황 | 서버의 답 | 화면의 처리 |
| --- | --- | --- |
| 허용하지 않은 방식 | `character_mode_not_allowed` | 허용한 방식만 보인다 |
| 이미 가져간 프리젠 | `pregen_taken` | `taken_by` 가 있으면 막는다. 죽은 프리젠(`dead`)은 아무도 고를 수 없다 |
| 이미 굴렸음 | `already_rolled` | 캐릭터 하나에 한 번이다. 방장이 다시 굴리기를 주면 한 번 더 된다 |
| 굴리지 않고 주사위 방식을 확정 | `not_rolled` | 굴리기를 먼저 누르게 한다 |
| 모집 중이 아님 | `not_recruiting` | 시작한 뒤에는 정하기를 막는다 |
| 시작 버튼 | `characters_missing` | 방장이 아니거나 캐릭터를 안 정한 사람이 있으면 막고, 누가 안 정했는지 보인다 |

**5. 상태**

| 상태 | 화면의 원칙 |
| --- | --- |
| 굴린 뒤 | 눈과 점수를 보이고, 점수를 능력치에 놓는 화면으로 간다. 다시 굴리려면 방장의 허락이 필요함을 안내한다 |
| 점수를 놓는 중 | 규칙의 범위와 총점을 실시간으로 계산해 보이되, 맞는지는 서버가 검사한다 |
| 죽은 뒤 | 새 캐릭터를 들이는 길을 보이고, 다음 라운드부터 선언한다고 안내한다 |
| 다른 사람이 정하는 중 | 누가 정했는지 `members` 로 보인다. 시작은 방장의 일이다 |

**6. PC 와 모바일**

- PC: 방식 고르기, 입력, 미리 보기를 한 화면에 둔다.
- 모바일: 단계로 나눈다(방식, 입력, 확인).

**7. 첫 출시**

들어간다(필수 TRPG 묶음). 보관함도 B5 에 넣는다.

**확인할 것**

- `pregens_too_few` 가 어느 때 나는지(프리젠만 허용한 테이블의 정원이 프리젠 수보다 클 때로 보인다)
- 점수 사기의 값표와 주사위 굴리는 법의 모양(`rules.point_buy`, `rules.score_roll`). 화면이 계산하려면 필요하다
- 능력치의 점수 범위와 이름표
- 보관함에서 가져올 때 능력치가 규칙에 맞지 않으면 서버가 거절하는지

### B6 테이블 방(플레이)

**1. 목적과 경로**

한 판을 하는 화면이다. 서술을 읽고, 이번 라운드의 행동을 선언하고, 판정 결과를 보고, 같이 앉은 사람과 이야기한다.

- 오는 경로: B3 로비에서 참가, B4 테이블을 만든 직후, 초대 코드로 참가(`POST /tables/join`), 내 테이블 목록(`GET /tables`)에서 이어하기
- 테이블의 상태: 모집 중, 진행 중, 끝남(`started_at`, `ended_at`). 채팅은 모집 중과 진행 중에 쓸 수 있고, 끝난 테이블에는 쓸 수 없다

**2. 보여 주는 정보와 출처**

| 영역 | 보이는 것 | 출처(게임 서버) |
| --- | --- | --- |
| 서술 | 지나간 라운드의 장면 글과 지금 라운드 | `GET /tables/{id}/rounds`, `GET .../rounds/current` 의 `scene`, `number`, `status` |
| 선언 | 선언을 받는 동안은 자기 것만 보이고, 마감하면(닫는 중부터) 모두의 글과 행동이 보인다 | `RoundOut.declarations[].content`, `action`(남의 것은 `null`) |
| 판정 | 눈, 목표값, 보정, 부상, 노려 치기, 불리 여부. 굴림은 공개라 모두에게 보인다 | `declarations[].outcome` |
| 기다리는 사람 | 아직 선언을 내지 않은 사람 | `waiting_for` |
| 마감 시각 | 선언을 받는 마감 | `deadline_at` |
| 서술 모델과 값 | 이 라운드에 쓴 모델, 값 | `narration_model`, `price`. 사람마다의 청구는 `GET .../rounds/{n}/charges`(앉은 사람만, 라운드를 연 뒤 몇 초 안에 걸린다. 그 전에는 `null`) |
| 죽음의 굴림 | 쓰러진 캐릭터의 굴림과 성공·실패 수 | `death_saves` |
| 도착 | 새로 들어온 사람 | `arrivals` |
| 장면의 인물 | 행동의 대상으로 고를 인물. 장면에 이름이나 호칭이 나온 인물만 | `GET .../rounds/current/people` |
| 채팅, 쪽지 | 판 채팅과 자기 쪽지함 | `GET .../chat`, 스트림의 `chat_message`, `whisper` |
| 입력 중 | 다른 사람이 글을 치는 중 | 스트림의 `typing`(받는 쪽이 5초쯤 뒤에 스스로 지운다) |
| 상태 패널(B7) | HP, 능력치, 부상, 소지품, 장소, 퀘스트, 맵 | `TableDetail.members[].character`(`hp`, `max_hp`, `death_successes`, `death_failures`, `dead`, `injuries`, `items`, `place_id`), `quests`, `map` |
| 일어난 일 | 물건, 퀘스트, 이동 같은 변화의 기록 | `GET .../events`, 스트림의 `table_event` |

화면에 보이는 값은 모두 서버가 준 것이다. 화면이 HP나 소지품을 계산하지 않는다.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 선언 내기·고치기 | `PUT .../rounds/current/declaration` `{content, action?}` | 다시 내면 앞의 것을 통째로 바꾼다. 행동을 빼고 다시 내면 행동도 없어진다. 모두가 내면 라운드가 닫히기 시작한다 |
| 행동 붙이기 | 위와 같음 | 한 선언에 행동은 하나다. 종류는 판정, 치료, 지목, 물건 쓰기, 건네기, 가기, 찾기, 쉬기(`engine/action.py`) |
| 채팅 쓰기 | `POST .../chat` | 쓰면 모두의 스트림으로 간다 |
| 입력 중 알리기 | `POST .../chat/typing` | 글자를 치는 동안 3초쯤에 한 번 부른다 |
| 나가기 | `DELETE .../members/me` | |
| 라운드 닫기(방장) | `POST .../rounds/current/close` | 선언을 기다리지 않고 넘어간다. 접수만 하고(202) 서술은 뒤에서 돈다. 닫는 중인 채 오래 멈춰 있으면 다시 불러 서술을 다시 맡긴다 |
| 테이블 운영(방장) | 내보내기, 방장 넘기기, 시작·끝내기, 서술 문체·모델, 시간 제한, 크레딧 기다리기, 쪽지 알림 | 첫 출시에 넣는다 |
| 결과를 정하는 권한(방장) | 물건 주기·빼앗기, 퀘스트 바꾸기, 캐릭터 옮기기, 장부 초안 받아들이기 | **임시 권한이다(#367).** 엔진의 규칙으로 옮겨 가며 지워질 것이므로 첫 출시의 화면에는 넣지 않는다. 퀘스트의 성공은 이제 엔진이 조건을 보고 정한다. 방장이 성공으로 바꾸면 409 `quest_success_by_engine` 이고, 방장은 퀘스트를 드러내기(`active`)와 실패(`failed`)로만 바꿀 수 있다 |

**4. 버튼이 비활성인 조건**

| 버튼 | 비활성일 때 |
| --- | --- |
| 선언 보내기 | 라운드가 열려 있지 않다(닫는 중, 닫힘). 테이블이 진행 중이 아니다. 글이 비었거나 서버의 길이 한도를 넘었다 |
| 행동 고르기 | 테이블의 `rules` 에 없는 행동이나 능력은 보이지 않는다(서버도 거절한다). 물건 쓰기·건네기는 내 소지품에서, 가기·찾기는 맵의 아는 장소에서 고른다 |
| 라운드 닫기 | 방장이 아니거나 라운드를 열고 있지 않다 |
| 채팅 | 끝난 테이블 |
| 서술을 기다리는 중 | 이 라운드의 서술 값을 걸지 못한 사람이 있으면 서버가 이벤트 `narration_credits_short`(`round`, `user_id`, `reason`)를 앉은 사람 모두에게 보낸다. `reason` 이 `insufficient` 면 크레딧, `gold_required` 면 골드가 모자란 것이다. 서버가 클라이언트에게 402 로 답하는 곳은 없다. 부족한 금액은 오지 않으므로 충전으로 가는 길만 보인다 |

**5. 상태**

공통 상태(아래)에 더해 이 화면만의 것이다.

| 상태 | 서버 쪽 근거 | 화면의 원칙 |
| --- | --- | --- |
| 닫는 중 | `status` 가 `closing`. 판정은 끝났고 서술이 뒤에서 돈다 | 판정 결과를 먼저 보이고, 서술이 오면 이어 붙인다. 다음 라운드가 열린 것은 스트림으로 온다 |
| 서술 실패 | `narration_failed_at`, `narration_failures` | 방장에게 다시 맡기는 길을 보인다. 다른 모델로 몰래 바꾸지 않는다 |
| 끊김 | 스트림이 끊김 | 마지막으로 받은 메시지의 `id` 를 `Last-Event-ID` 로 보내 다시 붙는다. 그 값은 "이벤트 번호-채팅 번호-쪽지 번호"다 |
| 서버가 닫음 | `closed` 메시지의 이유 `not_seated`, `table_ended`, `token_expired` | `token_expired` 는 토큰을 갱신하고 다시 붙는다. `not_seated` 는 자리가 없다는 안내, `table_ended` 는 끝난 판의 읽기 화면으로 보낸다 |
| 처음 붙기 | REST 로 지금까지를 읽는다 | 마지막 번호를 `events_after`, `messages_after`, `whispers_after` 에 적어 스트림을 연다 |

스트림은 `fetch` 로 읽는다. 브라우저의 `EventSource` 는 `Authorization` 머리말을 붙이지 못한다.

**6. PC 와 모바일**

- PC: 가운데에 서술과 선언, 한쪽에 상태 패널과 채팅을 함께 보인다. 단축키는 `I` 인벤토리, `C` 상태, `J` 퀘스트와 기록, `Esc` 닫기.
- 모바일: 서술과 선언 입력이 중심이다. 상태와 채팅은 필요할 때 펼친다. 선언 입력은 가상 키보드 위에 붙인다. 앱으로 감쌀 때 앱 복귀 뒤 스트림 재접속을 확인한다.

**7. 첫 출시**

들어간다(필수 TRPG 묶음). 방장의 결과를 정하는 임시 권한 화면과 B10(되돌리기)은 이후다.

**확인할 것**

- 죽거나 쓰러진 캐릭터의 선언을 서버가 받는지, 못 받으면 어떤 오류인지
- 서술이 만들어지는 동안의 조각이 스트림으로 나가는지. 모델 쪽은 흘려 받지만(`ai/streaming.py`) 앉은 사람에게 나가는지는 확인하지 못했다. 나가지 않으면 "닫는 중"에서 완성된 서술이 한꺼번에 온다
- `table_event` 의 종류 전체. 화면이 처리해야 할 이벤트 목록이 필요하다
- 선언 글의 길이 한도(`DECLARATION_MAX_LENGTH`)의 값

| 상태 | 근거 | 화면의 원칙 |
| --- | --- | --- |
| 시작 전 | 퀘스트가 비어 있고, 맵은 처음부터 아는 것만 있다 | 비어 있는 이유를 안내한다(시작하면 채워진다) |
| 맵이 없는 판 | `map` 이 `null` | 장소 칸을 숨긴다 |
| 값이 바뀜 | 스트림의 `table_event`(HP, 부상, 물건, 퀘스트, 이동) | 이벤트가 오면 테이블을 다시 읽는다. 한 라운드가 닫힐 때 이벤트가 여럿 오므로 묶어서 한 번만 읽는다 |
| 어긋남 | 화면의 값과 서버의 값이 다르다 | 서버가 맞다. 다시 읽은 값으로 덮는다 |
| 기한이 가까움·지남 | `due_at` | 지나면 서버가 다음에 닫히는 라운드에서 실패로 바꾼다. 화면이 스스로 바꾸지 않는다 |

값이 바뀔 때의 두 가지 길이다.

- 다시 읽기: 이벤트가 올 때마다 테이블 전체를 읽는다. 간단하고 서버와 어긋나지 않지만 요청이 늘어난다. 이벤트를 묶으면 한 라운드에 한두 번이다.
- 이벤트로 고치기: 이벤트의 내용으로 화면의 값을 고친다. 요청은 적지만 이벤트의 종류마다 처리를 짜야 하고, 하나를 놓치면 서버와 어긋난다.

첫 출시는 다시 읽기로 간다. 요청이 문제가 되면 그때 이벤트로 고치기를 일부 쓴다.

- PC: 오른쪽에 패널을 계속 열어 둔다. HP 와 부상은 늘 보인다.
- 모바일: 화면 위에 HP 한 줄만 늘 보이고, 나머지는 `C`, `I`, `J` 에 해당하는 탭으로 펼친다.

### B8 서술 모델 고르기·값 안내

**1. 목적과 경로**

방장이 테이블의 서술 모델을 고르고, 그 모델이 한 라운드에 얼마인지 미리 안다. 값은 결제 서버가 정하고, 게임 서버는 받은 값을 그대로 보여 준다.

- 오는 경로: B4 테이블 만들기의 "서술 모델", B6 테이블 방의 운영 메뉴(방장), 모델이 곧 은퇴한다는 알림.
- 나가는 길: 고르면 B4 또는 B6 으로 돌아간다.
- 따로 화면을 두기보다 B4·B6 안의 고르는 창(시트)으로 쓴다. 로그인한 사람에게만 열린다(가격 수집을 막으려는 서버의 뜻이다).

**2. 보여 주는 정보와 출처**

`GET /tables/narration-models` 의 `models[]` 한 줄이 `NarrationModelOut` 이다.

| 정보 | 서버의 칸 | 비고 |
| --- | --- | --- |
| 이름표, 보이는 이름 | `slug`, `display_name` | 고를 때 보내는 것은 `slug` 다 |
| 회사 | `vendor` | 서버가 회사, 보이는 이름 순서로 준다. 화면이 회사별로 묶는다 |
| 묶음 | `grade` | `basic`, `standard`, `premium`. 목록을 묶어 보이는 데만 쓴다 |
| 1인 1라운드의 값 | `credits` | 글자로 온다(`"120"`). 화면이 숫자로 바꾸어 계산하지 않고 그대로 보인다 |
| 내는 방법 | `tier` | `premium` 이면 골드(산 크레딧)로만 낸다. `standard`, `basic` 은 실버(무료 크레딧)를 먼저 쓰고 모자라면 골드 |
| 행사가 | `promo` | 지금 값이 행사가인가 |
| 예약된 바뀜 | `next.credits`, `next.tier`, `next.promo`, `next.effective_at` | `next.credits` 가 `null` 이면 그때부터 팔지 않는다. 화면이 "12월 1일부터 240", "11월 21일까지 행사가"처럼 미리 알린다 |
| 은퇴 | `retires_on` | 이 날부터 쓰지 않는다. 정해지지 않았으면 `null` |

- 목록에 있는 모델은 **지금 고를 수 있는 것**뿐이다. 모델 목록에서 켜져 있고, 은퇴하지 않았고, 결제 서버가 지금 팔고 있어야 한다. 목록에 없는 모델은 그 이유(꺼짐, 은퇴, 판매 중지)를 구분해 알려 주지 않는다.
- 응답의 `free` 가 참이면 결제 서버 없이 도는 서버다(로컬·시험). 모델은 모두 나오지만 `credits`, `tier` 가 `null` 이다. 값 칸을 숨긴다.
- 고른 모델의 값은 테이블에 이미 있는 값으로도 읽는다. 라운드를 열 때 서버가 그 모델의 지금 값을 알리고(`RoundOut.price`), 사람마다 실제로 홀드한 값은 `GET .../rounds/{n}/charges` 에 있다(B6).

**6. PC 와 모바일**

초안이다.

- PC: 회사별로 묶은 목록. 줄마다 이름, 값, 내는 방법(골드/실버), 행사·종료 표시. 오른쪽에 지금 고른 모델.
- 모바일: 아래에서 올라오는 시트. 줄을 누르면 고르고 닫는다. 값은 줄의 오른쪽에 둔다.

**7. 첫 출시**

들어간다(필수 TRPG 묶음). 값을 보이는 것까지가 첫 출시이고, "한 판에 대략 얼마" 같은 환산은 이후다.

**확인할 것**

- **"한 판에 대략 얼마"는 서버에 없다.** 서버가 주는 값은 1인 1라운드의 값뿐이다. 한 판은 라운드 수와 인원에 따라 달라서 화면이 어림으로 곱해 보일지, 서버가 어림값을 줄지 정해야 한다. 어림값이면 어떤 라운드 수를 기준으로 하는지도 정한다.
- 목록에 값이 없을 때(`free`)가 로컬 시험만인지, 실제로 값을 안 받는 서비스가 있을 수 있는지.
- 골드·실버 잔액은 게임 서버 응답에 없다. 고르는 창에서 "내 골드로 몇 라운드"를 보이려면 결제 서버의 지갑(A6)을 따로 읽는다. 읽을지, 라운드를 열 때 거절을 기다릴지 정한다.
- 모델의 소개글(어떤 문체인지, 빠른지)과 평가 결과를 보이는 칸은 서버에 없다. 이름과 묶음(`grade`)만 있다.
- 시나리오가 추천한 모델과 방장이 고른 모델이 다를 때 알림(`recommended_model` 이 이벤트에 실려 온다)을 어디에 어떻게 보일지.

### B9 제작 도구

**1. 목적과 경로**

제작자가 재료(세계관, 룰북, 로어북, 몬스터 모음)를 만들고, 그것을 모아 시나리오를 조립하고, 게시해서 공개한다.

- 오는 경로: 마이페이지(A5) 또는 탐색(B1)의 "만들기".
- 나가는 길: 공개하면 B2 시나리오 소개에 나타난다.
- 일이 길고 칸이 많다. 한 화면이 아니라 **재료 목록 → 재료 편집 → 시나리오 조립 → 게시와 공개**의 흐름이다.

**2. 보여 주는 정보와 출처**

모두 만든 사람 자신의 것만 읽고 쓴다. 남의 자산은 있어도 404(없는 것)이고, 다른 사람의 자산을 가리키면 422다.

| 재료 | 경로 | 칸 | 비고 |
| --- | --- | --- | --- |
| 세계관 | `/worlds` | `title`, `description`, `setting`(8000 자), `gm_notes`(4000 자) | `gm_notes` 는 GM 전용이라 테이블 참가자에게 가지 않는다 |
| 룰북 | `/rulebooks` | `title`, `description`, `gm_guide`(4000 자), `template` | 규칙(`rules`)을 직접 받지 않는다. 템플릿 이름만 고르고 규칙은 서버가 채운다. 응답에는 `rules` 가 있다 |
| 로어북 | `/lorebooks`, `/lorebooks/{id}/entries` | 로어북은 `title`, `description`. 항목은 `name`, `keywords`, `content`, `kind`, `true_names` | 항목의 종류(`kind`)는 `person`, `place`, `item`, `faction`, `species`, `legend`, `event`, `other` 다. 기본은 `other` |
| 몬스터 모음 | `/bestiaries`, `/bestiaries/{id}/monsters` | 모음은 `title`, `description`. 몬스터는 `name`, `content`, `kind`, `unique` | `unique` 는 판 전체에서 한 마리만 두는 네임드다 |
| 시나리오 | `/scenarios` | 아래 | |

공통:

- 제목은 앞뒤 공백을 떼고 1~100 자, 소개는 1000 자까지다.
- 목록은 `GET /worlds` 처럼 종류마다 있고, 쪽은 `limit`(기본 20, 최대 100)과 `offset`, 응답은 `items`, `total` 이다. 목록은 긴 글을 싣지 않는다. 열어야 긴 글이 온다.
- 지금 `visibility` 는 `private` 하나뿐이다. 재료는 공개하지 않는다.
- 재료는 등급을 가리지 않는다. 등급(`all`, `adult`)은 시나리오를 조립할 때 정한다.
- 모르는 칸이 오면 거부한다(`extra='forbid'`). 보낸 칸만 바뀐다(`PATCH`). 글을 비우려면 빈 문자열을 보낸다.

시나리오(`POST /scenarios`)는 **제목, 추천 서술 모델(`narration_model`)만 필수**이고 나머지는 비워 두고 임시 저장할 수 있다. 칸의 묶음과 한도:

| 묶음 | 칸 | 한도 |
| --- | --- | --- |
| 재료 연결 | `rulebook_id`, `world_id`, `lorebook_ids`, `bestiary_ids` | 로어북 10, 몬스터 모음 10 |
| 스타팅 | `openings` | 5 개, 하나에 2000 자 |
| 인원과 캐릭터 | `recommended_players`, `character_modes`, `pregens`, `default_sheet`, `player_made_hp`, `reroll_allowed` | 추천 인원 1~4, 프리젠 8 |
| 인물·물건·퀘스트 | `npc_sheets`, `items`, `starting_items`, `quests` | 인물 시트 100, 물건 규칙 100, 시작 물건 20, 퀘스트 50(조건은 퀘스트마다 5) |
| 지도 | `start_place`, `routes`, `landmarks` | 길 200, 명소 100 |
| 몬스터 배치 | `monster_sheets`, `encounters` | 몬스터 시트 100, 조우 50 |
| 서술 | `narration_style`, `narration_model`, `clock` | 문체는 안 보내면 정통. 시계는 안 보내면 1일째 8시, 한 라운드에 10분 |
| 등급 | `rating` | 안 보내면 `all`. 성인용은 직접 골라야 한다 |

| 행동 | 호출 | 동작 |

| --- | --- | --- |
| 게시할 조건이 모자람 | 409 `{detail, problems[]}` | `problems` 는 갖추지 못한 조건 **전부**다. 하나씩 고치고 다시 시도하지 않게 한 번에 준다. 화면이 칸을 짚어 보인다(아래 표) |
| 공개할 조건이 모자람 | 409 `{detail, problems[]}` | 같은 모양이다 |
| 다른 자산이 쓰는 재료를 지움 | 409 `{detail, used_by[{id, title}]}` | 쓰는 시나리오의 목록을 보이고 거기서 떼어 낸 뒤 다시 지우게 한다 |
| 가리키는 재료가 없음(남의 것 포함) | 422 | 어느 칸(`field`)인지 보이고 다시 고르게 한다 |
| 성인 인증 전에 성인용으로 올림 | 403 `code: adult_content_required` | 본인인증(A3)으로 안내한다 |

**6. PC 와 모바일**

초안이다.

- PC: 왼쪽에 재료 종류 목록, 가운데 편집, 오른쪽에 "게시 조건" 점검 패널. 시나리오는 칸이 많아 묶음(위의 표)마다 접는 섹션으로 둔다.
- 모바일: 편집은 읽기와 간단한 고치기까지만 두고, 긴 조립은 PC 를 권한다. 이 선택 자체를 정해야 한다(확인할 것).

**7. 첫 출시**

이후다([첫 출시의 범위](#첫-출시의-범위)). 다만 첫 출시의 B1~B8 은 공개된 시나리오가 있어야 하므로, 첫 시나리오는 이 화면 없이 넣어야 한다(아래 확인할 것).

**확인할 것**

- **B9 가 이후라면 첫 시나리오를 누가 어떻게 넣는지 정해야 한다.** 서버의 경로로 직접 넣을 수는 있다. 운영자가 스크립트로 넣을지, 제작자 몇 명에게만 이 화면을 열어 줄지 정한다.
- **게시 조건을 미리 알 길이 없다.** `problems` 는 게시를 시도해야 온다. 시나리오를 저장할 때 같은 검사를 돌려 주는 경로(드라이 런)가 있으면 화면이 실시간으로 점검 패널을 보일 수 있다. 서버에 더할지 정한다. (이슈 #428)
- 판의 로어북 색인(벡터)이 끝났는지 알려 주는 칸이 없다. 게시 직후 바로 테이블을 열었을 때 서술에 로어가 반영되는지의 기준이 필요하다.
- 시트, 길, 퀘스트, 조우의 모양이 크다. 화면이 이 칸들을 폼으로 짜는 데 필요한 응답 모양(`Sheet`, `RouteRule`, `QuestRule`, `Encounter`, `ItemRule`)은 이 문서에 옮기지 않았다. B9 를 시안으로 넘기기 전에 서버의 `app/assets/scenarios/schemas.py` 에서 칸마다 옮긴다.
- 몬스터 `kind` 의 값 목록, 룰북 `template` 의 선택지를 화면이 어디서 읽는지(응답에 목록이 있는지)는 확인하지 못했다.
- 재료를 공개해서 다른 제작자가 쓰게 하는 길이 없다(`visibility` 가 `private` 하나). 제품에서 약속하는지 정한다.
- 모바일에서 어디까지 편집하게 할지.

### B10 라운드 기록·되돌리기

**1. 목적과 경로**

지나간 라운드를 처음부터 순서대로 다시 읽는다. 중간에 들어온 사람이 이야기를 따라잡고, 끝난 판을 되읽는다. 되돌리기(잘못된 라운드를 물리기)는 서버에 없다(아래 확인할 것).

- 오는 경로: B6 테이블 방의 "지난 기록", 내 테이블 목록(`GET /tables`)에서 끝난 테이블.
- 나가는 길: B6.
- 읽기만 하는 화면이다. 별도 화면으로 두지 않고 B6 안에서 위로 스크롤하면 이어지는 기록으로 쓸 수 있다.

**2. 보여 주는 정보와 출처**

`GET /tables/{id}/rounds` 가 라운드를 **처음 것부터** 돌려준다. 한 줄이 `RoundOut` 이다. 번호로 하나만 읽는 길은 `GET .../rounds/{number}` 다.

| 정보 | 서버의 칸 | 비고 |
| --- | --- | --- |
| 번호 | `number` | 1 부터 |
| 장면 | `scene` | 이 라운드를 여는 GM 의 서술이다 |
| 상태 | `status` | `open`(선언을 받는 중), `closing`(서술 중), `closed` |
| 선언과 결과 | `declarations[]` 의 `character_name`, `content`, `action`, `outcome` | 선언을 마감하면 모두의 것이 보인다. 받는 중인 라운드는 남의 글과 행동이 `null` 이다 |
| 죽음의 굴림 | `death_saves[]` | 마감한 뒤 모두에게 보인다 |
| 새로 들어온 캐릭터 | `arrivals[]` | |
| 시각 | `created_at`, `closing_at`, `closed_at` | |
| 서술 모델과 값 | `narration_model`, `price` | |

- 쪽은 `limit`(기본 20, 최대 100)과 `offset` 으로 넘기고, `total` 이 전체 개수다.
- 이벤트로도 읽을 수 있다. `GET /tables/{id}/events?after=` 는 일어난 순서대로 주사위, HP, 물건, 퀘스트, 이동을 준다. 못 본 것만 받으려고 마지막 번호를 `after` 로 준다. 응답의 `last_sequence` 가 마지막 번호다. 화면이 라운드의 본문을 읽는 데는 `rounds` 를 쓰고, 일어난 일의 목록(타임라인)에는 `events` 를 쓴다.

**3. 할 수 있는 행동**

| 행동 | 호출 | 동작 |
| --- | --- | --- |
| 기록 읽기 | `GET /tables/{id}/rounds?limit=&offset=` | 처음 것부터 쪽으로 읽는다 |
| 라운드 하나 읽기 | `GET .../rounds/{number}` | 번호로 건너뛴다 |
| 일어난 일 읽기 | `GET .../events?after=` | 타임라인 |
| 되돌리기 | 없음 | 아래 확인할 것 |

**4. 버튼이 비활성인 조건**

- 이 테이블에 앉아 있어야 읽을 수 있다. 앉지 않은 사람에게는 "없는 테이블"이다(404). **나간 사람과 내보내진 사람은 자리가 지워지므로 그 판의 기록을 더 읽지 못한다.**
- 끝난 테이블은 앉아 있던 사람에게 그대로 읽힌다.

| 상황 | 서버의 답 | 화면의 처리 |

초안이다.

**7. 첫 출시**

읽기는 B6 안의 지난 기록으로 들어간다(`rounds` 는 B6 가 이미 쓴다). 별도 화면과 되돌리기는 이후다.

**확인할 것**

- **되돌리기는 서버에 없고, 있어야 하는지부터 정해야 한다.** 이 서버는 죽음, 끝난 퀘스트, 이미 확정한 서술 값을 되돌리지 않는 규칙 위에 있다. 선택지는 셋이다.
  - 기록만 읽게 하고 되돌리지 않는다. 가장 단순하고 상태가 어긋날 일이 없다.
  - 서술이 마음에 안 들 때 마지막 서술만 다시 맡긴다. 이미 있는 "서술 실패 시 다시 맡기기"의 연장이다. 판정과 상태 변경이 확정되기 전의 서술만 대상으로 해야 안전하다.
  - 라운드 단위로 상태를 복원한다. HP, 소지품, 퀘스트, 시계, 결제 홀드, 기억(벡터)까지 함께 되돌려야 해서 가장 무겁고 어긋나기 쉽다.
  - 우선은 첫째로 두고, 둘째를 이후에 검토하는 것을 권한다.
- 나간 사람이 그 판의 기록을 읽을 수 없다. "내가 했던 판 다시 읽기"를 제품에서 약속한다면 서버가 자리가 지워진 뒤에도 기록을 주는 길(또는 나갈 때 내려받기)을 만들어야 한다. (이슈 #428)
- 끝난 판의 **마지막 라운드의 결과 서술**이 어디에 실리는지 코드로 확인하지 못했다. 라운드의 `scene` 이 "이 라운드를 여는 서술"이라면, 마지막 라운드가 닫힌 뒤의 서술을 읽을 곳이 필요하다.
- 기록은 처음 것부터만 준다. 최근 것부터 읽으려면 `total` 로 `offset` 을 계산해야 한다. 서버에 정렬을 더할지 정한다.
- 서술 글 안 검색, 내려받기(텍스트로 저장)는 서버에 없다.

## 공통 상태

모든 화면에서 같은 방식으로 보여 주는 상태다.

| 상태 | 서버 쪽 근거 | 화면의 원칙 |
| --- | --- | --- |
| 로딩 | 요청 중 | 자리를 유지하는 표시. 긴 서술은 스트리밍으로 보인다 |
| 빈 화면 | 목록이 비었음 | 다음에 할 일을 안내 |
| 오류 | 오류 응답 `{"detail"}` | 원인이 아니라 할 수 있는 것을 알린다. 비밀이나 내부 값을 보이지 않는다 |
| 연결 끊김 | 실시간 스트림(SSE) 끊김 | 자동 재접속, 놓친 기록은 마지막 번호부터 이어 받는다 |
| 크레딧 부족 | 이벤트 `narration_credits_short`(`user_id`, `reason`) | 누가 모자란지와 무엇이 모자란지(크레딧, 골드)를 테이블 모두가 본다. 본인에게는 충전으로 가는 길을 보인다. 기다리는 시간(`credit_wait_seconds`)이 지나면 `member_dropped`(자리에서 뺌) 또는 `narration_credits_released`(값을 돌려주고 라운드는 멈춘 채) 가 온다 |
| 서술 막힘 | 이벤트 `narration_model_not_for_sale`(판매 중지 모델), `narration_credits_short` 의 `reason: gold_required`(골드 없는 멤버) | 누가 왜 막혔는지를 방장에게 알린다. 다른 모델로 몰래 바꾸지 않는다. 방장이 모델을 바꾸면 그 라운드의 값을 새 가격표로 다시 건다 |
| 권한 없음 | 401, 403 | 로그인으로 보내거나 이유를 알린다 |
| 너무 자주 요청 | 429 `too_many_attempts`(인증), 429 `retry_after`(게시판) | 남은 초를 보이고 그동안 버튼을 막는다. 서버마다 칸 이름이 다르다 |
| 토큰 만료 | 401 | 갱신을 한 번만 시도하고 다시 부른다. 갱신도 401 이면 로그인으로 보낸다. 요청마다 따로 갱신하지 않는다(갱신은 한 번에 하나) |
| 서버가 잠시 못 답함 | 503 | 로그아웃시키지 않는다. 결제는 실패로 보이지 않는다(A7) |
| 성인 등급 | 연령 확인 전 | 가리고, 인증으로 가는 길을 안내 |
| 점검·장애 | 점검 중 | 남은 크레딧과 진행 중인 판이 안전함을 알린다 |

## PC 와 모바일

- PC: 대화와 상태(캐릭터, 소지품)를 함께 보인다.
- 모바일: 대화 중심에 필요할 때 상태를 펼친다.
- 제작 도구는 PC 를 우선한다. 모바일은 읽기와 간단한 고치기까지.
- 모바일은 웹을 앱으로 감싸는 방식을 염두에 둔다. 확인할 것: 로그인 유지와 토큰 갱신, 출처와 쿠키, 앱 복귀 때 실시간 재접속, 가상 키보드, 뒤로 가기, 여백.
- UI 테마는 시나리오의 대표 장르 하나가 정한다. 태그는 여럿이고 검색용이며 테마를 바꾸지 않는다. 테마는 겹치지 않는다.
- 단축키 후보: `I` 인벤토리, `C` 상태, `J` 퀘스트와 기록, `Esc` 닫기, `Enter` 보내기와 `Shift+Enter` 줄 바꿈. 입력 중에는 문자 단축키를 막고, 한글 조합 확정 `Enter` 가 전송되지 않게 한다. 끄거나 바꿀 수 있게 할지는 미정.

## 프런트 구조

정했다(2026-10-18).

- **프런트는 하나다.** `/trpg`, `/chat`, `/story` 경로로 나눈 앱 하나를 둔다. 공통 구성요소는 `packages/ui` 로 분리해 두어 나중에 갈라낼 수 있게 한다.
- **앱은 웹을 감싸서 낸다**(Capacitor 같은 방식). 가장 싸게 가는 길이라 골랐다. 안드로이드 전용 개발은 하지 않는다([플랫폼과 제품 방향](platform.md)).
- **PC 와 모바일의 화면은 다르게 둘 수 있다.** 다만 처음에는 반응형 한 벌로 만들고, 구조가 정말 다른 화면만 뷰를 나눈다.

### 두 가지 축

| 축 | 갈리는 것 | 나누는 방법 |
| --- | --- | --- |
| 화면 크기(PC, 모바일) | 레이아웃, 패널을 나란히 놓을지 펼칠지 | 브레이크포인트. 필요한 화면만 뷰를 나눈다 |
| 실행 환경(브라우저, 앱 껍데기) | 결제, 푸시, 앱 복귀 후 재접속, 외부 링크, 저장소 | 얇은 `platform` 어댑터 하나 |

휴대폰 브라우저로 들어온 사람이 PC 화면을 보지 않게, 레이아웃은 환경이 아니라 화면 크기로 정한다.

### 화면마다

| 구분 | 화면 | 방식 |
| --- | --- | --- |
| 뷰를 나눈다 | B6 테이블 방, B7 상태 패널 | PC 는 대화와 상태를 함께, 모바일은 대화 중심에 상태를 펼친다 |
| 뷰를 나눈다 | B9 제작 도구 | PC 가 기본. 모바일은 읽기와 간단한 고치기 뷰만 |
| 반응형 한 벌 | A1~A12, B1~B5, B8, B10 | 목록, 폼, 지갑, 게시판은 레이아웃만 바꾼다 |
| 아직 | C(chat), D(story), E(관리자) | 해당 단계에서 정한다. 관리자는 PC 전용으로 둘 수 있다 |

뷰를 나눌 때는 서버 응답을 받아 가공하는 훅과 API 클라이언트를 뷰와 따로 둔다. 그래야 뷰만 갈아 끼우고, 규칙을 해석하는 코드가 둘로 갈라지지 않는다.

### `platform` 어댑터

화면은 `platform.pay()`, `platform.push()`, `platform.openExternal()` 같은 어댑터만 부른다. 웹은 토스 결제위젯, 앱은 스토어 결제로 구현한다. 앱을 내는 시점의 일이 어댑터 구현에 갇힌다.

### 앱 껍데기에서 확인할 것

1. **리프레시 쿠키.** 인증 서버는 httpOnly 쿠키로 14일짜리 리프레시 토큰을 준다. 앱의 WebView 는 페이지 출처가 `capacitor://localhost` 나 `https://localhost` 라서 API 서버와 출처가 다르다. `SameSite` 와 CORS 설정에 따라 갱신이 조용히 실패할 수 있다. 껍데기를 만들기 전에 가장 먼저 시험하고, 필요하면 인증 서버 쪽 설정을 바꾼다. (이슈 #429)
2. **결제 정책.** WebView 앱이어도 앱 안에서 크레딧 같은 디지털 재화를 파는 결제는 구글 결제를 써야 한다. 결제 서버에는 구글 영수증을 검증하는 경로가 없다(`channel` 은 `web` 하나). 앱에서 결제를 빼고 웹 충전으로 보내는 길은 정책 확인이 필요하다. iOS 는 애플 기준을 따로 본다. (이슈 #431)
3. **심사.** 웹 사이트를 그대로 감싼 앱은 심사에서 걸릴 수 있다. 푸시 알림이나 앱 복귀 처리 같은 앱다운 기능이 조금은 필요하고, 그러려면 A10 알림의 송신 쪽이 정해져야 한다.
4. **앱 복귀 후 재접속.** 백그라운드에 갔다 오면 실시간 스트림(SSE)이 끊겨 있다. 놓친 기록은 마지막 번호부터 이어 받는 방식을 이미 정했으니, 앱 복귀 이벤트에서 이를 부른다.

## 첫 출시의 범위

아래는 안이다. 정하지 않았다. A 의 칸을 채우며 걸린 것을 "다시 볼 것"에 적었다.

| 묶음 | 화면 |
| --- | --- |
| 필수(공통) | A1~A3, A5~A7, A10 |
| 필수(TRPG) | B1~B8 |
| 이후 | A4, A8, A9, A11, A12, B9, B10 |
| 별도 단계(chat) | C1~C6 |
| 별도 단계(story) | D1~D7 |
| 운영 시작 때 | E1~E8 중 E4, E3 부터 |

- 결제는 실제 결제가 아니라 테스트 모드다. 실제 결제 전에 사업자 등록과 전자결제 신청이 필요하다.

다시 볼 것:

- **A10 알림은 게임, 결제, 게시판이 모두 넣는다**(모델 은퇴, 제재, 결제와 청약철회, 환영과 곧 사라질 크레딧, 댓글과 답글). 읽지 않은 수는 화면이 다시 물어야 한다(실시간으로 밀어 주지 않는다).
- **A4 보호자 동의를 이후에 두면 미성년자는 충전하지 못한다.** 서버가 막는다(`payment.guardian_consent_required`). 첫 출시에서 미성년자를 받을지 정한다.
- **A8 청약철회, A9 출석을 이후에 두어도 서버에는 이미 있다.** 실제 결제를 연다면 A8 은 같이 열어야 할 수 있다(약관 확인). A9 는 무료 이용의 중심이니 앞당길지 정한다.
- **A11 은 읽기(공지)만 앞당길 수 있다.** 점검과 약관 변경을 알릴 곳이 필요하다.
- **A1 은 로그인 전에 공개 목록을 보이지 못한다**(게임 서버가 401). 소개문과 가입 유도만 둘지 서버를 열지 정한다.
