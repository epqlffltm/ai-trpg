# 플랫폼과 제품 방향

이 저장소가 만드는 제품이 무엇이고 어디로 가는지를 적는다. 서버의 구조는 [서비스 구조 명세](../architecture/services.md), 화면은 [화면 명세](screens.md)에 있다.

- 기준일: 2026-10-18
- **정한 것**과 **정하지 않은 것**을 나눠 적는다. 가격, 일정, 이름은 정하지 않았다.

## 정한 것

### 제품

- 하나의 플랫폼에 **독립된 제품 셋**을 둔다.
  - **TRPG**: AI 가 진행하고, 규칙과 상태를 서버가 관리하는 1~4인 텍스트 TRPG.
  - **chat**: 캐릭터 하나와의 1:1 대화.
  - **story**: 세계관 안에서 여러 인물을 만나며 이야기를 즐기는 형태. 인물마다 호감도가 있고, 장소를 옮기고, 엔딩이 있다.
- 계정과 결제(인증 서버, 결제 서버)는 공유한다. 서비스의 데이터는 서로 섞지 않는다.
- 제품 사이에 로어북, 캐릭터를 가져오고 복사하고 동기화하는 기능은 만들지 않는다. 공유하는 것은 형식(템플릿)과 코드다. [공용 코드 규칙](../architecture/shared-code.md).
- 제품의 순서는 TRPG 를 끝까지 플레이할 수 있게 마무리한 뒤 chat, 그다음 story 로 간다([순서](../architecture/services.md#순서)).

### 원칙

- 게임의 상태와 규칙 판정은 서버(엔진과 DB)가 정한다. 언어 모델은 서술, 대화, 행동 제안만 맡는다. 모델의 출력은 구조화된 값으로 받고 서버가 검증한 뒤에 적용한다.
  모델이 틀린 말을 해도 영구적인 상태가 훼손되지 않는다.
- 정확해야 하는 값(HP, 소지품, 퀘스트, 호감도, 크레딧)은 관계형 DB 에서 읽는다. 세계관, 로어, 기억은 임베딩과 벡터 검색을 쓴다.
- 외부 모델과 로컬 모델을 바꿔 끼울 수 있게 모델 호출은 한 곳으로 모은다.
- 모델의 호출은 호출마다 기록하고(누가, 어느 모델, 토큰, 걸린 시간, 성공 여부), 값은 선불 크레딧의 홀드로 받는다. 서술이 실패하면 홀드는 돌려준다.

### 사용자 화면

- 시나리오의 **대표 장르 하나**가 플레이 화면의 테마를 정한다. 태그는 여럿이고 검색용이며 화면을 바꾸지 않는다. 테마는 겹치지 않는다.
- 고전 게임 같은 분위기(패널, 상태 표시, 아이콘)를 쓰되, 긴 글을 읽는 것과 모바일 조작이 먼저다. 장식이 대화 영역을 차지하지 않는다.
- PC 는 대화와 상태(캐릭터, 소지품)를 함께 보이고, 모바일은 대화 중심에 필요할 때 상태를 펼친다. 제작 도구는 PC 를 우선한다.
- 화면 설계 전에 서비스와 핵심 경험, 흐름, 화면 목록, 화면별 정보·행동·상태를 문서로 정리한다. [화면 명세](screens.md).

### 모바일

- PC 와 모바일 웹이 같은 프런트를 쓰고, Capacitor 같은 방식으로 감싸 앱으로 낼 수 있는지 본다. 안드로이드 전용 개발은 계획하지 않는다.
- 확인할 것: 로그인 유지와 토큰 갱신, 출처와 쿠키, 앱 복귀, 실시간 재접속과 진행 복구, 가상 키보드, 뒤로 가기, 여백. 먼저 핵심 플레이 흐름을 실제 서버에 붙여 스마트폰으로 한 판을 해 보고, 앱 패키징도 일찍 시험한다.
- 앱스토어 결제는 결제 서버를 다시 만들지 않고 결제 경로를 하나 더하는 방식으로 본다. 구매 토큰의 서버 검증, 계정 연결, 토큰 재사용 방지, 지급 후 소비 처리와 재시도, 환불과 취소, 이미 쓴 크레딧의 처리를 정해야 한다. 처음 범위는 구독을 뺀 소비성 크레딧 묶음이다.

## 정하지 않은 것

- 가격, 모델의 출시 목록, 무료로 주는 양과 기한
- 사용자가 만든 캐릭터를 처음부터 열지, 제작자 보상과 정산
- 성인 등급 콘텐츠의 허용 범위(외부 모델 API 의 정책에 걸린다)
- 일정, 클라우드 사업자와 사양
- 플랫폼과 제품의 사용자용 이름
- chat 의 기억 구조(요약, 검색, 사용자가 보고 고치는 범위)
