# chat 서버 설계

대화가 한 턴을 이끄는 `chat-server` 를 만들기 전에, 무엇을 정했고 무엇을 아직 안 정했는지, 선택지와 대가를 한곳에 적는 문서다.
이 서버는 **chat**(캐릭터 하나와 1:1)을 맡는다. **story**(세계관 안의 여러 인물)는 `story-server` 가 따로 맡는다(2026-10-21). 둘이 함께 쓰는 것과 나눈 선은 [story-server 와 나눈 선](#story-server-와-나눈-선)에 있고, story 의 규칙(이벤트, 호감도, 고백과 엔딩)은 [story 서버 설계](story.md)에 있다.
서비스 구조는 [서비스 구조 명세](services.md), 공용 코드는 [공용 코드 규칙](shared-code.md), 화면은 [화면 명세](../product/screens.md)를 따른다.

## 한눈에

- 사용자는 **캐릭터**를 asset-server 에서 만들고, 캐릭터와 **대화**(세션)를 시작한다. 새로 시작할 때마다 새 대화가 생기고, 지난 대화는 목록에 남아 언제든 이어서 한다. 대화마다 모델, 페르소나, 기억이 따로 있다.
- 대화는 모델이 글을 쓰고 서버가 나머지를 쥔다. 크레딧, 소유, 연령 등급, 기억에 쓰이는 값은 모두 서버와 DB 가 소유하고, 모델은 말과 제안만 낸다. TRPG 와 같은 원칙이다.
- TRPG 와 코드는 나누고 데이터는 섞지 않는다. 계정과 크레딧은 인증, 결제 서버를 그대로 쓴다.
- 캐릭터, 세계관, 로어북, 지도, 물건의 원본은 asset-server 에 있다. chat 은 대화를 만들 때 게시된 판을 한 번 가져와 자기 DB 에 복사해 고정한다([자산 가져오기](#자산-가져오기)).
- 매 턴의 길에 엔진은 없다. 사용자의 말이 한 턴을 이끈다. 다만 **장소와 소지품, 상대의 차림, 호감도**는 첫 출시에 넣는다. 정확해야 하는 값이라 DB 가 소유하고, 바꾸는 규칙은 TRPG 와 같은 순수 함수(`shared/`)를 쓴다([장소와 소지품](#장소와-소지품)). 여러 인물과 이벤트, 엔딩은 story-server 의 일이다.
- 화면은 미연시의 그림(배경, 캐릭터, 일러스트)을 고전 게임의 UI(위에 그림 창, 아래에 대사창)에 담는다([그림](#그림), [화면 명세의 C](../product/screens.md#chat-화면의-공통-원칙)).

## 정한 것

2026-10-19 까지 사용자가 정한 것이다.

| 항목 | 정한 내용 |
| --- | --- |
| 범위 | chat(1:1)만 맡는다. 2026-10-19 에는 story 를 이 서버의 두 번째 모드로 두기로 했으나, 2026-10-21 에 `story-server` 로 나누기로 바꿨다. 함께 쓰는 코드는 `shared/` 에 둔다([서비스 구조](services.md#나누는-기준)) |
| 자산의 집 | 캐릭터, 세계관, 로어북, 지도, 물건의 원본은 asset-server. chat 은 시작할 때 판을 복사해 고정한다 |
| 장소와 소지품 | 첫 출시에 넣는다. 대화 중에 지도를 펼쳐 갈 곳을 보고 소지품을 연다. TRPG 에서 만든 지도, 물건, 위젯을 가져오고, 다른 서비스와의 차별점이다 |
| 호감도 | chat 에도 둔다(2026-10-20). 처음에는 사용자의 행동(선물, 장소, 처음 하는 일)과 엔진의 규칙만 바꾼다. 다음 단계에서 모델이 변화를 제안하고 서버가 상한 안에서 반영한다. 보이는 방식(숫자와 게이지, 단계 이름과 게이지)은 제작자가 캐릭터마다 고른다 |
| 의복 | 상대 캐릭터의 차림이다. 내가 준 옷을 상대가 입고, 지금 입은 옷이 프롬프트에 들어간다(2026-10-20) |
| 그림 | 배경(장소마다, 시간대마다), 캐릭터(대표 그림 하나, 표정은 나중), 일러스트(배경과 캐릭터를 대신하는 장면). 일러스트는 처음에 엔진의 조건으로 열고, 다음 단계에서 모델이 고르는 길을 더한다. 열린 일러스트는 계정마다 기록하고 갤러리에서 다시 본다. 해금 대상인지는 제작자가 고른다(2026-10-20) |
| 대화 시작 | 시작 상황만 고르고 들어간다. 페르소나와 모델은 지난번 것을 쓰고 대화 안에서 바꾼다(2026-10-20) |
| 페르소나 | 계정 하나에 모아 TRPG, chat, story 가 함께 쓴다. 만드는 곳은 따로 둔다(2026-10-20). 원본은 asset-server 이고, 대화를 시작하거나 바꿀 때 복사해 고정한다. 고친 뒤에는 대화 안에 "새 설정으로 바꾸기"를 보인다(2026-10-21, [asset 서버 설계](asset-server.md#계정-페르소나)) |
| 나이와 성별 | 캐릭터, NPC, 페르소나의 나이와 성별로 거르거나 막지 않는다. 나이 칸은 고르는 칸이다(2026-10-21). [성인 콘텐츠](#성인-콘텐츠) |
| 캐릭터 만들기 | PC 용 폼(C6). 1~2단계는 운영자만 쓰고, 3단계에서 일반 사용자에게 열 때 그대로 쓴다(2026-10-20) |
| 그림 저장 | 객체 저장소(S3, 서울)의 비공개 버킷. 로컬은 SeaweedFS. 올릴 때 서버가 검사하고, asset-server 가 권한을 본 뒤 nginx 가 캐시해 내준다(2026-10-20, [배포 설계의 그림 저장소](deployment.md#그림-저장소)) |
| 상태를 누가 바꾸는가 | 첫 출시는 사용자와 엔진이 시작한다(지도에서 장소 고르기, 물건 쓰기·건네기). 모델은 바뀐 상태를 받아 반응만 쓴다. 모델이 변경을 제안하는 것은 그다음 단계 |
| 대화 안의 물건 | 골드·실버와 별개인 대화 안의 것이다. 결제 서버와 이어지지 않고 돈으로 바꿀 수 없다 |
| 대화 수 | 새로 시작할 때마다 새 대화(세션)가 생기고, 지난 대화는 목록에 남아 언제든 이어서 한다. 여러 판을 나란히 띄워 두는 것이 아니다. 지금까지의 플레이를 복사해 새 대화를 만드는 기능은 나중(2단계 이후)에 넣는다(2026-10-20). 다른 서비스도 같은 방식 |
| 모델 선택 | 단독 플레이가 기본이라 사용자가 언제든 원하는 모델로 바꾼다 |
| 성인 콘텐츠 | chat 도 19금 허용, story 도 허용. 성인 인증은 인증 서버가 한 번만 한다. chat 서버는 인증하지 않고, 게임 서버처럼 보여 주는 등급만 거르고, 들어온 뒤에는 다시 보지 않는다 |
| 성인 허용 범위 | 폭넓게 둔다. 다만 모델의 `allows_adult` 는 공급자 약관을 확인한 뒤에 켠다 |
| 운영 | 신고 기반으로 한다. 운영자가 사적 대화를 훑지 않는다 |
| 무료 | 실버만 둔다. 하루 무료 횟수 같은 것은 두지 않는다 |
| 이벤트 | 이벤트나 기념일에는 무료로 풀 수 있다 |
| 나중 | 여유가 생기면 로컬 모델에 다른 이름을 붙여 "베이직" 등급으로 서비스 |
| 구독 | 예정일 뿐 정해지지 않았다. 이 문서는 소비성 크레딧만 다룬다 |
| 벡터 검색 | 로어북에서만 쓴다. 대화 기억에는 쓰지 않는다 |
| 다음 답 추천 | 별도 호출 없이, 같은 호출에서 선택지 셋을 함께 받는다 |
| 끊긴 말 | "이어서 출력" 버튼을 둔다 |
| 스트리밍 | 말을 보내는 POST 가 바로 SSE(`text/event-stream`)로 답한다. `POST /api/v1/chat/conversations/{id}/messages`, `POST /api/v1/chat/messages/{id}/regenerate`, `POST /api/v1/chat/messages/{id}/continue`. 서버가 `X-Accel-Buffering: no` 를 보내고 15초마다 하트비트(주석 줄)를 보낸다. 끊겨도 생성은 끝까지 저장하고, 앱은 다시 들어와 GET 으로 읽는다. 끊긴 스트림을 이어 받기는 첫 출시에 없다(2026-10-21) |
| 뒤의 일 | 요약과 임베딩은 서버 안의 일정한 돌기(`server_core.loops`)로 돌린다. 워커 컨테이너는 두지 않는다. 같은 이미지를 명령만 바꿔 워커로 띄울 수 있게 짜 두고, 부하가 보이면 그때 더한다(2026-10-21) |
| Redis | 요청 제한에만 쓴다(trpg 의 `app/limits` 와 같은 방식, `REDIS_URL` 이 비면 메모리). DB 번호는 chat 2, story 3(인증과 trpg 는 0). `REDIS_URL` 이 있으면 readiness 가 본다. 한 대화 한 생성은 Redis 잠금이 아니라 DB 의 조건부 UPDATE 다(2026-10-21) |
| 모델의 자리 | 대화는 외부 API 만 쓴다. 로어북 임베딩은 trpg 와 같은 Ollama 를 함께 쓴다(설정 이름도 같다: `EMBEDDING_BASE_URL`, `EMBEDDING_MODEL`). 로컬 대화 모델은 베이직 등급 때 설정으로 켠다(2026-10-21) |
| 환경 변수 | 서버 안에서는 머리 없이 다른 서버와 같은 이름을 쓴다(`DATABASE_URL`, `AUTH_JWKS_URL`, `JWT_AUDIENCE`, `REDIS_URL` 등). `CHAT_*` 머리는 다른 서버에 들어가는 값에만 붙인다(결제 서버의 `CHAT_SERVER_SECRET`, `CHAT_HOLD_TTL`)(2026-10-21) |
| 첫 PR | `shared/server-core`(#588)가 머지된 뒤에 그 위에 세운다. 뼈대(설정, `/health`, `/health/ready`, 인증, `GET /api/v1/chat/me`, 마이그레이션의 틀)와 CI 까지다. compose, `09-chat-role.sql`, nginx, 포트 검사를 같은 PR 에 맞춘다(#590)(2026-10-21) |

## 기본값으로 둔 것

사용자가 아직 답하지 않았거나 답이 없어서 제안으로 적은 것이다. 이의가 없으면 이대로 가고, 바꾸려면 이 문서와 함께 고친다.

| 항목 | 기본값 | 이유 |
| --- | --- | --- |
| 캐릭터 공개 | 처음에는 비공개 캐릭터와 공식 캐릭터만. 공개는 신고와 관리자 화면(E4)이 생긴 뒤 | 성인 콘텐츠를 허용하므로 공개 쪽의 검수 부담이 크다 |
| 끊긴 말의 과금 | [과금](#과금)의 표 | 말 하나에 일정 금액이라는 계획과 맞다 |
| 대화 기록의 모양 | 트리(`parent_id`) | 다시 생성과 직접 고치기가 모두 대안을 만든다 |
| 요약 모델 | 싼 모델을 따로 두고 원가는 서비스가 낸다 | TRPG 의 장부 초안 모델과 같은 방식 |
| 로어북 검색 | 상시 삽입 + 벡터, 토큰 상한 | [기억](#기억) |

## 권한의 선

| 값 | 소유 | 모델이 하는 일 |
| --- | --- | --- |
| 크레딧, 홀드, 청구 | 결제 서버 | 하지 않는다 |
| 누가 어느 캐릭터와 대화를 가졌는지 | chat DB | 하지 않는다 |
| 캐릭터 카드, 세계관, 로어북 항목, 지도, 물건의 정의 | 원본은 asset-server. chat DB 에는 고정한 복사본 | 읽기만 한다 |
| 페르소나 | asset-server. chat DB 에는 대화마다 복사한 사본 | 읽기만 한다 |
| 현재 장소, 소지품, 가 본 곳 | chat DB(메시지마다의 상태) | 읽기만 한다. 변경 제안은 그다음 단계이고, 그때도 서버가 검증한 뒤에만 반영한다 |
| 연령 등급, 성인 여부 | 서버(캐릭터의 등급, 사용자의 인증 상태) | 지키는 대상이지 정하는 쪽이 아니다 |
| 요약, 기억 메모 | chat DB. 모델이 쓴 것은 파생 데이터 | 요약을 제안한다. 서버가 저장하고, 원본 메시지는 항상 남는다 |
| 다음 답 선택지 | 응답에서 서버가 떼어 내 검증한 것 | 제안한다. 누르면 입력칸이 채워질 뿐이고, 보내면 일반 말과 같은 경로를 탄다 |

- 모델이 낸 구조 있는 값(선택지, 요약)은 서버가 모양과 길이를 검증한 뒤에만 저장한다. 어긋나면 그 값만 버리고 대화는 이어 간다.
- 모델이 말을 꾸며 낸 것이 영구 상태를 해치지 못하게, 영구 상태(크레딧, 소유, 등급)는 모델 출력과 만나지 않는다.

## 자산 가져오기

캐릭터, 세계관, 로어북(장소와 물건 항목 포함)의 원본은 asset-server 에 있다([서비스 구조 명세](services.md#계획인-것)). chat 은 원본을 읽지 않고, 대화를 만들 때 **게시된 판을 한 번 가져와 chat DB 에 복사해 고정한다.** 턴마다 asset-server 를 부르지 않는다.

| 질문 | 정한 것 |
| --- | --- |
| 언제 가져오나 | 대화를 만들 때. 대화가 쓰는 캐릭터, 세계관, 로어북, 지도, 물건의 판을 함께 |
| 무엇을 적어 두나 | 복사본마다 출처(서비스, 자산 id, 판). 외래키는 걸지 않는다 |
| 원본이 바뀌면 | 복사본은 그대로 둔다. 새 판이 있다고 알리기만 하고, 쓸지는 사용자가 고른다 |
| asset-server 가 죽으면 | 새 대화를 만들지 못한다. 진행 중인 대화는 복사본으로 돈다 |
| 누가 쓸 수 있나 | asset-server 가 판단한다(소유자나 공개). 첫 단계는 제작자 본인의 자산만 |
| 등급 | 성인 등급은 같이 온다. 나이로 거르는 검사는 하지 않는다 |
| 칸이 안 맞으면 | 공통 칸만 복사하고, chat 에 필요한 칸(인사말, 말투 예시 등)이 비면 만든 사람이 채운다 |

- 가져오는 시점이 한 번이라 서버 사이의 인증이 단순하다. 서명 비밀을 서버마다 따로 두는 기존 방식을 쓴다.
- asset-server 가 생기기 전에는 trpg-server 가 세계관과 로어북의 게시된 판을, asset-server 가 줄 것과 같은 모양의 API 로 내준다. chat 은 그 모양으로 짠다([순서](services.md#순서) 4).
- TRPG 의 NPC 를 chat 캐릭터로 가져오는 것은 칸이 많이 달라 첫 출시에 넣지 않는다([열린 질문](#열린-질문)).

## 데이터의 모양

스키마는 `chat`, 다른 서비스의 테이블을 직접 읽지 않는다. 앞의 넷(`characters`, `conversations`, `conversation_personas`, `messages`)은
만들었다(`chat-server/app/conversations/models.py`, chat-server README 의 "대화"). 모델 목록(`ai_models` 와 원가, 날짜판의 기록)도
만들었다(`chat-server/app/catalog/models.py`, README 의 "모델 목록"). 나머지는 초안이다.

| 테이블 | 주요 칸 | 비고 |
| --- | --- | --- |
| `characters` | `id`, `owner_id`, `source_id`(asset 의 캐릭터 id), `version`, `name`, `rating`, `document`(판의 문서 그대로), 가져온 때 | asset-server 에서 가져온 판의 사본. **사람마다, 판마다 하나**(`owner_id`, `source_id`, `version` 이 고유)라 같은 판으로 여러 번 시작해도 함께 쓴다. 동시에 가져와도 하나만 남는다(`ON CONFLICT DO NOTHING`). 사람마다 두는 것은 탈퇴 때 그 사람의 것만 지우기 위해서다. 목록이 될 수 없다(캐릭터 탐색은 asset 의 공개 목록이다) |
| `conversation_personas` | `conversation_id`, `source_id`(asset 의 페르소나 id), `revision`, 이름, 설명, 그림 id, 나이, 성별, 호칭, 말투 예시, 성격, 가져온 때 | asset-server 의 계정 페르소나를 대화마다 복사한 것. 페르소나 없이 시작한 대화에는 없다. 지금 것의 `revision` 과 다르면 "새 설정으로 바꾸기" |
| `conversations` | `id`, `owner_id`, `character_id`(위의 사본), `model_slug`, 제목, `start_title`, `start_situation`, `active_leaf_id`, 생성·수정 시각, 지운 시각 | 새로 시작할 때마다 하나. 한 캐릭터에 쌓인다. 기억과 모델은 대화마다. 시작 상황은 판의 것을 복사해 둔다(제목은 목록에, 상황은 모델에). `model_slug` 는 `ai_models` 를 가리킨다(고르지 않았으면 비어 있다). 생성 중 표시(`generating_since`)는 말을 보내는 길에서 더한다 |
| `ai_models`, `ai_model_costs`, `ai_model_snapshots` | 게임 서버의 모델 목록과 같은 칸, 그리고 `allows_adult` | 공용 파일(`ai_core/model_catalog.toml`)을 들여온 사본과 이 서버의 스위치(켜짐, `allows_adult`). 회사의 대체 모델은 없다 |
| `message_states` | `message_id`, `place_id`, 시각(시간대), 소지품, 가 본 곳, 상대의 차림, 호감도 | 상태가 바뀐 말에만 둔다. [장소와 소지품](#장소와-소지품). 호감도와 차림도 가지마다 다르므로 같은 행에 둔다 |
| `illustration_unlocks` | `owner_id`, `character_source`(서비스, 자산 id), `illustration_id`, 처음 연 시각 | 계정마다의 기록. 가지를 바꾸거나 대화를 지워도 남는다. 갤러리(C7)가 읽는다 |
| `messages` | `id`, `conversation_id`, `parent_id`, `role`, `content`, `status`, `suggestions`, `edited`, 시각 | `status`: `complete`, `partial`, `failed`. `parent_id` 가 같은 것이 서로 대안 |
| `generations` | `id`, `conversation_id`, `message_id`, `model`, 토큰 수, `hold_id`, 결과, 지연 | 호출 한 번의 기록이자 청구의 근거. 호출이 하나면 청구도 하나 |
| `summaries` | `conversation_id`, `covered_up_to`(메시지), 글, 시각 | 파생 데이터 |
| `memory_notes` | `id`, `conversation_id`, 글, 출처(`user` 또는 `summary`) | 사용자가 보고 고친다 |
| `lorebooks`, `lore_entries` | `source`, 이름, 항목: 글, 종류(장소·물건 등), 상시 여부, 임베딩 | asset-server 에서 가져온 복사본. 임베딩은 가져올 때 만드는 색인 |

- 대화가 무엇을 가리키는지는 서버마다의 칸이다. chat 은 캐릭터의 사본(`character_id`), story 는 세계관이다. 대화의 핵심을 `shared/conversation-core` 로 뽑을 때(#591) 공용 쪽은 그 칸을 모른다.
- `messages` 를 처음부터 트리로 둔다. 칸 하나 값이라 지금은 싸고, 선형에서 옮기는 일은 나중에 이관이 필요한 큰 일이다. 화면은 처음에 다시 생성의 대안만 보여도 된다.
- 대화 목록(`GET /api/v1/chat/conversations`)은 `?limit=&offset=` 이고, 마지막 말이 최근인 것부터다(`conversations` 의 수정 시각). 캐릭터로 거를 수 있다. 첫 화면의 이어하기(A1, 거르지 않고 `limit=5`)와 C2 의 이 캐릭터와의 대화가 같은 주소를 쓴다. 화면이 서비스마다 부르고 화면에서 놓으므로 trpg 의 `GET /tables`, story 의 세션 목록과 모양을 맞춘다(#593).
- 선택지는 `suggestions` 칸에만 둔다. 본문(`content`)에 섞으면 다음 호출의 프롬프트에 다시 들어가 모델이 선택지를 흉내 낸다.

## 장소와 소지품

대화 중에 지도를 펼쳐 어디로 갈지 보고, 소지품을 열어 지금 가진 것을 본다. 상태는 DB 가 소유하고, 모델은 읽고 반응만 한다.

**누가 바꾸는가.** TRPG 는 선언 → 엔진 → 서술의 두 단계지만, chat 은 한 번의 스트리밍 호출이다. 글이 나간 뒤에 상태를 검증하면 "반지를 줬다"고 썼는데 엔진이 거부하는 어긋남이 생긴다. 그래서 첫 출시는 변경을 사용자와 엔진이 시작하게 한다.

| 행동 | 처리 |
| --- | --- |
| 장소 이동 | 사용자가 지도에서 고른다. 서버가 아는 곳이고 길이 이어졌는지 검증한 뒤 반영한다 |
| 물건 쓰기, 건네기 | 사용자가 소지품에서 고른다. 서버가 가지고 있는지 검증한 뒤 반영한다. 건넬 때 한마디를 덧붙일 수 있고, 행동과 말을 한 턴에 붙여 반응을 한 번 받는다(한 번 청구). 옷이면 상대의 차림에 들어간다 |
| 호감도 | 위의 행동에 제작자가 적은 규칙대로 엔진이 바꾼다. 대화의 내용만으로는 움직이지 않는다(첫 출시). TRPG 의 NPC 태도(#479)와 같은 자리의 값이다 |
| 시각 | 이동에 걸리는 시간만큼 흐른다(TRPG 의 #265 와 같다). 배경의 시간대를 정한다 |
| 시작 소지품, 시작 장소 | 가져온 자산의 설정에서 온다 |
| 모델이 보는 것 | 현재 장소, 나가는 길의 이름, 소지품의 요약이 프롬프트에 들어간다 |

- 행동은 트리에 행동 말(`role` = `action`)로 붙는다. 행동 자체는 모델 호출이 아니라 청구하지 않는다. 이어서 모델의 반응을 생성하면 그것이 한 번의 말이고 한 번 청구한다.
- **분기와 상태.** 대화는 트리라서, 상태를 대화방당 하나로 두면 다시 생성이나 앞 가지로 돌아갈 때 소지품이 어긋난다(분기 밖에서 받은 선물이 남는다). 그래서 **상태를 메시지에 붙인다.** 상태가 바뀐 말에만 `message_states` 행을 두고, 나머지 말은 부모의 상태를 따른다. 현재 상태는 지금 보고 있는 가지의 끝에서 거슬러 올라가 읽는다. 롤백은 가지를 바꾸는 것으로 끝난다.
  - 선택지: 매번 전체를 담는 방식(이 안)과 변화분만 담아 재생하는 방식. 장소 하나와 수십 개 이하의 소지품이라 전체가 작고, 읽기가 단순해서 전체를 기본으로 한다.
- **지도.** 첫 출시는 열린 길과 안개(가 보면 알게 되는 곳)만 쓴다. 숨은 길과 찾기 판정은 TRPG 의 규칙이라 쓰지 않는다. TRPG 에서 길은 시나리오가 갖고 있어 chat 이 길을 어디에 정의할지는 열려 있다([공용 코드 규칙](shared-code.md#열린-질문)).
- **위젯.** 지도와 소지품은 서버가 상태 값을 끼워 그리는 화면이다. 모델이 출력하지 않아 토큰이 들지 않고 숫자가 틀리지 않는다.
- **규칙의 집.** 이동 가능 여부 계산, 물건 더하기·빼기 같은 순수 함수는 `shared/` 로 뽑는다(DB 를 모르는 모양). 저장은 chat 이 한다.
- **그다음 단계(첫 출시에 넣지 않는다).** 모델이 "선물을 준다"나 "이쪽으로 이동한다"를 제안하는 것. 다음 답 추천처럼 같은 응답 끝에 표식으로 제안을 받고, 허용 목록 안에서만 서버가 검증해 반영한다. 별도 호출은 정액 과금을 깨므로 쓰지 않는다. 어긋나면 화면에 확정된 결과를 따로 보여 준다.
- 함수는 하나의 책임만 갖는다: `check_move`, `apply_move`, `check_item_use`, `apply_item_use`, `load_current_state`, `save_state`, `render_state`.

## 그림

미연시의 방식이다. 화면의 위쪽 그림 창에 그린다([화면 명세의 C3](../product/screens.md#c3-대화)).

| 종류 | 붙는 곳 | 바뀌는 때 |
| --- | --- | --- |
| 배경 | 장소마다, 시간대마다. 시간대의 그림이 없으면 그 장소의 기본 배경 | 장소를 옮기거나 시간대가 바뀔 때 |
| 캐릭터 | 캐릭터마다 대표 그림 하나. 표정은 나중에 더한다(응답 끝의 표식을 서버가 검증하는 방식) | 바뀌지 않는다 |
| 일러스트 | 캐릭터마다 여럿. 조건이 맞은 뒤의 첫 응답에 붙어 배경과 캐릭터를 대신한다 | 엔진의 조건(장소, 호감도 단계, 처음 건넨 물건). 다음 단계에서 조건 없는 일러스트를 모델이 고른다 |

- 그림의 원본은 asset-server 가 갖고 파일은 객체 저장소(S3)에 둔다. 대화를 만들 때 가져오는 판에는 그림의 주소(id)만 들어간다.
- 모델은 그림을 고르지 않는다(첫 출시). 서버가 상태로 정하고, 응답과 함께 "이 말의 그림"을 내준다.
- 시간대의 그림이 없을 때 기본 배경의 색감만 바꿔 보이는 연출은 화면의 일이다. 서버는 시간대만 준다(나중).
- 열린 일러스트는 해금 대상인 것만 기록한다(`illustration_unlocks`).

## 한 번의 말이 지나가는 길

한 함수는 한 책임만 갖는다. 아래 순서의 각 줄이 함수 하나다.

1. `check_request` — 로그인, 대화의 소유, 요청 모양을 검사한다. 상태를 바꾸지 않는다.
2. `acquire_turn_lock` — 한 대화는 한 번에 하나의 생성만 받는다([실패와 동시성](#실패와-동시성)).
3. `save_user_message` — 사용자의 말을 트리에 붙인다.
4. `build_prompt` — 아래 다섯 함수를 부르고 순서대로 붙인다: `render_card`, `select_window`, `load_summary_and_notes`, `retrieve_lore`, `render_state`. 마지막에 `check_budget` 으로 토큰 예산을 지킨다.
5. `place_hold` — 가격표 이름 `chat.<모델>.i<입력 단계>.o<출력 단계>` 로 홀드를 건다. 모자라면 여기서 멈추고 말은 저장하되 생성하지 않는다.
6. `stream_generation` — 공급자 어댑터로 부르고 글을 흘려 보낸다.
7. `split_suggestions` — 스트림에서 본문과 선택지 표식을 가른다.
8. `save_assistant_message` — 받은 만큼 저장한다. 상태는 `complete` 나 `partial` 이다.
9. `settle_hold` — [과금](#과금)의 표대로 확정하거나 돌려준다.
10. `enqueue_summary` — 요약을 갱신할 때가 되었으면 비동기 작업으로 넘긴다. 실패해도 이 말의 결과에는 영향이 없다.

성인 등급 확인은 이 길에 없다. 등급은 캐릭터와 대화를 읽고 만드는 곳에서 한 번 거를 뿐이고, 말을 보내는 길은 다시 보지 않는다([성인 콘텐츠](#성인-콘텐츠)).

DB 접근, 외부 호출(공급자, 결제), 응답 만들기를 한 함수에 섞지 않는다. 그래야 각 줄을 공급자나 결제 없이 테스트할 수 있다.

## 과금

말 한 번에 **일정 금액**이다. 토큰 수에 따라 값이 바뀌지 않는다. 가격표의 입력, 출력 단계는 "이 값을 내면 이만큼까지 받는다"는 한도일 뿐이다.
참고 값(가안): 스탠다드 20~50원, 프리미엄 80~150원. 확정이 아니다.

| 상황 | 처리 |
| --- | --- |
| 정상으로 끝남 | 확정(청구) |
| 글자가 하나도 오기 전에 실패 | 홀드 반환(청구 없음) |
| 일부가 온 뒤 끊김, 사용자가 멈춤, 길이 한도에서 잘림 | 받은 부분을 `partial` 로 저장하고 청구한 뒤 "이어서" 버튼을 보인다 |
| "이어서" 누름 | 새 호출이라 새로 한 번 청구한다 |

- "이어서"를 새 호출로 보는 이유: 입력을 다시 보내고 모델 원가가 또 든다. 무료로 주면 반복해서 눌러 원가를 부풀릴 수 있다.
- TRPG 는 "이어 쓰기는 출력 약속을 넘으니 택하지 않는다"고 정했다. chat 은 사용자가 직접 누르는 버튼이라 사정이 다르다. 두 서비스의 결정이 다른 것이지 원칙이 어긋난 것이 아니다.
- "이어서"를 모델에게 시키는 방법은 공급자마다 다르다(어시스턴트 글을 미리 채워 이어 쓰게 하는 방식이 되는 곳도 있고 아닌 곳도 있다). 어댑터가 처리하고, 실제 API 를 붙일 때 확인한다.
- 사용자가 멈추면 서버가 공급자 호출도 끊는다. 끊지 않으면 청구하지 않는 글에 원가가 든다.
- 무료는 **실버**뿐이다. 실버는 스탠다드 등급에만 쓰이고 프리미엄은 골드만 쓴다(결제 서버의 기존 규칙). 환영 크레딧과 출석이 실버를 준다.
- 이벤트나 기념일의 할인은 가격표의 **행사가 줄**(`promo`)로 적는다. 행사가 줄은 끝난 뒤의 줄이 먼저 있어야 넣을 수 있어서 가격 목록이 "언제까지 이 값, 그 뒤 얼마"를 함께 보인다([결제 서버 README](../../billing-server/README.md)의 "행사가").
- **0 크레딧(완전 무료)은 가격표로 적지 못한다.** 가격표의 값은 1 부터다. 무료로 열고 싶으면 운영자가 명단의 사람들에게 이벤트 실버를 준다(결제 서버의 `cmd/grants`, 한 사람에 한 번). 실버는 스탠다드 등급에만 쓰인다.
- 베이직 등급(나중)은 가격표 줄의 등급을 `basic` 으로 적는 것으로 들어간다. 등급은 가격표 이름이 아니라 줄마다 적는다는 기존 규칙을 따른다.
- 구독은 정해지지 않았다.

## 대화 조작

| 조작 | 동작 |
| --- | --- |
| 다시 생성 | 같은 `parent_id` 아래 새 대안을 만든다. 새 호출이라 새로 청구한다 |
| 내 말 고치기 | 원본을 바꾸지 않고 새 대안(분기)을 만든다. 기록이 남는다 |
| 모델의 말 직접 고치기 | 그 말을 바로 고친다. `edited` 표시를 남긴다. 호출이 아니라 청구하지 않는다 |
| 이어서 출력 | `partial` 인 말에 이어 붙인다([과금](#과금)) |
| 대화 지우기 | 지운 시각을 적는다. 기록의 처리는 [열린 질문](#열린-질문) |

### 다음 답 추천

시스템 프롬프트에 "본문 뒤에 정해진 표식으로 감싼 선택지 셋을 써라"고 적어 같은 호출에서 받는다. 호출이 늘지 않아 싸다. 지켜야 할 것:

- **표식 처리.** 서버는 표식 앞까지만 사용자에게 흘리고, 표식이 시작되는지 보려고 끝 몇 글자를 잠시 붙잡는다. 표식이 청크 경계에 걸리기 때문이다.
- **검증.** 개수 0~3, 길이 상한, 빈 것 제거. 형식이 깨지면 선택지만 없애고 대화는 그대로 둔다. 오류로 만들지 않는다.
- 출력이 한도에서 잘려 선택지가 없을 수 있다. 괜찮다.
- 출력 토큰이 조금 늘어난다. 끄는 설정을 둔다.

## 기억

세 층이다. 모두 대화마다 따로 있다.

| 층 | 내용 | 비용과 위험 |
| --- | --- | --- |
| 최근 대화 | 토큰 예산 안에서 최신 말부터 채운다 | 가장 싸고 가장 정확하다 |
| 굴리는 요약 | 창 밖으로 밀려난 앞부분의 요약 | 모델이 쓴 글이라 틀리거나 흐려질 수 있다 |
| 기억 메모 | 사용자가 보고 고치는 짧은 글(요약이 제안할 수도 있다) | 틀린 기억을 사용자가 바로잡는다 |

- 요약은 파생 데이터다. `covered_up_to` 에 어디까지 요약했는지 적고, 원본 메시지는 항상 남긴다. 요약이 틀리면 원본에서 다시 만든다.
- **분기와 요약.** 사용자가 `covered_up_to` 보다 앞의 가지로 돌아가면 활성 경로에 그 말이 없어 요약이 맞지 않는다. 그때는 그 요약을 버리고 다시 만든다.
- 요약은 응답과 분리한 비동기 작업이고 싼 모델로 부른다. 원가는 서비스가 낸다. 실패해도 대화는 이어진다.
- 정확해야 하는 값(사용자 이름, 호칭)은 페르소나 칸(DB)에서 읽는다. 요약이나 검색에 맡기지 않는다.

### 로어북

- 항목은 사용자가 쓴 글이라 원본은 DB 행이다. 벡터는 거기서 만든 색인이고, 항목을 고치면 다시 만든다.
- 상시 삽입으로 표시한 항목은 항상 넣고, 나머지는 최근 말을 기준으로 벡터 검색해 가져온다. 가져오는 개수와 토큰에 상한을 둔다.
- 임베딩은 항목을 저장할 때 비동기로 만든다. 임베딩 호출 원가는 서비스가 낸다.
- 키워드 일치로 먼저 가고 벡터는 나중에 얹는 길도 있다(싸고 예측 가능). 지금은 로어북에 벡터를 쓴다는 결정을 따른다.
- 로어북의 형식은 TRPG 와 같이 쓸 수 있으나 데이터는 나누지 않는다([공용 코드 규칙](shared-code.md)).

## 성인 콘텐츠

chat 도 19금을 허용한다. 조건과 대가:

- **인증은 인증 서버가 한 번만 한다.** 본인인증의 생년월일로 인증 서버가 성인용 내용을 볼 수 있는지(`adult_content`)를 정해 access 토큰에 싣는다. 날짜로 정해지는 값이라 한 번 참이 되면 되돌아가지 않는다. chat 서버는 인증을 다시 하지 않고, 인증 서버를 부르지도 않는다.
- **chat 서버는 게임 서버와 같은 방식으로 등급만 거른다.** 토큰의 값을 읽는 함수 하나(`allowed_ratings`)가 이 사람이 보고 쓸 수 있는 등급을 정하고, 거르는 곳은 이 함수 하나다. 성인이 아니면 전체 이용가만 보인다.
  - 캐릭터 목록과 상세, 대화 만들기, 성인 캐릭터 쓰기가 이 함수를 쓴다. 이미 그 조건이 걸린 같은 쿼리 안에서 거르므로 추가 호출이나 부하가 없다.
  - 응답은 게임 서버와 같게 한다. 성인이 아닌 사람에게 성인 캐릭터는 없는 것이다(404). 자기 캐릭터를 성인 등급으로 쓰려는 비성인에게는 `adult_content_required`(403)로 인증으로 안내한다.
  - **들어온 뒤에는 다시 보지 않는다.** 말을 보내는 길에는 등급 확인이 없다. 정지된 계정은 갱신이 막혀 15분 안에 토큰이 끊기므로, 말마다 보지 않아도 길게 열려 있지 않다.
- **실제 본인인증이 먼저다.** 지금 인증 서버에는 가짜 인증 업체만 있고, 운영에서는 업체가 없으면 503 이다(이슈 #336, #59). 실제 인증 없이 성인 콘텐츠를 열 수 없다.
- **모델의 성인 허용은 폭넓게 켠다.** 이건 사람의 인증이 아니라 모델 목록의 속성이다. chat 서버의 모델 표에 `allows_adult` 칸을 두고(한 서비스만 쓰는 속성이라 공용 파일에는 두지 않는다, [공용 코드 규칙](shared-code.md#정한-것)), 성인 등급 대화는 그 칸이 참인 모델만 고르게 한다. 모델을 고르거나 바꿀 때 한 번만 본다.
  - 방향은 넓게 허용하는 것이다. 로컬 모델(베이직 등급 후보)과 약관이 성인 픽션을 막지 않는 공급자는 켠다.
  - 다만 약관이 성적 노골적 콘텐츠를 금지한다고 확인된 공급자(Anthropic, Google Gemini, DeepSeek 오픈 플랫폼)는 켜지 않는다. 켜면 키나 계정이 제재될 수 있고, 그 모델은 전체 이용가 대화에는 그대로 쓸 수 있어서 넓게 허용하는 방향과 어긋나지 않는다.
  - OpenAI, xAI, Mistral은 정책 문구와 실제 모델의 거절이 다르다. 원문 약관을 읽고 성인 평가 장면을 돌려 본 뒤에 켠다(모델 목록에 이미 있는 평가 장면 통과 절차에 한 줄을 더한다).
  - 약관은 자주 바뀐다. 켠 날짜와 근거를 기록해 둔다.
- **나이와 성별로 거르지 않는다(2026-10-21).** 캐릭터, NPC, 페르소나의 나이 칸은 고르는 칸이고, 서버는 나이나 성별로 게시, 등급, 역할을 막지 않는다. 아이가 나오는 어두운 이야기, 폭력, 비극, 논란이 될 주제를 막지 않는다. 말마다 검사하는 호출도 두지 않는다(비용이 늘지 않는다). 1인 플레이는 그대로 둔다.
  - 미성년 인물이 성적인 대상이 되는 것은 약관으로 금지한다(법이 그은 선이다). 지키는 것은 모델 공급자의 안전 검사와 신고다.
  - 대가: 안전 검사가 약한 모델(로컬의 베이직 후보, 성인 허용을 켠 공급자)에서는 그 선을 지키는 것이 모델에 달려 있다. [열린 질문](#열린-질문)에 둔다.
- **운영자는 대화를 읽지 않는다.** 능동적인 감시는 하지 않는다. 운영자가 보는 것은 다음뿐이다.
  - 공개한 캐릭터나 글에 들어온 신고(공개를 연 뒤).
  - 사용자가 직접 낸 제보. 제보는 사용자가 지목한 메시지만 첨부한다(AI가 부적절한 말을 했다, 설정에 결함이 있다 등).
  - 비공개 대화는 신고가 없으면 열람하지 않는다. 법적 요청 같은 예외와 보관 기간은 이용 약관과 개인정보 처리방침에 적는다.
- **앱과 스토어.** 앱을 스토어에 낼 때 성인 콘텐츠와 AI 생성 콘텐츠에 대한 정책이 걸린다. 앱에서는 성인 콘텐츠를 숨기고 웹에서만 열지 같은 선택이 필요할 수 있다. 정책을 확인한 뒤 정한다.
- 이것은 법률 검토가 아니다. 서비스를 열기 전에 청소년 보호와 음란물 관련 규정을 확인한다.

## 모델

- 모델은 **대화마다** 저장하고, 사용자가 언제든 바꿀 수 있다(`PUT /conversations/{id}/model`). 프롬프트는 말마다 DB 에서 다시 만드니 모델을 바꿔도 대화가 이어진다.
- 새 대화는 지난번 대화의 모델을 쓴다. 그 모델을 이 대화에 고를 수 없으면(꺼졌다, 은퇴했다, 성인 대화에 안 된다) 모델 없이 시작하고 화면이 고르게 한다. 사람이 직접 고른 모델을 쓸 수 없으면 422 다(2026-10-22).
- 말마다 청구가 그 순간의 모델의 가격표로 나간다. 바꾸는 순간부터 새 값이 적용된다.
- 모델마다 문맥 길이와 출력 한도가 다르다. 토큰 예산은 대화의 모델 등급에서 읽는다.
- 모델이 끝났거나 판매가 중지되면 몰래 다른 모델로 바꾸지 않는다. 사용자에게 알리고 고르게 한다. TRPG 의 원칙과 같고, 알림은 알림함으로 보낸다. 대화는 끝난 모델을 가리킨 채로 두고 읽을 때 `usable` 이 거짓으로 보인다. 그래서 게임 서버와 달리 회사의 대체 모델이 없다.
- 요약 모델과 임베딩 모델은 사용자가 고르는 모델과 별개로 서비스가 정한다.
- 공급자 호출은 어댑터로 분리하고, 같은 인터페이스로 로컬 모델과 외부 API 를 바꿔 끼울 수 있게 한다. 이 코드는 `shared/` 로 뽑는 일([공용 코드 규칙](shared-code.md))이 먼저다.

## 운영과 신고

운영자 한 사람이 모든 대화를 볼 수 없고, 볼 이유도 없다. 이 서비스의 운영은 **신고 기반**이다.

- **사적 1:1 대화는 읽지 않는다.** 신고나 법적 요청이 그 대화를 가리킬 때만 열고, 열 때마다 감사 기록을 남긴다(관리 서버의 감사 기록 계획과 같다). 누가 언제 무엇을 열었는지 남는 것이 운영자 자신을 지키는 길이기도 하다.
- **사람이 보지 않는 예방만 둔다.** 성인 등급 거르기(`allowed_ratings`), 신고 버튼과 숨김 경로. 모두 구조이지 감시가 아니다. 나이와 성별로 거르지 않는다.
- **신고가 닿는 곳.** TRPG 는 같이 하는 사람이 있고, 공개한 캐릭터와 이야기는 남이 플레이하다 결함을 신고한다. 혼자 하는 사적 대화에는 신고자가 없고, 읽는 사람도 없다.
- 불법 정보를 알게 되면 내리는 일은 운영자의 몫이다. 서비스를 열기 전에 관련 규정을 확인한다(법률 검토가 아니다).

### 공급자와 맞물리는 점

- **사용자별 식별자를 요청마다 보낸다.** OpenAI 는 개별 사용자를 가리키는 안정적인 식별자(`safety_identifier`, 이메일이나 내부 ID 는 해시해서)를 권장한다. 이 값이 있으면 위반한 사용자만 막히고 우리 조직 전체가 막히는 일을 줄인다. 다른 공급자의 방식은 어댑터를 만들 때 확인한다.
- **공급자의 경고는 운영자에게 온다.** OpenAI 문서에 따르면 조직이 높은 임계값을 반복해 넘으면 오류와 경고 이메일이 가고, 그 상태가 이어지면(문서상 보통 7일) 접근이 중단된다. 개별 사용자 차단은 OpenAI 쪽에서 풀 수 없다고 적혀 있다. 다른 공급자의 경고 절차는 확인하지 못했다. 경고를 받는 메일함을 정해 두고, 급할 때 쓸 수단은 모델을 끄는 것이다(모델 목록의 켜짐).
- **개별 사용자 차단 오류를 받으면** 그 사용자에게 사유를 알리고 끝낸다. 다른 모델로 몰래 넘기지 않는다. 넘기면 공급자의 차단을 우회하는 것이 된다.

### 단계

잦은 위반에는 단계를 둔다. 처음에는 운영자가 손으로 한다.

1. 경고: 당사자의 알림함에 알린다(알림 서버의 알림함이 이미 제재 알림에 쓰이고 있다).
2. 숨김: 문제의 캐릭터를 공개에서 내린다.
3. 정지: 인증 서버의 정지를 쓴다.

단계의 기준과 이의 제기 창구는 [열린 질문](#열린-질문)에 둔다. 메일로도 보낼지는 정하지 않았다.

## 실패와 동시성

- **한 대화에 한 생성.** 같은 대화에 두 요청이 동시에 오면 트리가 갈라지고 홀드가 겹친다. 선택지:
  - 대화 행에 `generating_since` 를 두고 조건부 UPDATE 로 잡는다(Postgres 만으로 되고, 오래된 잠금은 시간 제한으로 푼다).
  - Redis 잠금(빠르지만 인프라가 하나 더 든다).
  - 첫 번째로 정했다(2026-10-21). 서버가 죽어도 DB 에 남아서 시간 제한으로 풀리고 이미 쓰는 도구만으로 된다.
- **홀드가 남는 경우.** 홀드를 건 뒤 서버가 죽으면 확정도 반환도 못 한다. 결제 서버가 받아 준다. chat 서버가 건 홀드는 `CHAT_HOLD_TTL`(기본 10분) 뒤에 만료되고, 결제 서버의 정리 작업이 몇십 초 안에 돌려준다(크레딧은 한 번만 돌아간다).
  - 만료 시각이 지나도 정리 작업이 돌려주기 전에는 확정된다. 돌려준 뒤의 확정은 409 다. 기본값은 그 말을 청구 없이 두는 것이다(새 이름표로 다시 걸어 받지 않는다).
  - 생성이 10분을 넘을 수 있으면(긴 출력, 느린 로컬 모델) 남은 시간이 절반 아래일 때 연장한다. 연장도 지금부터 `CHAT_HOLD_TTL` 뒤다.
  - 이름표(`reference`)는 새로 만들 말마다 하나다. 다시 생성도 새 말이라 새 이름표다. 같은 요청을 다시 보내면 같은 이름표라 홀드가 둘 걸리지 않는다.
- **모델 장애.** 글자가 오기 전에 실패하면 홀드를 돌려주고 사용자에게 다시 시도를 안내한다. 같은 실패를 자동으로 되풀이하지 않는다. 재시도에는 예산을 둔다(TRPG 의 재시도 예산과 같은 방식).
- **스트림 끊김.** 앱을 닫거나 접속이 끊겨도 서버는 생성을 끝까지 저장한다. 돌아오면 저장된 말을 읽는다. 사용자가 명시로 멈춘 경우만 공급자를 끊는다. nginx 는 말을 보내는 세 경로에서 버퍼링을 끄고 trpg 의 스트림과 같은 동시 연결 제한(`limit_conn streams`)을 건다.
- **요청 제한.** 로그인한 사람마다 말의 속도에 제한을 둔다. 값은 설정으로 둔다.

## story-server 와 나눈 선

story 는 `story-server` 가 맡는다(2026-10-21). 규칙은 [story 서버 설계](story.md)에 있다. chat 과 한 턴의 모양(사용자의 말 → 스트리밍 답)이 같고, 다른 것은 참가자 수(여러 인물), 로어북이 붙는 곳(캐릭터가 아니라 세계관), 이벤트와 엔딩이다. 같은 것은 코드로 함께 쓰고, 데이터와 주소는 처음부터 나눈다.

| | chat-server | story-server |
| --- | --- | --- |
| 주소 | `/api/v1/chat/...` | `/api/v1/story/...` |
| 포트 | 8005 | 8007 |
| 토큰의 대상(`aud`) | `ai-trpg-chat` | `ai-trpg-story` |
| 스키마와 DB 계정 | `chat`(+`chat_test`), `09-chat-role.sql` | `story`(+`story_test`), `10-story-role.sql` |
| 결제의 서명 비밀과 가격 이름의 머리 | `CHAT_SERVER_SECRET`, `chat.<모델>...` | `STORY_SERVER_SECRET`, `story.<모델>...` |

함께 쓰는 코드는 `shared/` 에 있다([공용 코드 규칙](shared-code.md#후보)).

1. **서버의 공통부(`shared/server-core`).** 토큰 검증, 관측, 서버끼리의 서명. 두 서버 모두 처음부터 쓴다. 토큰의 대상과 서비스 이름은 설정으로 넘긴다.
2. **모델 호출(`shared/ai-core`).** 이 서버의 "한 번의 말"을 만들 때 trpg-server 에서 옮긴다(#499).
3. **대화의 핵심(`shared/conversation-core`).** 대화 트리, 다시 생성과 분기, 요약, 기억, 로어북 검색을 붙이는 순서, 스트리밍한 답을 저장하는 흐름. 이 서버 안에서는 `app/conversation/` 에 모아 두고, 이 폴더가 chat 만의 폴더를 가져오지 않게 테스트로 지킨다. story-server 를 만들 때 `shared/` 로 옮긴다.
4. **표는 서버마다 둔다.** story 는 자기 스키마에 같은 모양의 대화 표를 갖는다. 두 서버가 서로의 표를 읽지 않는다.

대가: 같은 모양의 표가 두 스키마에 있고, 서버, 대시보드, 경보, CI 가 한 벌씩 늘어난다. 대신 한 서버의 장애나 배포가 다른 제품을 멈추지 않고, 표에 `mode` 같은 갈래 칸을 두지 않아도 된다.

## 만드는 순서

작은 조각부터 올린다. 각 조각이 PR 하나 이상이다.

0. **준비.** `shared/server-core` 위에 서버의 뼈대(인증, 관측, 상태 확인)를 세운다([공용 코드 규칙의 언제 뽑는가](shared-code.md#언제-뽑는가)). `app/ai` 는 `shared/ai-core` 로 옮겼다(#499 의 1단계). chat 은 경로 의존으로 받는다. 모델 목록은 파일 원본(`ai_core/model_catalog.toml`)으로 바꿨다(2단계). chat 은 그 파일을 자기 표에 들여온다(`app/catalog/sync.py`, 한 번의 말의 첫 PR). 결제 서버에 chat 의 서명 비밀과 가격표 머리(`chat`)를 더한다. 포트(8005), DB 역할 스크립트(`09-chat-role.sql`), 프록시 주소를 확정한다. 판 가져오기 API 의 모양을 정한다([자산 가져오기](#자산-가져오기)).
1. **캐릭터와 대화.** 가져온 캐릭터, 페르소나, 대화 만들기와 목록. 성인 등급 거르기(`allowed_ratings`)를 함께 넣는다.
2. **한 번의 말.** 스트리밍, 홀드와 확정, 트리의 기본, 한 대화 한 생성. 다시 생성. 대화의 핵심은 `app/conversation/` 에 모은다([story-server 와 나눈 선](#story-server-와-나눈-선)). PR 셋으로 나눈다(2026-10-22): 모델 목록과 대화의 모델(했다), 결제 서버를 부르는 것(홀드, 확정, 돌려주기, 가격 목록. 게임 서버의 것을 옮기고 나중에 server-core 로. 했다. 모델 목록에 값이 붙고 팔지 않는 모델은 고르지 못한다), 말을 보내는 SSE 와 다시 생성(청구 기록과 정리 작업을 함께).
3. **조작.** 최근 대화 창, 다음 답 추천, 이어서 출력. 모델 바꾸기는 한 번의 말의 첫 PR 에 넣었다(새 대화가 지난번 모델을 쓸 수 없을 때 고를 길이 있어야 해서).
4. **세계관, 로어북, 지도, 물건 가져오기.** 장소와 물건 항목을 포함한다. 검색은 아직 없다.
5. **장소와 소지품.** 메시지마다의 상태, 이동, 물건 쓰기와 건네기, 위젯. 규칙의 순수 함수를 `shared/` 로 뽑는다.
6. **기억.** 굴리는 요약, 기억 메모.
7. **로어북 검색.** 임베딩 색인, 벡터 검색.
8. **공개.** 캐릭터 공개와 신고. 관리자 화면(E4)이 먼저다.
9. **이후.** story-server([story 서버 설계의 만드는 순서](story.md#만드는-순서)), 모델이 상태 변경을 제안하는 단계, 구독, 이미지, 음성, 먼저 말을 거는 기능(선톡은 서버가 시간을 재서 보내야 해서 알림 서버와 푸시가 먼저 필요하다), 베이직 등급.

## 열린 질문

- 성인 콘텐츠의 앱 스토어 정책과 앱에서의 노출. 외부 공급자의 약관(`allows_adult` 로 쓸 모델 후보).
- 공개한 캐릭터에 신고가 들어오면 얼마 안에 어떻게 조치해야 하는지(운영자의 의무). 공개를 열기 전에 확인한다.
- 실제 본인인증 업체와 시기(#336, #59). 이것이 있어야 성인 콘텐츠를 열 수 있다.
- 캐릭터를 공개할 때: 검수, 신고, 저작권(남의 작품 캐릭터), 제작자 정산([서비스 구조 명세](services.md#열린-질문)).
- 탈퇴나 삭제 때 대화 기록의 처리, 사용자가 기록을 내려받는 길.
- 이벤트 때 원가를 누가 얼마나 내는지. 할인은 행사가 줄로, 무료는 실버 지급으로 한다([과금](#과금)).
- 한 사용자의 캐릭터와 대화 수의 상한.
- 위반 단계의 기준(몇 번이면 숨김, 정지)과 이의 제기 창구. 알림함 말고 메일로도 보낼지.
- 공급자마다 사용자 식별자를 받는 방식과 경고 절차.
- 로어북 검색을 키워드 먼저로 할지 벡터로 바로 갈지.
- 판 가져오기 API 의 모양(JSON)과 인증. 템플릿의 정의와 같게 둘지([공용 코드 규칙](shared-code.md#열린-질문)).
- 지도의 길을 어디에 정의할지. TRPG 에서는 시나리오의 칸이다. 자산으로 올릴지, 캐릭터나 세계관에 붙일지.
- TRPG 의 NPC 를 chat 캐릭터로 가져오기. 칸이 서비스마다 달라 공통 칸만 복사하고 나머지는 채우게 하는 안이 기본이다.
- 상태 스냅샷의 크기 상한(소지품 개수)과 가 본 곳의 저장 방식.
- 모델이 상태 변경을 제안하는 단계의 허용 목록과 어긋났을 때의 화면.
- 대화 안의 물건을 얻는 길(상점, 이벤트, 선물). 첫 출시는 시작 소지품과 건네기뿐이다.
- 안전 검사가 약한 모델(로컬의 베이직 후보, 성인 허용을 켠 공급자)에서 약관의 금지선을 무엇으로 지키는지. 지금은 모델과 신고에 맡긴다(2026-10-21).
- 시각이 이동 말고 무엇으로 흐르는지. story 는 "시간 보내기"와 "하루 마치기" 행동으로 정했다([story 의 시각](story.md#시각)). chat 에도 둘지는 chat 의 장소와 소지품을 만들 때 정한다.
- 호감도의 규칙을 적는 모양. story 는 TRPG 의 퀘스트 조건 모양으로 정했다([story 의 조건](story.md#조건)). chat 의 선물 규칙도 같은 모양을 쓸지.
- 가져온 복사본이 늘어날 때 탈퇴와 삭제로 지울 곳이 늘어나는 문제.
