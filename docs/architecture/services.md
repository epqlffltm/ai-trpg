# 서비스 구조 명세

이 저장소를 이루는 서버와 서비스가 무엇이고, 어떻게 나뉘고, 서로 무엇으로 이어지는지를 한곳에 적는다.
서버를 더하거나 서버 사이의 길을 바꿀 때 이 문서를 먼저 고친다.

- 기준: `main` `4b383c2` (2026-10-18)
- 2026-10-19: 자산 서버(`asset-server`)를 두고, story 는 chat-server 의 모드로 맡기기로 한 결정을 반영했다. 그 밖의 표는 기준 커밋 그대로다.
- 2026-10-21: TRPG, chat, story 를 서버 셋으로 나누기로 했다(`story-server` 를 다시 둔다). 셋이 함께 쓰는 코드는 `shared/` 에 두고 서버마다 그대로 쓰거나 정해 둔 자리에서 재정의한다([공용 코드 규칙](shared-code.md)).
- **구현된 것**과 **계획인 것**을 나눠 적는다. 계획은 확정이 아니다. 정하지 않은 것은 [열린 질문](#열린-질문)에 있다.
- 규격의 원본은 각 서버의 README 와 [관측 규격](../observability.md)이다. 이 문서는 그것을 가리키기만 하고 같은 내용을 다시 적지 않는다. 둘이 다르면 서버의 README 가 맞다.

## 한눈에

```
                          프런트엔드 (React + TypeScript, 계획)
             사용자 화면 : 공통 껍데기 / TRPG / chat / story                관리자 화면
                                     │ REST, SSE
                                 프록시 (nginx)          /api/v1/<서비스>/...
   ┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
 auth      trpg       board     billing   notification  asset      chat       story      관리
 (Django)  (FastAPI)  (NestJS)  (Go)      (FastAPI)     (FastAPI)  (FastAPI,  (FastAPI,  (FastAPI,
                                                                    계획)      계획)      계획)
   │          │          │          │          │           │          │          │          │
 auth    game(+_test) board(+)  billing(+) notification(+) asset(+)  chat(+)    story(+)    ops
   └──────────┴──────────┴──────────┴──────────┴───────────┴──────────┴──────────┴──────────┘
                              PostgreSQL 한 대 (pgvector) + Redis

   빌드할 때 이미지에 함께 넣는 공용 코드: shared/server-core(토큰 검증, 관측), shared/ai-core(모델 호출) ...
   FastAPI 서버(trpg, notification, asset, chat, story)가 쓴다
```

- 서비스마다 프로세스, DB 스키마, DB 계정이 따로다. 서로의 테이블을 읽지 않고 API 로 주고받는다.
- 계정과 결제는 공용 서비스다. 어느 서비스든 로그인은 인증 서버가, 크레딧은 결제 서버가 맡는다.
- 사용자에게 보이는 제품은 셋이고 **서버도 셋**이다. **TRPG**(trpg-server), **chat**(chat-server, 1:1 캐릭터 대화), **story**(story-server, 세계관 안에서 여러 인물과 이야기를 즐기는 형태)(2026-10-21).
  셋은 같은 틀(FastAPI)이고 많은 것을 함께 쓴다. 함께 쓰는 코드는 `shared/` 에 두고, 서버마다 그대로 쓰거나 정해 둔 자리에서 재정의한다([공용 코드 규칙](shared-code.md)).
- 제작자가 만드는 자산(세계관, 로어북, 캐릭터)의 원본은 **asset-server** 가 갖는다. 서비스는 방이나 대화를 시작할 때 게시된 판을 자기 DB 로 복사해 고정하고, 대화와 게임의 상태는 섞지 않는다. 형식(템플릿)과 코드는 [공유한다](shared-code.md).

## 나누는 기준

서비스를 나누는 기준은 **데이터를 누가 갖는가**와 **한쪽이 죽어도 다른 쪽이 도는가**다. 코드를 재사용하려고 나누지 않는다.

- 한 서비스의 데이터는 그 서비스만 고친다. 다른 서비스가 필요하면 API 로 묻고 부탁한다.
- 서비스가 달라도 로그인은 하나(인증 서버)고 크레딧은 하나(결제 서버)다. 서비스마다 가입이나 결제를 새로 만들지 않는다.
- 코드와 형식을 공유하는 것은 실행 중에 서로를 부르지 않는다. 자산은 예외다. asset-server 가 원본을 갖고, 쓰는 서비스는 방이나 대화를 시작할 때 한 번 게시된 판을 가져와 복사해 고정한다. 턴마다 부르지 않는다. 이것은 [공용 코드 규칙](shared-code.md)에 따로 적는다.
- 한 서버는 한 가지 상호작용 방식을 맡는다. TRPG 는 주사위 판정과 엔진이 한 턴을 이끌고 여러 사람이 방을 함께 쓴다. chat 은 캐릭터 하나와, story 는 세계관 안의 여러 인물과 사용자의 말(대화)이 한 턴을 이끌고 한 사람이 쓴다. 엔진은 chat 과 story 의 매 턴 경로에 없고, 상태를 바꿀 때 쓰는 순수 함수(`shared/`)로만 쓴다.
- 판정이나 상태처럼 정확해야 하는 것은 서버(엔진과 DB)가 정하고, AI 모델은 서술과 대화와 제안만 맡는다. 모델의 출력은 구조화해서 받고 서버가 검증한 뒤에 적용한다.
  이 원칙은 TRPG, chat, story 모두에 적용된다.

## 서비스 사이의 길

사용자의 요청은 프록시를 거쳐 서비스로 들어간다. 서비스끼리 부를 때는 사용자의 토큰을 넘기지 않고, 두 서버만 아는 비밀로 요청에 서명한다.
서명의 모양과 받는 쪽이 기대는 답은 저장소의 서버 README 가 원본이다.

| 부르는 쪽 → 받는 쪽 | 무엇을 | 원본 |
| --- | --- | --- |
| 게임 → 결제 | 서술 값의 홀드, 확정, 반환, 연장. 가격 목록 받기 | `billing-server/README.md` 의 "홀드" |
| 인증 → 결제 | 환영 크레딧, 결제 자격(성년, 보호자 동의) 알림 | `billing-server/README.md` 의 "크레딧" |
| 결제 → 인증 | 미성년자의 결제와 청약철회를 보호자에게 알리라는 부탁(정리 작업이 보낸다) | `billing-server/README.md` 의 "정리 작업과 대사" |
| 결제 대행사 → 결제 | 결제 알림(웹훅). 본문의 결과를 믿지 않고 결제 대행사에 다시 묻는다 | `billing-server/README.md` 의 "주문과 결제" |
| 결제 → 결제 대행사 | 결제 승인, 취소, 결과 묻기 | `billing-server/README.md` 의 "주문과 결제" |
| 게임, 결제, 게시판 → 알림 | 사람에게 보낼 알림 넣기(`POST /api/v1/notification/service/{source}/notifications`). 서명 비밀은 넣는 서버마다 따로다(알림 서버의 `GAME_SERVER_SECRET`, `BILLING_SERVER_SECRET`, `BOARD_SERVER_SECRET`). 게임과 게시판은 일이 일어난 트랜잭션에서 발송함에 적고 5초마다 보낸다. 결제는 정리 작업이 주문과 지급에서 알릴 일을 찾아 보낸다 | `notification-server/README.md` 의 "알림 넣기" |
| 게임, 게시판, 결제, 알림 → 인증 | 공개키(JWKS)와 끊긴 세션의 목록 받기 | `auth-server/README.md` |

여러 서비스의 것을 한 화면에 보이는 곳(첫 화면의 이어하기, 갤러리, 계정의 기록)은 화면이 서비스마다 부르고 화면에서 놓는다. 모아 주는 서버를 두지 않는다(#593, [화면 명세의 A1](../product/screens.md#a1-첫-화면탐색)).
한 서비스가 죽어도 그 칸만 비고, 서버끼리 실행 중에 부르는 길이 생기지 않는다.

앞으로 생길 길(계획):

| 부르는 쪽 → 받는 쪽 | 무엇을 | 비고 |
| --- | --- | --- |
| chat, story → 결제 | 대화의 값을 홀드로 받기, 가격 목록 받기 | 게임 서버와 같은 방식. 서명 비밀은 서버마다 따로(`CHAT_SERVER_SECRET`, `STORY_SERVER_SECRET`)고, 비밀마다 쓸 수 있는 가격표 이름의 머리가 정해진다(chat 은 `chat`, story 는 `story`. [이름 규칙](#이름-규칙)). 결제 쪽의 chat 은 #578 로 붙었다. 지금은 chat 의 비밀로 `story` 도 열려 있어서 story 의 비밀을 더할 때 옮긴다 |
| 게임, chat, story → 자산 | 방이나 대화를 만들 때, 쓸 자산의 게시된 판을 가져와 자기 DB 에 복사해 고정한다. 턴마다 부르지 않는다 | 서명 비밀은 부르는 서버마다 따로 둔다. 쓸 수 있는 사람인지(소유자나 공개)와 등급은 asset-server 가 판단한다. 가져온 뒤 원본이 바뀌어도 복사본은 그대로고, 새 판이 있다고 알리기만 한다 |
| 인증 → 게시판 | 닉네임 바꾸기 알림 | 인증 서버에 그 기능이 생길 때 |
| 인증 → 결제, 알림, 게임, 게시판, asset | 탈퇴 알림(`POST /api/v1/<서버>/service/users/{public_id}/withdrawal`). 인증 서버의 발송함에서 2xx 까지 다시 보낸다. 서명 비밀은 받는 서버마다 따로 | [탈퇴](withdrawal.md). 결제는 이미 있는 비밀을 쓴다 |
| 관리 → 인증, 게시판, 결제, 게임, 자산, chat, story | 정지, 숨기기, 가격표 바꾸기, 결과를 모르는 주문 정하기 같은 관리자 작업 요청 | 각 서비스의 관리자용 API 를 부른다. 관리 서버가 다른 서비스의 DB 를 고치지 않는다 |
| 서비스 → 로그 수집기(Grafana Alloy) | 로그, 메트릭, 추적 | 관리 서버를 거치지 않는다. [관측 규격](../observability.md#수집기grafana-alloy를-붙일-자리) |

## 공용으로 쓰는 것

공용에는 세 가지가 있고, 서로 성질이 다르다.

| 종류 | 예 | 언제 묶이나 | 한쪽이 죽으면 |
| --- | --- | --- | --- |
| 공용 서비스 | 인증, 결제, 자산, 관리 | 실행 중에 API 로 | 의존하는 기능이 막힌다(예: 결제가 죽으면 서술 값을 받지 못한다). 자산은 새 방이나 대화를 시작할 때만 필요해서, 죽어도 진행 중인 것은 복사본으로 돈다 |
| 공용 코드 | `shared/` 의 서버 공통부, AI 호출, 템플릿 | 이미지를 빌드할 때 | 영향 없음(각 이미지에 이미 들어 있다) |
| 공용 인프라 | PostgreSQL, Redis, 프록시, 로그 수집기 | 실행 중에 | 인프라별로 다르다 |

공용 코드는 데이터를 공유하지 않는다. 형식과 함수만 공유한다. 자세한 규칙은 [공용 코드 규칙](shared-code.md).

## 이름 규칙

한 서비스의 이름은 여러 곳에 같은 글자로 박힌다. 한 번 정하면 바꾸기 번거로우므로 처음에 정한다.

| 곳 | 규칙 | 예 |
| --- | --- | --- |
| 폴더, 로그의 `service` 값 | `<이름>-server` 로 같게. 설정으로 바꾸지 않는다 | `chat-server` |
| DB 계정과 스키마 | 이름 그대로. 테스트 스키마는 `<이름>_test` | `chat`, `chat_test` |
| 초기화 스크립트 | `NN-<이름>-role.sql`, 다음 번호부터(`docker/postgres/init/` 의 마지막 번호 다음) | `09-chat-role.sql` |
| 토큰의 대상(`aud`) | `ai-trpg-<이름>` | `ai-trpg-chat` |
| 프록시 주소 | `/api/v1/<이름>/` | `/api/v1/chat/` |
| 이미지·워커·마이그레이션 | `<이름>-server`, `<이름>-migrate` 등 | `chat-migrate` |
| 결제를 부를 때의 서명 비밀 | `<이름>_SERVER_SECRET`. 서버마다 따로고 서로 같은 값이면 결제 서버가 켜지지 않는다 | `CHAT_SERVER_SECRET` |
| 결제 가격표의 이름 | `<제품>.<모델>.i<입력 단계>.o<출력 단계>`. 머리(`<제품>`)는 서비스 이름이고, 비밀마다 자기 머리의 이름만 홀드에 쓸 수 있다. 게임 서버만 예전부터 `narration` 이다. 단위는 같은 크레딧이고, 등급(`basic`, `standard`, `premium`)은 이름이 아니라 가격표의 줄마다 적는다 | `chat.gpt-6-luna.i0.o0` |

- 서비스 이름은 하는 일을 쓴다. 브랜드 이름을 쓰지 않는다. 사용자에게 보이는 이름이 바뀌어도 코드는 바뀌지 않게 하려는 것이다.
- 사용자에게 보이는 이름(플랫폼 이름, 제품 이름)은 서비스 이름과 별개이고 아직 정하지 않았다.
- 2026-10-18 에 정한 이름: `chat-server`, `notification-server`. 2026-10-19 에 `asset-server` 를 더했다. `story-server` 는 2026-10-19 에 두지 않기로 했다가 2026-10-21 에 다시 두기로 했다.

## 토큰과 권한

- 인증 서버가 RS256 으로 서명한 access 토큰(수명 15분)을 발급한다. 발급자는 `ai-trpg-auth`, 사용자는 토큰의 `sub`(`public_id`, UUID)로만 식별한다.
- **토큰 하나에 모든 서버의 이름이 `aud` 목록으로 실린다.** 각 서버는 자기 이름이 목록에 있는지만 본다. 목록은 `auth-server/config/settings.py` 의 `JWT_AUDIENCE` 한 곳이다.
- 서버를 더하면 그 이름을 `JWT_AUDIENCE` 에 더한다. 이미 발급된 토큰에는 새 이름이 없지만 15분이면 저절로 맞는다.
- 다른 서버는 인증 서버의 공개키(`GET /api/v1/auth/jwks`)로 검증만 한다. 가입과 로그인을 다른 서버에 중복으로 만들지 않는다.
- 관리자 권한은 사용자 API 에 섞지 않고, 따로 묶은 주소와 따로 된 인증으로 연다. 관리자 역할을 토큰에 싣는 방법은 정하지 않았다([열린 질문](#열린-질문)).

**알려진 대가.** 토큰 하나가 모든 서버에 유효하므로, 한 서버가 받은 토큰이 새면 15분 동안 다른 서버에도 쓸 수 있다.
서버가 늘고 사용자가 만든 콘텐츠를 다루는 서비스가 생길수록 이 위험이 조금씩 커진다.
대안은 서버마다 토큰을 따로 발급하는 것인데, 지금은 구현과 운영 비용 때문에 택하지 않았다.

## 데이터

- PostgreSQL 한 대에 서비스마다 스키마와 계정을 나눈다. 계정은 자기 스키마에 필요한 권한만 가진다. 차단은 `search_path` 가 아니라 실제 DB 권한으로 하고, 거부되는지 테스트한다.
- 서비스 사이에 외래키를 걸지 않는다. 사용자는 인증 서버의 `public_id` 로 가리킨다.
- 자산(세계관, 로어북, 캐릭터)의 원본은 `asset` 스키마에 있다. 쓰는 서비스는 시작할 때 게시된 판을 자기 스키마로 복사해 고정하고, 외래키 없이 출처(서비스, 자산 id, 판)만 적는다. 원본이 바뀌어도 복사본은 따라가지 않는다.
- 정확해야 하는 데이터(HP, 소지품, 퀘스트, 크레딧, 호감도)는 관계형 DB 가 기준이다. 세계관, 로어, 기억 같은 검색용 데이터는 임베딩(pgvector)으로 찾는다.
- Redis 는 캐시와 시도 제한 같은 곳에만 쓴다. 결제 기록과 게임의 확정 상태는 PostgreSQL 이 기준이다. 서버마다의 연결과 메모리의 몫은 [DB 와 Redis 의 한도](#db-와-redis-의-한도)에 있다.
- 운영 로그, 메트릭, 관리자 작업 이력은 관리 서버(`ops`)와 수집 저장소의 몫이고, 업무 원본(게임 판정, 결제 원장)은 각 서비스가 가진다.

## DB 와 Redis 의 한도

서버들은 PostgreSQL 한 대와 Redis 한 대를 함께 쓴다. 한 서버가 한도를 다 쓰면 다른 서버가 함께 멈추므로, 몫을 미리 나눈다(2026-10-21, #592).

### DB 의 연결

PostgreSQL 의 `max_connections` 는 기본값 100 이고, superuser 의 몫 3 을 빼면 서버들의 계정이 쓸 수 있는 것은 97 이다.
아래는 서버마다 한 대씩 띄울 때 쥘 수 있는 가장 많은 연결이다. 합이 97 안에 들게 나눈다.

| 쓰는 곳 | 몫 | 정하는 곳 |
| --- | --- | --- |
| trpg | 16 | 풀 5 + 10(`trpg-server/app/core/database.py`). 실시간 신호의 LISTEN 연결 1 은 풀 밖이다. server-core 로 옮길 때(#589) 설정으로 넘어온다 |
| chat | 10 | compose 의 `DB_POOL_SIZE` 5, `DB_MAX_OVERFLOW` 5 |
| story(계획) | 10 | chat 과 같다(#591) |
| notification | 5 | compose 의 2 + 3 |
| asset | 5 | compose 의 2 + 3. 그림은 S3 로 가고 DB 에는 줄만 쓴다 |
| billing | 12 | 서버 8, sweeper 2, cron 2(`billing-server/README.md` 에 잰 값) |
| board | 10 | TypeORM 의 `poolSize`(`board-server/src/database/database.options.ts`) |
| auth | 4 | gunicorn 의 워커 1(`WEB_CONCURRENCY`), mail, welcome-credits, cron 이 1 씩. Django 는 요청마다 연결을 맺고 닫는다 |
| 관리(계획) | 5 | 운영자만 쓴다 |
| 감시(monitor), 백업, 배포 중의 마이그레이션 | 3 | |
| **합** | **80** | 남는 17 은 auth 의 워커를 늘리거나 잰 뒤 몫을 고치는 데 쓴다 |

- **몫은 쓰는 양이 아니라 상한이다.** 붐빌 때만 넘침(overflow)까지 맺고 돌려주면 닫는다. DB 의 CPU 가 둘이라 동시에 도는 쿼리는 이보다 훨씬 적어야 빠르다(결제 서버가 잰 것으로는 연결 8 과 16 이 같은 빠르기다)
- **FastAPI 서버(server-core)의 몫은 compose 에 적는다.** 다시 빌드하지 않고 값만 바꾼다. 적지 않으면 SQLAlchemy 의 기본(5 + 10)이다. PC 에서 서버를 직접 띄울 때가 그렇다
- **AI 모델을 기다리는 동안 DB 연결을 쥐지 않는다.** 스트리밍(chat, story, trpg 의 서술)은 길게는 수십 초다. 그동안 연결을 쥐면 몫 10 이 동시에 말하는 10 명에서 막힌다
- 풀이 모자라면 메트릭 `db_pool_wait_seconds` 가 오른다. 전체가 한도에 가까우면 경보 `PostgresConnectionsNearLimit`(80%)가 울린다
- 서버를 두 대 이상 띄우면 그 서버의 몫이 대수만큼 곱해진다. 그때 이 표를 다시 센다
- 몫이 모자라면 차례로 본다. 먼저 몫을 다시 나눈다(재 보고). 그래도 모자라면 `max_connections` 를 올린다(연결마다 메모리를 조금 더 쓴다). PgBouncer 는 그다음이다. 컨테이너가 하나 늘고 asyncpg 의 prepared statement 설정을 바꿔야 한다
- staging 에서 실제 연결 수를 재서 이 표를 고친다(#491)

### Redis

| 쓰는 곳 | DB 번호 | 키의 머리 | 넣는 것 |
| --- | --- | --- | --- |
| auth | 0 | `auth:attempts` | 시도 횟수, IP 차단(기한이 있다) |
| trpg | 0 | `game:limit` | 로비 비밀번호와 채팅의 시도 횟수(기한이 있다) |
| chat | 2 | 서버가 정한다 | 요청 제한(기한이 있다) |
| story(계획) | 3 | 서버가 정한다 | 요청 제한(기한이 있다) |

- **메모리는 64MB 까지, 차면 `volatile-lru`.** 기한이 걸린 키 가운데 오래 안 쓴 것부터 내쫓는다. 지금 넣는 것은 모두 기한이 있는 시도 횟수라, 내쫓기면 제한이 조금 느슨해질 뿐이다. 내쫓으면 경보 `RedisEvictingKeys` 가 울린다
  - `noeviction` 을 고르지 않은 까닭: 차면 쓰기가 실패한다. trpg 는 Redis 가 막히면 닫힌 쪽으로 실패해(로비 비밀번호와 채팅이 503) 메모리가 찬 것이 서비스가 멈춘 것이 된다
- **버리면 안 되는 것은 Redis 에 두지 않는다.** 잠금, 큐, 확정된 상태는 PostgreSQL 에 둔다(chat 의 한 대화 한 생성은 DB 의 조건부 UPDATE, trpg 의 실시간 신호는 PostgreSQL 의 NOTIFY). 그런 것이 Redis 에 꼭 필요해지면 정책을 섞지 않고 인스턴스를 따로 둔다
- **캐시를 두게 되면 캐시용 인스턴스를 따로 둔다.** 정책(`maxmemory-policy`)이 인스턴스에 하나뿐이다
- DB 번호는 메모리도 정책도 나누지 않는다. 키를 나눌 뿐이다. 인증과 trpg 는 머리가 달라 0 을 함께 쓴다. 새 서버는 다음 번호를 쓰고 머리에 서버 이름을 붙인다

### 언제 나누는가

- DB 와 Redis 를 서버마다 따로 두는 것은 부하가 실제로 부딪힐 때다. 미리 나누면 VM 의 메모리와 백업, 감시가 그만큼 는다
- 먼저 나뉠 후보는 pgvector 를 쓰는 쪽(chat, story 의 기억과 로어)이다. 벡터 검색이 CPU 와 메모리를 가장 많이 쓴다
- 나눌 때도 서버는 자기 스키마와 자기 계정만 쓴다. 바뀌는 것은 접속 주소뿐이다

## 배포 형태

- 처음에는 서버 한 대(VM)에 Docker Compose 로 띄운다. 어디에, 어떻게 올리는지는 [배포 설계](deployment.md)에 있다. 쿠버네티스를 쓰지 않고, GPU 서버도 필요하지 않다(모델은 외부 API 를 부른다).
- 개발은 PC 에서 서버를 직접 띄우고, `docker compose --profile app` 으로 서버들을 한꺼번에 컨테이너로 띄워 볼 수 있다.
- 바깥에서는 프록시 하나로 들어온다. 서비스의 포트는 바깥에 열지 않는다. 열려 있는 포트는 CI(`port_scope.py`)가 검사한다.
- 컨테이너 수를 부하에 따라 자동으로 늘리고 줄이는 구조가 아니다. 서버를 여러 개 띄우려면 먼저 서버 한 대를 가정한 부분(게임 서버의 실시간 신호, 뒤에서 도는 작업의 중복 실행, 프로세스의 메모리에서 세는 재시도 예산 등)을 점검해야 한다.

| 무엇 | 곳 |

| 컨테이너 | `docker-compose.yml` 의 `<이름>-migrate`, `<이름>-server`(프로필 `app`) |
| 프록시 | `docker/nginx/templates/api.inc.template` 의 `/api/v1/<이름>/` 위치(로컬과 staging 이 함께 쓴다), 요청 수 제한(`http.inc.template`) |
| 비밀과 포트 검사 | `.github/scripts/secret_scope.py`, `port_scope.py`, `logging_scope.py` 의 표 |
| CI | `.github/workflows/<이름>-server.yml`, `ci.yml`, `.github/scripts/changed-servers.sh` |
| DB 와 Redis 의 몫 | [DB 와 Redis 의 한도](#db-와-redis-의-한도)의 표. FastAPI 서버는 compose 의 `DB_POOL_SIZE`, `DB_MAX_OVERFLOW`. Redis 를 쓰면 다음 번호와 키의 머리 |
| 관측 | `docs/observability.md` 의 서비스 이름 표와 작업, operation, 오류 코드 표 |
| 결제 (결제를 부르는 서버일 때) | `billing-server` 의 설정(`<이름>_SERVER_SECRET` 과 다른 비밀과 같은 값인지의 검사), 그 비밀로 열리는 주소, 비밀마다 쓸 수 있는 가격표 이름의 머리, 홀드에 부른 서버를 적는 칸(마이그레이션). 비밀이 늘면 `.github/scripts/secret_scope.py` 의 표와 `docker-compose.yml` 에서 비밀을 비우는 곳도 고친다 |
| 공용 코드 (FastAPI 서버일 때) | `pyproject.toml` 의 경로 의존(`shared/server-core` 등), compose 의 `build.additional_contexts`, Dockerfile 의 `COPY --from=shared`. CI 는 경로 의존을 읽어 저절로 고른다([공용 코드 규칙](shared-code.md#버전과-ci)) |
| 문서 | 루트 `README.md` 의 상태 표, `CONTRIBUTING.md` 의 구성 표, 이 문서 |

## 순서

계획이며 바뀔 수 있다.

1단계(운영자 혼자 TRPG, chat, story 를 끝까지)에 1~6 이 들어간다. VM 은 1단계가 끝난 뒤에 띄운다(2026-10-20, [화면 명세의 첫 출시의 범위](../product/screens.md#첫-출시의-범위)).

1. **API 목록.** 다섯 서버가 모두 OpenAPI 를 내고 `docs/api/` 에 파일로 모은다. CI 가 서버의 것과 같은지 본다. 프런트의 타입과 Stitch 에 넘길 목록이 이것이다(2026-10-21).
2. `shared/` 를 만든다. 먼저 서버의 공통부(`server-core`: 토큰 검증, 관측)를 알림과 asset 에서 뽑아 두 서버를 옮겼다(#588). chat 과 story 는 처음부터 그것을 쓴다. trpg-server 는 그 뒤에 하나씩 옮긴다(#589). AI 호출 코드(`ai-core`)는 trpg-server 안에서 경계를 정리했고(#496, #497, #498), `shared/` 로 옮기는 일은 chat-server 의 "한 번의 말"을 만들 때 한다(#499). 방식은 [공용 코드 규칙의 정한 것](shared-code.md#정한-것)에 있다.
3. `asset-server` 를 새로 만들고, 새 종류인 캐릭터를 처음부터 거기서 만든다. 같은 때에 trpg-server 가 세계관과 로어북의 게시된 판을, asset-server 가 나중에 줄 것과 같은 모양의 API 로 내준다.
4. `chat-server` 의 첫 버전. 캐릭터를 쓴 대화(판 가져오기), 스트리밍 대화, 다시 생성, 자동 요약 기억, 모델 등급과 크레딧, 장소와 소지품. TRPG 의 지도, 물건, 인물을 공용 템플릿으로 올려 쓴다. 자세한 순서는 [chat 서버 설계](chat-server.md#만드는-순서).
5. `story-server` 의 첫 버전. 여러 인물, 호감도(NPC 의 태도에서 이어 가는 수치), 이벤트와 엔딩(조건으로 드러나는 퀘스트의 모양). 규칙은 [story 서버 설계](story.md)에 있다(2026-10-20). chat 과 같은 대화의 핵심은 그때 `shared/conversation-core` 로 뽑아 함께 쓴다.
6. 프런트엔드와 화면. 백엔드(1~5)가 거의 다 된 뒤 화면 명세와 API 목록으로 Stitch 의 시안을 받고, 디자인의 요소만 뽑아 React 로 쓴다. 프런트 하나에 TRPG, chat, story 를 경로로 나눈다([화면 명세의 프런트 구조](../product/screens.md#프런트-구조), 2026-10-21).
7. 배포. VM 을 띄운다([배포 설계](deployment.md)). 로그·메트릭·추적 수집과 경보, staging 의 운영 설정과 TLS(#451), 바깥 백업, VM 준비 순서는 붙여 두었다.
8. 관리 서버의 첫 버전(공개 베타 전, 2단계 동안). 신고 처리, 비용 집계, 지금 명령으로 하는 결제 운영 작업(가격표, 가격 할 일, 결과를 모르는 주문). 잔액 환불은 아직 없는 기능이라 설계가 필요하다([열린 질문](#열린-질문)).
9. 세계관과 로어북(항목 포함)을 trpg-server 에서 asset-server 로 옮긴다. 쓰는 쪽이 복사본을 들고 있어서 chat 은 거의 안 바뀐다. 이전은 따로 설계한다.

## 열린 질문

정하지 않았다. 확정으로 가정하지 않는다.

**토큰과 권한**
- 토큰의 대상 이름의 접두사 `ai-trpg-` 를 그대로 둘지. 플랫폼 이름이 정해지면 바뀔 수 있다.
- 관리자 역할을 토큰에 싣는지, 인증 서버에 묻는지.
- 서버마다 토큰을 따로 발급하는 구조로 갈지(위의 "알려진 대가").

**결제와 정산**
- 잔액 환불(설계가 필요함). 남은 산 크레딧을 돌려줄지, 돌려준다면 어느 주문에서 얼마를 부분 취소할지, 수수료와 무료 크레딧은 어떻게 할지. 지금 있는 것은 7일 안의 청약철회(쓰지 않은 주문의 전액 취소)뿐이다.
- 제작자 정산을 어느 서비스가 맡는지. 사용자가 만든 캐릭터를 열 때 필요하다.
- 탈퇴: 남은 골드는 알리고 소멸, 걸린 홀드는 돌려준다, 7일 유예([탈퇴](withdrawal.md)). 남은 것은 법정 보존 뒤의 처리와 게임·chat 기록의 세부(그 문서의 열린 질문).
- 실제로 돈을 받는지(사업자, 환불 규정, 세금).

**콘텐츠와 연령**
- 성인 등급 콘텐츠의 허용 범위. 외부 모델 API 의 정책에 걸린다.
- 사용자가 만든 캐릭터를 첫 베타부터 열지. 열면 신고 처리와 검수가 베타에 필요해진다.

**구조**
- 관리 서버의 이름, 포트, 스키마 이름(`ops` 는 우선의 안).
- 토큰의 대상(`ai-trpg-game`), DB 스키마(`game`), 환경 변수(`GAME_*`), 주소(`/api/v1/game/`)도 `trpg` 로 바꿀지. 지금은 계약과 저장된 데이터라서 그대로 둔다(#480).
- 페르소나는 계정 하나에 모아 세 서비스가 함께 쓴다. 원본은 asset-server 이고, TRPG 의 보관함은 계정 페르소나를 가리키는 시트(능력치, 룰북)가 된다(2026-10-21, [asset 서버 설계](asset-server.md#계정-페르소나)).
- 남의 공개 자산을 가져오는 권한과 라이선스. 처음에는 제작자 본인이 자기 자산을 쓰는 것만 허용한다.
- Django 관리자(`/admin/`)를 남길지, 관리 서버가 대신하면 닫을지.
- 서버 아홉 개(인증, 게임, 게시판, 알림, 결제, 자산, chat, story, 관리)를 한 대에 올릴 때의 메모리와 클라우드 사양.
- 서비스 사이 API 의 버전과 계약을 어디에 적을지.
- 플랫폼과 제품의 사용자용 이름.
