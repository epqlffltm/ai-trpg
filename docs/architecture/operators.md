# 운영자 권한

운영자(어드민)가 누구인지, 서비스마다 무엇을 더 할 수 있는지, 그때 무엇을 남기는지를 정한다.
2026-10-18 에 정했다. 구현하는 PR 이 이 문서의 "구현" 칸을 고친다. 인증 서버의 `roles` 는 #389, 게임 서버의 성인 등급 예외는 #390, 운영자 읽기는 #391, 제재는 #392 다.

## 한눈에

- 운영자인지는 **인증 서버가 정하고 access 토큰에 싣는다**(`roles`). 다른 서버는 토큰을 읽기만 한다. 서버마다 운영자 목록을 따로 두지 않는다.
- 운영자는 성인 인증의 확인을 받지 않는다. 문제가 된 성인용 시나리오와 테이블도 봐야 하기 때문이다.
- 운영자는 남의 시나리오의 내부(진행 지침, GM 전용 설정, 로어북처럼 AI 에 들어가는 글)와 테이블의 기록(서술, 대화, 귓속말)을 본다. chat 이 생기면 대화와 캐릭터 설정도 본다.
- 운영자가 남의 것을 볼 때마다 **누가, 언제, 무엇을, 왜** 보았는지 지울 수 없게 남긴다.
- 제재는 셋이다. 시나리오의 공개 내리기(그 판은 다시 공개하지 못한다), 공개 금지(블랙리스트), 테이블 끝내기. 사용자 정지는 인증 서버가 한다([제재](#제재)).

## 누가 운영자인가

**인증 서버의 그룹 `operators`** 에 든 계정이다. 운영자를 넣고 빼는 것은 인증 서버의 관리자 화면(`/admin/`)에서 한다.

- Django 의 `is_staff`(관리자 화면에 들어가는 권한)와 나눈다. 관리자 화면을 쓰는 권한과 서비스의 운영 권한은 다른 것이라, 필요한 권한만 주려는 것이다.
- 인증 서버는 access 토큰을 만들 때마다(로그인, 갱신) 그룹을 다시 읽어 싣는다. 닉네임, `adult_content` 와 같은 자리다.

```json
{"sub": "…", "nickname": "…", "adult_content": false, "roles": ["operator"]}
```

- `roles` 는 글자의 목록이다. 일반 사용자는 빈 목록이다.
- 받는 서버는 목록에 `"operator"` 가 정확히 있을 때만 운영자로 본다. 칸이 없거나, 목록이 아니거나, 모르는 역할은 일반 사용자로 본다. 토큰을 거부하지는 않는다.
- 역할을 빼면 늦어도 access 토큰의 수명(15분) 뒤에 사라진다. 바로 막아야 하면 인증 서버에서 그 사람의 세션을 끊는다. 끊긴 세션의 목록을 받는 서버(게임, 게시판, 결제)는 30초쯤 안에 막는다.

**택하지 않은 것.**

| 안 | 택하지 않은 까닭 |
| --- | --- |
| 서버마다 설정(환경 변수)에 운영자 목록 | 서버가 늘수록 목록이 서버 수만큼 생겨 어긋난다. 바꾸려면 서버를 다시 켜야 하고, 누가 언제 넣었는지 남지 않는다 |
| 서버마다 DB 에 운영자 표(예전의 게시판) | 서비스마다 목록이 갈라진다(게시판에서는 운영자인데 게임에서는 아닌 사람). 등급 판정처럼 자주 보는 곳이 DB 를 물어야 한다 |

로그인 서버가 토큰에 역할을 싣고 서비스는 읽기만 하는 것이 업계의 흔한 방식이다(Auth0 의 `permissions`, Keycloak 의 `realm_access.roles`, Cognito 의 `cognito:groups`, Firebase 의 custom claims).
데이터마다의 세밀한 권한(이 사람이 이 테이블에 앉아 있나)은 지금처럼 각 서비스가 정한다.

**게시판.** 토큰의 역할을 읽는다(공용 코드 `server_core/auth/tokens.py` 의 `read_is_operator`, 게임 서버와 같은 규칙). 예전의 게시판 `operators` 표는 지웠다. `GET /api/v1/board/me` 가 `is_operator` 를 돌려주어 화면이 운영자만 쓰는 버튼을 미리 보이거나 숨길 수 있다.

## 운영자가 더 할 수 있는 것

일반 사용자의 API 와 운영자의 API 를 나눈다. 일반 API 에 섞이는 예외는 **성인 등급의 판정 한 곳**뿐이다.

### 게임 서버

| 무엇 | 어디서 | 구현 |
| --- | --- | --- |
| 성인 등급의 확인을 받지 않는다. 성인용 목록과 상세를 보고, 성인용 테이블을 만들고 들어오고, 성인용 시나리오를 쓴다 | 일반 API. 등급을 가르는 곳(`app/assets/ratings.py` 의 `allowed_ratings`) 한 곳이 "성인용을 볼 수 있음 또는 운영자"를 본다 | 됨(#390) |
| 남의 시나리오를 본다. 초안과 판 모두, 판에 굳힌 내용 전부(룰북의 진행 지침, 세계관의 GM 전용 설정, 로어북, GM 메모, 프리젠, 몬스터) | 운영자 API(`/api/v1/game/admin/scenarios/{id}`, `.../versions/{number}`) | 됨(#391). 초안이 가리키는 재료(룰북, 세계관, 로어북)는 아직이다. 테이블은 판으로 돌므로 판에서 본다 |
| 남의 테이블을 본다. 테이블의 상태, 기록(서술, 행동, 판정), 테이블 대화, 귓속말, 장부 초안, 라운드의 기억 | 운영자 API(`/api/v1/game/admin/tables/{id}`, `/events`, `/messages`, `/whispers`) | 됨(#391): 상태와 굳힌 판의 내용, 기록, 대화, 귓속말. 장부 초안과 라운드의 기억은 아직이다 |
| AI 에 보낸 입력과 AI 의 답 | 보낸 메시지의 원문은 저장하지 않는다(AI 호출 기록에는 지문, `prompt_version`, 들어간 로어북 항목과 기억의 번호만 있다). 모델의 답은 30일 동안 남지만 API 로 내보내지 않는다(DB 에 닿는 사람만 본다). 운영자는 판과 기록으로 무엇이 들어갔는지 본다. 운영자 API 로 열지는 [정하지 않은 것](#정하지-않은-것) | - |

- 운영자 API 는 앉아 있는지, 만든 사람인지를 보지 않는다. 운영자인지만 본다. 운영자가 아니면 404 다(운영자 주소가 있다는 것을 알리지 않는다).
- 운영자 API 는 **읽기만** 한다. 제재는 [순서](#순서)의 3단계다.
- 운영자가 일반 API 로 남의 테이블에 들어가면 그 테이블의 참가자가 된다(다른 사람에게 보인다). 몰래 보는 것은 운영자 API 로만 한다.

### asset 서버

| 무엇 | 어디서 | 구현 |
| --- | --- | --- |
| 공개 캐릭터의 신고를 보고 처리한다(받아들이면 숨긴다) | `GET /api/v1/asset/admin/character-reports`, `PUT .../admin/characters/{id}/reports/outcome` | 했다(#678) |
| 캐릭터를 숨기고 푼다. 숨긴 캐릭터는 남에게 보이지 않고 주인만 쓴다 | `PUT /api/v1/asset/admin/characters/{id}/hidden` | 했다(#678) |

- 조치는 `operator_actions` 에 남긴다(아래 [감사 기록](#감사-기록)과 같은 칸, 덧붙이기만). 신고의 목록은 운영자에게 보낸 것이라 보기 기록을 남기지 않는다.
- 숨김과 풀기는 캐릭터의 주인에게, 신고의 처리는 신고한 사람마다 알림함에 간다([asset 서버의 알림 보내기](../../asset-server/README.md#알림-보내기)).
  처리 알림에는 결과(숨김, 기각)와 사유를 싣지 않는다. 신고한 사람이 결과로 상대를 짐작하거나 운영 판단을 두고 다투지 않게 한다(2026-10-23 유저 결정).

### chat 서버

| 무엇 | 어디서 | 구현 |
| --- | --- | --- |
| 신고된 캐릭터의 답과 신고 때 굳힌 앞의 말(여섯)을 본다. 사유 필수, 볼 때마다 `operator_reads` | `GET /api/v1/chat/admin/message-reports/{id}?reason=` | 했다(#678) |
| 신고를 처리한다(`operator_actions`). 캐릭터를 숨기는 것은 asset 의 운영자 API 다 | `PUT /api/v1/chat/admin/message-reports/{id}/outcome` | 했다(#678) |

- 사적 대화는 운영자가 열지 않는다. 신고하는 순간 그 답과 앞의 말을 신고에 굳혀 두고, 운영자는 그것만 본다(대화 전체를 여는 API 는 없다).
- 처리하면 신고한 사람의 알림함에 간다([chat 서버의 신고](../../chat-server/README.md#신고)). asset 처럼 결과와 사유는 싣지 않는다.

계획(아직 하지 않은 것):

- 운영자는 남의 대화 기록과 캐릭터 설정(페르소나, 프롬프트에 들어가는 글)을 운영자 API 로 본다(법적 요청 같은 예외일 때).
- 성인 등급의 확인을 받지 않는다. 판정은 게임 서버처럼 함수 한 곳이다.
- [감사 기록](#감사-기록)을 같은 모양으로 남긴다.

### story 서버

### 결제와 인증

- 결제: 지금 운영 작업은 명령(`cmd/prices`, `cmd/pricereviews`, `cmd/orders`, `cmd/grants`)이다. 관리 서버가 생기면 관리자용 주소로 연다([services.md](services.md)).
- 인증: 운영자를 넣고 빼는 것은 인증 서버의 관리자 화면이다.

## 제재

2026-10-18 에 정했다(#392). 게임 서버의 운영자 API(`POST /api/v1/game/admin/...`)로 한다. 모두 본문에 사유(`reason`)를 받는다.

| 제재 | 무엇이 일어나나 | 막지 않는 것 |
| --- | --- | --- |
| 시나리오 제재(`/scenarios/{id}/sanction`) | 공개를 내린다. **그 판은 다시 공개하지 못한다**(403 `version_sanctioned`). 공개 중이 아니면 409 `not_published` | 제작자가 그 판으로 혼자 테이블을 여는 것. 고쳐서 **새 판을 내면 바로 공개**된다(운영자의 확인 없이. 다시 문제가 되면 또 제재되고 수가 쌓인다). 이미 그 판으로 열린 테이블은 그대로다 |
| 공개 금지(블랙리스트) | 그 사람은 어떤 판도 공개하지 못한다(403 `publishing_banned`). **제재된 시나리오가 정해진 수(`PUBLISHING_BAN_THRESHOLD`, 기본 3)에 닿으면 저절로** 오른다. 운영자가 직접 올리고(`/users/{id}/publishing-ban`) 푼다(`.../lift`). 풀면 그 뒤의 제재부터 다시 센다 | 자기 시나리오나 남의 시나리오로 플레이하는 것. 이미 공개 중인 다른 시나리오는 그대로다 |
| 테이블 끝내기(`/tables/{id}/end`) | 방장이 끝낸 것과 같다. 앉은 사람에게 이벤트로 "운영자가 끝냈다"(`by: operator`)가 보인다. 운영자가 누구인지, 사유는 보이지 않는다. 걸린 서술 값은 정리 작업이 돌려준다 | 기록은 앉았던 사람이 계속 읽는다 |
| 사용자 정지 | **지금은 인증 서버의 명령**(`suspend_account --kind <사유의 종류>`, `restore_account`)으로 한다. 모든 서비스에 통한다. 사유의 종류(spam, abuse, fraud, illegal, other)와 사유는 정지의 기록에 남는다(#634). 관리 서버가 생기면 그쪽으로 옮긴다 | - |
| IP 막기 | **지금은 인증 서버의 명령**(`block_network <주소 또는 대역> --reason --days`, `unblock_network`)으로 한다. 불법 행위로 정지한 사람이 새 계정으로 돌아오는 것을 막는다. 그 주소의 가입, 로그인, 토큰 갱신을 거절하고 막혔다고 알린다. 기본 30일, 길어야 365일(#638). 관리 서버가 생기면 그쪽으로 옮긴다 | - |

- 제재는 감사 기록(`operator_actions`)과 한 트랜잭션에서 커밋한다. 제재가 되지 않았으면 기록도 없다. 저절로 오른 공개 금지는 운영자가 한 일이 아니라 따로 적지 않는다(그 원인인 시나리오 제재가 적힌다).
- 같은 사람의 공개 금지를 정하는 일은 사람마다 잠그고 한다. 두 시나리오가 동시에 제재되어도 수를 빠뜨리지 않는다.
- 시나리오 제재, 공개 금지와 풀기는 당사자의 알림함에 간다(#385, [게임 서버의 알림 보내기](../../trpg-server/README.md#알림-보내기)). 사유와 운영자는 싣지 않는다. 사유는 신고 번호나 메모라 신고한 사람이 드러날 수 있다. 테이블 끝내기는 알리지 않는다(앉은 사람이 이벤트로 본다).

## 감사 기록

운영자가 **남의 것**을 볼 때마다 한 줄을 남긴다. 자기 것을 볼 때와 성인 등급의 예외로 일반 API 를 쓸 때는 남기지 않는다(그것은 일반 사용자의 일이다).

| 칸 | 뜻 |
| --- | --- |
| 운영자 | 토큰의 `sub` |
| 시각 | 서버의 시계 |
| 무엇 | 종류(시나리오, 판, 테이블, 귓속말 등)와 ID |
| 사유 | **필수.** 신고 번호나 짧은 글(200자). 없으면 운영자 API 가 422 다 |
| 요청 식별자 | `request_id`([관측 규격](../observability.md)) |

제재(`operator_actions`)도 같은 칸으로 남긴다(무엇 대신 제재의 종류와 대상). 로그의 `operation` 은 `operator.act` 다.

- 기록은 그 서비스의 DB 에 덧붙이기만 하는 표로 둔다(DB 트리거로 고치기와 지우기를 막는다. 결제의 원장과 같다).
- 본 내용은 기록에 싣지 않는다. 무엇을 보았는지만 남긴다.
- 같은 내용을 로그에도 남긴다(`operation`: `operator.read`). 로그는 수집되기 전에 사라질 수 있어서 DB 가 원본이다.
- 관리 서버가 생기면 관리 서버가 서비스마다의 기록을 모아 보여 준다([관리 서버의 경계](../observability.md#관리-서버의-경계)의 "관리자가 한 조작의 감사 기록"). 그때 옮길지 모아 볼지 정한다.

## 사용자에게 알릴 것

실제로 서비스를 열기 전에 개인정보 처리방침과 이용약관에 적는다.

- 신고 처리와 운영을 위해 운영자가 시나리오, 테이블의 기록, 대화, **귓속말**을 볼 수 있다.
- 운영자가 볼 때마다 기록이 남는다.

문구와 법적 요건은 서비스를 열 때 따로 확인한다. 이 문서는 법률 검토가 아니다.

## 알려진 대가

- **운영자의 토큰이 새면 15분 동안 남의 것을 다 본다.** 일반 사용자의 토큰보다 위험이 크다. 감사 기록이 남는 것이 첫 방어선이다. 운영자 계정의 2단계 인증은 [정하지 않은 것](#정하지-않은-것)이다.
- **게임 서버의 열린 스트림은 세션을 끊어도 바로 닫히지 않는다.** 새 요청은 30초쯤 안에 막히지만, 이미 열린 테이블 스트림은 토큰이 만료될 때(15분) 닫힌다.
- **일반 API 에 예외가 한 곳 섞인다**(성인 등급). [서비스 구조 명세](services.md)의 "관리자 권한은 사용자 API 에 섞지 않는다"의 예외다. 판정이 함수 하나라 넓어지지 않게 지킨다.

## 정하지 않은 것

- 제작자에게 제재의 까닭을 알릴지와 그 길(지금은 사유를 알림에 싣지 않는다. 운영자가 따로 쓰는 안내문을 둘지). 시나리오 제재를 풀 길(지금은 새 판을 내는 것뿐이다).
- 운영자 역할을 더 나눌지(신고 처리자와 전체 관리자).
- 운영자 계정의 2단계 인증.
- AI 에 보낸 입력의 원문을 남길지, AI 호출 기록(모델의 답, 30일)을 운영자 API 로 열지. 열면 운영에 도움이 되지만 저장하고 내보내는 개인 정보가 는다.
- 감사 기록의 보관 기간.
- 운영자의 화면(관리 서버의 화면인지, 같은 프런트의 운영자 화면인지).
