# 공용 코드 규칙

여러 서비스가 같은 코드나 형식을 쓸 때 지킬 것을 적는다. 서비스의 구조는 [서비스 구조 명세](services.md)에 있다.

- 기준: `main` `4b383c2` (2026-10-18)
- `shared/` 는 아직 없다. 이 문서는 만들기 전에 정해 두는 규칙이다.

## 원칙

1. **형식과 함수는 공유하고, 데이터는 공유하지 않는다.** 서비스마다 자기 스키마에 자기 표를 가진다. 한 서비스의 행을 다른 서비스가 읽거나 가리키지 않는다.
2. **빌드 시점에만 묶는다.** 공용 코드는 각 서비스의 이미지에 들어간다. 실행 중에 다른 서비스를 부르거나, 볼륨을 함께 쓰지 않는다. 한 서비스가 죽어도 다른 서비스의 공용 코드는 그대로 돈다.
3. **서비스 사이의 DB 경계는 그대로다.** 공용 코드가 있어도 다른 서비스의 테이블을 읽거나 외래키를 거는 일은 없다.
4. **두 번째 사용자가 생길 때 뽑는다.** 한 서비스에서 쓰이는 것을 처음부터 공용으로 만들지 않는다([언제 뽑는가](#언제-뽑는가)).
5. **서비스 고유의 개념은 올리지 않는다.** 한 서비스에만 뜻이 있는 것은 공용 코드에 넣지 않는다.

## 공유하는 것과 공유하지 않는 것

| | 공유 | 공유하지 않음 |
| --- | --- | --- |
| 코드 | 외부 모델 호출, 스트리밍, 토큰 어림과 사용량 기록의 모양, 모델 정보, 공통 오류 | 서비스별 프롬프트, 대화나 서술 로직 |
| 형식(템플릿) | 로어북 항목, 세계관, 페르소나, 지도, 물건, 인물의 필드와 검증 규칙 | 각 서비스가 그 위에 얹는 필드 |
| 검색 | 키워드와 벡터 검색의 순수 함수, 거리 기준 | 어떤 후보를 읽어 오는지(서비스의 DB) |
| 데이터 | 없음 | 모든 행. 복사도 동기화도 하지 않는다 |
| 규칙 | 아이템을 더하고 상한을 넘으면 거르는 계산 같은 순수 함수 | 판정, 쓰러짐, 부상, 호감도 규칙처럼 서비스에만 뜻이 있는 것 |

- 서비스 사이에 로어북이나 캐릭터를 가져오고 복사하고 동기화하는 기능은 만들지 않는다. 공유의 목적은 중복을 줄이는 것이다.
- ORM 모델(표)은 서비스마다 둔다. 공유하는 것은 필드의 형식과 순수 함수다.

## 후보

### AI 호출 (`shared/ai-core`)

게임 서버의 `app/ai` 에서 뽑는다. 창구(OpenAI 호환, Claude, Gemini), 스트리밍, 토큰 예산, 원가 기록, 재시도 예산이 이미 있다.
다만 `app/ai` 는 다른 폴더에 기대는 곳이 있어서, 그대로 떼어 낼 수는 없다(기준 `4b383c2`).

| `app/ai` 가 기대는 곳 | 무엇을 가져오나 | 뽑을 때 |
| --- | --- | --- |
| `app/catalog` (`lookup`, `models`, `rules`, `offers`) | 모델 목록. 모델의 창구, API 이름, 켜짐 여부, 사고 방식, 원가 단가 | **가장 큰 문제.** 모델 목록은 게임 서버의 표(`ai_models` 등)다. [열린 질문](#열린-질문) |
| `app/core` (`loops`, `jobs`, `database`) | 뒤에서 도는 작업의 틀, DB 기반 | 공용 코드에 필요한 최소한만 인터페이스로 받거나 서비스 쪽에 둔다 |
| `app/observability` | 작업 식별자(`job_scope`, `new_job_id`) | 관측 규격의 식별자. 서버마다 같은 구현이 필요하다 |
| `app/assets/models` | 표를 만들 때 쓰는 도우미(`one_of`) | 표는 서비스마다 두므로 공용으로 가져가지 않는다 |
| `app/billing` (`catalog/offers.py` 가 가져온다) | 가격 목록, 서술 등급 | 판매가는 결제 서버가 정한다. 서술 등급은 게임 서버의 개념이라 공용으로 올리지 않는다 |

| 공용으로 올릴 후보 | 서비스에 남는 것 |
| --- | --- |
| 모델 호출 창구와 스트리밍, 토큰 예산의 어림, 사고 글 처리, 재시도 예산, 공통 오류, 사용량과 원가를 담는 값의 모양 | 호출 기록의 표, 서비스별 프롬프트, 서술 등급과 판매가, 모델 목록을 읽는 방식(아래 질문) |

- 추론(thinking) 글은 저장하지 않고, 오류에 본문을 싣지 않는다. 이 규칙은 공용 코드로 올라가도 그대로다.
- API 키는 서버의 설정에만 둔다. 로그, 오류, 기록에 싣지 않는다.

### 템플릿

TRPG, chat, story 가 비슷한 모양으로 쓰는 것들이다. 같은 필드를 쓰고, 뜻은 서비스마다 다르다.

| 템플릿 | 공유하는 모양 | 서비스마다 다른 것 |
| --- | --- | --- |
| 로어북 항목 | 이름, 키워드(최대 5개), 본문. 키워드와 벡터 검색 | 검색 결과를 프롬프트에 넣는 방법 |
| 세계관 | 이름, 소개, 설정 글(공개용과 비공개용) | 시나리오에 붙이는지, 캐릭터 묶음의 상위인지 |
| 페르소나 | 이름과 설명, 말투 | TRPG 는 캐릭터 시트와 이어지고, chat 은 대화 상대에게 나를 알리는 설정 |
| 지도 | 장소, 길, 길의 조건, 장소에 있는 인물, 시간 | TRPG 는 이동에 판정과 조우가 붙고, story 는 이동이 만나는 인물과 장면을 바꾼다 |
| 물건과 소지품 | 물건의 정의, 소지품 표, 얻고 잃는 규칙과 개수 상한 | TRPG 는 장비와 소모품의 효과, story 는 선물과 호감도 |
| 인물(NPC) | 프로필, 말투, 위치, 일과 | TRPG 는 전투 성질, chat 과 story 는 호감도 단계와 해금 |

- 지도, 물건, 인물은 TRPG 에서 쓰는 중인 것이 먼저 완성되어야 한다. 그 설계를 할 때 story 의 쓰임(이동과 선물)도 함께 놓고 본다.
- 하나의 공통 층으로 묶어 보면, 이들은 **세계의 상태**(장소, 물건, 인물, 관계 변수)와 **서버가 검증해서 바꾸는 규칙**이다. 이 층은 TRPG 엔진 전체가 아니다.

## 언제 뽑는가

- AI 호출 코드는 이미 세 가지 모델의 창구까지 있고, chat 이라는 두 번째 사용자가 확실하므로 chat 을 시작하기 전에 뽑는다. 다만 `app/ai` 가 모델 목록과 작업 기반에 기대고 있어서, 뽑기 전에 그 경계부터 정해야 한다(위의 표).
- 템플릿은 게임 서버에서 먼저 만들고, chat 이나 story 가 실제로 쓰려고 할 때 뽑는다. 처음부터 공용 패키지로 만들지 않는다.
  두 서비스에 맞는 모양인지 쓰임을 보기 전에 공용으로 만들면 둘 다에 맞지 않는 모양이 되기 쉽다.
- 뽑을 때는 한 번에 하나씩 뽑는다. 뽑는 동안 원래 자리의 코드를 다른 PR 이 고치지 않게 알린다.

## 버전과 CI

- 템플릿마다 형식 번호를 둔다. 게임 서버의 판 형식이 이미 번호를 올리며 옛 형식을 읽을 때 지금 모양으로 바꿔 읽는다. 같은 방식을 쓴다.
- 공용 코드가 바뀐 PR 은, 그것을 쓰는 모든 서비스의 CI 를 돌린다.
- 형식을 바꾸는 변경은 옛 형식을 읽을 수 있게 하고, 서비스마다 한 번에 따라가지 않아도 되게 한다.
- 공용 코드에는 그것을 쓰는 서비스 중 어느 한 곳에만 있는 개념(전투 판정, 호감도 등)을 넣지 않는다.

## 주도권

- 처음에는 게임 서버를 만드는 쪽이 공용 코드의 변경을 주도하고, 나중에 쓰는 서비스가 따라간다. 공용 코드 때문에 한 서비스의 진행이 다른 서비스에 막히는 일을 줄이려는 것이다.
- 공용으로 올라간 뒤에 형식을 바꿀 때는, 쓰는 서비스를 모두 확인하고 한 PR 에서 맞춘다.
- 게임 서버의 `app/ai`, `app/lore`, `app/memory`, `app/assets` 는 공용 후보이므로 고칠 때는 이 문서를 읽고 쓰임을 확인한다.

## 열린 질문

- **모델 목록(`app/catalog`)을 어떻게 나눌지.** 모델 목록(`ai_models`, `ai_model_costs`, `ai_model_snapshots`)은 게임 서버의 스키마에 있고, 모델의 이름표(slug)는 결제 서버의 가격 코드가 그대로 쓴다.
  chat 도 같은 모델을 부르므로 목록이 필요하다. 선택지는 셋이다.
  (1) 서비스마다 같은 모양의 표를 두고 같은 관리 명령으로 채운다. 데이터를 공유하지 않는 원칙에는 맞지만, 원가 단가와 날짜판을 서비스마다 따로 고쳐야 한다.
  (2) 목록을 한 서비스가 맡고 API 로 준다. 단가를 한곳에서 고치지만 서비스가 하나 늘고, 그 서비스가 죽으면 호출이 막힌다.
  (3) 목록을 파일(버전을 붙인 설정)로 두고 공용 코드에 넣는다. 가장 단순하지만 모델을 켜고 끄는 일이 배포가 된다.
- 서버마다 uv 프로젝트를 따로 두는 구조에서 `shared/` 를 어떻게 가져올지(경로 의존성, 복사). 서버 폴더마다 Dockerfile 이 있고 빌드가 서버 폴더 안에서 이루어지므로, 빌드 범위에 `shared/` 를 넣는 방법도 정해야 한다.
- 공용 코드의 변경이 어느 서비스의 CI 를 부르는지를 `changed-servers.sh` 가 어떻게 판단하게 할지.
- 템플릿을 Python 패키지로 둘지, 형식만 스키마(JSON Schema 등)로 두고 서비스마다 구현할지. 서비스의 기술이 Python 이 아닌 경우(게시판, 결제)에는 코드를 공유할 수 없다.
- 호출 기록의 표를 서비스마다 같은 모양으로 둘지.
