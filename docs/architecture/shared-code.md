## 원칙

1. **형식과 함수는 공유하고, 상태 데이터는 공유하지 않는다.** 서비스마다 자기 스키마에 자기 표를 가진다. 한 서비스의 행을 다른 서비스가 읽거나 가리키지 않는다.
   **예외는 자산이다.** 제작자가 만든 자산(세계관, 로어북, 캐릭터)은 asset-server 가 원본을 갖고, 쓰는 서비스는 방이나 대화를 시작할 때 게시된 판을 자기 스키마로 복사해 고정한다. 판은 바뀌지 않으므로 복사해도 안전하다. 대화와 게임의 상태, 크레딧은 이 예외에 들지 않는다.
2. **코드는 빌드 시점에만 묶는다.** 공용 코드는 각 서비스의 이미지에 들어간다. 실행 중에 다른 서비스를 부르거나, 볼륨을 함께 쓰지 않는다. 한 서비스가 죽어도 다른 서비스의 공용 코드는 그대로 돈다.
   자산을 가져오는 일은 코드의 공유가 아니라 데이터의 복사이고, 방이나 대화를 시작할 때 한 번 일어난다. 턴마다 부르지 않으므로 asset-server 가 죽어도 진행 중인 것은 돈다.
3. **서비스 사이의 DB 경계는 그대로다.** 공용 코드가 있어도 다른 서비스의 테이블을 읽거나 외래키를 거는 일은 없다.
4. **두 번째 사용자가 생길 때 뽑는다.** 한 서비스에서 쓰이는 것을 처음부터 공용으로 만들지 않는다([언제 뽑는가](#언제-뽑는가)).
5. **서비스 고유의 개념은 올리지 않는다.** 한 서비스에만 뜻이 있는 것은 공용 코드에 넣지 않는다.
   예: 서술 등급과 판매가(TRPG 와 결제), 이벤트와 엔딩(story), 판정과 라운드(TRPG). 공용 코드는 그런 개념을 모르고, 서버가 [정해 둔 자리](#재정의하는-법)에 끼운다.

## 공유하는 것과 공유하지 않는 것

| | 공유 | 공유하지 않음 |
| --- | --- | --- |
| 코드 | 서버의 공통부(토큰 검증, 관측, 서버끼리의 서명, DB 연결, 뒤에서 도는 일의 틀), 외부 모델 호출, 스트리밍, 토큰 어림과 사용량 기록의 모양, 모델 정보, 공통 오류. 나중에 대화의 핵심(대화 트리, 요약, 기억) | 서비스별 프롬프트, 서술 로직, 서버마다의 지표와 구간 이름, 설정 값 |
| 형식(템플릿) | 로어북 항목, 세계관, 페르소나, 지도, 물건, 인물의 필드와 검증 규칙 | 각 서비스가 그 위에 얹는 필드 |
| 검색 | 키워드와 벡터 검색의 순수 함수, 거리 기준 | 어떤 후보를 읽어 오는지(서비스의 DB) |
| 데이터 | 없음. 다만 자산의 게시된 판은 시작할 때 복사해 간다 | 대화, 방, 크레딧 같은 상태. 동기화는 하지 않는다 |
| 규칙 | 아이템을 더하고 상한을 넘으면 거르는 계산, 지도의 아는 곳과 이동 가능 여부 계산 같은 순수 함수 | 판정, 쓰러짐, 부상, 호감도 규칙, 숨은 길을 찾는 판정처럼 서비스에만 뜻이 있는 것 |

- 서비스 사이를 오가는 것은 asset-server 의 게시된 판뿐이다. 서비스끼리 직접 주고받지 않는다. 원본이 바뀌어도 복사본을 자동으로 맞추지 않고, 새 판이 있다고 알리기만 한다.
- 첫 단계는 제작자 본인이 자기 자산을 쓰는 것만 허용한다. 남의 공개 자산은 허락과 라이선스를 따로 정한 뒤에 연다.
- ORM 모델(표)은 서비스마다 둔다. 공유하는 것은 필드의 형식과 순수 함수다.

| 패키지 | 담는 것 | 쓰는 서버 | 만드는 때 |
| --- | --- | --- | --- |
| `shared/server-core` | 토큰 검증, 관측, 서버끼리의 서명, DB 연결, 뒤에서 도는 일의 틀, 알림 발송함 | FastAPI 서버 모두(trpg, notification, asset, chat, story, 나중에 관리) | 지금. 쓰는 서버가 이미 넷이다 |
| `shared/ai-core` | 모델 호출 | trpg, chat, story | chat-server 의 "한 번의 말"을 만들 때(#499) |
| `shared/conversation-core` | 대화 트리, 다시 생성과 분기, 요약, 기억, 로어북 검색을 붙이는 법. 지금은 SSE, 흘려보내기, 최근 대화의 창, 로어북 고르기, 답의 블록 | chat, story | 만들었다(#591). story 서버가 세션을 만들기 바로 앞 |

### 서버의 공통부 (`shared/server-core`)

FastAPI 서버들이 함께 쓰는 공통부다(#588). 알림 서버와 asset 서버가 쓰고, chat 과 story 는 처음부터 쓰고, trpg 는 #589 에서 옮겼다.
쓰는 법과 열어 둔 자리의 예는 [shared/server-core/README.md](../../shared/server-core/README.md)에 있다.

| `server_core` 의 자리 | 담는 것 | 서버마다 다른 것과 넘기는 법 |
| --- | --- | --- |
| `settings` | 설정의 공통 칸(DB, 인증 서버, 로그, 수집기)과 그 검사(`CoreSettings`) | 서버의 설정이 물려받아 이름(`service_name`)과 기본값(`db_schema`, `jwt_audience`)을 주고 제 칸을 더한다 |
| `auth` | 공개 키(`jwks`), 끊긴 세션(`revocations`), 토큰 검증(`tokens`), FastAPI 의존성(`CurrentUser`, `OptionalUser`) | 토큰의 대상은 설정. 앱은 `app.state` 에 설정, 공개 키, 끊긴 세션을 붙인다 |
| `observability` | 로그의 모양과 가리기, 식별자, 요청의 미들웨어 셋, 추적, 메트릭(요청, DB, 작업, SSE), 할 일 없던 바퀴 버리기 | 서비스 이름은 설정. 스트림인 주소는 `StreamRoutes` 로 미들웨어에 넘긴다. 서버만의 계측기는 `InstrumentSet` 으로 더한다. span 을 보내기 전에 끼우는 것은 `configure_tracing(wrap=)` |
| `service_auth` | 서버끼리의 서명 만들기와 확인 | 비밀의 이름과 받는 쪽의 목록은 서버의 설정 |
| `database` | 엔진, 세션의 틀, 요청마다의 세션, 이름 짓는 규칙 | search_path 에 더할 스키마, 풀의 크기는 `create_engine` 에 넘긴다. 표의 부모(`Base`)는 서버마다 둔다 |
| `loops` | 뒤에서 일정하게 도는 일의 틀 | 바퀴의 일은 서버의 것 |
| `notifications` | 알림 서버로 보내는 발송함의 칸, 쿼리, 서명해 넣기, 다시 보내기, 보내는 작업과 그 설정(`NotificationSettings`) | 표(`Base` 와 마이그레이션), 서버 이름(주소와 비밀), 무엇을 누구에게 알릴지는 서버의 것. 쿼리는 쓰는 서버(asset)의 테스트가 실제 DB 로 본다 |
| `testing` | 서버들의 테스트가 함께 쓰는 도구(가짜 인증 서버, span 과 메트릭을 모으는 것, 가짜 수집기, 로그 읽기) | 운영 코드는 가져오지 않는다 |

- 각 서버의 `app/core/config.py` 는 서버에 남는다. 공용 코드는 설정 파일을 읽지 않고, 서버가 만든 설정을 받는다([재정의하는 법](#재정의하는-법)).
- 서버만의 일(TRPG 의 `jobs.py`, `dice.py`, 라운드와 AI 호출의 지표 등)은 서버에 남는다. AI 호출의 지표(`ai_*`)는 `ai-core` 로 간다(#499).
- 옮길 때 trpg 의 모양을 기본으로 올렸다(trpg 가 바란 자리, 2026-10-21). 알림 서버와 asset 서버에 생긴 차이는 둘이다.
  - 작업의 span(`job_span`)은 걸린 span 이 있으면 그 아래에 놓인다. 두 서버의 작업은 서버가 뜰 때 시작해 걸린 span 이 없으므로 지금처럼 바퀴마다 새 추적이다.
  - 공용 코드가 남긴 로그 줄의 `logger` 가 `app.observability.*` 에서 `server_core.observability.*` 로 바뀌었다. 칸의 모양과 `service` 는 그대로다.
- 공용 코드의 테스트는 DB 없이 돈다. DB 에 닿는 것(쿼리의 span, 연결을 기다린 시간)은 쓰는 서버의 테스트가 실제 DB 로 본다.

### AI 호출 (`shared/ai-core`)

게임 서버의 `app/ai` 를 폴더째 옮겼다(2026-10-22, #499 의 1단계). 패키지 이름은 `ai_core` 다. 창구(OpenAI 호환, Claude, Gemini, Z.ai, DeepInfra), 스트리밍, 토큰 예산, 원가, 재시도 예산, 임베더, 호출 기록의 모양이 있다. 쓰는 법은 [shared/ai-core/README.md](../../shared/ai-core/README.md) 에 있다.
옮기기 전에 `app/ai` 가 다른 폴더에 기대던 곳(기준 `0930cf9`. 21개 파일 가운데 7개)을 trpg-server 안에서 정리했다(아래 표).
`shared/ai-core/tests/test_boundary.py` 가 `ai_core` 에서 서버의 모듈(`app.*`), 다른 공용 패키지(`server_core` 등), 관측의 코드(`opentelemetry`)를 가져오면 실패한다. 예외는 없다.
2단계(모델 목록을 버전 붙인 파일 원본으로 바꾸고 서비스마다 들여오기)는 2026-10-22 에 했다. 원본은 `ai_core/model_catalog.toml`, 읽고 모양을 보는 것은 `ai_core/catalog_file.py` 다. 창구에 맞는 칸과 방식, 분류(`Grade`)의 규칙도 `catalog_contract` 로 올렸다. 게임 서버는 `app/catalog/sync.py` 로 들여온다. chat 도 같은 이름의 파일로 들여온다(게임 서버의 것을 줄여 옮겼다. 회사의 대체 모델이 없고 `allows_adult` 가 있다). 들여오는 코드가 두 벌인 것은 story 가 생겨 세 벌이 될 때 공용으로 올릴지 정한다(server-core 나 ai-core 의 DB 쪽). story 는 모델을 부르기 시작할 때 같은 파일을 들여온다.

| `app/ai` 가 기대던 곳(옮기기 전) | 무엇을 가져왔나 | 정리한 것 |
| --- | --- | --- |
| `app/catalog` (`lookup`, `models`, `rules`) | 모델 목록의 계약: 열거형(`Provider`, `ReasoningStyle`, `TokenLimitField`), 값 모양(`CatalogModel`, `UnitCost`), 읽는 쪽의 약속(`ModelLookup`), 순수 규칙(`always_thinks`, `is_offered`, `is_retired`). `routing`, `anthropic`, `gemini`, `thinking`, `costs` 가 가져온다. DB 는 가져오지 않는다 | 계약을 `app/ai/catalog_contract.py` 로 옮겼다. `app/catalog` 가 거기서 가져온다(#496, #506). DB 를 읽는 `DbModelLookup` 과 표(`ai_models` 등), `offers`, 원가 반올림(`round_cost_usd`)은 `app/catalog` 에 남았다 |
| `app/core` (`loops`, `jobs`, `database`) | 뒤에서 도는 작업의 틀, DB 기반. `retention`(글 보관 기한 지우기)과 `models`(호출 기록의 표)가 가져온다 | `models`, `repository`, `call_log`(`DbCallLog`), `retention` 을 `app/ai_log` 로 옮겼다(#497, #508). 기록을 받는 곳의 모양(`CallLog`)과 기록 한 줄(`CallRecord`)은 `app/ai/calls.py` 에 남았다 |
| `app/observability` | 작업 식별자(`job_scope`, `new_job_id`). `retention` 이 가져온다 | `retention` 과 함께 `app/ai_log` 로 갔다(#508) |
| `app/assets/models` | 표를 만들 때 쓰는 도우미(`one_of`). 호출 기록의 표가 가져온다 | 표와 함께 `app/ai_log` 로 갔다(#508) |
| `app/billing` (`catalog/offers.py` 가 가져온다) | 가격 목록, 가격표의 등급 | 판매가와 등급은 결제 서버가 정한다. 그것으로 고를 수 있는 모델을 맞춰 붙이는 것(`offers`)은 서비스에 남는다 |

| 공용으로 올릴 후보 | 서비스에 남는 것 |
| --- | --- |
| 모델 호출 창구와 스트리밍, 토큰 예산의 어림, 사고 글 처리, 재시도 예산, 공통 오류, 사용량과 원가를 담는 값의 모양 | 호출 기록의 표, 서비스별 프롬프트, 판매가와 고를 수 있는 모델(시나리오의 추천 모델, 회사의 대체 모델), 모델 목록을 읽는 방식(아래 질문) |

- 추론(thinking) 글은 저장하지 않고, 오류에 본문을 싣지 않는다. 이 규칙은 공용 코드로 올라가도 그대로다.
- API 키는 서버의 설정에만 둔다. 로그, 오류, 기록에 싣지 않는다.

### 템플릿

TRPG, chat, story 가 비슷한 모양으로 쓰는 것들이다. 같은 필드를 쓰고, 뜻은 서비스마다 다르다.
템플릿의 원본 모양은 asset-server 가 갖는 자산의 모양이다. 서비스마다 다른 것은 받는 쪽이 복사본에 자기 표로 얹고, 가져올 때 비어 있는 필드(예: chat 의 첫 인사)는 받는 쪽에서 채운다.

| 템플릿 | 공유하는 모양 | 서비스마다 다른 것 |
| --- | --- | --- |
| 로어북 항목 | 이름, 키워드(최대 5개), 본문. 키워드와 벡터 검색 | 검색 결과를 프롬프트에 넣는 방법 |
| 세계관 | 이름, 소개, 설정 글(공개용과 비공개용) | 시나리오에 붙이는지, 캐릭터 묶음의 상위인지 |
| 페르소나 | 이름, 설명, 그림, 나이, 성별, 호칭, 말투 예시, 성격. 원본은 asset-server 의 계정 페르소나(2026-10-21) | TRPG 는 계정 페르소나를 가리키는 시트(능력치)를 따로 두고, chat 은 대화 상대에게 나를 알리는 설정으로 쓴다 |
| 지도 | 장소, 길, 길의 조건, 장소에 있는 인물, 시간 | TRPG 는 이동에 판정과 조우가 붙고, story 는 이동이 만나는 인물과 장면을 바꾼다 |
| 물건과 소지품 | 물건의 정의, 소지품 표, 얻고 잃는 규칙과 개수 상한 | TRPG 는 장비와 소모품의 효과, story 는 선물과 호감도 |
| 인물(NPC) | 프로필, 말투, 위치, 일과 | TRPG 는 전투 성질, chat 과 story 는 호감도 단계와 해금 |

- 지도, 물건, 인물은 TRPG 에서 쓰는 중인 것이 먼저 완성되어야 한다. 그 설계를 할 때 story 의 쓰임(이동과 선물)도 함께 놓고 본다.
- 하나의 공통 층으로 묶어 보면, 이들은 **세계의 상태**(장소, 물건, 인물, 관계 변수)와 **서버가 검증해서 바꾸는 규칙**이다. 이 층은 TRPG 엔진 전체가 아니다.

### 대화의 핵심 (`shared/conversation-core`)

chat 과 story 는 사용자의 말이 한 턴을 이끈다는 점이 같다. 대화 트리(다시 생성, 분기), 요약, 기억, 로어북 검색을 프롬프트에 붙이는 순서, 스트리밍한 답을 저장하는 흐름이 같다. 다른 것은 참가자 수, 로어북이 붙는 곳(캐릭터 대 세계관), 이벤트와 엔딩이다.

- chat-server 를 먼저 만들면서 이 부분을 한 폴더(`app/conversation/`)에 모아 두고, `app/conversation` 이 chat 만의 폴더를 가져오지 않게 경계를 지켰다(AI 호출의 #498 과 같은 테스트).
- 그 폴더를 파일째 `shared/conversation-core` 로 옮겼다(2026-10-24, #591). 쓰는 법과 있는 것은 [shared/conversation-core/README.md](../../shared/conversation-core/README.md)에 있다.
  - 옮긴 때: story 서버가 세션과 한 번의 말을 만들기 바로 앞이다. 원칙 4(두 번째 사용자가 생길 때)를 따르되, story 의 첫 PR 이 chat 의 코드를 옮기는 일과 story 의 기능을 함께 싣지 않게 먼저 옮겼다. 옮기는 PR 은 import 만 바꾸고 동작을 바꾸지 않는다
  - 경계: 서버의 코드(`app.*`), 다른 공용 패키지(`server_core`, `ai_core`), 관측을 가져오지 않는다(`tests/test_boundary.py`). 지금은 표준 라이브러리만 쓴다
  - 옮긴 것 가운데 상태 바꾸기의 제안(`changes`)과 표정(`expressions`)은 chat 이 먼저 쓴다. story 는 호감도의 제안을 chat 과 함께 나중에 쓰고(story 설계의 "호감도"), 표정은 인물마다의 그림에 쓴다. 블록의 모양만 여기 있고 무엇을 허락하는지는 서버가 정한다
  - 대화 트리와 요약은 아직 chat 의 표(`app/conversations`, `app/memory`)에 붙어 있어 옮기지 않았다. story 가 같은 흐름을 쓸 때 표에 기대지 않는 부분을 뽑는다
- 표(ORM 모델)는 서버마다 둔다. chat 은 `chat` 스키마에, story 는 `story` 스키마에 같은 모양의 대화 표를 갖는다(원칙 1).

## 재정의하는 법

서버가 공용 코드를 그대로 쓰거나 일부를 바꿔 쓰는 방법은 셋뿐이다(2026-10-21). 설정의 클래스(`CoreSettings`)만은 서버의 설정이 물려받는다. 칸을 더하고 기본값을 주는 것이라 "설정 값"의 한 모양이다.

| 방법 | 언제 | 예 |
| --- | --- | --- |
| **설정 값을 넘긴다** | 값만 다를 때 | 토큰의 대상(`audience="ai-trpg-story"`), 서비스 이름, DB 풀 크기. 서버의 `config.py` 가 읽어 공용 코드의 함수나 클래스에 넘긴다 |
| **주입한다** | 같은 모양의 다른 구현이 필요할 때 | 공용 코드가 `Protocol` 로 모양을 정하고, 서버가 구현을 넘긴다. 테스트에서 가짜를 넘기는 것과 같은 길이다(예: 끊긴 세션을 묻는 곳, 시계) |
| **정해 둔 자리에 더한다** | 서버만의 것을 덧붙일 때 | 공용 코드가 받는 자리를 열어 둔다: 지표와 구간을 더하는 함수, 로그에 칸을 더하는 함수, 토큰에서 칸을 더 꺼내는 함수. 서버는 그 자리에 자기 것을 넘긴다 |

하지 않는 것:

- **공용 코드의 클래스를 아무 곳이나 상속해 덮어쓰지 않는다.** 공용 코드의 안쪽이 바뀌면 덮어쓴 서버가 말없이 깨진다. 바꿀 자리가 필요하면 공용 코드에 그 자리를 연다.
- **공용 코드를 복사해 고쳐 쓰지 않는다.** 같은 코드가 두 벌이 되는 것을 막으려고 뽑는 것이다. 서버의 사정이 정말 다르면 공용으로 올리지 않고 서버에 둔다(원칙 5).
- 공용 코드가 서버의 모듈(`app.*`)을 가져오지 않는다. 공용 코드의 테스트가 이를 확인한다.

이름이 `_` 로 시작하는 것은 서버가 가져오지 않는다. 공용 코드의 안쪽이라 말없이 바뀔 수 있다.

## 소개 글의 HTML

제작자는 소개 글(story 의 세계관 소개, chat 의 캐릭터 소개, TRPG 의 시나리오 소개)을 HTML 로 자유롭게 꾸민다. 그림도 넣는다. 다른 AI 캐릭터 챗 서비스들이 그렇게 한다(2026-10-20 결정). CSS 는 인라인 스타일(`style` 속성)만 허락한다.

스크립트가 없어도 HTML 과 인라인 CSS 로 할 수 있는 나쁜 일이 있다. 그래서 거른다.

| 막는 것 | 까닭 |
| --- | --- |
| `script`, 이벤트 속성(`onclick` 등), `iframe`, `object`, `embed`, `form`, `input`, `button`, `meta`, `link`, `style` 태그 | 스크립트, 다른 페이지 끼워 넣기, 가짜 입력 창 |
| CSS 의 `position`, `z-index`, `transform` | 소개 칸 밖으로 나와 화면 전체를 덮는 가짜 로그인 창(UI 덮어쓰기) |
| CSS 에서 `url()` 을 받는 속성(`background`, `background-image`, `border-image`, `list-style-image`, `cursor` 등) | 바깥 주소를 불러 보는 사람의 IP 를 흘린다 |
| 바깥 주소의 그림 | 위와 같다. 그림은 우리 그림 저장소에 올린 것(그림의 id)만 쓴다 |
| `https` 가 아닌 링크(`javascript:`, `data:` 등) | 스크립트와 피싱 |

허락하는 것:

- 태그: 문단과 제목, 목록, 표, 강조, 줄바꿈과 가로줄, `div`, `span`, `img`(우리 저장소의 그림만), `a`(`https` 만, `rel="noopener noreferrer"` 를 붙이고 바깥 링크라고 표시한다), `details`/`summary`.
- CSS 속성: 글자(`color`, `font-size`, `font-weight`, `font-style`, `text-align`, `text-decoration`, `line-height`, `letter-spacing`), 상자(`margin`, `padding`, `border`, `border-radius`, `background-color`, `width`, `max-width`, `height`, `max-height`), 배치(`display`, `flex` 와 `grid` 의 속성, `gap`). 값에 `url(` 이 있으면 그 속성을 뺀다.

**두 겹으로 거른다**(2026-10-20 결정).

1. **게시할 때 서버가 거른다.** asset-server 가 게시할 때 위의 허용 목록으로 걸러 거른 것만 저장한다. 거른 것(빠진 태그와 속성)은 게시 결과의 `problems[]` 로 제작자에게 보인다. 파이썬의 `nh3` 를 쓴다. 태그, 태그마다의 속성, CSS 속성 하나하나를 허용 목록으로 거른다(`filter_style_properties`). 그림의 주소는 속성 거르기 함수(`attribute_filter`)로 우리 저장소의 것만 남긴다. 거르는 함수와 허용 목록은 한곳에 두고 함께 쓴다. 처음에는 쓰는 곳이 asset-server 하나라서 그 안(`app/content/html.py`)에 `app.*` 를 가져오지 않는 모듈로 둔다(#567). 두 번째로 쓰는 곳(TRPG 의 시나리오 소개를 asset-server 로 옮기는 PR)에서 `shared/` 로 옮긴다(원칙 4, 2026-10-21).
2. **화면이 그릴 때 한 번 더 거른다.** 같은 허용 목록으로 DOMPurify 를 거친다. 서버의 거르기에 빈틈이 있어도 여기서 막는다.

- 소개는 넘치면 잘리는 상자(`overflow: hidden`, `contain: content`) 안에만 그린다. `position` 을 막았으므로 상자 밖에 닿지 못한다.
- 화면의 CSP 는 그림을 우리 그림 저장소에서만 받게 한다(`img-src`). 세 번째 겹이다. 화면을 내주는 곳의 CSP 는 [배포 설계의 열린 질문](deployment.md#열린-질문)에 있다.
- 글의 크기에 상한을 둔다(기본 50KB, 그림 제외).
- **고르지 않은 것:** 스크립트를 막은 별도 출처의 iframe 에 그리기. 가장 안전하지만 높이, 테마, 글꼴을 넘기는 일이 번거롭고 모바일에서 스크롤이 겹친다. 공개 베타에서 문제가 생기면 더한다. 서버에서만 거르기는 빈틈이 하나만 있어도 바로 뚫려 버렸다.
- TRPG 의 시나리오 소개는 지금 글(최대 5000자)이다. 소개를 asset-server 로 옮길 때 이 규칙으로 바꾼다.

## 언제 뽑는가

- **서버의 공통부(`server-core`)는 지금 뽑는다(2026-10-21).** 쓰는 서버가 이미 셋이고(trpg, notification, asset), chat 과 story 가 더해진다. 순서는 아래와 같다.
  1. notification 과 asset 에서 뽑아 `shared/server-core` 를 만들고 두 서버를 옮긴다. 두 서버의 코드가 거의 같아 차이가 적다. 같은 PR 에서 compose 의 `additional_contexts`, 두 서버의 Dockerfile, `changed-servers.sh` 가 경로 의존을 읽게 하는 일, CI 를 함께 바꾼다(#588. 끝).
  2. chat-server 와 story-server 는 처음부터 `server-core` 를 쓴다.
  3. trpg-server 는 그 뒤에 한 폴더씩 옮긴다(인증, 관측, 서명 순). 지표와 구간이 다른 곳은 [정해 둔 자리](#재정의하는-법)로 넘긴다.
     첫 PR(#589 의 1/3)에서 설정(`CoreSettings`), 인증, 작업의 틀(`loops`), 관측의 문맥과 식별자를 옮겼다. 인증이 다른 서버를 부를 때 붙이는 추적의 문맥이 둘로 갈리지 않게 함께 옮겼다.
     두 번째(2/3)에서 나머지 관측과 DB 연결을 옮겼다. 게임 서버만의 계측기는 `InstrumentSet`, 테이블의 스트림은 `StreamRoutes` 로 넘긴다. 풀의 크기는 설정에서 읽는다(기본은 그대로 5 + 10).
     세 번째(3/3)에서 서버끼리의 서명(`server_core.service_auth`)과 알림 발송함(`server_core.notifications`, 이름 `game`)을 옮겨 끝냈다. 게임 서버에 남은 것은 탈퇴 알림을 받는 의존성(본문 크기, 인증 서버의 비밀), 발송함의 표, 무엇을 누구에게 알릴지다.
- AI 호출 코드는 단계로 뽑는다. 먼저 trpg-server 안에서 `app/ai` 가 다른 폴더를 가져오지 않게 경계를 정리했다(#496, #497, #498. 끝). 다음으로 `shared/ai-core` 로 폴더째 옮겼다(#499 의 1단계, 2026-10-22. 끝). 두 번째로 쓰는 곳인 chat 의 "한 번의 말"이 바로 뒤라, 그 PR 이 커지지 않게 옮기는 일만 먼저 했다. 모델 목록을 파일 원본으로 바꾸는 것(2단계)은 chat 이 모델을 부를 때 한다.
- 템플릿은 asset-server 를 만들 때 정한다. 캐릭터는 처음부터 asset-server 에서 만들고, 세계관과 로어북은 trpg-server 에서 옮겨 온다. chat 이라는 두 번째 사용자가 확실하므로 일찍 정한다.
  그 밖의 템플릿(지도, 물건, 인물)은 chat 이 실제로 쓰려고 할 때 뽑는다. 처음부터 공용 패키지로 만들지 않는다.
  두 서비스에 맞는 모양인지 쓰임을 보기 전에 공용으로 만들면 둘 다에 맞지 않는 모양이 되기 쉽다.
- 뽑을 때는 한 번에 하나씩 뽑는다. 뽑는 동안 원래 자리의 코드를 다른 PR 이 고치지 않게 알린다.

## 버전과 CI

- 템플릿마다 형식 번호를 둔다. 게임 서버의 판 형식이 이미 번호를 올리며 옛 형식을 읽을 때 지금 모양으로 바꿔 읽는다. 같은 방식을 쓴다.
- 공용 코드가 바뀐 PR 은, 그것을 쓰는 모든 서비스의 CI 를 돌린다. 쓰는 서비스는 `changed-servers.sh` 가 서버마다 `pyproject.toml` 의 경로 의존(`path = "../shared/<이름>"`)을 읽어 고른다. 따로 표를 두지 않는다. 새 서버가 공용 코드를 쓰기 시작하면 저절로 잡힌다.
- 공용 코드 자체는 `.github/workflows/shared.yml` 이 본다(린트, 모양, 의존성 취약점, 테스트, 커버리지 95). 패키지마다 작업이 하나다(`server-core`, `ai-core`, `conversation-core`). 패키지가 늘면 작업을 하나 더한다.
- 서버는 경로 의존을 editable 로 받는다. 이미지에는 `uv sync --no-editable` 로 설치된 모양을 담아, 실행 단계에 `shared/` 가 없다.
- 형식을 바꾸는 변경은 옛 형식을 읽을 수 있게 하고, 서비스마다 한 번에 따라가지 않아도 되게 한다.
- 공용 코드에는 그것을 쓰는 서비스 중 어느 한 곳에만 있는 개념(전투 판정, 호감도 등)을 넣지 않는다.

## 주도권

- `shared/server-core` 는 인프라와 문서를 맡는 쪽이 만들고 고친다. notification 과 asset 을 옮기는 일도 그쪽이 한다. trpg-server 를 옮기는 일은 게임 서버를 만드는 쪽이 한다(2026-10-21).
- `shared/ai-core` 와 `shared/conversation-core` 는 게임 서버와 chat, story 를 만드는 쪽이 주도하고, 나중에 쓰는 서비스가 따라간다. 공용 코드 때문에 한 서비스의 진행이 다른 서비스에 막히는 일을 줄이려는 것이다. `app/ai` 를 `shared/ai-core` 로 옮기는 일(#499 의 1단계)만 인프라와 문서를 맡는 쪽이 했다(2026-10-22).
- 공용으로 올라간 뒤에 형식을 바꿀 때는, 쓰는 서비스를 모두 확인하고 한 PR 에서 맞춘다.
- 게임 서버의 `app/lore`, `app/memory`, `app/assets`, 그리고 게임 서버의 `app/observability`(게임만의 계측기) 는 공용 후보이므로 고칠 때는 이 문서를 읽고 쓰임을 확인한다. `server-core` 로 옮기는 동안 그 폴더를 다른 PR 이 고치면 알린다.
- `ai_core` 가 서버의 모듈, 다른 공용 패키지, 관측의 코드를 가져오면 테스트가 실패한다(`shared/ai-core/tests/test_boundary.py`, #498). 예외를 두지 않는다. 필요하면 경계를 다시 의논한다.

## 열린 질문

- 모델 목록, `shared/` 를 가져오는 법, CI 는 [정한 것](#정한-것)으로 옮겼다.
- 템플릿을 Python 패키지로 둘지, 형식만 스키마(JSON Schema 등)로 두고 서비스마다 구현할지. 서비스의 기술이 Python 이 아닌 경우(게시판, 결제)에는 코드를 공유할 수 없다.
- 호출 기록의 표를 서비스마다 같은 모양으로 둘지.
- `server-core` 가 서버끼리의 서명에서 무엇까지 맡을지. 지금 서명은 Python 서버(trpg, notification)와 Go(결제), NestJS(게시판), Django(인증)에 한 벌씩 있다. 형식은 서버마다 같게 맞춰 두었고, `server-core` 는 Python 쪽만 하나로 묶는다.
- 관리 서버도 `server-core` 를 쓸지. 관리 서버를 만들 때 정한다(쓰는 쪽이 기본안).
- asset-server 가 판을 내주는 API 의 모양(JSON)을 템플릿의 정의로 삼을지, 따로 스키마를 둘지.
- 판을 가져온 뒤 원본에 새 판이 나왔을 때, 쓰는 쪽이 복사본을 어떻게 바꿀지(알림만 하고 사용자가 고르는 것이 기본안).
- 지도의 길(장소 사이의 연결)을 어디에 정의할지. 지금 TRPG 에서 길은 시나리오의 칸이다. chat 이 지도를 쓰려면 자산으로 올릴지, 캐릭터나 세계관에 붙일지 정해야 한다.
