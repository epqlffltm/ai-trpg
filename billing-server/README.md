# 결제 서버

[![billing-server](https://github.com/epqlffltm/ai-trpg/actions/workflows/billing-server.yml/badge.svg)](https://github.com/epqlffltm/ai-trpg/actions/workflows/billing-server.yml)

[ai-trpg](../README.md)의 결제 서버. 크레딧의 충전, 잔액, 차감을 맡는다. Go 로 만든다.

**실제 결제가 아니다. 연습과 테스트를 위한 서버다.** 실제 돈을 받지 않고, 실제 결제 대행사(PG)에 붙지 않는다.
결제 대행사의 자리에는 정해 둔 대로 답하는 가짜를 꽂는다. 그 밖의 것(주문, 원장, 중복 방지, 잔액)은 실제처럼 만든다.

지금은 충전까지 있다. 인증 서버가 발급한 토큰의 주인을 알아보고, 그 사람이 상품을 주문해 가짜 결제 대행사로 치르면
산 크레딧이 들어온다. 사용자가 한 번 받는 환영 크레딧(무료)도 있다. 잔액과 원장을 보여 준다.
크레딧을 쓰는(차감) 주소는 아직 없다. 5단계에서 생긴다.
회원가입과 로그인은 하지 않는다. [인증 서버](../auth-server/README.md)가 발급한 토큰을 공개키로 검증만 한다.

## 실행

명령은 모두 `billing-server` 폴더 안에서 실행한다. `go` 명령과 설정 파일(`.env`)이 현재 폴더를 기준으로 동작한다.

### 요구 사항

- Go 1.27 이상 (`go version` 으로 확인한다)
- 루트의 [공용 인프라](../README.md)가 떠 있어야 한다

Go 는 파이썬의 uv 와 가상 환경에 해당하는 것을 따로 깔지 않는다. 언어에 들어 있다.

| 하는 일 | 파이썬 서버들 | 이 서버 |
| --- | --- | --- |
| 의존성 목록과 잠금 | `pyproject.toml`, `uv.lock` | `go.mod`, `go.sum` |
| 의존성 받기 | `uv sync` | `go mod download` (빌드할 때 저절로 받는다) |
| 실행 | `uv run uvicorn ...` | `go run ./cmd/server` |
| 테스트 | `uv run pytest` | `go test ./...` |
| 모양 맞추기 | `ruff format` | `gofmt` |
| 정적 검사 | `ruff check` | `go vet` |

### DB 계정과 스키마

`billing` 계정과 스키마 둘(개발용 `billing`, 테스트용 `billing_test`)은 초기화 스크립트(`docker/postgres/init/04-billing-role.sql`)가 만든다.
이 스크립트는 데이터 볼륨이 비어 있는 첫 기동 때만 실행된다.
스크립트를 추가하기 전에 만든 볼륨이라면 한 번 직접 실행한다. 루트의 `.env`에 `BILLING_DB_PASSWORD`를 적고
컨테이너를 다시 만든 뒤(`docker compose up -d`), 저장소 루트에서 실행한다.
`trpg`는 루트 `.env`의 `POSTGRES_USER`와 `POSTGRES_DB` 값이다.

```
docker compose exec db psql -v ON_ERROR_STOP=1 -U trpg -d trpg -f /docker-entrypoint-initdb.d/04-billing-role.sql
```

`docker compose up -d` 는 DB 컨테이너를 새 환경 변수로 다시 만든다. 데이터는 볼륨에 있어서 남지만 DB 가 잠깐 내려간다.
다른 서버의 테스트가 돌고 있으면 끝난 뒤에 한다.

`billing` 계정은 이미 있는데 `billing_test` 스키마만 없는 볼륨이라면(테스트용 스키마를 더하기 전에 만든 볼륨) 스키마만 만든다.
스크립트를 통째로 다시 돌리면 계정이 이미 있다는 오류로 멈춘다. 저장소 루트에서 실행한다.

```
docker compose exec db psql -v ON_ERROR_STOP=1 -U trpg -d trpg -c "CREATE SCHEMA IF NOT EXISTS billing_test AUTHORIZATION billing"
```

### 설치와 실행

```
cd billing-server
cp .env.example .env
go run ./cmd/migrate up
go run ./cmd/server
```

`.env`의 `DATABASE_URL`에 루트 `.env`의 `BILLING_DB_PASSWORD`와 같은 비밀번호를 적는다.
처음 실행할 때 의존성을 받느라 시간이 걸린다. 다음부터는 받아 둔 것을 쓴다.

`.env`의 `PG_WEBHOOK_SECRET`에는 32자 이상의 아무 글자를 적는다. 결제 대행사의 알림에 붙은 서명을 확인하는 비밀이다.
예시 파일의 값은 일부러 짧게 두었다. 바꾸지 않으면 서버가 뜨지 않는다. 직접 짓지 않고 만들어 넣으려면
`billing-server` 폴더에서 아래를 실행한다. 만든 값은 화면에 찍히지 않고 `.env`의 끝에 한 줄로 붙는다.
예시 파일에서 복사한 `PG_WEBHOOK_SECRET` 줄이 이미 있으면 그 줄을 먼저 지운다.

```
$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); Add-Content .env ("`nPG_WEBHOOK_SECRET=" + [BitConverter]::ToString($b).Replace('-','').ToLower())
```

macOS, Linux 에서는 이렇게 한다.

```
printf '\nPG_WEBHOOK_SECRET=%s\n' "$(openssl rand -hex 32)" >> .env
```

`go run ./cmd/migrate up` 은 테이블을 만든다. 서버는 테이블을 스스로 만들지 않는다. 새 마이그레이션 파일을 받을 때마다 다시 돌린다.
자세한 것은 [마이그레이션](#마이그레이션)에 있다.

확인한다.

```
curl http://127.0.0.1:8003/health
curl http://127.0.0.1:8003/health/ready
```

둘 다 `{"status":"ok"}` 가 나오면 된다. 끌 때는 `Ctrl+C` 다. 처리 중인 요청이 끝나기를 기다린 뒤 꺼진다.

토큰이 필요한 주소는 인증 서버도 떠 있어야 확인할 수 있다. 인증 서버에서 받은 access 토큰을 머리말에 싣는다.

```
curl -H "Authorization: Bearer <access 토큰>" http://127.0.0.1:8003/api/v1/billing/me
curl -H "Authorization: Bearer <access 토큰>" http://127.0.0.1:8003/api/v1/billing/wallet
```

한 번도 충전하지 않았으면 잔액은 `{"paid":"0","free":"0","total":"0"}` 이다. 충전해 보는 방법은 [주문과 결제](#주문과-결제)에 있다.

## 설정

환경 변수로 읽는다. 현재 폴더에 `.env`가 있으면 그것도 읽는다. 같은 이름이 둘 다 있으면 환경 변수가 이긴다.
운영과 CI 는 `.env` 없이 환경 변수만으로 돈다.

| 이름 | 기본값 | 뜻 |
| --- | --- | --- |
| `DATABASE_URL` | 없음(필수) | PostgreSQL 접속 주소. `postgres://billing:비밀번호@127.0.0.1:5432/trpg` |
| `DB_SCHEMA` | `billing` | 테이블이 놓이는 스키마. 소문자, 숫자, 밑줄만 받는다. 테스트는 이 값과 상관없이 `billing_test` 를 쓴다 |
| `AUTH_JWKS_URL` | 없음(필수) | 인증 서버가 공개키를 내주는 주소. `http://127.0.0.1:8000/api/v1/auth/jwks` |
| `JWT_ISSUER` | `ai-trpg-auth` | 토큰을 발급한 서버의 이름(`iss`). 인증 서버의 `JWT_ISSUER` 와 같아야 한다 |
| `JWT_AUDIENCE` | `ai-trpg-billing` | 이 서버의 이름. 토큰의 대상(`aud`)에 이 이름이 있어야 받는다 |
| `HOST` | `127.0.0.1` | 서버가 요청을 받는 주소 |
| `PORT` | `8003` | 서버가 요청을 받는 포트. 인증 서버는 8000, 게임 서버는 8001, 게시판 서버는 8002 를 쓴다 |
| `DEBUG` | `false` | 개발용 동작(등록한 주소 목록 같은 자세한 출력)을 켠다 |
| `SPEND_FREE_FIRST` | `true` | 크레딧을 쓸 때 무료 크레딧부터 쓴다. `false` 면 산 크레딧부터 쓴다 |
| `FREE_CREDIT_TTL` | `168h` | 무료 크레딧이 지급된 뒤 사라질 때까지의 시간. `168h`, `30m`, `90s` 처럼 단위를 붙인다. 1초보다 짧을 수 없다 |
| `WELCOME_CREDITS` | `1000` | 사용자가 한 번 받는 환영 크레딧(무료)의 양. 0 이면 주지 않는다. 100만까지 |
| `PG_WEBHOOK_SECRET` | 없음(필수) | 결제 대행사의 알림에 붙은 서명을 확인하는 비밀. 32자 이상. 로그와 오류에 싣지 않는다 |

`FREE_CREDIT_TTL` 은 날 단위(`7d`)를 받지 않는다. Go 의 시간 표기에 날이 없다. 1주일은 `168h` 다.
두 값은 서버를 다시 띄워야 바뀐다. 바꾸면 그 뒤의 일에만 적용된다([크레딧](#크레딧)).
마이그레이션 명령(`cmd/migrate`)은 `DATABASE_URL` 과 `DB_SCHEMA` 만 읽는다.

잘못된 설정이면 서버가 뜨기 전에 오류로 끝난다. 틀린 것이 여럿이면 한 번에 모두 알려 준다.
오류에는 변수의 이름만 싣고 값은 싣지 않는다. `DATABASE_URL`에는 비밀번호가 들어 있다.

파이썬 서버들의 접속 주소는 `postgresql+asyncpg://`처럼 드라이버 이름이 붙는다. 이 서버는 `postgres://`로 시작한다.
주소의 나머지(계정, 비밀번호, 주소, 포트, DB 이름)는 같은 모양이다.

## API

상태를 확인하는 주소 둘은 API 주소(`/api/v1/billing`) 밖에 있다.
프록시와 관리 도구가 부르는 것이라 버전이 없다. 로그인이 필요 없다.

| 주소 | 답 | 뜻 |
| --- | --- | --- |
| `GET /health` | 200 `{"status":"ok"}` | 프로세스가 살아 있다. DB 를 보지 않는다 |
| `GET /health/ready` | 200 `{"status":"ok"}` 또는 503 `{"status":"unavailable"}` | DB 가 3초 안에 답하면 200, 아니면 503 |

- **둘로 나눈 이유.** DB 가 죽었다고 `/health`까지 실패하면, 프로세스를 다시 띄워도 낫지 않는 문제에 재시작만 되풀이된다.
  살아 있는지와 요청을 받을 수 있는지는 다른 질문이다. 게임 서버와 같은 나눔이다.
- **503 에 이유를 싣지 않는다.** 드라이버의 오류에는 접속 주소와 계정 이름이 들어 있을 수 있다.

`/api/v1/billing` 아래의 주소는 모두 로그인이 필요하다. `Authorization: Bearer <access 토큰>` 머리말을 싣는다.

| 주소 | 답 | 뜻 |
| --- | --- | --- |
| `GET /api/v1/billing/me` | 200 `{"user_id":"..."}` | 토큰의 주인(인증 서버의 `public_id`) |
| `GET /api/v1/billing/wallet` | 200 `{"paid":"80","free":"30","total":"110"}` | 토큰의 주인이 지금 쓸 수 있는 크레딧. 산 것, 무료, 둘의 합 |
| `GET /api/v1/billing/wallet/entries` | 200 `{"entries":[...],"next_before":"41"}` | 토큰의 주인의 원장. 최근 것부터 |
| `POST /api/v1/billing/wallet/welcome` | 201 `{"granted":"1000","expires_at":"..."}` | 환영 크레딧을 받는다. 한 사용자가 한 번만. 두 번째부터는 409 |
| `GET /api/v1/billing/products` | 200 `{"products":[...]}` | 파는 상품. 번호, 이름, 값(원), 크레딧 |
| `POST /api/v1/billing/orders` | 201 또는 200, 주문 | 주문을 만든다. `Idempotency-Key` 머리말이 있어야 한다 |
| `GET /api/v1/billing/orders/{id}` | 200, 주문 | 토큰의 주인의 주문 하나 |
| `POST /api/v1/billing/orders/{id}/confirm` | 200 또는 202, 주문 | 결제의 승인을 요청한다. 승인되면 크레딧이 들어온다 |

로그인 없이 받는 주소가 하나 있다. 결제 대행사가 부른다. 토큰 대신 본문의 서명을 확인한다.

| 주소 | 답 | 뜻 |
| --- | --- | --- |
| `POST /api/v1/billing/webhooks/payment` | 200 `{"received":true}` | 결제 대행사의 알림. 결과를 모르던 주문을 마저 끝낸다 |

주문 주소들의 요청과 응답, 상태 코드는 [주문과 결제](#주문과-결제)에 있다.

- **누구의 지갑인지는 토큰에서만 정한다.** 주소나 쿼리로 사용자 번호를 받지 않는다. 남의 지갑을 읽는 요청은 만들 수 없다.
- **양은 숫자가 아니라 글자다**(`"80"`). 이유는 [크레딧](#크레딧)의 "단위"에 있다.
- **지갑이 없는 사용자도 200 이다.** 모두 `"0"` 이고 원장은 빈 목록이다. 읽는 것만으로 지갑을 만들지 않는다.

원장의 한 줄은 이렇게 생겼다.

```json
{
  "id": "42",
  "operation_id": "99999999-8888-4777-8666-555555555555",
  "kind": "paid",
  "reason": "spend",
  "amount": "-20",
  "order_id": null,
  "created_at": "2026-03-02T09:00:00Z"
}
```

| 칸 | 뜻 |
| --- | --- |
| `id` | 줄의 번호. 나중에 적힌 줄이 더 크다. 64비트 정수라 글자로 준다 |
| `operation_id` | 한 번의 변경이 남긴 줄들을 묶는다. 무료 30 과 산 것 20 을 함께 쓰면 두 줄이 같은 값이다 |
| `kind` | `paid`(산 크레딧) 또는 `free`(무료 크레딧) |
| `reason` | `deposit`(산 크레딧이 들어옴), `grant`(무료 크레딧 지급), `spend`(씀), `expire`(무료 크레딧이 기한이 지나 사라짐) |
| `amount` | 늘었으면 양수, 줄었으면 음수 |
| `order_id` | 이 크레딧이 들어온 주문. 주문으로 들어온 줄이 아니면 `null` |

원장을 나눠 읽는 쿼리는 둘이다.

| 쿼리 | 기본값 | 뜻 |
| --- | --- | --- |
| `limit` | 20 | 한 번에 읽는 줄 수. 1 부터 100 까지 |
| `before` | 없음 | 이 번호보다 앞선 줄만 읽는다. 응답의 `next_before` 를 그대로 넣는다 |

`next_before` 가 `null` 이면 더 읽을 것이 없다. 쪽 번호(`page=3`)를 쓰지 않는 이유는 읽는 사이에 새 줄이 생겨도
같은 줄이 두 번 나오거나 빠지지 않게 하려는 것이다. 값이 틀리면 400 이다.

토큰에 문제가 있을 때의 답은 둘이다. 게임 서버와 같다.

| 답 | 언제 | 클라이언트가 할 일 |
| --- | --- | --- |
| 401 `{"detail":"인증이 필요합니다."}` + `WWW-Authenticate: Bearer` | 토큰이 없거나 받아들일 수 없다 | 토큰을 갱신하거나 다시 로그인한다 |
| 503 `{"detail":"지금은 인증을 확인할 수 없습니다. ..."}` + `Retry-After: 60` | 공개키를 구할 수 없어 맞는지 틀린지 모른다 | 잠시 뒤 다시 시도한다. 로그아웃시키지 않는다 |

401 에는 이유를 싣지 않는다. 만료인지 서명이 틀렸는지를 알려 주면 토큰을 꾸며 내는 쪽에 도움이 된다.

## 주문과 결제

**실제 돈을 받지 않는다.** 결제 대행사의 자리에 정해 둔 대로 답하는 가짜가 꽂혀 있다(`internal/payment/fake.go`).
흐름과 상태, 실패했을 때의 처리는 실제 결제 대행사를 쓸 때와 같게 만들었다.

**흐름**

```
1. GET  /products                상품을 본다
2. POST /orders                  주문을 만든다 (pending)
3. (결제창에서 인증한다. 결제 대행사가 그 결제에 번호를 붙여 준다)
4. POST /orders/{id}/confirm     그 번호로 승인을 요청한다 (paid 또는 failed)
5. GET  /orders/{id}             결과를 모르는 채로 끝났으면 나중에 다시 본다
```

3번이 가짜에서는 없다. 결제창이 없으므로 결제 번호를 클라이언트가 지어서 보낸다. 번호의 앞머리가 결과를 정한다.

**상품.** `internal/catalog/catalog.go` 에 코드로 적혀 있다. 1원에 1크레딧이고, 많이 산다고 더 주지 않는다.

| 번호 | 값 | 크레딧 |
| --- | --- | --- |
| `credits-1000` | 1,000원 | 1,000 |
| `credits-5000` | 5,000원 | 5,000 |
| `credits-10000` | 10,000원 | 10,000 |
| `credits-30000` | 30,000원 | 30,000 |

**주문 만들기.** 본문에는 상품의 번호만 적는다. 값과 크레딧의 양은 서버가 상품 목록에서 찾는다. 클라이언트가 보낸 금액을 쓰지 않는다.

```
POST /api/v1/billing/orders
Idempotency-Key: 4f0c2b1e-7a52-4d43-9a57-2f6f0d0e9b11
{"product_id": "credits-1000"}
```

`Idempotency-Key` 는 클라이언트가 요청마다 새로 지어 붙이는 키다(영문자, 숫자, 밑줄, 붙임표로 8자에서 128자. UUID 면 된다).
응답을 받지 못해 같은 요청을 다시 보낼 때는 **같은 키**를 붙인다. 서버는 주문을 새로 만들지 않고 먼저 만든 것을 돌려준다.

| 답 | 언제 |
| --- | --- |
| 201 | 주문을 새로 만들었다 |
| 200 | 같은 키로 이미 만든 주문을 돌려준다 |
| 400 | 키가 없거나 모양이 틀렸다. 그런 상품이 없다. 본문이 JSON 이 아니다 |
| 409 | 같은 키로 다른 상품을 주문했다. 다시 보낸 요청이 아니라 다른 요청이다 |

**주문의 모양**

```json
{
  "id": "aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeeeee",
  "product_id": "credits-1000",
  "price": 1000,
  "credits": "1000",
  "status": "pending",
  "failure_code": null,
  "created_at": "2026-03-02T09:00:00Z",
  "paid_at": null
}
```

값(`price`)은 원이라 소수가 없어서 숫자로 준다. 크레딧은 다른 주소들처럼 글자다.

**상태.** 한 방향으로만 흐른다.

```
pending -> confirming -> paid
                      -> failed
```

| 상태 | 뜻 |
| --- | --- |
| `pending` | 주문을 만들었다. 아직 결제 대행사를 부르지 않았다 |
| `confirming` | 결제 대행사에 승인을 요청했다. 답을 받기 전이거나, 답을 받지 못했다 |
| `paid` | 승인되었다. 크레딧이 들어갔다 |
| `failed` | 거절되었다. 돈이 나가지 않았다. `failure_code` 에 이유가 있다 |

**승인 요청.** 본문에는 결제 번호만 적는다. 금액은 받지 않는다. 주문에 적힌 값을 결제 대행사에 보낸다.

```
POST /api/v1/billing/orders/{id}/confirm
{"payment_key": "fake_ok_1a2b3c"}
```

| 답 | 언제 |
| --- | --- |
| 200, `status` 가 `paid` | 승인되었다 |
| 200, `status` 가 `failed` | 거절되었다. 요청은 잘 처리된 것이라 200 이다. 결과는 본문으로 안다 |
| 202, `status` 가 `confirming` | 결제 대행사의 답을 받지 못했다. 결과를 모른다 |
| 400 | 결제 번호의 모양이 틀렸다 |
| 404 | 그런 주문이 없다. 남의 주문도 같은 답이다 |
| 409 | 이 주문이 이미 다른 결제 번호로 진행되었다. 또는 그 결제 번호가 다른 주문에 쓰였다 |

같은 결제 번호로 몇 번을 불러도 된다. 크레딧은 한 번만 들어간다. 끝난 주문이면 그대로 돌려주고,
`confirming` 이면 결제 대행사에 결과를 물어 마저 끝낸다.

**가짜 결제 대행사가 알아듣는 결제 번호.** 앞머리 뒤에는 아무 글자나 붙여 결제마다 다르게 만든다.
한 번 쓴 번호는 다른 주문에 다시 쓸 수 없다.

| 앞머리 | 승인 요청의 답 | 실제 결과(조회하면 나오는 것) |
| --- | --- | --- |
| `fake_ok_` | 승인 | 승인 |
| `fake_declined_` | 거절(`card_declined`) | 거절 |
| `fake_timeout_ok_` | 답이 오지 않는다 | 승인 |
| `fake_timeout_declined_` | 답이 오지 않는다 | 거절 |
| `fake_lost_` | 답이 오지 않는다 | 결제 대행사도 아직 모른다 |
| 그 밖의 것 | 거절(`unknown_payment_key`) | 거절 |

**답을 받지 못했을 때.** 결제에서 가장 조심할 곳이다. 승인을 요청했는데 답이 오지 않았다면 돈이 나갔을 수도 있고 아닐 수도 있다.
이것을 실패로 적으면 돈을 받고 크레딧을 안 주게 된다. 성공으로 적으면 돈을 안 받고 크레딧을 준다.
그래서 어느 쪽으로도 적지 않고 `confirming` 에 둔다. 끝내는 길은 둘이다.

- 클라이언트가 같은 결제 번호로 승인을 다시 요청한다. 서버는 승인을 또 요청하지 않고 결제 대행사에 **결과를 묻는다**
- 결제 대행사가 알림(웹훅)을 보낸다

`fake_lost_` 처럼 결제 대행사도 모르는 채로 남으면 주문은 계속 `confirming` 이다. 오래 남은 것을 정리하는 일은 대사(7단계)에서 한다.

**결제 대행사의 알림(웹훅).** 승인 요청과 별개로, 결제 대행사가 결과를 서버에 알려 주는 길이다. 보조 수단이다.

- 로그인 없이 받는다. 그 대신 본문에 서명이 있어야 한다. 머리말 `X-Payment-Signature: t=<보낸 시각>,v1=<서명>`.
  서명은 `<보낸 시각>.<본문>` 을 `PG_WEBHOOK_SECRET` 으로 서명한 값이다(HMAC-SHA256)
- 서명이 없거나 맞지 않으면 401 이다. 시각이 5분 넘게 벌어진 알림도 401 이다. 가로챈 알림을 나중에 다시 보낼 수 없다
- 서명이 맞아도 본문에 적힌 결과를 믿지 않는다. 주문 번호와 결제 번호만 읽고 결제 대행사에 다시 묻는다
- `confirming` 인 주문만, 결제 번호가 그 주문의 것과 같을 때만 끝낸다. 그 밖의 알림은 아무것도 하지 않고 200 이다.
  결제 대행사가 같은 알림을 여러 번 보내도 된다
- 결제 대행사에 묻지 못했으면 503 이다. 결제 대행사가 알림을 다시 보내게 하려는 것이다

가짜 결제 대행사는 따로 떠 있는 서버가 아니라서 알림을 스스로 보내지 못한다. 명령이 대신 보낸다.
서버와 같은 `.env` 에서 비밀과 주소를 읽어 서명한다.

```
go run ./cmd/fakepg notify <주문 번호> <결제 번호>
```

**손으로 해 보기.** 서버와 인증 서버가 떠 있고 access 토큰이 있을 때다. PowerShell 에서 한다.
`curl.exe` 로 JSON 본문을 보내면 따옴표가 PowerShell 의 판에 따라 다르게 넘어가서, 여기서는 `Invoke-RestMethod` 를 쓴다.

```
$h = @{ Authorization = "Bearer <access 토큰>"; "Idempotency-Key" = "my-first-order-0001" }
$base = "http://127.0.0.1:8003/api/v1/billing"
$o = Invoke-RestMethod -Method Post -Uri "$base/orders" -Headers $h -ContentType "application/json" -Body '{"product_id":"credits-1000"}'
Invoke-RestMethod -Method Post -Uri "$base/orders/$($o.id)/confirm" -Headers $h -ContentType "application/json" -Body '{"payment_key":"fake_ok_0001"}'
Invoke-RestMethod -Uri "$base/wallet" -Headers $h
```

셋째 줄이 주문을 만들고, 넷째 줄이 치르고, 다섯째 줄이 잔액을 보여 준다. 다시 해 보려면 `Idempotency-Key` 와 결제 번호를 새것으로 바꾼다.
같은 키로 다시 보내면 새 주문이 아니라 먼저 만든 주문이 오고, 한 번 쓴 결제 번호는 다른 주문에 못 쓴다.

결제 번호를 `fake_timeout_ok_0002` 로 쓰면 주문이 `confirming` 으로 오고 잔액이 그대로다. 그 뒤에 아래를 돌리면 주문이 `paid` 가 되고 잔액이 는다.

```
go run ./cmd/fakepg notify $o.id fake_timeout_ok_0002
```

**알려진 한계**

- 환불이 없다. 정한 규칙이 아직 없고, 요청하는 쪽(관리 서버)도 서버 간 인증도 없다
- 답도 없고 결제 대행사도 모르는 주문은 `confirming` 에 남는다. 정리하는 주기 작업은 7단계다
- 주문을 만들어 놓고 치르지 않은 `pending` 주문도 그대로 남는다
- 가짜 결제 대행사는 기억하는 것이 없다. 결제 번호만 보고 답한다. 그래서 금액이 맞는지, 그 번호가 정말 결제창에서 나온 것인지는 보지 않는다.
  같은 번호로 주문 둘을 치르지 못하게 하는 것은 이 서버의 DB 다
- 가짜가 꽂혀 있는 한 누구나 `fake_ok_` 로 크레딧을 얻는다. 이 서버를 실제로 공개하면 안 된다

## 크레딧

**종류는 둘이다.**

| | 산 크레딧(`paid`) | 무료 크레딧(`free`) |
| --- | --- | --- |
| 생기는 길 | 주문을 치른다([주문과 결제](#주문과-결제)) | 지급. 지금은 환영 크레딧 하나다(아래) |
| 사라지는가 | 사라지지 않는다 | 지급된 뒤 `FREE_CREDIT_TTL`(1주일)이 지나면 사라진다 |
| 어디에 있나 | 지갑(`wallets.paid_balance`)의 한 칸 | 지급 하나가 한 줄(`free_grants`). 줄마다 남은 양과 사라지는 시각이 있다 |

**환영 크레딧.** 사용자가 `POST /api/v1/billing/wallet/welcome` 을 부르면 무료 크레딧 `WELCOME_CREDITS`(기본 1,000)를 받는다.
본문은 없다. 양은 서버의 설정이 정하고, 받는 사람은 토큰의 주인이다.

- 한 사용자가 **한 번만** 받는다. 두 번째부터는 409 다. 받은 것을 다 썼거나 1주일이 지나 사라진 뒤에도 다시 받지 못한다
- 다른 무료 크레딧과 똑같이 `FREE_CREDIT_TTL` 뒤에 사라진다. 응답의 `expires_at` 이 그 시각이다
- `WELCOME_CREDITS` 를 0 으로 두면 꺼진다. 주소는 404 로 답한다
- 양을 바꿔도 이미 받은 사람이 차이만큼 더 받지는 않는다

"한 번만"은 지급 묶음에 붙는 이름(`free_grants.grant_key`)으로 지킨다. 환영 크레딧의 이름은 `welcome` 이다.
한 사용자가 같은 이름의 지급을 둘 가질 수 없게 DB 의 유일 색인이 막는다. 이름이 없는 지급은 몇 번이고 줄 수 있다.
나중에 "이벤트마다 한 번" 같은 지급이 생기면 이름만 새로 지으면 된다.

가입할 때 저절로 주는 쪽이 더 자연스럽다. 그러려면 인증 서버가 이 서버를 불러야 하는데 서버 간 인증(5단계)이 아직 없다.
그때까지는 사용자가 직접 받는다.

**쓰는 순서.** `SPEND_FREE_FIRST` 가 `true`(기본값)면 무료 크레딧을 먼저 쓰고 모자란 만큼만 산 크레딧에서 뺀다.
`false` 면 그 반대다. 무료 크레딧끼리는 설정과 상관없이 **먼저 사라지는 것부터** 쓴다.
가진 것이 모자라면 되는 데까지 빼지 않는다. 하나도 빼지 않고 거절한다.

**설정을 바꾸면 그 뒤의 일에만 적용된다.** 기한을 바꿔도 이미 지급한 크레딧의 기한은 그대로다. 사라지는 시각은 지급할 때 정해 DB 에 적는다.
쓰는 순서는 바꾼 뒤의 차감부터 달라진다.

**단위.** 크레딧은 정수다. DB 에는 "가장 작은 단위가 몇 개인가"를 `BIGINT` 로 적고, Go 에서는 `credit.Amount` 타입으로 다룬다.
소수(`float`)는 쓰지 않는다. `0.1 + 0.2` 가 `0.3` 이 되지 않는다.
지금은 가장 작은 단위가 1 크레딧이다. 나중에 소수 크레딧이 필요해지면 바꿀 곳은 둘이다.

1. `internal/credit/amount.go` 의 `Scale` 을 올린다. 4 로 올리면 1 크레딧이 가장 작은 단위 10000 개가 되어 `"12.3456"` 을 적을 수 있다
2. 마이그레이션 하나로 이미 저장된 양에 10000 을 곱한다

DB 의 칸과 API 의 모양은 그대로다. 그래서 API 는 처음부터 양을 글자로 준다. 숫자로 주다가 소수가 생기면
클라이언트가 `float` 로 읽어 값이 틀어진다. 글자를 읽고 쓰는 규칙은 자릿수 0 과 4 에서 미리 테스트해 두었다.

**지금의 값과 원장.** 지갑과 지급 묶음은 "지금 얼마인가"이고, 원장(`ledger_entries`)은 "왜 그렇게 되었는가"다.
크레딧이 바뀔 때마다 같은 트랜잭션에서 둘을 함께 바꾼다. 그래서 늘 이렇다.

- 산 크레딧의 잔액 = 원장의 `paid` 줄의 합
- 지급 묶음의 남은 양 = 그 묶음을 가리키는 원장 줄의 합

원장은 덧붙이기만 한다. 고치거나 지우는 SQL 은 DB 의 트리거가 거절한다. 틀린 줄은 지우지 않고 반대 줄을 덧붙여 바로잡는다.

**동시에 온 요청.** 한 사용자의 크레딧을 바꾸는 일은 모두 그 사용자의 지갑 줄을 먼저 잠근다(`SELECT ... FOR UPDATE`).
같은 사용자의 변경은 한 줄로 선다. 가진 것이 100 일 때 10 씩 스무 번을 한꺼번에 써도 열 번만 되고 열 번은 거절된다.
다른 사용자의 요청은 서로 기다리지 않는다.

**DB 가 스스로 막는 것.** 코드가 틀려도 아래는 DB 에서 멈춘다(`CHECK`, 외래 키, 트리거).

- 잔액과 남은 양이 0 아래로 내려가는 것, 남은 양이 준 양보다 많아지는 것
- 원장의 줄을 고치거나 지우는 것
- 말이 안 되는 줄: 모르는 종류나 이유, 양이 0, 충전인데 음수, 산 크레딧이 사라졌다는 줄, 지급 묶음이 없는 무료 크레딧의 줄
- 지갑이 없는 사용자의 줄
- 한 사용자가 같은 이름의 지급(환영 크레딧)을 두 번 받는 것
- 주문 하나로 크레딧이 두 번 들어오는 것, 결제 한 건으로 주문 둘을 치르는 것, 한 사용자가 같은 키로 주문 둘을 만드는 것
- 상태와 맞지 않는 주문: 결제 번호가 있는 `pending`, 치른 시각이 없는 `paid`, 이유가 없는 `failed`

**무료 크레딧이 사라지는 방식.** 사라지는 시각이 지난 묶음은 그 순간부터 잔액에 세지 않는다. 따로 도는 작업이 없어도 정확하다.
"사라졌다"는 원장의 줄(`expire`)은 그 사용자의 **다음 변경** 때 함께 적는다. 읽기는 DB 를 바꾸지 않는다.

**알려진 한계**

- 무료 크레딧이 사라진 뒤 그 사용자에게 변경이 없으면, 잔액은 이미 줄었는데 원장에는 `expire` 줄이 아직 없다.
  다음 변경 때 적힌다. 변경이 없는 사용자의 것까지 적어 주는 주기 작업은 대사(7단계)와 함께 넣는다
- 크레딧을 쓰는 주소가 없다. 지금은 테스트만 부른다
- 환영 크레딧은 계정마다 한 번이다. 계정을 여러 개 만들면 여러 번 받는다. 막으려면 계정을 만드는 쪽(인증 서버)에서 막아야 한다
- 시각은 DB 가 아니라 서버의 시계로 정한다. 서버를 여러 대 띄우면 서버끼리 시계가 맞아야 한다(NTP)
- 한 번에 넣거나 쓸 수 있는 양은 1조(`wallet.MaxAmount`)까지다

## 마이그레이션

테이블을 만들고 바꾸는 SQL 은 `migrations/` 에 파일로 둔다. [goose](https://github.com/pressly/goose) 가 순서대로 적용하고,
어디까지 적용했는지를 스키마 안의 표(`goose_db_version`)에 적는다. 명령은 `billing-server` 폴더에서 실행한다.

```
go run ./cmd/migrate up       아직 적용하지 않은 것을 모두 적용한다
go run ./cmd/migrate status   파일마다 적용되어 있는지 보여 준다
go run ./cmd/migrate down     마지막으로 적용한 것 하나를 되돌린다
```

`down` 은 그 파일이 만든 테이블과 **그 안의 데이터를 지운다.** 개발용 DB 에서만 쓴다.

서버와 같은 설정(`.env` 의 `DATABASE_URL`, `DB_SCHEMA`)을 읽는다. 접속 주소를 명령 줄에 적지 않는다.
어느 스키마를 바꾸는지 첫 줄에 찍는다. 테스트용 스키마는 손으로 맞추지 않는다. 테스트가 스스로 적용한다([테스트](#테스트)).

**새 마이그레이션을 더할 때**

1. `migrations/` 에 다음 번호의 파일을 만든다(`00002_무엇을_하는지.sql`). `-- +goose Up` 아래에 적용할 SQL, `-- +goose Down` 아래에 되돌릴 SQL 을 적는다
2. 테이블 이름에 스키마를 붙이지 않는다. 같은 파일이 `billing` 과 `billing_test` 에 함께 쓰인다
3. 이미 main 에 들어간 파일은 고치지 않는다. 바꿀 것이 있으면 새 파일을 더한다
4. `go run ./cmd/migrate up`, `down`, `up` 을 차례로 돌려 되돌리기까지 확인한다(CI 도 같은 것을 돌린다)
5. 쿼리가 바뀌었으면 Go 코드를 다시 만든다(아래)

**SQL 에서 Go 코드 만들기(sqlc)**

쿼리는 패키지마다 `queries.sql` 에 SQL 로 적는다(`internal/wallet`, `internal/order`). [sqlc](https://sqlc.dev) 가 그것을 읽어 Go 함수(`walletdb/`, `orderdb/`)를 만든다.
만들어진 코드는 커밋한다. 그래서 **쿼리를 고치지 않는 한 sqlc 를 깔 필요가 없다.** 쿼리나 테이블을 고쳤을 때만 다시 만든다.

```
sqlc generate
```

버전은 CI 와 같은 1.31.1 을 쓴다. 까는 방법은 둘이다. 도커 쪽은 Go 도구를 따로 깔지 않아도 된다.

```
go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1
docker run --rm -v "${PWD}:/src" -w /src sqlc/sqlc:1.31.1 generate
```

`walletdb/` 와 `orderdb/` 의 파일은 손으로 고치지 않는다. 다음에 만들 때 덮어쓰인다. CI 가 커밋된 코드와 SQL 이 어긋나는지 본다(`sqlc diff`).

## 토큰 검증

인증 서버의 DB 를 보지 않는다. 공개키로 서명을 확인하고 토큰 안에 적힌 값만 본다.
규칙은 [게임 서버](../game-server/README.md#토큰-검증)와 같다. 인증 서버가 죽었을 때 두 서버가 똑같이 굴어야 한다.

**확인하는 것**

- 서명 방식이 `RS256` 인가. 토큰이 스스로 적어 온 방식을 믿지 않는다. 서명이 없는 토큰(`none`)이나 공개키를 비밀키처럼 써서 만든 토큰(`HS256`)을 받지 않는다
- 인증 서버의 키로 서명됐는가
- 만료되지 않았는가(`exp`). 없으면 거부한다. 서버 간 시계 차이는 10초까지 봐준다
- 인증 서버가 발급했는가(`iss`)
- 이 서버에 쓰라고 발급됐는가(`aud` 에 `ai-trpg-billing`)
- access 토큰인가(`token_type`). refresh 토큰도 같은 키로 서명되므로 종류를 따로 본다
- 주인(`sub`)이 UUID 인가

**공개키를 기억하는 규칙** (`internal/jwks/cache.go`)

1. 처음 필요할 때 가져와 1시간 기억한다. 서버가 뜰 때는 가져오지 않는다. 인증 서버가 죽어 있어도 이 서버는 뜬다
2. 기억에 없는 키 ID(`kid`)가 오면 다시 가져온다. 인증 서버가 키를 바꾼 경우다
3. 다시 가져오기는 60초에 한 번만 시도한다. 가짜 `kid` 를 쏟아부어 인증 서버를 두드리게 만들 수 없고, 죽은 인증 서버를 요청마다 기다리지 않는다
4. 다시 가져오기에 실패하면 기억하던 키를 계속 쓴다. 인증 서버가 죽어도 이미 로그인한 사용자의 요청은 계속 처리한다

**받아들이는 키**

RSA 키만, 2048비트 이상만 기억한다. 지수가 1 이거나 짝수인 키는 버린다. 문서의 키 하나가 이상해도 나머지는 쓴다.
키를 가져오는 주소는 설정(`AUTH_JWKS_URL`)의 것만 쓴다. 토큰 안에 적힌 주소는 쓰지 않는다.
문서는 1MB 까지만 읽고, 인증 서버의 답은 5초까지만 기다린다.

**알려진 한계**

- 로그아웃과 계정 정지가 access 토큰의 만료(15분)까지 반영되지 않는다
- 인증 서버가 뺀 키를 최대 1시간 믿는다. 키가 새서 급히 빼야 하면 이 서버를 다시 띄운다
- 기억 시간이 끝난 뒤 인증 서버가 답 없이 죽어 있으면, 60초에 한 번 다시 가져오는 순간의 요청들이 최대 5초 기다린다

## 테스트

```
go test ./...
```

DB 를 쓰는 테스트가 있다. 루트의 인프라가 떠 있고 `billing-server/.env`에 `DATABASE_URL`이 있어야 한다.
접속 주소가 없으면 건너뛰지 않고 실패한다. 건너뛰면 DB 테스트가 한 번도 돌지 않았는데 통과한 것으로 보인다.

테이블을 쓰는 테스트는 개발용과 같은 DB 의 `billing_test` 스키마에서 돈다. 개발용 데이터(`billing` 스키마)를 건드리지 않는다.
스키마 이름은 `.env` 에서 읽지 않고 테스트 코드에 적혀 있다(`internal/testenv`). `.env` 에 무엇을 적든 테스트가 개발용 스키마로 가지 않는다.
**테스트용 스키마의 마이그레이션은 테스트가 스스로 적용한다.** `go test ./...` 만 돌리면 된다.
`billing_test` 스키마가 없다는 오류가 나면 [DB 계정과 스키마](#db-계정과-스키마)의 마지막 명령으로 만든다.

테스트는 테이블을 비우지 않는다. 테스트마다 새 사용자 번호를 만들어 쓰므로 서로의 줄이 섞이지 않는다.
원장은 지울 수 없게 막아 두었고, 그 막음도 테스트의 대상이다. 쌓인 줄을 치우려면 테스트용 스키마를 되돌렸다 다시 적용한다.

```
$env:DB_SCHEMA='billing_test'; go run ./cmd/migrate down; go run ./cmd/migrate up; Remove-Item Env:DB_SCHEMA
```

macOS, Linux 에서는 이렇게 한다.

```
DB_SCHEMA=billing_test go run ./cmd/migrate down && DB_SCHEMA=billing_test go run ./cmd/migrate up
```

커밋하기 전에 CI 와 같은 것을 돌린다.

```
gofmt -l .
go vet ./...
go test ./...
```

`gofmt -l .` 는 모양이 어긋난 파일의 이름을 찍는다. 아무것도 나오지 않아야 한다. 고칠 때는 `gofmt -w .` 다.

CI 는 테스트를 경쟁 감지기와 함께 돌린다(`go test -race`). 두 흐름이 같은 값을 동시에 건드리면 실패한다.
Windows 에서는 C 컴파일러(gcc)를 따로 깔아야 `-race` 가 돈다. 깔지 않았으면 로컬에서는 빼고 돌리고 CI 에 맡긴다.

무엇을 보는가.

- 설정(`internal/config`): 기본값, 틀린 값의 거부, 여러 오류를 한 번에 알리기, 오류에 값이 실리지 않는 것. DB 없이 돈다
- DB(`internal/database`): `billing` 계정으로 붙는지, `search_path`가 `billing` 하나인지, 자기 스키마 둘(`billing`, `billing_test`)에 테이블을 만들 수 있는지,
  **다른 서비스의 스키마(`auth`, `game`, `game_test`)에 들어갈 수 없는지**, DB 를 새로 만들 권한이 없는지,
  접속 주소가 틀렸을 때 오류에 주소가 실리지 않는 것, 풀을 만드는 것만으로는 연결하지 않는 것
- 공개키(`internal/jwks`): 문서에서 쓸 수 있는 키만 고르는 것, 가져오기의 실패(상태 코드, 형식, 크기, 시간 초과), 위의 규칙 넷,
  동시에 온 요청 50개가 인증 서버를 한 번만 부르는 것, 가져오는 동안에도 아는 키의 요청이 멈추지 않는 것
- 토큰(`internal/auth`): 멀쩡한 토큰의 통과, 위의 "확인하는 것" 하나하나의 거부, `none`·`HS256`·`RS512` 의 거부,
  키를 구할 수 없는 것과 토큰이 틀린 것을 다른 오류로 알리는 것
- 주소(`internal/httpapi`): `/me`의 200, 401, 503 과 머리말, 가짜 인증 서버와 실제 캐시·검증기를 이어 본 것,
  `/health`가 DB 를 부르지 않는 것, `/health/ready`의 200 과 503, 503 에 이유가 실리지 않는 것,
  DB 에 준 시간에 제한이 있는 것, 처리 중의 패닉이 500 으로 바뀌는 것,
  지갑 주소 둘의 200, 400, 401, 500, 토큰의 주인의 지갑만 읽는 것, 500 에 DB 의 오류가 실리지 않는 것, 실제 DB 까지 이어 본 것,
  주문 주소들의 201·200·202·400·404·409·500, 본문에 값이나 다른 사용자를 적어도 쓰지 않는 것, 응답에 결제 번호를 싣지 않는 것,
  알림 주소가 토큰 없이 서명만으로 받는 것, 서명이 틀리면 본문을 읽지도 않는 것, 사용자의 토큰이 서명을 대신하지 못하는 것,
  실제 주문 서비스·지갑·DB 로 주문 → 승인 → 잔액, 답이 없는 결제 → 알림 → 잔액까지 이어 본 것,
  환영 크레딧의 201·409·404·401, 요청에 양이나 다른 사용자를 적어도 쓰지 않는 것, GET 으로는 받지 못하는 것
- 양(`internal/credit`): 글자로 쓰고 읽는 규칙을 자릿수 0, 1, 4, 8 에서. 소수, 지수, 빈칸, 넘치는 값의 거부. JSON 에 글자로 나가는 것
- 마이그레이션(`internal/migrate`): 모든 파일이 테스트용 스키마에 적용되는 것, 다시 적용해도 되는 것, 넷이 한꺼번에 적용해도 부딪치지 않는 것,
  접속 주소가 틀렸을 때 오류에 주소가 실리지 않는 것
- 지갑(`internal/wallet`): 실제 PostgreSQL 에서 돈다. 시계는 테스트가 돌린다
  - 어디서 얼마씩 뺄지 정하는 계산(DB 없이): 두 가지 순서, 여러 묶음에 걸친 차감, 하나 모자랄 때의 거절, 큰 값에서 넘치지 않는 것
  - 넣기, 주기, 쓰기와 그때마다 원장에 적히는 줄. 모자라면 한 줄도 바뀌지 않는 것. 범위를 벗어난 양의 거절
  - 기한: 사라지기 바로 전(백만분의 1초 전)까지는 있고 그 순간에 없어지는 것, 묶음마다 따로 사라지는 것, 사라진 것을 쓸 수 없는 것,
    읽기가 아무것도 적지 않는 것, 다음 변경이 `expire` 줄을 한 번만 적는 것, 기한 설정을 바꿔도 이미 준 것은 그대로인 것
  - 동시성: 10 씩 스무 번을 한꺼번에 써서 열 번만 되는 것, 두 종류에 걸친 동시 차감, 지갑이 없는 사용자에게 한꺼번에 넣기,
    넣기·주기·쓰기를 섞은 뒤에도 지금의 값과 원장이 맞는 것
  - DB 가 스스로 막는 것([크레딧](#크레딧))을 SQL 을 직접 보내 하나하나 확인
  - 잔액을 확인하는 테스트는 그때마다 "지금의 값 = 원장의 합"도 함께 본다
  - 한 번만 주는 지급: 두 번째의 거절, 다 쓰거나 사라진 뒤에도 거절, 이름과 사용자마다 따로인 것,
    스무 요청이 함께 와도 한 번만 주는 것, 같은 이름의 둘째 줄을 DB 가 거절하는 것
  - 주문으로 넣기: 부르는 쪽의 트랜잭션이 되돌려지면 크레딧도 없던 일이 되는 것, 같은 주문으로 두 번 넣으면 DB 가 거절하는 것
- 상품(`internal/catalog`): 번호가 겹치지 않는 것, 값과 크레딧이 DB 와 지갑이 받는 범위인 것, 1원에 1크레딧인 것
- 결제 대행사(`internal/payment`): 가짜가 결제 번호의 앞머리대로 답하는 것. 알림의 서명이 본문, 시각, 비밀을 모두 덮는 것,
  모양이 틀린 서명과 오래된 서명과 미래의 서명의 거부, 비밀이 짧으면 아무 서명도 받지 않는 것
- 주문(`internal/order`): 실제 PostgreSQL 에서 돈다. 지갑은 진짜를 쓰고 결제 대행사만 정해 둔 대로 답하는 것으로 바꾼다
  - 만들기: 값과 크레딧이 상품 목록에서 오는 것, 같은 키로 다시 보내면 같은 주문인 것, 스무 요청이 같은 키로 함께 와도 주문이 하나인 것,
    같은 키로 다른 상품이면 거절, 키는 사용자마다 따로인 것
  - 승인: 승인되면 주문이 `paid` 가 되고 크레딧이 들어가고 원장이 그 주문을 가리키는 것, 거절되면 크레딧이 없는 것,
    결제 대행사에 주문의 값을 보내는 것, 다시 불러도 승인을 또 요청하지 않고 크레딧이 한 번인 것,
    다른 결제 번호로 바꿀 수 없는 것, 결제 한 건으로 주문 둘을 못 치르는 것, 남의 주문은 없는 주문과 같은 답인 것
  - 답을 받지 못했을 때: `confirming` 에 남고 오류도 실패도 아닌 것, 다시 부르면 승인이 아니라 조회로 끝내는 것(승인, 거절, 아직 모름 셋 다)
  - 함께 되거나 함께 안 되는 것: 크레딧을 넣다 실패하면 주문도 `paid` 가 안 되고, 다시 부르면 마저 끝나는 것
  - 동시성: 같은 결제 번호의 스무 요청이 함께 와도 승인 요청 한 번, 크레딧 한 번. 서로 다른 결제 번호의 열 요청은 하나만 주문을 차지하는 것
  - 요청을 보낸 쪽이 연결을 끊어도 끝까지 적는 것, 결제 대행사의 답을 10초까지만 기다리는 것
  - 알림: 결과를 모르던 주문을 끝내는 것, 여러 번 와도 크레딧이 한 번인 것, 끝낼 것이 없는 알림과 결제 번호가 다른 알림을 무시하는 것,
    결제 대행사에 묻지 못하면 오류인 것
  - DB 가 스스로 막는 것을 SQL 을 직접 보내 확인

## CI

`.github/workflows/billing-server.yml`. `billing-server/`나 DB 초기화 스크립트가 바뀐 PR 과 main 푸시에서 돈다.

1. DB 계정과 스키마 만들기 (로컬과 같은 초기화 스크립트. `auth`, `game` 도 만든다. 그 스키마에 못 들어가는지 테스트가 본다)
2. Go 설치 (`go.mod`에 적힌 버전)
3. `go.mod`와 `go.sum`이 코드와 맞는지 (`go mod tidy -diff`)
4. 모양 검사 (`gofmt -l .`)
5. 정적 검사 (`go vet ./...`)
6. 만들어진 코드가 SQL 과 맞는지 (`sqlc diff`)
7. 빌드 (`go build ./...`)
8. 마이그레이션을 개발용 스키마에 적용하고, 되돌리고, 다시 적용한다. 되돌리는 SQL 이 틀렸으면 여기서 드러난다
9. 테스트 (`go test -race ./...`). 경쟁 감지기를 켠다. 테스트용 스키마를 쓰므로 8번과 부딪치지 않는다

- `cmd/`는 실행 파일의 시작점, `internal/`은 이 서버 안에서만 쓰는 코드다. Go 는 `internal/` 아래의 패키지를
  다른 모듈이 가져다 쓰지 못하게 막는다. 서버끼리 코드를 나눠 쓰지 않는다는 약속을 컴파일러가 지킨다.
- 폴더 하나가 패키지 하나다. 파이썬의 파일 하나가 모듈인 것과 다르다. 같은 폴더의 파일들은 서로를 가져오지 않고 그냥 쓴다.
- `walletdb/` 와 `orderdb/` 의 파일에는 다른 파일처럼 맨 위의 경로 주석이 없다. 도구가 만드는 파일이라 `Code generated by sqlc. DO NOT EDIT.` 로 시작한다.

## 설계 메모

**웹 프레임워크는 gin 이다.** Go 에서 가장 널리 쓰여 자료와 예제가 많다. 요청의 JSON 을 구조체에 담고 검사하는 기능이 들어 있다.
대가는 핸들러가 gin 의 것(`*gin.Context`)을 받는다는 것이다. 그래서 gin 을 아는 코드는 `internal/httpapi` 안에만 둔다.
설정, DB, 그리고 앞으로 만들 원장과 주문의 코드는 gin 을 모른다.

**미들웨어를 직접 고른다(`gin.New`).** `gin.Default()`는 요청 기록과 패닉 복구를 붙여서 준다. 같은 둘을 직접 붙였다.
무엇이 붙었는지가 `NewRouter` 한 곳에서 보이고, 뒤에 인증이나 요청 ID 를 더할 자리가 분명하다.

**DB 는 pgx 로 쓴다.** PostgreSQL 전용 드라이버다. 연결 풀(`pgxpool`)이 들어 있다.
SQL 을 직접 쓴다. 결제는 잠금(`FOR UPDATE`)과 조건이 붙은 `UPDATE` 한 줄 한 줄이 정합성을 지키는 곳이라, 실행되는 SQL 이 보여야 한다.

**SQL 은 손으로 쓰고, 그것을 부르는 Go 코드는 sqlc 가 만든다.** ORM 은 SQL 을 대신 만들어 줘서 무엇이 실행되는지가 가려진다.
SQL 을 Go 문자열로 적고 결과를 손으로 옮겨 담으면, 칸의 순서나 타입이 어긋나도 실행해 봐야 안다.
sqlc 는 마이그레이션 파일에서 테이블의 모양을 읽어 쿼리마다 타입이 맞는 함수를 만든다. 칸 이름을 틀리면 코드를 만들 때 실패한다.
대가는 도구가 하나 늘고, 만들어진 코드를 커밋해 두어야 한다는 것이다. 어긋나는지는 CI 가 본다.

**마이그레이션은 goose 를 라이브러리로 넣어 `cmd/migrate` 로 돌린다.** goose 를 명령 줄 도구로 따로 깔아 쓰는 길도 있다.
그 길은 서버의 의존성이 늘지 않지만, 사람마다 도구를 깔아 버전을 맞춰야 하고 접속 주소를 명령 줄이나 환경 변수로 넘겨야 한다.
라이브러리로 넣으면 `go run ./cmd/migrate up` 하나로 끝나고, 서버와 같은 `.env` 를 읽고, 테스트가 테스트용 스키마를 스스로 맞출 수 있다.
대가는 `go.mod` 에 goose 가 들어오고, goose 가 요구하는 버전에 맞춰 함께 쓰는 의존성 몇 개(`golang.org/x/...`)의 버전이 올라간 것이다.
goose 가 지원하는 다른 DB 의 드라이버는 실행 파일에 들어가지 않는다. 가져다 쓰는 패키지만 빌드된다.

**서버가 뜰 때 마이그레이션을 저절로 적용하지 않는다.** 서버를 여러 대 띄우면 저마다 테이블을 바꾸려 든다.
배포와 스키마 변경을 따로 되돌릴 수도 없다. 사람이 명령으로 적용한다. 다만 두 곳에서 한꺼번에 돌려도 안전하게 DB 의 잠금(advisory lock)을 건다.

**잔액을 지갑에 들고 있고, 원장은 기록이다.** 원장만 두고 조회할 때마다 합치는 길도 있다. 테이블이 하나라 어긋날 일이 없다.
그 대신 두 요청이 한꺼번에 잔액보다 많이 쓰려 할 때 잠글 줄이 없고, 원장이 길어질수록 조회가 느려진다.
지갑의 줄을 두면 그 줄을 잠가 같은 사용자의 변경을 줄 세울 수 있고, 잔액이 0 아래로 내려가는 것을 DB 의 `CHECK` 가 막는다.
대가는 지갑과 원장이 어긋날 수 있다는 것이다. 그래서 둘을 늘 같은 트랜잭션에서, 한 함수 안에서 함께 바꾼다(`write.go` 의 `movePaid`, `takeFromGrant`, `openGrant`).
어긋났는지 주기적으로 맞춰 보는 일(대사)은 7단계다. 게임 서버가 "지금의 상태가 기준이고 이벤트는 기록"으로 둔 것과 같은 구조다.

**무료 크레딧은 잔액 하나가 아니라 지급 묶음들이다.** 기한이 없다면 산 크레딧처럼 지갑에 칸 하나를 더 두면 된다.
기한이 있으면 "30 가운데 10 은 내일, 20 은 엿새 뒤에 사라진다"를 알아야 해서 지급마다 줄이 필요하다.
무료 크레딧의 잔액을 지갑에 따로 들고 있지 않는 이유도 기한이다. 들고 있으면 사라지는 바로 그 순간에 누군가 그 칸을 줄여 줘야 한다.
그 작업이 늦으면 그동안 잔액이 틀린다. 읽을 때 "아직 사라지지 않은 줄의 합"을 구하면 늘 맞다.
살아 있는 묶음은 사용자마다 몇 개뿐이고(1주일 안에 받은 것), 그것만 찾는 색인을 두었다.

**시각은 DB 의 `now()` 가 아니라 서버가 넘긴다.** 만료는 "지금"과 견주는 일이라 시계가 둘이면 경계에서 어긋난다.
서비스가 시계를 밖에서 받으므로(`wallet.NewService` 의 `now`), 테스트가 1주일을 기다리지 않고 시계를 돌려 본다.
넘기기 전에 UTC, 백만분의 1초로 맞춘다. DB 가 적는 정밀도와 같게 해야 방금 적은 시각과 다시 읽은 시각이 같다.

**어디서 뺄지 정하는 계산과, 그대로 빼는 일을 나눈다.** `plan.go` 는 숫자만 받아 계획을 돌려준다. DB 를 모른다.
쓰는 순서 같은 규칙이 여기에만 있어서 DB 없이 경우를 다 시험할 수 있다. `write.go` 는 계획대로 뺄 뿐이다.

**결제 대행사를 부르는 동안 DB 트랜잭션을 열어 두지 않는다.** 주문의 줄을 잠근 채로 다른 서버의 답을 기다리면,
그 서버가 느려질 때 이 서버의 DB 연결이 바닥난다. 그래서 일을 셋으로 나눈다. 부르기 전에 `confirming` 으로 적고(짧은 문장 하나),
결제 대행사를 부르고(트랜잭션 밖), 답을 받은 뒤 새 트랜잭션에서 결과를 적는다.
대가는 그 사이에 서버가 죽으면 주문이 `confirming` 에 남는다는 것이다. 그 주문은 결과를 모르는 주문과 같은 길로 끝낸다.
`confirming` 이라는 상태가 따로 있는 까닭이 이것이다. "결제 대행사를 불렀을 수도 있다"는 표시가 없으면, 죽었다 살아난 서버가
그 주문을 치르지 않은 주문으로 알고 다른 결제를 받는다.

**상태는 "지금 이 상태일 때만" 바꾼다.** `UPDATE ... WHERE status = 'confirming'` 처럼 조건을 달고, 바뀐 줄을 돌려받았는지 본다.
같은 요청 스무 개가 함께 와도 한 요청만 줄을 돌려받고, 그 요청만 크레딧을 넣는다. 먼저 읽고 나서 바꾸는 방식은 읽은 뒤에 남이 바꿀 수 있다.
그 위에 DB 가 한 번 더 막는다. 원장은 주문 하나에 충전 줄 하나만 받는다(`ledger_entries_order_once`).
코드가 틀려 같은 주문을 두 번 처리해도 둘째는 거절되고, 그 트랜잭션이 통째로 되돌려진다.

**주문을 치르는 일과 크레딧을 넣는 일은 한 트랜잭션이다.** 주문 서비스가 트랜잭션을 열고, 그것을 지갑에 넘겨 그 안에서 넣게 한다
(`wallet.DepositForOrder`). 지갑이 스스로 트랜잭션을 열면 "주문은 치렀는데 크레딧이 없다"가 생길 수 있다.
잠그는 순서는 늘 주문의 줄 다음에 지갑의 줄이다. 지갑만 잠그는 다른 변경과 서로를 기다리며 멈추는 일(교착)이 없다.

**중복 방지 키는 주문을 만들 때만 받는다.** 승인 요청은 받지 않는다. 주문 번호와 결제 번호가 이미 그 요청을 가리켜서,
같은 요청을 다시 보내면 스스로 같은 결과가 된다. 주문을 만드는 요청은 그런 번호가 없어서 클라이언트가 키를 붙여야 한다.
키를 DB 의 유일 제약으로 지킨다(`INSERT ... ON CONFLICT DO NOTHING`). 먼저 있는지 읽고 없으면 넣는 방식은 두 요청이 함께 "없다"를 읽는다.

**답을 받지 못한 결제를 다시 부르면 승인이 아니라 조회를 한다.** 승인을 또 요청하면 결제 대행사에 따라 돈이 두 번 나간다.
조회는 몇 번을 해도 안전하다.

**알림(웹훅)의 본문을 믿지 않는다.** 서명은 "결제 대행사가 보냈다"를 알려 주지만, 비밀이 새면 누구나 만들 수 있다.
그래서 알림은 "이 주문을 다시 봐라"는 신호로만 쓰고, 결과는 결제 대행사에 직접 묻는다.
승인 요청을 다시 받았을 때와 같은 코드가 돈다. 결과를 적는 길이 하나라서 두 길이 다르게 굴 일이 없다.

**요청을 보낸 쪽이 연결을 끊어도 승인은 끝까지 간다.** 결제 대행사가 돈을 받은 뒤에 사용자가 창을 닫을 수 있다.
그때 멈추면 답을 받고도 적지 못한다. 그래서 승인과 알림의 처리는 요청의 취소를 따라가지 않는다(`context.WithoutCancel`).
끝없이 기다리지는 않는다. 결제 대행사의 답은 10초까지만 기다린다.

**결제 대행사는 모양(`payment.Provider`)만 알린다.** 주문의 코드는 가짜인지 진짜인지 모른다.
가짜는 결제 번호의 앞머리로 답을 정하고 기억하는 것이 없다. 실제 결제 대행사의 테스트용 카드 번호와 같은 생각이다.
기억이 없으니 서버를 다시 띄워도 여러 대를 띄워도 같은 답이 나온다. 대가는 금액이 맞는지를 가짜가 보지 못한다는 것이다.

**상품을 코드에 둔다.** DB 에 두면 배포 없이 가격을 바꿀 수 있지만, 그것을 고치는 관리 화면과 권한이 있어야 쓸모가 있다. 지금은 없다.
주문이 만들 때의 값과 크레딧을 스스로 적어 두므로, 나중에 DB 로 옮겨도 지난 주문은 그대로다.

**"한 번만"을 지급 묶음의 이름과 DB 의 유일 색인으로 지킨다.** 지갑에 "환영 크레딧을 받았다"는 칸을 두는 길도 있다.
그러면 한 번만 주는 지급이 생길 때마다 칸이 늘어난다. 이름은 글자라서 새 지급에 마이그레이션이 필요 없다.
코드는 지갑의 줄을 잠근 채로 받은 적이 있는지 먼저 본다. 색인은 그 확인이 빠졌을 때의 두 번째 막음이다.
받은 것이 남아 있는지가 아니라 받은 적이 있는지를 본다. 남은 것을 보면 다 쓴 사람이 또 받는다.

**환영 크레딧은 POST 로만 받는다.** 주소를 여는 것(GET)만으로 상태가 바뀌면, 링크를 미리 읽는 프로그램이나 검색 로봇이 대신 받아 버린다.

**지갑을 읽는 주소는 읽는 것만 받는다(`WalletReader`).** 핸들러가 받는 것에 넣기와 쓰기가 없다.
잔액을 보여 주는 주소가 실수로 크레딧을 바꾸는 코드는 컴파일되지 않는다.

**서명 검증은 라이브러리에 맡기고, 키를 기억하는 부분만 직접 쓴다.** 서명을 확인하는 코드는 직접 쓰지 않는다(`golang-jwt`).
키를 언제 가져오고 얼마나 기억할지는 직접 쓴다. 키 캐시가 든 라이브러리는 기본 동작이 이 프로젝트의 규칙과 다르다
(뒤에서 스스로 주기적으로 다시 받고, 모르는 `kid` 의 요청을 기다리게 한다). 맞추려면 옵션과 그 옵션의 테스트가 다시 필요하다.
직접 쓰면 게임 서버와 같은 규칙을 그대로 옮길 수 있고, 여기에 버그가 있어도 "가짜 토큰이 통과한다"가 아니라 "검증이 멈춘다" 쪽으로 드러난다.

**동시에 온 요청은 `singleflight` 로 묶는다.** 키가 없을 때 요청 여럿이 동시에 오면 한 번만 가져오고 나머지는 그 결과를 기다린다.
기다리지 않고 지나가면 키가 아직 없어서 멀쩡한 토큰을 거부한다. 게임 서버에서 처음에 났던 버그다. Go 팀의 패키지(`golang.org/x/sync/singleflight`)에 맡긴다.
가져오는 동안 잠금을 쥐지 않는다. 쥐고 있으면 그동안 아는 키로 온 요청까지 멈춘다.
가져오는 일은 먼저 온 요청의 취소를 따라가지 않는다. 한 사용자가 연결을 끊었다고 같이 기다리던 요청들의 가져오기가 실패하면 안 된다.

**로그인이 필요한 주소는 묶음에 미들웨어를 한 번 붙인다.** `/api/v1/billing` 아래의 주소에 하나씩 붙이지 않는다.
새 주소를 더하면서 검증을 빠뜨리는 일이 없다. FastAPI 의 `Depends` 는 함수마다 적지만, gin 은 주소의 묶음에 붙이는 방식이 기본이다.

**풀을 전역 변수로 두지 않는다.** `cmd/server`가 만들어 라우터에 넘기고, 끌 때 닫는다. 게임 서버가 엔진을 `app.state`에 두는 것과 같은 이유다.
테스트가 가짜 DB 를 넣은 라우터를 여러 개 만들 수 있다.

**풀을 만드는 것만으로는 DB 에 연결하지 않는다.** DB 가 죽어 있어도 서버는 뜨고, `/health/ready`가 503 으로 그 사실을 알린다.
뜨는 순서에 기대지 않는다.

**다른 서비스의 테이블은 DB 권한이 막는다.** `billing` 계정은 `auth`, `game` 스키마에 들어갈 권한이 없다.
`search_path`를 `billing` 하나로 맞추지만 그것은 이름을 줄여 쓰게 해 줄 뿐이다. 스키마 이름을 붙여 쓰면 어디든 가리킬 수 있다.
막는 것은 권한이고, 테스트가 그 권한을 확인한다. 거꾸로 다른 서버의 계정도 `billing` 스키마에 들어오지 못한다.
잔액은 결제 서버의 API 로만 읽고 바꾼다.

**설정을 읽는 곳을 밖에서 받는다.** `config.Load`는 "이름으로 값을 찾는 함수"를 받는다. 서버는 `os.LookupEnv`를, 테스트는 맵을 넘긴다.
테스트가 개발자의 `.env`나 환경 변수에 흔들리지 않는다.

**종료 신호에 차례로 끈다.** `Ctrl+C`나 `SIGTERM`을 받으면 새 요청을 받지 않고, 처리 중인 요청을 10초까지 기다린 뒤 풀을 닫는다.
결제 요청이 처리 도중에 끊기는 일을 줄인다. 끊겨도 돈이 맞게 하는 것은 뒤에 넣을 중복 방지 키의 일이다.

**`main` 과 `run` 을 나눈다.** `log.Fatal`은 프로세스를 바로 끝내서 `defer`가 돌지 않는다.
`run`이 오류를 돌려주면 풀을 닫고 나서 끝난다.

**테스트는 같은 DB 의 다른 스키마(`billing_test`)에서 돈다.** 게임 서버, 게시판 서버와 같은 방식이다.
테스트용 DB 를 새로 만들려면 계정에 DB 를 만드는 권한을 줘야 한다. 스키마를 나누면 그 권한이 필요 없다.
다른 두 서버는 테스트 전에 테스트용 스키마에 마이그레이션을 손으로 적용한다. 이 서버는 테스트가 스스로 적용한다.
마이그레이션이 실행 파일에 들어 있어서 할 수 있는 일이다.
