# 인증 서버

[![auth-server](https://github.com/epqlffltm/ai-trpg/actions/workflows/auth-server.yml/badge.svg)](https://github.com/epqlffltm/ai-trpg/actions/workflows/auth-server.yml)

[ai-trpg](../README.md)의 인증 서버. 회원가입, 로그인, 토큰 발급을 맡는다. Django와 DRF로 만들었다.
다른 서버는 이 서버가 발급한 토큰을 공개키로 검증만 한다.
휴대폰 본인인증과 나이(성인 여부)도 맡는다. 본인인증을 마친 사용자에게 환영 크레딧을 주라고 [결제 서버](../billing-server/README.md)에 맡기는 일도 한다.
이 서버가 다른 서버를 부르는 것은 그것 하나다.

## 실행

공용 인프라(PostgreSQL, Redis)가 떠 있어야 한다. 띄우는 방법은 [루트의 설명서](../README.md#실행)에 있다.
명령은 저장소 루트에서 시작한다고 보고 적었다. 파일 경로도 저장소 루트 기준이다.

### 설치와 실행

```
cd auth-server
cp .env.example .env
uv sync
```

`auth-server/.env`에 `SECRET_KEY`를 채우고, `DATABASE_URL`의 비밀번호를
루트 `.env`의 `AUTH_DB_PASSWORD`와 같은 값으로 맞춘다.

JWT 서명용 개인키를 만든다. `keys/jwt-private.pem`에 저장되고 커밋되지 않는다.
파일은 주인만 읽을 수 있는 권한(`0600`)으로 만들어진다.

```
uv run python scripts/generate_jwt_key.py
```

```
uv run python manage.py migrate
uv run python manage.py createsuperuser
uv run python manage.py runserver
```

`http://127.0.0.1:8000/admin/` 에서 관리자 화면에 로그인한다.

메일 설정을 하지 않으면 메일은 실제로 나가지 않고 `runserver`를 띄운 터미널에 출력된다.
인증 코드는 거기서 읽는다. 실제로 보내려면 아래 "메일 발송"을 따른다.

### 메일 발송 (선택)

`auth-server/.env`에 메일 서버 설정을 넣는다. Gmail이라면 2단계 인증을 켠 뒤
[앱 비밀번호](https://myaccount.google.com/apppasswords)를 만들어 넣는다. 계정의 비밀번호가 아니다.

```
SMTP_HOST=smtp.gmail.com
SMTP_USER=내주소@gmail.com
SMTP_PASSWORD=앱비밀번호16자리
DEFAULT_FROM_EMAIL=AI TRPG <내주소@gmail.com>
```

메일 서버 설정이 있으면 서버는 메일을 직접 보내지 않고 발송함(DB)에 적기만 한다.
보내는 것은 워커다. 서버와 따로 띄운다.

```
uv run python manage.py send_outgoing_mail
```

### 환영 크레딧 (선택)

휴대폰 본인인증을 마친 사용자는 결제 서버에서 무료 크레딧(실버)을 한 번 받는다(#336). 주는 것은 결제 서버고,
이 서버는 "이 사용자에게 주라"고 맡긴다. 설정하지 않아도 가입과 로그인은 된다. 맡길 일이 DB 에 쌓여 있다가 설정한 뒤에 나간다.

`auth-server/.env`에 두 값을 적는다.

```
BILLING_URL=http://127.0.0.1:8003
BILLING_SECRET=결제 서버의 AUTH_SERVER_SECRET 과 같은 값
```

`BILLING_SECRET`은 두 서버만 아는 비밀이다. 32자 이상이다. 요청에 서명할 때 쓰고, 결제 서버가 보낸 보호자 결제 알림의 서명을 확인할 때도 쓴다(#352).
설정의 이름은 게임 서버와 같다(`BILLING_URL`, `BILLING_SECRET`). 결제 서버를 부르는 서버는 같은 이름을 쓴다. **값은 서버마다 다르다.**
게임 서버의 값은 결제 서버의 `GAME_SERVER_SECRET`, 이 서버의 값은 `AUTH_SERVER_SECRET` 과 짝이다.
결제 서버의 `.env`에 `AUTH_SERVER_SECRET`으로 같은 값이 있어야 한다. 값을 화면에 찍지 않고 두 파일에 함께 넣으려면
저장소 루트에서 아래를 실행한다(PowerShell).

```
$b = New-Object byte[] 32; [Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); $s = [BitConverter]::ToString($b).Replace('-','').ToLower(); Add-Content auth-server/.env "`nBILLING_SECRET=$s"; Add-Content billing-server/.env "`nAUTH_SERVER_SECRET=$s"; Remove-Variable s, b
```

macOS, Linux 에서는 이렇게 한다.

```
s=$(openssl rand -hex 32); printf '\nBILLING_SECRET=%s\n' "$s" >> auth-server/.env; printf '\nAUTH_SERVER_SECRET=%s\n' "$s" >> billing-server/.env; unset s
```

이 설정의 이름은 처음에 `BILLING_SERVICE_SECRET` 이었다. 그 이름으로 적어 둔 `.env` 는 아래 한 줄로 새 이름의 줄을 더한다(값은 찍히지 않는다).
옛 줄은 쓰이지 않으니 지워도 된다.

```
$s = (Select-String -Path auth-server/.env -Pattern '^BILLING_SERVICE_SECRET=(.+)$').Matches[0].Groups[1].Value; Add-Content auth-server/.env "`nBILLING_SECRET=$s"; Remove-Variable s
```

```
s=$(sed -n 's/^BILLING_SERVICE_SECRET=//p' auth-server/.env); printf '\nBILLING_SECRET=%s\n' "$s" >> auth-server/.env; unset s
```

맡기는 것은 워커다. 서버와 따로 띄운다. 결제 서버도 떠 있어야 한다.
같은 워커가 결제 자격(성년이 되는 날, 보호자 동의)도 결제 서버에 알린다(설계 메모의 "결제 자격 알림").

```
uv run python manage.py send_welcome_credits
```

#336 전에는 이메일 인증 때 받았다. 그때 받은 계정은 본인인증을 해도 다시 받지 않는다.
그 무렵의 관리 명령 `request_welcome_credits`(이미 가입한 계정에 적기)는 없앴다. 이제 받을 계정은 본인인증 때 적힌다.

### 본인인증 (가짜 업체)

휴대폰 본인인증은 본인확인 업체(NICE, KCB 같은 곳)의 화면에서 하고, 받은 글자(`token`)를 이 서버에 낸다.
실제 업체는 사업자 계약이 있어야 붙일 수 있어서 지금은 가짜 업체(`IDENTITY_PROVIDER=fake`)뿐이다.
개발 환경은 적지 않아도 가짜 업체로 뜬다. 가짜 업체는 `token` 에 적힌 DI 와 생일을 그대로 믿는다.

```
fake:<DI>:<생일 YYYY-MM-DD>      예: fake:person-1:1990-05-17
```

DI 는 업체가 사람마다 주는 값이다. 같은 DI 는 같은 사람이다. 영문, 숫자, `+/=_-` 로 128자까지 쓴다.
운영(`APP_ENVIRONMENT=production`)에서는 가짜 업체를 고를 수 없다(서버가 뜨지 않는다). 적지 않으면 `disabled` 로 떠서
본인인증이 `503`(`code: identity_unavailable`)으로 끝난다. 가짜 업체를 운영에서 쓰면 누구나 아무 생일이나 적어 성인이 된다.
`staging`(VM 에 올린 운영자용 서버)에서는 가짜 업체로 뜬다. 남이 들어오는 것은 nginx 의 허용 주소가 막는다.

### 테스트

실제 PostgreSQL과 Redis에서 돈다. 인프라가 떠 있어야 한다.

```
cd auth-server
uv run python manage.py test
```

테스트가 지나간 줄의 비율(커버리지)은 이렇게 본다. 재는 대상은 `pyproject.toml` 의 `[tool.coverage.run]` 이다(마이그레이션과 테스트는 뺀다).

```
uv run coverage run manage.py test
uv run coverage report
```

테스트에서는 비밀번호 해셔를 가벼운 것으로 바꾼다(`config/test_runner.py`). 기본 해셔는 일부러
느리게 만든 계산이라 가입과 로그인을 반복하는 테스트 시간의 대부분을 차지한다.
당시 137개 기준 122.0초에서 4.5초로 줄었다. `runserver`와 측정 스크립트는 원래의 해셔를 쓴다.

시도 횟수 제한도 테스트에서는 꺼 둔다. 켜 두면 로그인을 반복하는 테스트가 서로를 막는다.
제한을 검증하는 테스트만 켜고 돌며, 개발용 횟수와 섞이지 않게 Redis 키의 앞머리를 따로 쓴다.

테스트 실행기는 테스트용 DB(`test_trpg`)를 만들고 지운다. 그래서 `auth` 계정에 `CREATEDB` 가 있어야 한다.
이 권한은 개발과 CI 에서만 준다. 루트 `.env` 의 `AUTH_DB_ALLOW_TEST_DB=true` 로 DB 볼륨을 처음 만들 때 붙는다(#20).

### 린트와 모양

```
cd auth-server
uv run ruff check .
uv run ruff format .
```

규칙은 저장소 루트의 `ruff.toml` 이다. 게임 서버와 같은 규칙과 모양(작은따옴표, 한 줄 120자)을 쓴다.
`ruff check`는 쓰지 않는 import나 정의되지 않은 이름 같은 문제를 실행하지 않고 찾고, `ruff format`은 모양을 맞춘다.
커밋하기 전에 둘 다 돌린다. CI 는 고치지 않고 검사만 한다.
Django 가 만든 마이그레이션(`accounts/migrations/`)은 손으로 쓴 코드가 아니라 둘 다 건너뛴다.

## API

인증 서버의 API는 `/api/v1/auth/` 아래에 있다. 요청과 응답은 JSON이다.

| 메서드 | 경로 | 설명 | 인증 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/signup` | 가입 1단계. 이메일로 인증 코드를 보냄(다시 보내기도 이것) | 불필요 |
| POST | `/api/v1/auth/signup/verify` | 가입 2단계. 인증 코드 확인. 가입 티켓 발급 | 불필요 |
| POST | `/api/v1/auth/signup/complete` | 가입 3단계. 아이디, 닉네임, 비밀번호, 만 14세 이상 확인, 동의로 계정 생성 | 가입 티켓 |
| POST | `/api/v1/auth/login` | 로그인 시작. 비밀번호를 확인하고 인증 코드를 메일로 보냄 | 불필요 |
| POST | `/api/v1/auth/login/verify` | 인증 코드 확인. access 토큰과 refresh 쿠키 발급 | 로그인 티켓 |
| POST | `/api/v1/auth/login/resend` | 로그인 인증 코드 재발송 | 로그인 티켓 |
| POST | `/api/v1/auth/password/change` | 비밀번호 변경. 다른 기기는 로그아웃 | 필요 |
| POST | `/api/v1/auth/password/reset` | 비밀번호 재설정 링크를 메일로 보냄 | 불필요 |
| POST | `/api/v1/auth/password/reset/confirm` | 재설정 링크의 토큰으로 새 비밀번호 설정 | 재설정 토큰 |
| POST | `/api/v1/auth/refresh` | refresh 쿠키로 새 access 토큰 발급 | refresh 쿠키, 허용한 Origin |
| POST | `/api/v1/auth/logout` | 이 기기의 refresh 토큰 폐기 | refresh 쿠키, 허용한 Origin |
| POST | `/api/v1/auth/logout-all` | 모든 기기의 세션 종료 | 필요 |
| GET | `/api/v1/auth/jwks` | 토큰 검증용 공개키 목록 | 불필요 |
| GET | `/api/v1/auth/session-revocations` | 끊긴 세션의 목록. 다른 서버가 만료 전의 토큰을 거부하는 데 쓴다 | 불필요 |
| GET | `/api/v1/auth/me` | 내 계정 정보와 본인인증 상태 | 필요 |
| GET | `/api/v1/auth/public-names?ids=` | 다른 사람의 닉네임을 공개 ID 로 한꺼번에 찾음(100개까지) | 불필요 |
| GET | `/api/v1/auth/consents` | 동의를 받는 항목마다 지금의 판(이용약관, 개인정보 수집·이용, 선택 동의) | 불필요 |
| GET | `/api/v1/auth/me/consents` | 내 동의 상태(항목마다) | 필요 |
| PUT | `/api/v1/auth/me/consents/{item}` | 그 항목에 동의한다. 본문 `{"version": 1}` | 필요 |
| DELETE | `/api/v1/auth/me/consents/{item}` | 선택 항목의 동의를 철회한다 | 필요 |
| POST | `/api/v1/auth/identity/verify` | 휴대폰 본인인증. 본인확인 업체에서 받은 `token` 을 낸다 | 필요 |
| POST | `/api/v1/auth/guardian/request` | 미성년자가 보호자에게 결제 동의를 부탁한다. 보호자의 메일로 동의 링크가 간다 | 필요 |
| POST | `/api/v1/auth/guardian/consent` | 보호자가 동의한다. 메일의 동의 링크와 보호자의 본인인증 | 동의 링크 |
| POST | `/api/v1/auth/guardian/revoke` | 보호자가 동의를 철회한다 | 철회 링크 |

API 밖에 상태 확인 주소가 둘 있다. 다른 세 서버와 같은 뜻이다(`config/health.py`).
`GET /health` 는 늘 200, `GET /health/ready` 는 DB 에 닿으면 200, 닿지 않으면 503 이다. 바깥에서는 프록시가 막는다.
둘 다 HEAD 도 받는다(본문 없이 같은 상태 코드). 확인 요청이 끝난 줄은 성공이면 `debug`, 503 이면 `warning` 이라 운영의 로그를 메우지 않는다(`docs/observability.md` 의 "요청이 끝난 줄").

인증이 필요한 API에는 `Authorization: Bearer <access_token>` 헤더를 붙인다.

회원가입은 세 단계다(#271). 이메일의 주인임을 먼저 확인하고, 계정은 마지막에 만든다.

1. `/signup`에 `email`을 보낸다. `202`가 오고, 그 이메일로 6자리 인증 코드가 간다. 코드는 5분 동안 유효하다.
   코드를 다시 받을 때도 이것을 부른다. 코드는 1분에 1통, 1시간에 5통까지만 나간다
2. `/signup/verify`에 `email`, `code`를 보낸다. `200`과 함께 가입 티켓(`signup_ticket`)이 온다. 티켓은 30분 동안 유효하다.
   아직 계정은 없다. 코드가 틀리면 `400`이고, 다섯 번 틀리면 그 코드는 버려진다
3. `/signup/complete`에 `signup_ticket`, `username`, `nickname`, `password`, `age_over_14`(`true`), `consents` 를 보낸다. `201`이 오면 가입이 끝나 로그인할 수 있다.
   `age_over_14` 는 "만 14세 이상입니다" 확인이다. `false` 이거나 없으면 `400` 이다. 자기 신고라 실제 나이는 본인인증에서 다시 본다.
   `consents` 는 동의한 항목과 그 판이다(`{"terms": 1, "privacy": 1, "marketing": 1}`). 필수 항목(`terms`, `privacy`)이 없거나,
   판이 지금의 것(`GET /consents`)이 아니거나, 모르는 항목이면 `400` 이다. 넣지 않은 선택 항목은 동의하지 않은 것이다. 아래 [동의](#동의)
   아이디, 닉네임, 비밀번호가 규칙에 맞지 않거나 아이디나 닉네임이 겹치면 `400`으로 어느 값인지 알려 준다. 티켓은 그대로 다시 쓸 수 있다

`/signup`은 새 이메일이든 이미 가입된 이메일이든 같은 `202` 응답을 준다. 이미 가입된
이메일이면 코드 대신 그 주소로 안내 메일을 보낸다. 가입된 이메일로는 코드를 받을 수 없으니 2단계에서 막힌다.

| 3단계의 응답 | 뜻 |
| --- | --- |
| `201` | 가입을 마쳤다. 로그인한다(로그인도 이메일 코드를 받는다) |
| `400` 필드 오류 | 아이디, 닉네임, 비밀번호, 만 14세 이상 확인, 동의(`consents`) 중 그 값을 받을 수 없다 |
| `400` `code: signup_ticket_invalid` | 티켓이 틀렸거나 만료됐다. 1단계부터 다시 한다 |
| `409` `code: email_registered` | 그 이메일로 이미 가입을 마쳤다(같은 티켓을 두 번 썼다) |
| `409` | 방금 다른 가입이 같은 아이디, 닉네임 또는 이메일을 가져갔다 |

로그인도 두 단계다.

1. `/login`에 `username`, `password`를 보낸다. `202`와 `login_ticket`이 오고,
   가입한 이메일로 6자리 인증 코드가 간다. 토큰은 아직 나오지 않는다
2. `/login/verify`에 `login_ticket`, `code`를 보낸다. `200`과 함께 `access_token`, `token_type`,
   `expires_in`이 오고 refresh 쿠키가 설정된다

`/login`의 실패 응답은 세 가지다.

| 상태 | 뜻 |
| --- | --- |
| `401` | 아이디가 없거나 비밀번호가 틀렸다. 둘을 구분하지 않는다 |
| `403` `code: email_not_verified` | 비밀번호는 맞지만 가입 이메일 인증을 끝내지 않았다 |
| `429` `code: login_code_unavailable` | 비밀번호는 맞지만 코드를 지금은 보낼 수 없다. `retry_after`(초) 뒤에 다시 시도한다 |

`login_ticket`은 10분 동안 유효하다. 쓸 수 없는 티켓에는 `401`과 `code: login_ticket_invalid`가 오고,
그때는 `/login`부터 다시 한다. 코드는 1분에 1통, 1시간에 5통까지 나간다. 코드를 맞게 쓰면
1분 대기는 풀려서, 로그아웃한 직후나 다른 기기에서 바로 다시 로그인할 수 있다.

비밀번호를 바꾸는 방법은 두 가지다.

| | 변경 (`/password/change`) | 재설정 (`/password/reset`) |
| --- | --- | --- |
| 상황 | 로그인한 상태 | 비밀번호를 잊어 로그인하지 못함 |
| 본인 확인 | access 토큰과 현재 비밀번호 | 메일로 받은 링크의 토큰 |
| 요청 본문 | `current_password`, `new_password` | 요청은 `email`, 확인은 `email`, `token`, `new_password` |
| 끝난 뒤 | 다른 기기만 로그아웃. 이 기기는 새 토큰을 받음 | 모든 기기 로그아웃. 새 비밀번호로 로그인 |

`/password/reset`은 가입된 주소든 아니든 같은 `202` 응답을 준다. 가입된 주소면 재설정 링크가 간다.
링크는 `PASSWORD_RESET_URL#email=...&token=...` 모양이고 30분 동안, 한 번만 쓸 수 있다.
링크가 가리키는 곳은 프론트의 재설정 화면이다. 그 화면이 `#` 뒤의 값을 읽어
`/password/reset/confirm`에 보낸다. 비밀번호가 바뀌면 어느 쪽이든 계정의 이메일로 알림이 간다.

본인인증(#336)은 로그인한 뒤에 한다. `/identity/verify` 에 본인확인 업체에서 받은 `token` 을 보낸다.
계정마다 한 번, 사람마다 한 계정이다. 인증을 마치면 환영 크레딧이 적힌다.

| 응답 | 뜻 |
| --- | --- |
| `201` | 인증을 마쳤다. 본문의 `identity` 가 상태다(아래). 토큰은 다시 주지 않는다. `/refresh` 를 부르면 `adult_content` 가 실린 토큰이 온다 |
| `400` `code: identity_token_invalid` | 업체가 그 `token` 을 모른다. 업체의 화면부터 다시 한다 |
| `403` `code: identity_under_age` | 만 14세 미만이다. 계정을 막고 가입할 때 받은 정보를 지웠다. 세션이 끊기고 refresh 쿠키가 지워진다 |
| `409` `code: identity_already_verified` | 이 계정은 이미 인증했다 |
| `409` `code: identity_in_use` | 다른 계정이 이미 그 사람으로 인증했다 |
| `503` `code: identity_unavailable` | 지금은 본인인증을 받지 않는다(`IDENTITY_PROVIDER=disabled`) |

`/me` 와 인증의 응답에 실리는 상태는 이런 모양이다. 날짜는 한국 날짜로 그날그날 다시 센다.
미성년자도 그날이 지나면 다시 인증하지 않아도 저절로 바뀐다.

```json
"identity": {"verified": true, "legal_adult": false, "adult_content": true}
```

| 칸 | 뜻 | 기준 |
| --- | --- | --- |
| `verified` | 본인인증을 마쳤다 | |
| `legal_adult` | 민법의 성년이다. 결제가 본다 | 만 19세 생일부터 |
| `adult_content` | 성인용 내용을 볼 수 있다 | 만 19세가 되는 해의 1월 1일부터(청소년 보호법) |

본인인증을 하지 않은 계정은 셋 다 `false` 다. 나이를 모르면 성인으로 보지 않는다.
`/me` 에는 보호자 동의의 상태(`guardian_consent`)도 실린다. `none`(요청한 적 없음), `requested`, `consented`, `revoked` 중 하나다.
다시 동의를 받아야 하는 필수 항목(`consents_pending`, 예: `["terms"]`)도 실린다. 아래 [동의](#동의)

미성년자(성년 전)는 보호자가 동의해야 결제할 수 있다(#336). 결제를 막는 것은 결제 서버다(#337). 보호자는 계정을 만들지 않는다.

1. 미성년자가 `/guardian/request` 에 `guardian_email` 을 보낸다. `202` 가 오고 그 주소로 동의 링크가 간다(7일).
   링크는 `GUARDIAN_CONSENT_URL#token=...` 모양이다. 다시 요청하면 앞서 보낸 링크는 쓸 수 없게 된다
2. 보호자가 링크의 화면에서 휴대폰 본인인증을 하고, 화면이 `/guardian/consent` 에 `consent_token`(링크의 `token`)과
   `identity_token`(보호자가 업체에서 받은 것)을 보낸다. 보호자와 미성년자에게 메일이 간다. 보호자의 메일에 철회 링크가 있다
3. 보호자가 철회 링크(`GUARDIAN_REVOKE_URL#token=...`)의 화면에서 `/guardian/revoke` 에 `revoke_token` 을 보낸다.
   두 번 보내도 `200` 이다(`revoked` 가 이번에 철회했는지다)

| 응답 | 뜻 |
| --- | --- |
| `403` `code: identity_verification_required` | (요청) 본인인증을 먼저 한다 |
| `409` `code: guardian_not_needed` | 이미 성년이다. 동의가 필요 없다 |
| `409` `code: guardian_consent_active` | (요청) 보호자가 이미 동의했다. 보호자를 바꾸려면 지금의 보호자가 먼저 철회한다 |
| `400` `guardian_email` 필드 오류 | (요청) 자기 이메일을 적었다 |
| `429` `code: guardian_request_unavailable` | (요청) 1분에 1통, 하루에 5통까지다. `retry_after`(초) 뒤에 다시 한다 |
| `400` `code: guardian_link_invalid` | 링크가 틀렸거나 만료됐거나 새 요청으로 바뀌었다. 위조와 만료를 구분하지 않는다 |
| `403` `code: guardian_not_adult` | (동의) 보호자가 성년이 아니다 |
| `409` `code: guardian_is_minor` | (동의) 미성년자 본인의 휴대폰으로 인증했다 |
| `400` `code: identity_token_invalid`, `503` `code: identity_unavailable` | (동의) 본인인증과 같다 |

### 다른 사람의 이름

목록과 소개 화면은 다른 서버에서 만든 사람의 공개 ID(`creator_id`)만 받는다. 이름은 화면이 이 서버에 한꺼번에 묻는다(#532, `accounts/public_names.py`).

```
GET /api/v1/auth/public-names?ids=<공개 ID>,<공개 ID>
→ 200 {"names": [{"public_id": "…", "nickname": "플레이어1"}, {"public_id": "…", "nickname": null}]}
```

- **닉네임만 내준다.** 이메일, 아이디, 나이, 본인인증 여부는 내주지 않는다. 닉네임은 원래 남에게 보이는 이름이다
- **로그인 없이 읽는다.** 공개 목록을 로그인 없이 읽기 때문이다(#530). 토큰을 붙여도 보지 않는다. 공개 ID 는 난수(UUID 4)라 차례로 넣어 계정을 찾을 수 없다
- 받은 차례대로 답한다. 같은 ID 는 한 번만이다. 한 번의 쿼리다
- **없는 ID 와 만 14세 미만으로 막은 계정은 `nickname` 이 `null` 이다.** 둘을 나누지 않는다. 화면은 "탈퇴한 사용자"로 보인다. 정지된 계정은 이름이 그대로 보인다
- 목록이 비었거나, UUID 가 아닌 것이 있거나, 100개를 넘으면 `400` `code: public_ids_invalid` 다
- 브라우저가 60초 기억한다(`Cache-Control: public, max-age=60`). 다른 서버는 이름을 적어 두지 않으므로 이름이 바뀌면 그 뒤로 바로 보인다

### 동의

이용약관과 개인정보 수집·이용의 동의를 받고 기록한다(#450, `accounts/consents.py`). 문서의 글은 서버에 없다. 화면이 항목과 판으로 보인다.

| 항목(`item`) | 무엇 | 필수 |
| --- | --- | --- |
| `terms` | 이용약관 | 예 |
| `privacy` | 개인정보 수집·이용 | 예 |
| `marketing` | 마케팅 정보 수신 | 아니오 |
| `ai_training` | 대화 기록의 AI 학습 이용 | 아니오 |

- **판은 코드의 표(`POLICIES`)에 있다.** 항목마다 번호와 시행일이다. 1판은 변호사 검토 전 초안의 판이다. 판을 올리는 것은 PR 이다.
  `GET /consents` 가 지금의 판을 준다(로그인 없이). 개인정보 처리방침은 동의를 받는 문서가 아니라 알리는 문서라 항목이 아니다
- **가입할 때 필수 항목에 지금의 판으로 동의해야 한다.** 판을 받는 까닭은 화면이 보인 문서가 지금의 것인지 보려는 것이다
- **기록은 덮어쓰지 않고 쌓는다**(`ConsentRecord`: 계정, 항목, 판, 동의 또는 철회, 시각). 항목마다 마지막 줄이 지금의 상태다.
  IP 와 기기는 적지 않는다. 관리자 화면은 조회만 한다
- **선택 항목은 언제든 동의하고 철회한다.** 필수 항목은 철회하지 못한다(`400` `consent_required`). 탈퇴로 한다
- **중요한 변경은 판을 올린다.** 필수 항목의 판이 오르면 그 항목이 `consents_pending` 에 실린다(토큰을 주는 응답과 `/me`).
  맞춤법이나 연락처 같은 고침은 판을 올리지 않는다(모두가 다시 동의해야 한다)
- **다시 동의하기 전까지는 다른 서버를 쓰지 못한다.** 그 사람의 access 토큰은 대상(`aud`)이 인증 서버(`ai-trpg-auth`)뿐이다(`accounts/tokens.py` 의 `audience_for`).
  다른 서버는 `aud` 에 자기 이름이 없어 `401` 이다. 인증 서버는 받는다. 아래 "다시 동의하는 차례"
- 이 기능 전에 가입한 계정은 기록이 없어 필수 둘이 `consents_pending` 에 실린다. 그 계정도 동의하기 전까지 같다. 관리 명령으로 만든 운영자 계정도 같다
- 만 14세 미만으로 막은 계정의 기록은 막을 때 지운다. 그 나이의 본인 동의는 쓸 수 없다. 만 14세 이상은 본인이 동의한다(개인정보 보호법 22조의2)

**다시 동의하는 차례.** 화면은 토큰을 받을 때마다(로그인, `/refresh`, 비밀번호 변경) 응답의 `consents_pending` 을 본다.

1. `consents_pending` 이 비어 있지 않으면 다른 화면으로 가지 않고 동의 화면을 연다. 그 access 토큰으로 다른 서버를 부르면 `401` 이다
2. `GET /consents` 로 새 판을 읽어 보이고, 항목마다 `PUT /me/consents/<항목>` `{"version": n}` 으로 받는다
3. `/refresh` 를 부른다. `consents_pending` 이 `[]` 이고 모든 서버의 이름이 실린 토큰이 온다

```json
{"access_token": "…", "token_type": "Bearer", "expires_in": 900, "consents_pending": ["terms"]}
```

- 막힌 동안에도 인증 서버의 주소(`/me`, `/me/consents`, `/consents`, `/refresh`, `/logout`, 비밀번호 변경 등)는 그대로 쓴다. 계정을 다루는 일이다
- 다른 서버를 고치지 않는다. 그 서버들은 이미 `aud` 에 자기 이름이 있는지 본다. 막는 곳이 인증 서버 하나다
- refresh 토큰은 좁히지 않는다. 인증 서버만 읽는다
- 판을 올리기 전에 나간 access 토큰은 수명(15분)까지 모든 서버에 통한다. 판을 올린 뒤 길어야 15분이다
- 갱신을 막지 않고 좁은 토큰을 주는 까닭: 갱신을 `403` 으로 막으면 access 토큰이 끊겨 동의하는 주소도 부를 수 없다. 동의할 길이 닫힌다
- `JWT_AUDIENCE` 에 `ai-trpg-auth` 가 없으면 서버가 뜨지 않는다(`config/security.py` 의 `require_own_audience`). 그 사람은 동의를 마칠 길이 없기 때문이다

`GET /me/consents` 의 답. 동의하지 않았거나 철회했으면 `agreed_version` 과 `agreed_at` 이 `null` 이다.

```json
{"items": [{"item": "terms", "required": true, "version": 1, "agreed_version": 1, "agreed_at": "2026-10-20T09:00:00Z", "pending": false}, ...]}
```

| 응답 | 뜻 |
| --- | --- |
| `200` | 동의, 철회, 읽기 모두 바뀐 뒤의 상태 전체를 준다. 이미 그 판에 동의했거나 이미 철회했으면 아무것도 적지 않는다 |
| `409` `code: consent_outdated` | (동의) 판이 지금의 것이 아니다. 화면이 옛 문서를 보였다. `GET /consents` 를 다시 읽는다 |
| `400` `code: consent_required` | (철회) 필수 항목이다 |
| `404` `code: consent_item_unknown` | 그런 항목이 없다 |

### 시도 횟수 제한

정해진 시간 안에 허용된 횟수를 넘으면 `429`와 `code: too_many_attempts`가 온다.
`retry_after`(초)와 `Retry-After` 헤더가 기다릴 시간이다. 무엇을 기준으로 셌는지는 알려 주지 않는다.

| API | 기준 | 세는 것 | 한도 |
| --- | --- | --- | --- |
| `/login` | IP | 모든 시도 | 10분에 30번 |
| `/login` | 계정과 IP의 쌍 | 틀린 시도 | 15분에 5번 |
| `/signup` | IP | 모든 시도(다시 보내기 포함) | 1시간에 10번 |
| `/password/reset` | IP | 모든 시도 | 1시간에 5번 |
| `/password/change` | 사용자 | 현재 비밀번호를 틀린 시도 | 15분에 5번 |

IPv6는 주소 하나가 아니라 앞 64비트가 같은 묶음을 한 곳으로 센다.

`admin`, `root` 같은 예약어 아이디(번호만 붙인 `admin1`, `root_2` 도 포함)로 1시간 안에 3번 로그인을 시도한 IP는 그 1시간이 끝날 때까지 로그인이 막힌다.
이때는 `429`가 아니라 평소와 같은 `401`이 온다. 맞는 비밀번호를 넣어도 같다.

### 토큰 두 종류

| | access 토큰 | refresh 토큰 |
| --- | --- | --- |
| 수명 | 15분 | 14일 (쓸 때마다 새것으로 교체) |
| 전달 | 응답 본문 | httpOnly 쿠키 (`Path=/api/v1/auth`, `SameSite=Strict`) |
| 쓰는 곳 | 인증 서버와 다른 서버의 API | 인증 서버의 `/refresh`, `/logout` |
| 프론트의 보관 | 메모리 | 브라우저가 보관. 스크립트는 읽을 수 없음 |

access 토큰이 만료되면 프론트는 `/refresh`를 호출해 새 access 토큰을 받는다.
`/refresh`가 `401`이면 다시 로그인해야 한다. 응답의 `consents_pending` 이 비어 있지 않으면 동의 화면으로 간다([동의](#동의)의 "다시 동의하는 차례").

`/refresh`와 `/logout`은 허용한 출처(`REFRESH_COOKIE_ALLOWED_ORIGINS`)에서 온 요청만 받는다.
`Origin` 머리말이 다르거나, 없거나, `null` 이면 `403`(`code: origin_not_allowed`)이고 쿠키는 그대로 둔다.
브라우저는 POST 에 `Origin` 을 저절로 붙이므로 프론트가 할 일은 없다.
curl 로 시험할 때는 `-H 'Origin: http://localhost:8080'` 처럼 직접 붙인다.

프론트는 `/refresh`를 한 번에 하나만 호출해야 한다. 같은 refresh 토큰으로 두 요청이
동시에 가면 하나만 성공하고, 나머지는 폐기된 토큰의 재사용으로 처리되어 모든 세션이 끊긴다.
한 번 끊긴 뒤에 다시 로그인한 세션은, 그 옛 토큰이 다시 들어와도 끊기지 않는다(거부만 한다, #272).

### 다른 서버에서 토큰을 검증하는 방법

1. 토큰 머리말의 `kid`를 읽는다
2. `/api/v1/auth/jwks`에서 `kid`가 같은 공개키를 고른다. 키 목록은 캐시해 둔다
3. 그 키로 서명을 검증한다. 알고리즘은 `RS256`만 허용한다
4. `iss`가 `ai-trpg-auth`인지, `aud`에 자기 서버 이름이 있는지, `exp`가 지나지 않았는지 확인한다
5. 끊긴 세션이 아닌지 확인한다(#274). `/api/v1/auth/session-revocations` 를 30초마다 받아 기억해 두고,
   토큰의 `sub` 를 SHA-256 으로 바꾼 값(16진수 64자)이 목록에 있으면서 토큰의 `ver` 가 그 줄의 `min_ver` 보다 작으면 401 로 거부한다

끊긴 세션의 목록은 이런 모양이다. 한 사용자에 한 줄이다.

```json
{
  "revocations": [{"sub_sha256": "08f6625d…c0ed", "min_ver": 3}],
  "refresh_interval_seconds": 30
}
```

- 세션을 끊으면(비밀번호 변경과 재설정, refresh 재사용, 모든 기기 로그아웃, 계정 정지) 그 사용자의 세션 버전이 오르고 목록에 실린다.
  `ver` 가 `min_ver` 보다 작은 토큰은 끊기기 전에 발급된 것이다
- 끊은 지 access 토큰의 수명(15분)에 1분을 더한 만큼이 지나면 목록에서 빠진다. 그 전의 access 토큰은 이미 만료되었다
- 예: `sub` 가 `0d3f7a52-6f0a-4c1e-9d55-2b8a4c1f7e90` 이면 `sub_sha256` 은 `08f6625d1aecc747bd6122bbf85ef9fb3fc0f25f7986169f057f12639fe6c0ed` 다.
  `sub` 의 글자 그대로(소문자, 붙임표 포함)를 UTF-8 로 해시한다
- 목록을 받지 못하면 마지막으로 받은 목록을 그대로 쓴다. 한 번도 받지 못했으면 이 확인을 건너뛴다(공개키도 없으면 어차피 503 이다)
- `ver` 가 없는 토큰은 0 으로 본다

토큰 하나에 모든 서버의 이름이 실린다(`JWT_AUDIENCE`). 프론트는 토큰 하나로 모든 서버를 부른다.
다시 동의할 필수 항목이 남은 사람의 토큰에는 `ai-trpg-auth` 하나만 실린다([동의](#동의)).

| 서버 | `aud` 에서 찾는 이름 |
| --- | --- |
| 게임 서버 | `ai-trpg-game` |
| 게시판 서버 | `ai-trpg-board` |
| 결제 서버 | `ai-trpg-billing` |
| 알림 서버 | `ai-trpg-notification` |
| asset 서버 | `ai-trpg-asset` |
| chat 서버(아직 없다) | `ai-trpg-chat` |

서버가 늘면 `config/settings.py`의 기본값과 `.env.example`에 이름을 더한다. `.env`에 `JWT_AUDIENCE`를 적어 둔 곳은 그 줄도 고친다.
고치기 전에 발급한 access 토큰에는 새 이름이 없다. 수명이 15분이라 그 뒤로는 저절로 맞는다.
대상마다 토큰을 따로 발급하지 않는 이유: 프론트 하나가 같은 사용자로 모든 서버를 부른다. 토큰을 서버마다 받아 들게 하면 발급과 갱신이 복잡해지고 얻는 것이 작다.
한 서버에서 샌 토큰이 다른 서버에도 통한다는 대가가 있다. access 토큰의 짧은 수명이 그 창을 줄인다.

토큰의 `sub`는 회원의 `public_id`다.

access 토큰에는 회원의 닉네임(`nickname`)도 실린다. 게시판 서버가 글쓴이의 이름을 보여 주는 데 쓴다. 쓰지 않는 서버는 무시하면 된다.
refresh 토큰에는 싣지 않는다. 갱신할 때마다 그때의 닉네임을 DB 에서 다시 읽어 싣는다.
토큰은 서명만 되어 있고 암호화되어 있지 않아 누구나 읽는다. 그래서 남에게 보이라고 만든 닉네임만 싣고, 이메일 같은 개인정보는 싣지 않는다.

access 토큰에는 성인용 내용을 볼 수 있는지(`adult_content`, 참이나 거짓)도 실린다(#336). 게임 서버가 성인용 시나리오를 가르는 데 쓴다(#59).
위의 `identity.adult_content` 와 같은 값이다. 생일이나 나이는 싣지 않는다. 갱신할 때마다 그날의 한국 날짜로 다시 정한다.
본인인증 직후나 만 19세가 되는 해의 1월 1일에는 다음 갱신(늦어도 15분 뒤)부터 바뀐다. 이 클레임이 없는 옛 토큰은 거짓으로 본다.

access 토큰에는 역할(`roles`, 글자의 목록)도 실린다(#389). 운영자면 `["operator"]`, 아니면 `[]` 다.
운영자는 Django 그룹 `operators` 에 든 계정이다(마이그레이션 `0019` 가 그룹을 만든다). `is_staff` 와는 상관없다.
받는 서버는 목록에 `"operator"` 가 정확히 있을 때만 운영자로 보고, 이 클레임이 없는 옛 토큰은 일반 사용자로 본다.
운영자가 서비스마다 무엇을 더 하는지는 [운영자 권한](../docs/architecture/operators.md)에 있다.
갱신할 때마다 그룹을 다시 읽으므로, 그룹에서 빼면 다음 갱신(늦어도 15분 뒤)부터 빠진다. 바로 막아야 하면 그 계정의 세션을 끊는다.

## API 목록

주소마다 받는 요청과 돌려주는 응답의 모양(OpenAPI)이다(#558). 화면의 타입과 디자인 도구에 넘기는 것은
그것을 뽑은 [`docs/api/auth.openapi.json`](../docs/api/auth.openapi.json)이다([API 목록](../docs/api/README.md)).
위의 표는 읽기 쉽게 줄인 것이다. 칸의 모양과 상태 코드가 다르면 목록이 맞다.

- **뷰에 적은 모양이 목록이 된다(drf-spectacular).** 뷰는 손으로 만든 dict 를 돌려주는 `APIView` 라서 응답의 모양을 스스로 알아낼 수 없다.
  뷰의 메서드마다 `@extend_schema` 로 요청, 상태 코드마다의 응답을 적는다. 오류와 목록만의 모양은 `accounts/api_schema.py` 에 있다
- **응답을 바꾸면 모양도 고친다.** 테스트가 받은 응답을 모두 목록과 견준다(`config/schema_check.py`, 테스트 실행기가 건다).
  목록에 없는 상태 코드, 없는 칸, 더 붙은 칸이 있으면 그 응답을 받은 테스트가 `SchemaMismatchError` 로 실패한다.
  목록의 객체는 적은 칸만 받는다(`additionalProperties: false`)
- **모양을 적지 않은 뷰가 있으면 실패한다.** 목록을 만들 때 경고가 하나라도 있으면 멈춘다(`--fail-on-warn`). 테스트도 같은 명령을 돈다
- 고친 뒤에는 저장소 루트에서 다시 뽑아 함께 커밋한다. 뽑지 않으면 CI 의 `api-docs` 가 실패한다

  ```
  uv run --no-project python tools/export_openapi.py auth
  ```

  서명 키와 DB 없이 뜬다(`JWT_PRIVATE_KEY_PATH` 를 비운다). `DEBUG` 를 끄고 뽑아 운영과 같은 목록이다
- **운영 서버는 목록의 주소를 열지 않는다.** `DEBUG=true` 일 때만 `/api/v1/auth/openapi.json` 과 화면(`/api/v1/auth/docs`)이 열린다.
  다른 서버(FastAPI)와 같은 자리다
- 견주지 않는 응답: 목록에 없는 주소와 방식(관리자 화면, HEAD, 405), 어느 주소에도 맞지 않은 404, 서버의 오류(500, Django 의 기본 오류 화면),
  스트림, 줄바꿈이 든 머리말을 보낸 요청. 요청은 견주지 않는다(테스트가 일부러 틀린 요청을 보낸다)

## 로그와 요청 식별자

네 서버가 같은 규격으로 로그를 남긴다. 규격의 전부는 [docs/observability.md](../docs/observability.md)에 있다. 여기는 이 서버에서 알아 둘 것만 적는다.

- 로그는 표준 오류(stderr)에 **한 줄에 JSON 하나**로 나간다. 모든 줄에 `timestamp`, `level`, `service`(`auth-server`), `environment`, `version`, `message` 가 있다.
- 요청마다 식별자가 붙는다. 요청의 `X-Request-ID` 머리말이 영문자, 숫자, `.`, `_`, `-` 로 된 8~64자면 그대로 쓰고, 아니면 새 UUID 로 바꾼다.
  정한 값은 **모든 응답의 `X-Request-ID` 머리말**로 돌려준다. 오류가 났을 때 이 값으로 로그를 찾는다.
- 요청이 끝나면 한 줄이 남는다. 주소는 실제 값이 아니라 틀로 적는다(`/api/v1/auth/login`). 머리말, 주소 뒤에 붙은 값, 본문은 적지 않는다.
- 4xx 는 `info`, 5xx 는 `error` 다. 처리하지 못한 예외는 호출 기록과 함께 로그에만 남고, 응답에는 정해진 말과 `X-Request-ID` 만 간다.
- 비밀번호, 토큰, 이메일 주소 같은 값은 로그에 넘기지 않는다. 실수로 넘겨도 나가기 직전에 한 번 더 가린다(이름이 `password`, `token` 같은 칸, 글 속의 JWT 와 이메일의 모양).
- 식별자는 로그를 찾는 데만 쓴다. 누구의 요청인지는 토큰만이 말한다.

| 환경 변수 | 기본값 | 뜻 |
| --- | --- | --- |
| `APP_ENVIRONMENT` | `development` | 환경의 이름. 로그의 `environment` 칸. 운영에서는 `production` |
| `APP_VERSION` | `dev` | 배포한 코드의 버전. 로그의 `version` 칸. 운영에서는 git SHA 나 이미지 태그 |
| `LOG_LEVEL` | `info` | 이 수준부터 남긴다. `debug`, `info`, `warning`, `error` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | 비어 있음(보내지 않음) | span 과 메트릭을 OTLP(HTTP)로 미는 수집기(Alloy)의 주소. `http://alloy:4318` 처럼 경로 없이 적는다([추적](#추적), [메트릭](#메트릭)) |
| `OTEL_METRIC_EXPORT_INTERVAL` | `15000` | 메트릭을 보내는 간격(밀리초, 1000 이상). 다른 서버와 같은 이름이다 |

다섯 값 모두 비밀이 아니다. 모양이 틀리면 서버가 뜨지 않는다. 모든 로그 줄에 실리는 값이라 줄바꿈이나 따옴표가 든 값을 받지 않는다.

개발할 때 줄이 읽기 불편하면 `jq` 로 본다. JSON 이 아닌 줄(프레임워크가 뜰 때 찍는 안내)은 건너뛴다.

```bash
uv run python manage.py runserver 2>&1 | jq -rR 'fromjson? | [.timestamp, .level, .message, .route // "", .status_code // ""] | @tsv'
```

**이 서버에서 다른 것.**

- 워커와 예약 명령(`send_outgoing_mail`, `send_welcome_credits`, `delete_unverified_users`, `send_security_digest`)은 요청이 아니라 작업이다. 로그에 `request_id` 대신 `job_id` 가 붙는다.
  메일 워커는 1초마다 돌아서, 잘 끝난 것은 `debug` 로 남긴다. 실패만 `error`(`error_code: job.failed`)로 남는다.
- **`APP_ENVIRONMENT=production` 이면 `SMTP_HOST` 를 꼭 적어야 한다.** 적지 않으면 서버가 뜨지 않는다.
  `SMTP_HOST` 가 없으면 메일을 보내지 않고 터미널에 찍는데, 거기에는 받는 사람의 주소와 인증 코드가 그대로 나온다. 운영에서는 그것이 로그에 남는다.
  `staging` 은 메일 서버 없이 뜬다. 인증 코드가 찍힌 줄이 로그 모으기(Loki)에 14일 남으니 메일 서버를 붙이기 전까지 그렇다는 것을 안다.
- **`APP_ENVIRONMENT` 가 `staging` 이나 `production` 이면 `DEBUG=true` 를 쓸 수 없다.** Django 는 `DEBUG` 가 켜져 있으면 예외의 응답에 호출 기록과 설정값을 실어 보낸다.
- Django 가 스스로 찍던 요청 줄(`runserver` 의 `"GET /api/... 200"`)은 껐다. 주소 뒤에 붙은 값까지 찍었고, 요청이 끝난 줄과 겹친다.
- 테스트를 돌릴 때는 로그를 찍지 않는다(`config/test_runner.py`). 로그를 보는 테스트는 `assertLogs` 로 직접 잡는다.

코드는 `observability/` 에 있다. `identifiers.py`(식별자의 규칙), `context.py`(요청과 작업 동안 식별자를 들고 있는 곳),
`redaction.py`(가리는 규칙), `formatter.py`(JSON 한 줄), `setup.py`(Django 의 `LOGGING`), `middleware.py`(요청), `jobs.py`(작업).

## 추적

요청, 결제 서버를 부르는 것, 쿼리, 워커와 예약 명령을 span 으로 남겨 `OTEL_EXPORTER_OTLP_ENDPOINT` 로 민다. 수집기가 Tempo 에 넘긴다.
규칙과 까닭은 [관측 규격](../docs/observability.md)의 "3. 추적"에 있다. 알림 서버의 것을 옮겼고, 이 서버에서 다른 것은 "붙인 것 (인증 서버의 추적)"에 있다.
주소가 비어 있으면 span 이 생기지 않고 로그는 지금과 같다. 테스트(`manage.py test`)는 주소가 있어도 내보내지 않는다.

| span | 이름 | 코드 |
| --- | --- | --- |
| 요청 | `POST /api/v1/auth/login`(메서드와 경로의 틀). 상태 확인은 걸지 않는다 | `observability/request_spans.py` |
| 결제 서버를 부르는 것 | `HTTP POST` | `observability/http_spans.py`, `accounts/billing_client.py` |
| 쿼리 | `db SELECT accounts_user`(종류와 첫 테이블) | `observability/db_spans.py` |
| 워커와 예약 명령 | `operation`(`mail.deliver_outgoing`, `account.delete_unverified`). 한 바퀴가 새 추적 하나다 | `observability/jobs.py` 의 `run_as_job` |

- 로그의 `trace_id` 가 span 의 trace id 와 같다. 요청의 span 에는 `request_id`, 작업의 span 에는 `job_id` 를 싣는다
- 싣지 않는 것: 주소의 경로와 뒤의 값, 머리말, 본문(비밀번호와 인증 코드), SQL 의 문장과 값(이메일, 비밀번호의 해시), 예외의 글. 쿼리가 실패하면 SQLSTATE 만 적는다
- 요청이나 작업 밖의 쿼리(서버가 뜰 때의 확인)는 span 을 걸지 않는다
- 워커가 할 일 없이 돈 바퀴(처리한 수 `handled` 가 0 이고 실패하지 않은 것)는 그 추적을 통째로 보내지 않는다(`observability/idle_rounds.py`)
- 받은 `traceparent` 가 "기록하지 않음"(flags `00`)이어도 남긴다

## 메트릭

요청, DB, 메일, 시도 횟수 제한, 워커와 예약 명령을 세어 `OTEL_EXPORTER_OTLP_ENDPOINT` 로 15초마다 민다. 수집기가 Prometheus 에 넘긴다.
이름과 label 은 [관측 규격](../docs/observability.md)의 "메트릭"에 있다. 알림 서버의 것을 옮겼고, 이 서버에서 다른 것은 "붙인 것 (인증 서버의 메트릭)"에 있다.
주소가 비어 있으면 세기만 하고 보내지 않는다. 테스트(`manage.py test`)는 주소가 있어도 내보내지 않는다.

| 메트릭 | label | 세는 곳 |
| --- | --- | --- |
| `http_server_requests_total`, `http_server_request_duration_seconds`, `http_server_active_requests` | `method`, `route`(경로의 틀), `status_code` | `observability/request_metrics.py`. `MIDDLEWARE` 의 맨 앞이다 |
| `db_up` | 없음 | `config/health.py`. 준비 상태 확인이 본 DB. 연결 풀이 없어 `db_pool_*` 는 내지 않는다 |
| `background_jobs_started_total`, `background_jobs_finished_total`, `background_jobs_running`, `background_job_duration_seconds` | `operation`, `result` | `observability/jobs.py` 의 `run_as_job`. 워커의 한 바퀴와 예약 명령 한 번 |
| `background_jobs_queued` | `operation`(`mail.deliver_outgoing`) | 메일 워커가 바퀴마다 발송함에 남은 메일을 센다 |
| `emails_sent_total` | `kind`(메일의 종류), `result`(`sent`, `retried`, `discarded`) | `accounts/outbox.py`. 한 통을 보내 본 시도마다 |
| `auth_rate_limited_total`, `auth_rate_limits_unavailable_total` | `limit`(제한의 이름) | `accounts/attempt_limits.py`. 막은 것과, Redis 에 묻지 못해 세지 않고 통과시킨 것 |

- gunicorn 은 앱을 워커가 갈라진 뒤에 불러온다(`gunicorn.conf.py` 의 `preload_app = False`). 보내는 스레드가 워커마다 뜨고, 워커마다 `service.instance.id` 가 다르다
- 예약 명령은 끝날 때 한 번 민다. 간격을 기다리기 전에 끝나서다
- 메일의 종류는 발송함의 칸 `kind`(`accounts.models.MailKind`)다. 종류를 더하면 관측 규격의 표에도 더한다
- 대시보드는 Grafana 의 `auth-server`(`docker/grafana/dashboards/auth-server.json`), 경보는 `docker/prometheus/rules/ai-trpg.yml` 의 `auth-server` 묶음이다
- 테스트는 `observability/tests/metrics.py` 로 메모리에 모아 이름, 단위, label 을 본다. 보내는 길은 `observability/tests/test_metrics_setup.py` 가 가짜 수집기로 본다


## CI

PR과 `main` 푸시마다 GitHub Actions가 인증 서버를 검사한다. `auth-server/`,
`docker/postgres/init/`, 워크플로 파일, 함께 쓰는 ruff 규칙(루트의 `ruff.toml`) 중 하나가 바뀐 경우에만 돈다.

1. 의존성 설치 (`uv sync --locked`): `uv.lock`과 `pyproject.toml`이 어긋나면 실패한다
2. 린트 (`ruff check`)
3. 모양 검사 (`ruff format --check`): 고치지 않고 검사만 한다
4. 의존성 취약점 검사 (`pip-audit`): 운영 이미지에 들어가는 의존성(dev 제외)에 알려진 취약점이 있으면 실패한다.
   `uv.lock` 에 잠긴 그대로를 해시와 함께 넘긴다. 고칠 수 없어 받아들이기로 한 것은 워크플로의 `--ignore-vuln` 에 까닭과 함께 적는다
5. 설정 검사 (`manage.py check`). 그 전에 이 실행에서만 쓰고 버릴 JWT 키를 만든다
6. 운영 설정의 배포 검사 (`check --deploy --fail-level WARNING`)
7. 마이그레이션 누락 검사 (`makemigrations --check --dry-run`): 모델을 바꾸고
   마이그레이션을 만들지 않았으면 실패한다
8. 테스트 (`coverage run manage.py test`): 테스트를 돌리며 지나간 줄을 센다
9. 커버리지 요약: 합계와 덜 지나간 파일을 작업 요약(Summary)에 적는다
10. 커버리지 기준: 합계가 94% 아래면 실패한다(워크플로의 `COVERAGE_MIN`, 처음 잰 값은 96%). 요약을 먼저 적으므로 실패해도 어느 파일이 덜 지나갔는지 남는다. 기준은 처음 잰 값보다 조금 낮게 잡았다. 커버리지가 오르면 기준도 올리고, 내릴 때는 PR 에 까닭을 적는다.

CI도 로컬과 같은 초기화 스크립트로 `auth` 계정을 만들어 그 계정으로 테스트한다.
슈퍼유저로 테스트하면 권한 때문에 실패할 코드가 CI를 통과하기 때문이다.

## 설계 메모

### 계정

**아이디와 이메일을 분리한다.** 로그인은 아이디로 하고, 이메일은 인증 코드를 받는 용도로만 쓴다.
아이디는 영문 소문자, 숫자, 밑줄만 허용해 이메일 주소를 아이디로 쓸 수 없게 한다.
이메일 중복은 대소문자를 무시하는 DB 제약으로 막는다.

**외부에는 정수 PK 대신 UUID(`public_id`)를 내보낸다.** 정수 PK는 가입자 수와
가입 순서를 추측하게 해 준다. 정수 PK는 내부 조인용으로 남긴다.

### 토큰

**토큰은 RS256으로 서명하고 공개키를 JWKS로 내보낸다.** 개인키는 인증 서버만 갖는다.
다른 서버는 공개키로 검증만 하므로 토큰을 만들 수 없다. 대칭키(HS256)를 서버끼리 공유하면
검증만 해야 할 서버도 토큰을 위조할 수 있다.

**키 ID(`kid`)는 공개키의 해시로 정한다.** 이름을 사람이 붙이지 않으므로, 키를 바꾸면 ID도
자동으로 바뀐다. JWKS가 목록인 것은 키를 교체하는 동안 옛 키와 새 키를 함께 내보내기 위해서다.
해시는 파일의 글자가 아니라 늘 같은 모양으로 다시 쓴 PEM 에서 계산한다. 윈도우에서 저장해 줄바꿈이 바뀌어도 같은 키는 같은 ID 다.

**서명 키는 하나, 검증 키는 여럿이다(#21).** 새 토큰은 서명 키로만 서명하고, 받은 토큰은 머리말의 `kid` 로
검증 키 목록(서명 키 + `JWT_EXTRA_PUBLIC_KEY_PATHS`)에서 공개키를 고른다. 모르는 `kid` 나 `kid` 가 없는 토큰은 거부한다.
인증 서버 자신도 이 목록으로 검증해야 한다. 키를 바꾼 뒤에도 옛 키로 서명한 refresh 토큰(14일)을 받아야 사용자가 로그아웃되지 않는다.
검증만 하는 키는 공개키 파일로 받는다. 옛 개인키를 남겨 둘 까닭이 없다.
키를 다루는 곳은 `accounts/key_ring.py` 하나다. 지금은 설정(파일)에서 읽고 바꿀 때 서버를 다시 띄운다.
키를 DB 에 두고 다시 띄우지 않고 바꾸게 되면 그 모듈의 `current_key_ring` 만 바꾼다(개인키를 DB 에 두면 암호화가 필요하다).

**access 토큰은 15분만 유효하다.** 다른 서버는 인증 서버에 묻지 않고 서명과 만료만 확인한다.
탈취된 토큰을 중간에 취소할 방법이 없으므로 수명을 짧게 잡는다.

**끊긴 세션은 목록으로 다른 서버에 알린다(#274).** 세션을 끊어도(비밀번호 변경, 계정 정지) 다른 서버는 세션 버전을 몰라
그 사용자의 access 토큰을 만료까지 받았다. 그래서 끊긴 세션의 목록을 JWKS 처럼 내주고, 다른 서버가 30초마다 받아 간다.
끊은 뒤 네 서버에서 막히기까지 30초쯤 걸린다.
- 요청마다 인증 서버에 묻는 길(introspection)은 하지 않았다. 인증 서버가 모든 요청의 단일 장애점이 된다
- 공용 Redis 에 적는 길도 하지 않았다. 결제 서버는 Redis 를 쓰지 않고, Redis 가 죽었을 때의 정책을 서버마다 따로 정해야 한다
- access 수명을 줄이는 것만으로는 바로 막히지 않고 refresh 가 늘어난다
- 목록은 로그인 없이 열린다. 사용자를 `sub` 의 SHA-256 으로만 실어 누가 끊겼는지(정지되었는지) 밖에서 알 수 없다.
  `sub` 는 무작위 UUID 라 해시에서 거꾸로 찾을 수 없다
- 줄은 access 수명이 지나면 빠지므로 목록은 늘 작다. 고를 때는 회원의 "세션을 끊은 시각"(`sessions_revoked_at`)을 본다.
  세션 버전과 같은 UPDATE 문에서 적는다
- 회원을 지우면 목록에서도 빠진다. 지운 회원의 access 토큰은 다른 서버에서 만료까지 통한다. 급하면 먼저 정지하고 15분 뒤에 지운다

**계정 정지는 관리 명령으로 한다.** 계정을 막고(`is_active`), 세션 버전을 올리고, 사유를 보안 이벤트에 남기는 것을 한 트랜잭션에서 한다(`accounts/suspension.py`).
관리자 화면에서는 `is_active` 를 고칠 수 없다. 화면에서 끄면 세션 버전이 오르지 않아 다른 서버에 알려지지 않는다.
정지를 풀어도 세션 버전은 되돌리지 않는다. 정지 전의 토큰은 계속 쓸 수 없고 사용자는 다시 로그인한다.

**refresh 토큰은 httpOnly 쿠키에 담는다.** 14일짜리라 탈취 피해가 크다. 스크립트가 읽을 수 없는
곳에 두면 XSS로는 훔칠 수 없다. 쿠키 경로를 인증 API로 제한해 다른 요청에는 실리지 않고,
`SameSite=Strict`로 다른 사이트에서 시작된 요청에도 실리지 않는다. access 토큰은 다른 서버에도
보내야 해서 쿠키에 담지 않는다.

**쿠키를 쓰는 `/refresh`와 `/logout`은 `Origin` 을 허용 목록과 비교한다(`accounts/origin_check.py`).**
`SameSite` 는 "사이트"(등록한 도메인) 단위라, 같은 도메인의 다른 하위 도메인(예: `chat.example.com`)에서 보낸 요청에는 쿠키가 실린다.
그 페이지가 `/logout` 을 부르면 사용자가 로그아웃되고, `/refresh` 를 부르면 토큰이 돌아간다. 그래서 출처를 직접 본다.
목록과 글자 그대로 같아야 한다(대소문자는 보지 않는다). 앞부분만 같은 `https://play.example.com.evil.test` 는 다르다.
`Origin` 이 없거나 `null`(파일, 샌드박스 iframe)이면 어디서 왔는지 모르므로 거부한다.
거부할 때는 쿠키를 지우지 않는다. 지우면 이 검사가 막으려는 "다른 곳의 페이지가 로그아웃시키기"가 그대로 된다.
거부는 로그에만 남기고 DB 의 보안 이벤트로는 남기지 않는다. 누구나 일으킬 수 있어 요청 수만큼 행이 쌓인다.
Django 의 CSRF 토큰도 생각했으나 하지 않았다. 주소 둘을 위해 프론트가 토큰을 읽어 매번 실어야 한다.
직접 만든 머리말(`X-Requested-With`)을 요구하는 방법은 CORS 설정에 기대는 간접 방어라 하지 않았다.
`/logout-all` 은 검사하지 않는다. access 토큰(`Authorization`)으로 본인을 확인하고, 다른 곳의 페이지는 그 토큰을 실을 수 없다.

**refresh 토큰은 쓸 때마다 교체하고, 폐기된 토큰이 다시 쓰이면 모든 세션을 끊는다.**
폐기된 토큰이 다시 들어왔다는 것은 정상 사용자와 공격자 중 한쪽이 옛 토큰을 쓴 것이다.
누가 진짜인지 가릴 수 없으므로 양쪽 다 끊고 다시 로그인하게 한다.
끊는 것은 그 토큰이 지금 세션 버전의 것일 때뿐이다(#272). 이미 끊은 뒤의 지난 세대 토큰은 거부만 한다.
그러지 않으면 한 번 끊긴 뒤에도 옛 토큰을 가진 사람이 만료(14일)까지 다시 보낼 때마다 버전이 오르고,
새로 로그인한 세션까지 또 끊긴다. 옛 토큰이 남을 강제로 로그아웃시키는 수단이 된다.
같은 토큰으로 동시에 들어온 요청은 행 잠금으로 하나만 통과시킨다.

**세션을 한 번에 끊는 장치는 세션 버전(`token_version`)이다.** 토큰에 버전을 넣어 발급하고,
회원의 버전을 올리면 그 전의 토큰이 전부 무효가 된다. 토큰을 하나씩 찾아 폐기할 필요가 없다.
다른 서버는 버전을 확인할 수 없어 옛 access 토큰이 최대 15분 통한다.

**폐기 기록은 PostgreSQL에 둔다(simplejwt의 블랙리스트 테이블).** 폐기 여부는 갱신과 로그아웃
때만 확인하므로 조회가 드물다. Redis 캐시를 덧붙이면 두 저장소가 어긋나는 순간 폐기된 토큰이
통과할 수 있어 쓰지 않는다. 발급한 토큰의 원문은 저장하지 않고 토큰 ID만 남긴다.

**access 토큰에 닉네임을 싣는다(`nickname`).** 게시판 서버가 글쓴이의 이름을 알아야 한다. 길이 셋 있었다.
인증 서버에 "번호들 → 닉네임" API 를 열면 늘 최신이지만, 다른 서버가 목록을 읽을 때마다 인증 서버를 부르고, 인증 서버가 죽으면 이름이 빠진다.
닉네임이 바뀔 때 인증 서버가 알리는 길은 바로 반영되지만, 지금은 닉네임을 바꾸는 API 가 없어 알릴 일이 없다.
토큰에 실으면 서버끼리 부르지 않는다. 받는 서버는 이름을 적어 두고, 로그인한 요청이 올 때 토큰의 이름과 다르면 고친다.
닉네임을 바꾸는 기능이 생기면 그때 인증 서버가 알리는 길을 더한다. 옛 이름이 풀려 다른 사람이 가져가면 잠시 두 사람이 같은 이름으로 보일 수 있기 때문이다.
클레임 이름은 OpenID Connect 의 표준 이름(`nickname`)을 따른다.

**토큰의 서명과 검증, 폐기 기록 테이블은 simplejwt에 맡긴다.** 그 위에 세 가지를 직접 얹었다.
머리말의 `kid`(simplejwt는 넣지 않는다), 로그인 뷰, refresh 회전이다. simplejwt의 내장 갱신에는
폐기된 토큰이 다시 쓰였을 때 모든 세션을 끊는 동작이 없다. 발급은 함수 하나(`issue_token_pair`)로
감싸, 로그인 흐름이 바뀌어도 그대로 쓴다.

### 이메일 인증 코드

**이메일 인증 코드는 Redis가 아니라 PostgreSQL에 둔다.** 로그인마다 인증 코드가 필요한데,
로그인은 이미 PostgreSQL 없이는 동작하지 않는다. 코드를 Redis에 두면 로그인이 의존하는 것이
하나 더 늘어 Redis 장애가 곧 로그인 장애가 된다. 양도 로그인 한 번에 코드 하나라 Redis의 속도가
필요하지 않다. 회원과 용도마다 행을 하나만 두고 덮어써서 테이블이 불어나지 않는다.
Redis는 없어도 서비스가 도는 보조 장치(시도 횟수 제한)에만 쓸 예정이다.

**인증 코드는 원문이 아니라 비밀키를 섞은 해시로 저장한다.** 6자리는 100만 가지뿐이라 그냥
해시하면 전부 대입해 바로 풀린다. 회원과 용도도 함께 섞어 다른 행의 해시를 옮겨 쓸 수 없게 한다.

**코드 검증은 다른 트랜잭션 안에서 실행할 수 없게 막는다.** 틀린 횟수는 반드시 저장되어야 한다.
바깥 트랜잭션이 있으면 검증 실패 예외가 그 트랜잭션까지 되돌려 횟수가 사라지고, 횟수 제한 없이
코드를 추측할 수 있게 된다. 검증 블록을 `durable`로 선언해 중첩 자체를 오류로 만든다.

### 회원가입

**가입 응답으로 이메일의 가입 여부를 알려 주지 않는다.** "이미 가입된 이메일입니다"라고
답하면 누구나 특정 이메일의 가입 여부를 확인할 수 있다. 새 이메일이든 가입된 이메일이든 같은
응답을 주고, 가입된 주소의 주인에게는 메일로 알린다. 아이디와 닉네임의 중복은 숨기지 않는다.
닉네임은 어차피 공개되는 값이고, 아이디는 알려 주지 않으면 가입 자체를 할 수 없다.

**이메일을 먼저 확인하고, 가입 내용은 그 뒤에 받는다(#271).** 예전에는 1단계에서 아이디와 비밀번호까지 받아
미인증 계정을 만들고, 코드가 맞으면 인증된 것으로 바꿨다. 같은 이메일로 다시 가입하면 그 계정을 고쳐 썼다.
그래서 남의 이메일을 아는 사람이 그 사람의 가입 도중에 자기 아이디와 비밀번호로 다시 가입하면,
재발급 제한 때문에 새 코드가 나가지 않아 이메일 주인은 처음 받은 코드를 넣고, 그 코드가 바뀐 내용을 확정했다.
코드를 가입 내용에 묶는 것(내용이 바뀌면 코드를 버린다)으로는 다 막히지 않는다. 바뀐 내용의 새 코드가 다시 이메일 주인에게 가기 때문이다.
지금은 가입 내용을 정하려면 가입 티켓이 있어야 하고, 티켓은 그 이메일의 코드를 맞힌 사람만 받는다.
미인증 계정을 고쳐 쓰는 일이 없어져, 고쳐 쓰는 쪽과 인증하는 쪽의 잠금 순서가 엇갈리는 문제도 함께 사라졌다.

**가입 티켓은 DB 에 적지 않는다.** 로그인 티켓처럼 서버의 비밀키로 서명한다(`accounts/signup_tickets.py`, 용도마다 다른 salt).
한 번만 쓰이는 것은 DB 가 지킨다. 이메일은 대소문자를 무시하고 하나뿐이라, 같은 티켓의 두 번째 가입은 저장에서 막힌다(`409`).
티켓은 이메일 하나만 담는다. 아이디나 비밀번호가 규칙에 걸려 다시 보내도 같은 티켓을 쓴다.

**가입 코드는 계정이 아니라 이메일에 붙는다(`SignupCode`).** 계정이 생기기 전이기 때문이다. 발급과 검증의 규칙(대기 1분,
1시간에 5통, 다섯 번 틀리면 폐기, 해시에 서버의 비밀키와 자리를 섞기)은 회원의 인증 코드와 같은 코드(`accounts/email_codes.py`)를 쓰고,
자리만 다르다. 가입된 주소로 가는 안내 메일도 같은 행으로 센다. 두 경우가 같은 제한을 써야 메일의 수로 가입 여부가 드러나지 않는다.

**응답 시간도 맞춘다.** 1단계는 새 이메일이면 코드를 발급하고 코드 메일을 적고, 가입된 이메일이면 같은 행의 횟수만 세고
안내 메일을 적는다. 둘 다 DB 쓰기가 두 번이고 비밀번호 해싱은 없다(비밀번호는 3단계에서 받는다).
`scripts/measure_signup_timing.py`로 이메일마다 처음 보내는 요청을 100회씩 번갈아 잰 중앙값이다(샌드박스, 같은 기계의 PostgreSQL).

| 경우 | 중앙값 | 새 이메일 대비 |
| --- | --- | --- |
| 새 이메일 | 5.6 ~ 5.8 ms | 기준 |
| 가입된 이메일 | 5.7 ~ 5.8 ms | 0.98 ~ 1.00배 |

예전 흐름은 1단계에서 비밀번호를 해싱해, 가입된 이메일일 때 해싱을 건너뛰면 51배 빨라졌다. 그래서 일부러 한 번 해싱했다.
지금은 1단계에 비밀번호가 없어 맞출 것이 없다.

**옛 흐름의 미인증 계정은 마이그레이션으로 지웠다(`0013_delete_pending_users`).** 인증할 길(옛 `signup/verify`)이 없어져
아이디, 닉네임, 이메일을 붙잡은 채 영영 쓸 수 없는 계정이 되기 때문이다. 옛 흐름에서도 1시간이 지나면 지우던 계정이다.

**이메일 인증 전의 기존 계정은 데이터 마이그레이션으로 인증 처리했다.** 인증 필드를 추가하면
기존 계정은 값이 비어 로그인이 막힌다. 가입 시각을 인증 시각으로 채웠다.
관리자 계정(`createsuperuser`)은 만들 때부터 인증된 것으로 둔다.

### 로그인

**로그인의 두 요청은 서명한 티켓으로 잇는다.** 2단계에서 아이디를 다시 받으면, 아이디만 아는
제3자가 틀린 코드를 5번 보내 남의 코드를 폐기시킬 수 있다. 비밀번호를 통과한 쪽에게만 티켓을 주고,
2단계는 티켓이 있어야 받는다. 티켓은 DB에 저장하지 않고 서버의 비밀키로 서명한다
(`django.core.signing`). 인증 서버만 만들고 확인하므로 access 토큰과 달리 공개키가 필요 없다.
티켓에는 `public_id`와 세션 버전만 담아, 모든 기기 로그아웃 뒤에는 진행 중이던 로그인도 끊긴다.

**발급 제한을 가입에서는 숨기고 로그인에서는 알린다.** 가입은 상대가 누구인지 모르는 자리라
제한에 걸려도 같은 응답을 준다. 로그인 1단계를 통과한 쪽은 비밀번호를 증명했으므로,
숨길 이유가 없고 숨기면 오지 않는 메일을 기다리게 된다. `429`와 기다릴 시간을 준다.

**코드를 맞게 쓰면 1분 대기를 푼다.** 대기는 원하지 않는 메일이 연달아 가는 것을 막는 장치다.
코드를 맞혔다는 것은 메일함의 주인이 직접 받아 썼다는 뜻이다. 풀지 않으면 다른 기기에서 바로
로그인할 때 1분을 기다려야 한다. 1시간 5통 제한은 그대로 두고, 틀린 코드는 대기를 풀지 못한다.

### 비밀번호 변경과 재설정

**비밀번호 재설정에는 6자리 코드가 아니라 긴 토큰을 쓴다.** 재설정은 이메일 주소만 알면 누구나
요청할 수 있고, 통과하면 계정이 통째로 넘어간다. 6자리 코드는 1시간에 25번(코드 5개 × 5번)
추측할 수 있어, 한 계정을 1년 동안 노리면 맞힐 확률이 약 20%다. 로그인에서는 비밀번호를 먼저
통과해야 코드 단계에 오므로 같은 코드가 문제되지 않는다. 토큰은 256비트라 추측할 수 없다.
코드와 같은 테이블, 같은 발급 제한, 같은 해시 저장을 쓰고 값의 길이와 유효 시간만 다르다.

**토큰은 틀린 횟수로 폐기하지 않는다.** 추측할 수 없는 값이라 횟수 제한이 지키는 것이 없다.
오히려 세면, 이메일 주소만 아는 제3자가 틀린 값을 보내 남의 재설정을 방해할 수 있다.

**재설정 링크는 API가 아니라 프론트 화면을 가리킨다.** 메일 서비스와 보안 프로그램은 메일 속
링크를 미리 열어 본다. 링크를 여는 것만으로 무언가 바뀌면 사용자가 누르기 전에 토큰이 소비된다.
링크는 화면을 열기만 하고, 변경은 사용자가 낸 POST 요청이 한다. 토큰은 `?`가 아니라 `#` 뒤에 둔다.
`#` 뒤는 브라우저가 서버로 보내지 않아 접속 기록과 Referer에 남지 않는다.

**새 비밀번호의 규칙 검사는 토큰이 맞은 뒤에 한다.** "아이디와 비슷한 비밀번호입니다"라는 답은
그 계정이 있다는 사실을 알려 준다. 토큰이 틀리면 비밀번호가 어떻든 같은 오류를 준다.
검사에 걸리면 토큰은 소비되지 않아, 비밀번호만 고쳐 같은 링크로 다시 시도할 수 있다.

**비밀번호 저장과 세션 종료는 한 트랜잭션이다.** 변경과 재설정이 같은 함수로 검사, 저장,
세션 종료를 함께 한다. 비밀번호는 바뀌었는데 옛 세션이 살아 있는 경로가 없다. 세션 종료는
세션 버전을 올리는 것이라 access 토큰, refresh 토큰, 진행 중이던 로그인 티켓이 한꺼번에 무효가 된다.

**비밀번호가 바뀌면 알림 메일을 보낸다.** 변경에 메일 확인 절차를 더하지 않았다. 로그인한 사람은
이미 비밀번호와 이메일 코드를 통과했고 현재 비밀번호도 다시 입력한다. 확인 절차는 사용자를
번거롭게 하지만 알림은 그렇지 않고, 본인이 모르게 바뀐 경우를 알아챌 수 있게 한다.

### 메일 발송

**메일은 요청 안에서 보내지 않는다. 발송함에 적고 워커가 보낸다.** 요청 안에서 보내면 두 가지가
깨진다. 메일 서버와 통신하는 시간(보통 0.5~2초)이 응답 시간에 그대로 드러나, 메일을 보낸 요청
(가입된 주소)과 보내지 않은 요청(없는 주소)이 구분된다. 응답 본문을 맞춘 것이 소용없어진다.
그리고 메일 서버가 느리거나 죽으면 가입과 로그인이 함께 느려지거나 실패한다.

**발송함은 PostgreSQL 테이블이다(outbox 패턴).** 스레드는 실패하면 메일이 사라지고 재시도할 수 없다.
Celery 같은 작업 큐는 Redis를 중개자로 써서, 로그인이 Redis에 의존하게 된다. 인증 코드를
PostgreSQL에 둔 이유와 어긋난다. 테이블에 적는 방식은 PostgreSQL만 쓰고, 적는 일이 계정 생성이나
코드 발급과 같은 트랜잭션에 들어간다. "계정은 만들어졌는데 보낼 메일은 없는" 상태나 그 반대가
생기지 않는다. 메일 서버는 DB의 트랜잭션에 참여할 수 없지만, "보낼 메일이 있다는 사실"은 참여할 수 있다.

**워커는 메일을 차지하고, 트랜잭션 밖에서 보내고, 짧게 마무리한다(#24).** 세 걸음이다.

1. 차지하기: 짧은 트랜잭션에서 보낼 메일 하나를 잠그고(`select_for_update`), 상태를 `보내는 중`으로,
   시도 횟수를 하나 올리고, 다음 시도 시각을 임대가 끝나는 시각(지금 + 2분, `MAIL_CLAIM_LEASE`)으로 바꿔 커밋한다.
   다른 워커가 차지하는 중인 행은 기다리지 않고 건너뛴다(`skip_locked`)
2. 보내기: 트랜잭션도 잠금도 없이 메일 서버와 통신한다
3. 마무리: 보냈으면 행을 지우고, 실패했으면 대기 상태로 돌려 다음 시도 시각을 정한다. 둘 다 "보내는 중이고 시도 횟수가 차지할 때 그대로인 행"에만 한다

예전에는 행을 잠근 채 메일 서버의 답을 기다렸다. 메일 서버의 시간 제한(`SMTP_TIMEOUT`, 10초)은 연결, 인사, 암호화, 인증, 보내기의
단계마다 따로 걸려서, 한 통이 수십 초 동안 트랜잭션과 DB 연결을 쥘 수 있었다. 워커를 늘리면 늘린 만큼 연결이 묶였다.

- 워커가 보내는 도중 죽으면, 임대가 끝난 뒤 다른 워커가 그 메일을 다시 가져간다(`warning` 로그, 마지막 오류 칸에 적힌다).
  앞의 워커가 이미 보냈다면 두 번 간다. 예전에도 "보낸 뒤 커밋 전에 죽으면 다시 보낸다"였다. 인증 코드 메일은 두 번 와도 해가 없다
- 임대가 끝나 다른 워커가 가져간 뒤에 앞의 워커가 늦게 끝나면, 시도 횟수가 달라져 있어 아무것도 고치지 않는다(`warning` 로그).
  다음 워커의 차지를 대기 상태로 되돌리거나 지우지 않는다
- 2분은 메일 서버와의 여러 단계보다 넉넉하고, 버리는 시각(5분) 안에 한 번 더 차지할 여유가 남는 길이다
- refresh 토큰 회전의 잠금은 반대로 기다린다. 같은 토큰의 두 번째 요청은 첫 번째가 끝난 뒤 거부되어야 하기 때문이다

**실패한 메일은 간격을 두 배씩 늘려 다시 보내고, 5분이 지나면 버린다.** 5초, 10초, 20초 순이다.
메일 서버가 죽어 있을 때 쉬지 않고 두드리지 않는다. 5분은 인증 코드의 유효 시간이다.
그 뒤에 도착하는 코드는 쓸모가 없다. 사용자에게는 알리지 않는다. 응답은 이미 나갔고,
사용자는 메일이 오지 않으면 재발송을 누른다. 운영자는 관리자 화면의 "보낼 메일"과 로그에서 본다.

**발송함의 본문은 암호화해서 적는다.** 메일 본문에는 인증 코드와 재설정 토큰이 원문으로 들어 있다.
코드를 해시로만 저장해 놓고 발송함에 본문을 그대로 두면, DB를 읽을 수 있는 사람이 보내기 전의
코드와 토큰을 얻는다. 특히 재설정 토큰은 이메일과 함께 있으면 비밀번호를 바꿀 수 있다.
워커가 원래 본문을 보내야 하므로 해시가 아니라 암호화(Fernet)다. 키는 따로 저장하지 않고
`SECRET_KEY`에서 만든다. DB만으로는 읽을 수 없고 서버의 비밀키가 함께 있어야 한다.
복호화할 수 없는 메일(비밀키가 바뀌었거나 값이 고쳐진 경우)은 바로 버린다.
보낸 행은 즉시 지우고 버린 행은 본문을 비운다. 로그에는 본문도 받는 사람 주소도 적지 않는다.

### 환영 크레딧

**본인인증을 처리하면서 결제 서버를 부르지 않는다. 적어 두고 워커가 맡긴다.** 메일과 같은 구조다(outbox).
인증하는 자리에서 바로 부르면 결제 서버가 죽어 있을 때 둘 중 하나를 골라야 한다. 인증을 실패시키거나, 크레딧을 못 주고 넘어가거나.
적어 두면 인증은 결제 서버와 상관없이 끝나고, 결제 서버가 살아나면 지급된다. 적는 일은 본인인증의 기록을 적는 일과 같은 트랜잭션이다.
인증은 됐는데 줄 일은 적히지 않은 경우가 생기지 않는다.

**이메일 인증이 아니라 본인인증 때 준다(#336).** 이메일은 얼마든지 만들 수 있다. 예전에는 메일함(주소를 소문자로 바꾸고 `+` 뒤를 뗀 것)마다
한 번으로 묶었지만, 주소를 여럿 가진 사람은 여러 번 받았다. 휴대폰 본인인증의 DI 는 사람마다 하나라 한 사람이 한 번 받는다.

**메일과 달리 버리지 않는다.** 인증 코드는 5분 뒤에 쓸모가 없지만 크레딧은 늦게 줘도 쓸모가 있다.
실패하면 간격을 두 배씩 늘려(5초, 10초, ...) 다시 맡기고, 간격은 1시간에서 멈춘다. 결제 서버가 하루를 죽어 있어도 살아나면 나간다.

**같은 사용자로 몇 번을 맡겨도 한 번만 들어간다.** 그것은 결제 서버가 지킨다. 워커가 결제 서버를 부른 뒤 결과를 적기 전에 죽으면
그 줄은 다시 나가고, 결제 서버는 "이미 받았다"고 답한다. 그래서 워커는 "적어도 한 번"만 지키면 된다.

**받는 것은 사람마다, 계정마다 한 번이다.** 결제 서버는 사용자 번호마다 한 번만 준다. 그것만으로는
계정을 지우고 새 계정에서 다시 본인인증을 하면 번호가 새로 생겨 또 받는다. 그래서 "이 사람은 이미 받았다"를 이 서버가 적어 둔다.
한 사람은 한 계정에서만 본인인증을 하지만(아래의 "본인인증"), 계정을 지우면 그 기록도 지워져 새 계정에서 다시 인증할 수 있다.
환영 크레딧의 줄은 지우지 않으므로 그때도 다시 받지 못한다.
#336 전에 이메일 인증으로 받은 계정은 그 줄의 열쇠가 메일함의 것이다(주소를 소문자로 바꾸고 `+` 뒤를 뗀 것). 그래서 계정(공개 ID)으로도 한 번 더 막는다.

**사람의 기록과 맡길 일의 목록이 같은 테이블이다(`WelcomeCredit`).** 따로 두면 "기록은 있는데 맡길 일은 없는" 줄을 맞춰야 한다.
한 줄이 "이 사람은 받기로 했다"이고, 그 줄의 상태가 "맡겼는가"다. 끝난 줄도 지우지 않는다. 지우면 기록이 사라진다.
관리자 화면에서도 지울 수 없다.

**DI 가 아니라 비밀키로 서명한 값을 적는다(`recipient_key`).** 본인인증의 사람 열쇠와 같은 값이다. 이 줄은 계정을 지운 뒤에도 남는다.
`SECRET_KEY`를 섞은 HMAC 이라 DB 만으로는 사람을 알아낼 수 없다. 옛 줄의 메일함 열쇠와는 섞는 값(salt)이 달라 겹치지 않는다.
받는 사용자는 공개 ID 로만 적고 외래 키로 두지 않는다. 계정이 지워져도 줄은 남아야 한다.

**결제 서버는 토큰이 아니라 요청의 서명으로 이 서버를 확인한다.** 사용자의 토큰으로 "나에게 크레딧을 줘"를 부를 수 있으면
위의 사람 규칙이 소용없다. 두 서버만 아는 비밀로 요청의 메서드, 주소, 본문, 시각을 서명한다(`accounts/service_signature.py`).
비밀을 머리말에 그대로 싣지 않는다. 서명은 그 요청에만 쓸 수 있고 5분 뒤에는 못 쓴다.
받는 쪽의 규칙은 [결제 서버의 설명서](../billing-server/README.md#홀드)에 있다. 두 서버의 테스트에 같은 서명 값이 적혀 있어,
한쪽의 계산이 바뀌면 그쪽의 테스트가 깨진다.

**요청은 표준 라이브러리(`urllib`)로 보낸다.** 부르는 주소가 하나고 요청이 단순하다. HTTP 라이브러리를 의존성에 더할 만큼이 아니다.
환경 변수의 프록시를 쓰지 않고, 다른 주소로 가라는 답을 따라가지 않게 해 두었다. 서명한 요청이 우리가 고르지 않은 곳으로 가면 안 된다.

**알려진 한계**

- `SECRET_KEY`를 바꾸면 사람 열쇠가 모두 달라진다. 그 전에 받은 사람이 새 계정으로 다시 받을 수 있게 된다.
  본인인증의 "한 사람 한 계정"도 같이 풀린다. `SECRET_KEY` 는 바꾸지 않는 값으로 다룬다
- 휴대폰을 여럿 가진 사람(다른 명의 포함)은 여러 번 받는다. 본인확인으로 막을 수 있는 것은 명의까지다
- 결제 서버가 환영 크레딧을 꺼 둔 동안(`WELCOME_CREDITS=0`) 가입한 사용자는 나중에 켜도 받지 않는다. 맡길 일은 끝난 것으로 적힌다
- 워커는 행을 잠근 채로 결제 서버의 답을 기다린다(최대 5초). 메일 워커는 차지하고 트랜잭션 밖에서 보내는 방식으로 바꿨다([#24](https://github.com/epqlffltm/ai-trpg/issues/24)).
  이 워커는 아직 예전 방식이다. 묶이는 시간이 5초까지라 짧지만, 워커를 늘릴 때는 같은 방식으로 바꾼다

### 본인인증

**휴대폰 본인확인 한 번으로 "한 사람"과 "나이"를 함께 안다(#336).** 이메일 인증으로는 둘 다 알 수 없다.
업체가 주는 것 가운데 DI(이 서비스에서 그 사람의 식별값)와 생일만 쓴다. 이름, 전화번호, 성별은 받아도 넘기지 않는다(`accounts/identity_providers.py`).
업체를 고르는 곳은 설정 하나(`IDENTITY_PROVIDER`)다. 실제 업체를 붙일 때 그 파일에 업체 하나를 더한다. 결제 서버의 가짜 결제 대행사와 같은 생각이다.

**나이의 기준이 둘이다.** 민법은 만 19세 생일부터 성년이고(결제), 청소년 보호법은 만 19세가 되는 해의 1월 1일부터 청소년이 아니다(성인용 내용).
그래서 날짜를 둘 적는다(`legal_adult_from`, `adult_content_from`). 2월 29일생은 그날이 없는 해에 3월 1일부터 나이를 먹는다(민법 160조).
날짜는 한국 날짜로 자른다. 서버의 시각은 UTC 라 그대로 자르면 아침 9시까지 하루가 늦다(`accounts/age.py`).

**이미 지난 날짜는 적지 않는다.** 성인의 `legal_adult_from` 은 곧 생일이다. 성인은 두 칸을 비워 "이미 지났다"로 둔다.
미성년자만 날짜가 남고, 그날이 오면 다시 인증하지 않아도 상태가 바뀐다. 생일과 DI 는 어디에도 적지 않는다. DI 는 서명한 값(사람 열쇠)만 적는다.

**한 사람 한 계정은 DB 가 지킨다.** 사람 열쇠가 하나뿐이라는 유일 제약이 마지막 방어다. 두 계정이 같은 사람으로 함께 인증해도 하나만 적힌다.
같은 계정의 두 요청은 계정의 줄을 잠가 차례로 지나간다. 거절은 보안 이벤트(`identity_in_use`)로 남긴다. 부모의 휴대폰이나 계정 여러 개를 운영자가 알아본다.
업체에는 트랜잭션 밖에서 묻는다. 업체가 느려도 DB 의 잠금을 오래 쥐지 않는다.

**만 14세 미만은 계정을 막고 모은 개인정보를 지운다.** 개인정보 보호법(22조의2)은 만 14세 미만의 개인정보를 보호자의 동의 없이 모으지 못하게 한다.
가입 때 "만 14세 이상" 확인(자기 신고)을 받지만 이메일만으로는 나이를 알 수 없어, 본인인증에서 알게 된 때 막는다.
계정의 줄은 지우지 않는다. 지우면 세션 버전이 사라져 다른 서버에 끊긴 세션을 알릴 수 없고, 이미 발급된 access 토큰이 15분까지 통한다.
그래서 정지처럼 막고 세션을 끊은 뒤 아이디, 닉네임, 이메일, 비밀번호를 비운다(`removed-<번호>`, `<번호>@removed.invalid`).
붙임표는 아이디와 닉네임이 받지 않는 글자라 사용자가 먼저 가져갈 수 없다. 그 주소로 남은 코드와 보낼 메일도 지운다.
인증 기록은 만들지 않는다. 생일도 DI 도 남지 않는다.

**인증의 응답은 토큰을 다시 주지 않는다.** 비밀번호 변경처럼 새 쌍을 주면 쿠키 속의 옛 refresh 토큰이 폐기되지 않은 채 14일을 산다.
화면이 `/refresh` 를 부르면 옛 토큰이 폐기되면서 `adult_content` 가 실린 새 토큰이 온다.

**알려진 한계**

- 미성년자가 부모의 휴대폰으로 인증하면 막을 수 없다. 인증 기록은 남는다(민법 17조: 속임수로 성년이라 믿게 했으면 취소할 수 없다)
- 보호자에게 결제를 알리는 메일은 결제 서버의 #337 뒤에 붙인다
- 만 14세 미만으로 막은 계정의 보안 이벤트에 남은 IP 는 지우지 않는다. 30일 뒤 다른 이벤트와 함께 지워진다
- 계정을 지우면 인증 기록도 지워져 같은 사람이 새 계정에서 다시 인증할 수 있다. 환영 크레딧은 다시 받지 못한다

### 보호자 동의

**보호자는 계정을 만들지 않는다.** 보호자에게 가입부터 시키면 동의를 받기가 어렵다. 메일의 링크와 보호자의 휴대폰 본인인증이 확인이다.
철회도 계정 없이 메일의 링크로 한다. 링크에는 미성년자의 공개 ID 와 일회 값을 서명해 넣는다(`accounts/guardian_links.py`). DB 에 링크를 적지 않는다.
일회 값은 새로 요청할 때 바뀐다. 그래서 앞서 보낸 동의 링크와, 철회한 뒤 다시 요청했을 때의 옛 철회 링크가 쓸 수 없게 된다.
동의 링크와 철회 링크는 서명에 섞는 값이 달라 서로의 자리에 쓸 수 없다.

**보호자는 한 명이고, 동의한 동안에는 바꿀 수 없다.** 미성년자가 보호자를 바꿀 수 있으면 아무 성인에게 다시 동의를 받아
보호자의 철회를 피할 수 있다. 바꾸려면 지금의 보호자가 철회한다. 미성년자는 철회하지 못한다.

**보호자는 성년이고 미성년자 본인이 아니어야 한다.** 보호자의 본인인증에서 생일과 DI 를 받아, 성년인지와 미성년자의 사람 열쇠와 같은지를 본다.
관계(부모인지)는 확인하지 않는다. 서류를 받지 않기로 했다. 남는 것은 동의한 사람의 사람 열쇠와 시각이다. 다툼이 생기면 그것으로 맞춰 본다.
보호자가 여러 미성년자(형제)에게 동의하는 것은 막지 않는다.

**보호자의 이메일은 요청부터 철회까지만 둔다.** 동의 링크, 결제 알림, 철회 확인을 보내려고 적는다. 철회하면 비운다.
요청 메일은 1분에 1통, 하루에 5통까지다. 미성년자가 남의 메일함에 링크를 퍼붓지 못하게 한다.

**동의의 끝은 적지 않는다.** 동의는 미성년자가 성년이 되는 날까지다. 그 날짜는 이미 본인인증에 있고, 결제 서버가 함께 받아 스스로 센다.

### 결제 자격 알림

**결제 서버는 결제할 때 이 서버를 부르지 않는다.** 부르면 이 서버가 죽었을 때 결제가 멈추고, 결제마다 서버 사이의 호출이 하나 는다.
그래서 이 서버가 미리 알려 둔다(`accounts/payment_eligibility.py`). 환영 크레딧과 같이 적어 두고 워커가 보낸다.
워커는 환영 크레딧의 워커(`send_welcome_credits`, compose 의 `auth-welcome-credits`)가 한 바퀴에 함께 한다. 이름은 처음 맡은 일의 것이다.

**사건이 아니라 지금의 상태를 버전과 함께 보낸다.** 보내는 것은 성년이 되는 날(성년이면 비움)과 보호자 동의가 있는가 둘이다.
"동의함", "철회함" 같은 사건을 보내면 순서가 뒤집히거나 하나가 빠졌을 때 결제 서버의 상태가 틀린다.
상태와 버전을 보내면 결제 서버는 가진 것보다 높은 버전만 받으면 된다. 늦게, 두 번, 건너뛰어 도착해도 마지막 상태로 맞는다.
계정마다 한 줄이고, 바뀔 때마다 버전이 오른다. 줄이 쌓이지 않는다.

**보내는 동안 줄을 잠가 두지 않는다.** 짧은 트랜잭션에서 줄을 차지하고(다음 시도 시각을 30초 뒤로 민다) 트랜잭션 밖에서 보낸다.
잠근 채로 결제 서버를 기다리면 그동안 그 사용자의 동의와 철회가 멈춘다. 보내는 사이에 상태가 또 바뀌면 버전이 올라 있어 다음 바퀴에 다시 나간다.
워커가 보내다 죽으면 30초 뒤에 다른 워커가 다시 보낸다. 알린 버전은 줄어들지 않는다.

**알려진 한계**

- 결제 서버가 받기 전(본인인증 직후 몇 초, 워커나 결제 서버가 멈춘 동안)에는 결제 서버가 "본인인증 전"으로 본다. 결제가 막히는 쪽으로 틀린다
- 계정을 지우면 그 줄도 지워진다. 결제 서버에 남은 상태는 그대로다. 지운 계정은 로그인할 수 없어 결제도 못 한다
- 미성년자가 성년이 된 뒤에도 보호자의 이메일이 남는다. 성년이 된 뒤 정리하는 일은 아직 없다

### 보호자 결제 알림

**미성년자가 결제하거나 청약철회하면 동의한 보호자에게 메일로 알린다(#352).** 결제 서버는 보호자의 이메일을 모른다.
결제 서버가 알릴 일을 서명해 보내면(`POST /api/v1/auth/service/guardian-notices`) 이 서버가 보호자의 이메일로 메일을 적는다(`accounts/guardian_notices.py`).
메일에는 상품, 금액, 시각(한국 시각)과 철회 링크가 있다. 주문과 종류(결제, 청약철회)마다 한 번이다. 결제 서버가 다시 보내도 메일은 한 번 간다.
그새 보호자가 철회했거나 계정이 지워졌으면 메일 없이 "알릴 보호자가 없음"으로만 남긴다.

**법의 의무가 아니라 안전장치다.** 게임산업법(12조의3 ①4, 시행령 8조의3)의 이용내역 고지(월 1회 이상)는 중소기업이면 적용되지 않는다.
결제마다 알리면 다툼("보호자는 몰랐다")에서 근거가 되고, 보호자가 바로 철회할 기회가 된다. 나중에 의무가 생겨도 월 1회를 넘는다.

**메일만 쓴다.** 문자와 알림톡은 건당 돈이 들고 알림톡은 사업자 등록이 먼저다. 시행령도 고지 방법에 전자우편을 든다.
동의 요청 메일과 동의 확인 메일에 "결제 알림은 이 이메일로만 보낸다"를 적는다. 보호자는 그것을 보고 동의한다.

**보냈다는 것을 남긴다(`MailReceipt`).** 발송함의 줄은 보내면 지운다(본문에 인증 코드가 있어서). 그래서 결제 알림은 기록을 붙여 적고,
메일 서버가 받으면 그 시각을, 끝내 못 보내면 버린 시각을 적는다. 받는 사람과 본문은 적지 않는다. 받는 사람이 읽었는지는 알 수 없다.
결제 알림은 하루가 지나야 버린다(인증 코드는 5분).

**결제 서버의 서명을 확인한다.** 비밀은 `BILLING_SECRET` 이다(결제 서버의 `AUTH_SERVER_SECRET` 과 같은 값). 이 서버가 결제 서버를 부를 때와 같은 짝이다.
서명에 주소가 들어가므로 한쪽 방향의 요청을 다른 방향의 주소에 쓸 수 없다. 앞뒤로 5분이 넘게 벌어진 서명은 받지 않는다.
그래서 compose 의 `auth-server` 에도 `BILLING_SECRET` 을 준다(전에는 환영 크레딧의 워커만 받았다). 프록시는 `/api/v1/auth/service/` 를 바깥에 열지 않는다(404).

### 시도 횟수 제한

**시도 횟수는 Redis에 세고, Redis가 죽으면 막지 않는다.** 인증의 1차 방어(비밀번호, 인증 코드,
코드의 오답 제한)는 전부 PostgreSQL에 있다. 횟수 제한은 그 앞에서 속도를 늦추는 보조 장치다.
Redis 장애가 로그인 장애가 되면 안 되므로, Redis에 닿지 못하면 경고 로그를 남기고 통과시킨다.
연결과 응답을 0.2초까지만 기다린다. Redis가 죽어 있으면 즉시 실패하지만, 응답 없이 멈춰 있으면
명령마다 그만큼 기다린다. 로그인 한 번이 Redis를 서너 번 부르므로 로그인마다 0.6~0.8초가 늘어난다.

**그래서 Redis 앞에 차단기를 둔다(#26, `config/redis_client.py`).** 연달아 3번 실패하면 열어서 30초 동안
Redis에 묻지 않고 바로 통과시킨다. 30초가 지나면 요청 하나로 시험해, 성공하면 닫고 실패하면 다시 30초 연다.
결과(제한 없이 통과)는 차단기가 없을 때와 같고, 기다리는 시간과 요청마다 쌓이던 경고 로그만 없어진다.
Redis가 살아난 뒤 제한이 다시 켜지기까지 최대 30초가 걸린다.
Redis의 오류(`RedisError`)만 센다. 코드의 실수 같은 다른 예외는 Redis가 아프다는 신호가 아니다.
차단기는 [pybreaker](https://pypi.org/project/pybreaker/)를 쓴다. 열림, 시험, 닫힘의 전환을 직접 짜면 틀리기 쉽다.
상태는 프로세스마다 따로 있다. pybreaker 는 상태를 Redis에 두는 기능도 있지만, 죽은 Redis에 둘 수는 없다.
pybreaker 의 `call()` 은 명령이 끝날 때까지 잠금을 쥐어, 한 프로세스의 Redis 명령이 한 줄로 선다.
gunicorn 의 sync 워커는 프로세스에 스레드가 하나라 손해가 없다. 스레드 워커(gthread)로 바꾸면 다시 본다.

**횟수 올리기와 유효 시간 걸기는 Lua 스크립트 하나다.** 따로 보내면 횟수를 올린 직후 서버가
죽었을 때 유효 시간이 없는 키가 남아, 그 대상은 영영 막힌다. 구간은 첫 시도에서 시작해 고정된다.
경계에 걸치면 짧은 시간에 최대 2배까지 허용되지만, 속도를 늦추는 용도에는 충분하다.
Redis 키에는 IP나 아이디를 그대로 넣지 않고 해시를 넣는다.

**로그인 실패는 계정만으로 세지 않고 계정과 IP의 쌍으로 센다.** 계정만으로 세면 남의 아이디로
일부러 틀려서 주인을 잠글 수 있다. 쌍으로 세면 다른 곳에 있는 주인은 영향을 받지 않는다.
대신 IP를 바꿔 가면 계정마다 IP당 5번씩 시도할 수 있다. 그 경우는 로그인 2단계의 이메일 코드가 막는다.
없는 아이디도 똑같이 센다. 있는 아이디만 막히면 막히는지 여부로 가입 여부가 드러난다.
막힌 동안에는 맞는 비밀번호도 확인하지 않는다.

**실패 횟수는 비밀번호를 확인하기 전에 세고, 맞았으면 지운다.** 처음에는 "막혔는지 확인, 비밀번호 확인,
틀렸으면 세기" 순서였다. 그러면 동시에 들어온 요청들이 전부 "아직 한도 전"을 보고 통과해 한도보다
많이 확인받는다. 먼저 세면 Redis가 요청마다 다른 횟수를 돌려주므로 한도까지만 통과한다.
동시 요청 20개를 보내 5개만 비밀번호 확인까지 가고 15개는 `429`인 것을 확인했다.

**IP별 제한은 DRF의 throttle로, 실패 횟수 제한은 뷰에서 건다.** throttle은 뷰가 실행되기 전에
돌아서 결과를 모른다. 모든 시도를 세는 제한에는 맞고, 실패만 세는 제한에는 맞지 않는다.
DRF에 들어 있는 `SimpleRateThrottle`은 쓰지 않고 `BaseThrottle`에 위의 Redis 코드를 연결했다.
기본 구현은 횟수를 읽고 쓰는 것이 따로라 동시 요청에서 새고, 캐시가 죽으면 `500`이 된다.
어느 길로 막히든 응답이 같도록 예외 처리기 한 곳에서 `429`를 만든다.
`django-axes`도 검토했다. 로그인 실패 잠금만 맡을 수 있고, IP를 꺼내려고 service가 `request`를
받아야 해서 쓰지 않았다.

**요청자의 IP는 "신뢰할 프록시의 수"로 정한다.** `X-Forwarded-For`는 요청을 보내는 쪽도 적을 수
있다. 프록시는 뒤에 주소를 붙이므로, 뒤에서 `TRUSTED_PROXY_COUNT`번째만 믿는다. 기본값 0은 헤더를
보지 않는다. 이 값이 실제 구조보다 크면 누구나 IP를 지어낼 수 있고, 작으면 모든 요청이 프록시의
IP로 보여 한 사람의 시도가 모두를 막는다.

**예약어 아이디로 로그인을 반복해 시도한 IP는 막고, 막혔다고 알려 주지 않는다.** 예약어는
누구도 아이디로 쓸 수 없어서 그 시도는 오타로 일어나지 않는다. 1시간 안에 3번이면 막는다.
처음에는 한 번에 막았다. 공유기 뒤의 여러 사람이 한 IP로 보이는데, 한 사람의 한 번으로 모두가
막히는 것은 지나쳐서 3번으로 바꿨다. 막힌 IP에는 평소의 `401`을 주고, 비밀번호를 확인할 때만큼의
시간을 일부러 쓴다. 바로 응답하면 응답 시간으로 막힌 것이 드러난다. 로그인만 막는다.

**예약어는 이름 그 자체와 번호만 붙인 변형(`admin1`, `root_2`, `운영자0001`)이다.** 밑줄은 없어도 되고
숫자는 1~4자리다. 가입(아이디, 닉네임)과 로그인 감시가 `is_reserved_name` 하나를 같이 쓴다. 로그인이
가입보다 넓게 보면, 가입이 허용한 이름의 주인이 자기 로그인 세 번으로 IP를 막기 때문이다. 규칙을
넓히기 전에 만든 계정이 있을 수 있어서, 그 아이디의 계정이 있으면 로그인에서 세지 않는다. 편집 거리,
글자 치환(`r00t`), 부분 일치(`badminton`)는 보지 않는다. 오탐이 늘고 판정을 예측하기 어렵다.

### 보안 이벤트

**보안 이벤트는 막히기 시작한 순간에 한 번만 남긴다.** 횟수는 Redis에서 사라지므로 남겨야 할
사실은 PostgreSQL에 적는다. 막힌 뒤의 요청마다 적으면 공격자가 요청 수만큼 행을 쌓을 수 있다.
입력된 아이디 문자열은 남기지 않는다. 아이디 칸에 비밀번호를 잘못 넣는 일이 흔하다.
실제로 있는 계정일 때만 그 계정을 연결한다.

**요약 메일은 시간으로 자르지 않고 "알렸는가"를 행에 표시해 고른다.** "지난 1시간"으로 자르면
실행이 늦을 때 사건이 빠지고 두 번 돌 때 겹친다. 메일을 발송함에 적는 것과 표시하는 것이
한 트랜잭션이라 사건마다 정확히 한 번 알린다. 보내지 못하고 버린 메일도 같은 이벤트로 남겨
요약에 실린다. 한 번에 1,000건까지만 읽고 나머지는 다음 실행으로 넘긴다. 한도가 없으면 사건이
많이 쌓였을 때 전부를 메모리에 올리고 잠근다. 이벤트는 30일 뒤에 지운다.

**남긴 이벤트마다 로그 한 줄도 남긴다**(`warning`, `error_code: security.event`). 로그 모으기(Loki)에서
같은 요청의 다른 줄과 `request_id`, `trace_id` 로 이어 본다. 저장한 뒤에 남겨서 되돌린 이벤트의 줄은 없다.
줄에는 종류(`security_event`), 이벤트의 번호(`security_event_id`), 대상 계정의 공개 ID(`user_id`)만 싣는다.
IP 와 운영자의 사유는 싣지 않는다. 로그는 더 넓게 퍼지는 곳이라 번호로 관리 화면에서 찾아본다.

### 코드 구조

**검증, 생성, HTTP 처리를 나눈다.** Serializer는 입력 검증만, service는 계정 생성만,
뷰는 요청과 응답 변환만 한다. DRF 관례는 Serializer의 `create()`에 생성 로직을 두는 것인데,
그러면 검증과 상태 변경이 한 클래스에 섞인다.

**중복은 두 번 막는다.** service의 사전 조회는 어느 값이 겹쳤는지 알려 주는 용도다.
동시에 들어온 요청은 사전 조회를 둘 다 통과할 수 있으므로, 최종 방어는 DB의 유니크 제약이고
그때는 `409`로 응답한다. 가입 3단계의 검사(아이디가 이메일과 겹치는지, 비밀번호가 아이디나 이메일과 비슷한지)는
티켓 속의 이메일이 있어야 판단할 수 있어서, 중복 조회와 함께 Serializer가 아니라 service에 둔다.

**API의 기본 권한은 "인증된 사용자만"이다.** 공개 API는 뷰에서 직접 열어야 한다.
권한 설정을 빠뜨린 뷰가 열려 있는 것보다 닫혀 있는 쪽이 안전하다.

**API 목록은 뷰에 적은 모양에서 뽑고, 테스트가 받은 응답으로 견준다(#558).** 세 길이 있었다.

- 뷰에 적기만 하기(drf-spectacular). 작다. 적은 모양이 코드와 어긋나도 잡지 못한다. 뷰가 dict 를 손으로 만들어서 어긋나기 쉽다
- 손으로 쓴 목록 + 테스트(결제 서버의 방식). drf-spectacular 를 쓰지 않는다. 뷰와 목록이 두 곳에 떨어진다
- 뷰에 적고 + 테스트가 받은 응답을 견주기. 고른 것이다

견주는 일은 테스트 실행기가 Django 의 테스트 클라이언트를 감싸 건다. 테스트 파일마다 고치지 않아도 800 개가 넘는 HTTP 테스트가 모두 견준다.
처음 걸었을 때 공개키(JWKS)의 응답에 목록에 없던 `key_ops` 가 있는 것을 잡았다(PyJWT 가 붙인다).
견주는 도구(openapi-core)는 테스트에만 쓴다(dev 의존성). 서버는 요청마다 목록으로 검사하지 않는다.

## 운영 메모

**운영자를 넣고 빼는 법(#389).** 관리자 화면(`/admin/`)의 회원 → 그 계정 → 권한의 "그룹"에서 `operators` 를 넣거나 뺀다.
`is_staff`(관리자 화면에 들어가는 권한)는 따로다. 운영자에게 관리자 화면까지 줄 필요는 없다.
넣은 뒤에는 그 사람이 다시 로그인하거나 토큰을 갱신해야 실린다. 운영자는 다른 서버에서 남의 시나리오, 테이블의 기록, 귓속말까지 보므로 꼭 필요한 사람만 넣는다.

**운영에서 띄우는 법.** `runserver` 는 개발용이다. 컨테이너(`Dockerfile`)는 gunicorn 으로 띄우고, 설정은 `gunicorn.conf.py` 에 있다.
프로세스 수는 `WEB_CONCURRENCY` 로 정한다(적지 않으면 1). gunicorn 이 스스로 남기는 줄도 공통 규격의 JSON 으로 나간다.
`DEBUG` 를 끄면 Django 가 정적 파일을 내주지 않는다. 관리자 화면의 CSS 와 JS 는 whitenoise 가 `STATIC_ROOT` 에서 내준다.
이미지를 만들 때 `collectstatic` 으로 모아 둔다. 개발 중에는 `STATIC_ROOT` 를 적지 않는다.
모든 서버를 함께 컨테이너로 띄우는 법은 [저장소 README](../README.md#4-모든-서버를-컨테이너로-선택)에 있다.

**서명 키는 서버만 갖는다(#274).** 개인키로는 누구의 토큰이든 만들 수 있다. 그래서 그 키를 쓰는 프로세스(요청을 받는 서버)에만 준다.
`JWT_PRIVATE_KEY_PATH` 가 비면 설정이 키를 읽지 않는다(`config/jwt_keys.py`). 메일·환영 크레딧의 워커, cron, 마이그레이션은 서명하지 않으므로 compose 가 경로를 비우고 키 폴더를 붙이지 않는다.
- 키가 없는 프로세스가 토큰을 만들거나 JWKS 를 내려 하면 `SigningKeyUnavailableError` 다(`accounts/key_ring.py`). 빈 JWKS 를 내면 다른 서버가 모든 토큰을 거부하므로 내지 않는다
- 요청을 받는 서버의 입구(`config/wsgi.py`, `config/asgi.py`)는 키가 없으면 뜨지 않는다. 키 없이 뜬 서버는 첫 로그인에서야 실패한다
- 경로를 적었는데 파일이 없는 것은 지금처럼 뜨지 않는다. 비운 것과 잘못 적은 것은 다르다
- PC 에서 직접 띄울 때는 바뀌는 것이 없다. `.env` 의 경로(기본 `keys/jwt-private.pem`)를 모든 명령이 함께 읽는다

**JWT 키 교체(#21).** 세 단계다. 단계마다 설정을 고치고 인증 서버를 다시 띄운다. 다른 세 서버는 고치지 않는다.
그쪽은 JWKS 를 기억해 두고(게임·결제 서버 5분, 게시판 서버 1시간), 모르는 `kid` 가 오면 다시 받아 간다.

1. 새 키를 미리 알린다. 새 개인키를 만들고 공개키를 꺼내 검증 키에 넣는다. 서명은 아직 옛 키다.
   ```
   uv run python scripts/generate_jwt_key.py keys/jwt-private-next.pem
   uv run python scripts/export_jwt_public_key.py keys/jwt-private-next.pem keys/jwt-public-next.pem
   ```
   `.env` 에 `JWT_EXTRA_PUBLIC_KEY_PATHS=keys/jwt-public-next.pem` 을 적고 다시 띄운다. JWKS 에 키가 둘 실린다. **1시간 넘게** 둔다(다른 서버의 JWKS 기억 시간 중 가장 긴 것).
2. 서명을 바꾼다. 옛 키의 공개키를 꺼내 두고, 새 개인키를 서명 키 자리로 옮긴다.
   ```
   uv run python scripts/export_jwt_public_key.py keys/jwt-private.pem keys/jwt-public-old.pem
   ```
   옛 `keys/jwt-private.pem` 을 지우고 `keys/jwt-private-next.pem` 을 `keys/jwt-private.pem` 으로 이름을 바꾼다.
   `.env` 를 `JWT_EXTRA_PUBLIC_KEY_PATHS=keys/jwt-public-old.pem` 으로 고치고 다시 띄운다(`jwt-public-next.pem` 은 이제 서명 키라 지운다).
   compose 는 서명 키의 경로를 `keys/jwt-private.pem` 으로 정해 두므로 파일 이름을 바꾸는 방식으로 한다.
3. **14일 뒤** 옛 키를 뺀다. `JWT_EXTRA_PUBLIC_KEY_PATHS` 를 비우고 다시 띄운 뒤 `keys/jwt-public-old.pem` 을 지운다.
   14일은 refresh 토큰의 수명이다. 그 전에 빼면 옛 키로 받은 refresh 토큰이 모두 거부되어 그 사용자들이 다시 로그인해야 한다.

설정이 틀리면 서버가 뜨지 않는다: 공개키 파일이 없다, 공개키가 아니다(개인키를 넣었다), 같은 키가 두 번 들어 있다(서명 키와 같은 것도).

**키가 샜을 때(긴급 폐기).** 1단계 없이 새 개인키를 서명 키 자리에 두고, 샌 키는 검증 키에 넣지 않은 채 다시 띄운다.
인증 서버는 샌 키로 서명한 토큰을 바로 거부하고, 모든 사용자가 다시 로그인한다.
다른 세 서버는 JWKS 를 기억하는 동안 샌 키로 만든 access 토큰을 받을 수 있다. 게임·결제 서버는 최대 5분이고,
인증 서버에 닿지 못해도 마지막으로 받은 지 30분이 지나면 키를 버린다(#274). 게시판 서버는 아직 1시간이다. 그보다 급하면 그 서버들을 다시 띄운다.

**운영 환경의 보안 설정(#19).** `APP_ENVIRONMENT=production` 이면 따로 켜지 않아도 아래가 켜진다(`config/security.py`).
- 세션 쿠키와 CSRF 쿠키(관리자 화면)에 Secure 를 붙인다.
- refresh 쿠키의 Secure(`REFRESH_COOKIE_SECURE`)를 끄면 서버가 뜨지 않는다. `DEBUG` 를 켜도, 메일 서버(`SMTP_HOST`)가 없어도 뜨지 않는다.
- `ALLOWED_HOSTS` 에 실제 도메인을 적는다. 비어 있으면 모든 요청이 400 이다.
  nginx 는 `Host` 를 받은 그대로(도메인) 넘긴다. compose 가 덮는 값(`localhost,127.0.0.1,auth-server`)에 도메인을 더한다. `auth-server` 는 다른 서버가 공개키를 받는 이름이라 빼지 않는다.
- `REFRESH_COOKIE_ALLOWED_ORIGINS` 에 화면을 여는 주소를 https 로 적는다. 비어 있거나 http 가 섞이면 뜨지 않는다.
  개발에서는 적지 않으면 compose 의 nginx 주소(`http://localhost:8080`, `http://127.0.0.1:8080`)다. `PROXY_PORT` 를 바꿨으면 같이 적는다.

**staging(VM 에 올린 운영자용 서버).** `APP_ENVIRONMENT=staging` 도 도메인과 HTTPS 뒤에 있다(바깥에 연 환경, `config/environments.py`).
`.env.example` 은 로컬 개발의 값(`DEBUG=true`, `REFRESH_COOKIE_SECURE=false`)이라 그대로 옮기면 틀린 채로 뜰 수 있어서, 전송의 안전은 운영과 같이 막는다.

| | development | staging | production |
| --- | --- | --- | --- |
| `DEBUG=true` | 된다 | 뜨지 않는다 | 뜨지 않는다 |
| `REFRESH_COOKIE_SECURE=false` | 된다 | 뜨지 않는다 | 뜨지 않는다 |
| `REFRESH_COOKIE_ALLOWED_ORIGINS` | 적지 않으면 compose 의 nginx 주소 | 꼭 적는다. https 만 | 꼭 적는다. https 만 |
| 메일 서버 없이(터미널 메일) | 된다 | 된다 | 뜨지 않는다 |
| 가짜 본인인증(`IDENTITY_PROVIDER=fake`) | 기본 | 기본 | 뜨지 않는다. 기본은 `disabled` |
| 관리자 화면 쿠키의 Secure | 없다 | 없다 | 붙는다 |

`TRUSTED_PROXY_COUNT` 가 1 이상이면 프록시가 넘기는 `X-Forwarded-Proto` 로 "원래 HTTPS 였다"를 안다(`SECURE_PROXY_SSL_HEADER`).
HTTPS 로 넘기기와 HSTS 는 인증 서버가 하지 않는다. 서버 넷 앞의 nginx 가 TLS 와 함께 맡는다(배포 단계에서 켠다).
인증 서버가 넘기면 컨테이너끼리의 HTTP 호출(공개키 받기, 상태 확인)이 301 로 튕긴다. 그래서 `check --deploy` 의 두 경고(W004, W008)는 이유를 적어 꺼 두었다.
CI 가 운영 설정으로 `check --deploy --fail-level WARNING` 을 돌린다. 경고가 하나라도 새로 생기면 실패한다.

관리자 화면은 SSH 터널로 `http://localhost:8000/admin/` 에서 연다. 쿠키가 Secure 여도 브라우저가 `localhost` 와 `127.0.0.1` 은
HTTP 로도 주고받는다(Chromium 으로 로그인까지 확인했다). 다른 주소(서버의 IP 등)로 HTTP 로 열면 쿠키가 버려져 로그인이 되지 않는다.

**DB 계정의 권한(#20).** 운영에서는 루트 `.env` 에 `AUTH_DB_ALLOW_TEST_DB` 를 적지 않는다. 그러면 `auth` 계정에 `CREATEDB` 가 붙지 않는다.
이 값은 볼륨을 처음 만들 때만 읽힌다. 이미 만든 볼륨에서 빼려면 관리 계정으로 `ALTER ROLE auth NOCREATEDB;` 를 한 번 돌린다.

**저장소의 compose 로 띄우면** 아래의 워커와 주기 명령이 저절로 돈다. 워커는 `auth-mail`, `auth-welcome-credits`, 주기 명령은 `auth-cron`(시각은 `docker/cron/auth.crontab`)이다.
PC 에서 직접 띄울 때는 아래의 명령을 손으로 돌린다.

**만료된 토큰 기록 정리.** 발급 기록과 폐기 기록은 토큰이 만료된 뒤에도 테이블에 남는다.
배포 환경에서는 아래 명령을 하루에 한 번 실행한다.

```
uv run python manage.py flushexpiredtokens
```

**오래된 가입 코드 정리.** 가입은 인증된 계정만 만들어 미인증 계정은 더 생기지 않는다(#271).
대신 코드를 받기만 하고 가입을 끝내지 않은 이메일의 행(`SignupCode`)이 남는다. 마지막 발급에서 1시간이 지난 행은
지킬 제한도 쓸 코드도 없어 아래 명령으로 지운다. 명령의 이름은 cron 과 작업 이름을 바꾸지 않으려고 그대로 두었다.
배포 환경에서는 하루에 한 번 실행한다.

```
uv run python manage.py delete_unverified_users
```

**메일 워커.** 메일 서버 설정이 있으면 서버와 함께 항상 떠 있어야 한다. 멈춰 있으면 메일이 발송함에
쌓였다가 5분 뒤에 버려진다. 여러 개 띄워도 된다. 메일 서버와 통신하는 동안 DB 의 연결을 쥐지 않는다.

```
uv run python manage.py send_outgoing_mail
```

**환영 크레딧 워커.** 결제 서버를 함께 띄운다면 서버와 함께 떠 있어야 한다. 멈춰 있어도 잃는 것은 없다. 맡길 일이 쌓였다가 다시 뜨면 나간다.
여러 개 띄워도 된다. `BILLING_SECRET`이 없으면 시작하지 않고 오류로 끝난다.

```
uv run python manage.py send_welcome_credits
```

**두 워커의 상태.** 한 바퀴를 DB 에 닿아 끝낼 때마다 심장박동 파일(`HEARTBEAT_FILE`)의 시각을 바꾼다(#258).
compose 는 이 값을 `/tmp/heartbeat` 로 넣고, 2분 안에 바뀌었으면 `healthy` 로 본다. DB 에 닿지 못하면 워커는 돌지만 `unhealthy` 다.
PC 에서 직접 돌릴 때는 비워 둔다(파일을 쓰지 않는다). 규격은 `docs/observability.md` 의 "워커의 상태"다.

밀려 있는 것은 관리자 화면의 "환영 크레딧"에서 상태를 "맡기기 전"으로 걸러 본다. 시도 횟수와 마지막 오류가 남아 있다.
마지막 오류가 `401`이면 두 서버의 비밀이 다르거나 시계가 5분 넘게 벌어진 것이다. 조회만 된다. 지우면 그 사람이 다시 받을 수 있게 되어 막아 두었다.

**보내지 못한 메일 확인.** 관리자 화면의 "보낼 메일"에서 상태를 "버림"으로 걸러 본다.
받는 사람, 제목, 시도 횟수, 마지막 오류가 남아 있다. 본문은 지워져 있다.
확인이 끝난 기록은 그 화면에서 지운다.

**계정 정지와 풀기.** 사유는 보안 이벤트(관리자 화면의 "보안 이벤트")에 남고 요약 메일에도 실린다. 비밀번호나 이메일 주소 같은 것을 적지 않는다.
정지하면 그 사용자의 토큰이 인증 서버에서 바로, 다른 서버에서 30초 안에 거부된다.

```
uv run python manage.py suspend_account <아이디> --reason "<사유>"
uv run python manage.py restore_account <아이디> --reason "<사유>"
```

**보안 이벤트 요약.** `auth-server/.env`의 `SECURITY_DIGEST_TO`에 운영자의 주소를 넣고, 아래 명령을
한 시간에 한 번 실행한다. 새 이벤트가 있을 때만 메일이 간다. 30일이 지난 이벤트도 이때 지운다.
전체 기록은 관리자 화면의 "보안 이벤트"에 있다. 조회만 된다.

```
uv run python manage.py send_security_digest
```

**프록시 뒤에 둘 때.** `TRUSTED_PROXY_COUNT`를 서버 앞에 선 프록시의 수로 맞춘다. 맞추지 않으면
모든 요청이 프록시의 IP로 보여 IP별 제한이 모든 사용자를 함께 막는다.
저장소의 compose 로 띄우면 앞에 nginx 가 하나 있고 compose 가 `1`을 넘긴다. 관리자 화면은 nginx 가 막으므로 `127.0.0.1:8000`에 직접 붙어서 연다.

**Redis 장애.** 로그에 `시도 횟수를 셀 수 없어 제한 없이 통과시켰다`가 찍히면 시도 횟수 제한과
IP 차단이 꺼져 있는 상태다. 로그인은 계속 된다. 그동안에는 보안 이벤트도 남지 않는다.
연달아 실패하면 `Redis 를 쓸 수 없어 차단기를 열었다`가 찍히고, 그 뒤로는 요청마다 남지 않는다.
Redis가 계속 죽어 있으면 30초마다(시험이 실패할 때마다) 이 줄이 다시 찍힌다.
`Redis 가 돌아와 차단기를 닫았다`가 찍히면 제한이 다시 켜진 것이다. 줄은 프로세스(워커)마다 따로 찍힌다.

**아직 하지 않은 것.** 할 일은 [GitHub Issues](https://github.com/epqlffltm/ai-trpg/issues)에서 관리한다.
이 문서에 목록을 따로 두지 않는다. 두 곳에 적으면 한쪽이 낡는다.

| 묶음 | 이슈 |
| --- | --- |
| 배포 전에 해야 하는 것 | 없음 |
| 규모가 커지면 할 것 | [#25](https://github.com/epqlffltm/ai-trpg/issues/25) 로그 수집과 대시보드 |
| 프론트에서 할 것 | [#30](https://github.com/epqlffltm/ai-trpg/issues/30) refresh를 한 번에 하나만, [#31](https://github.com/epqlffltm/ai-trpg/issues/31) 비밀번호 재설정 화면 |

인증 서버의 것만 보려면 [`auth-server` 라벨](https://github.com/epqlffltm/ai-trpg/issues?q=is%3Aissue+is%3Aopen+label%3Aauth-server)로 거른다.

## 자주 겪는 문제

**로컬에서 로그인은 되는데 `/refresh`가 항상 `401`이다**

`auth-server/.env`에 `REFRESH_COOKIE_SECURE=false`가 없는 경우다. 기본값은 HTTPS에서만
쿠키를 보내는 것이라, HTTP로 도는 로컬에서는 브라우저가 쿠키를 싣지 않는다.

**내 PC에서 로그인이 계속 `401`이거나 `429`다**

개발 중에 틀린 비밀번호나 예약어 아이디로 여러 번 시험하다가 내 IP가 막힌 경우다.
기다리거나, 개발용 Redis에서 횟수를 지운다.

```
docker compose exec redis redis-cli --scan --pattern "auth:attempts:*"
docker compose exec redis redis-cli del <지울 키>
```

**인증 코드 메일이 오지 않는다**

메일 서버 설정(`SMTP_HOST`)이 없으면 메일은 나가지 않고 `runserver`를 띄운 터미널에 출력된다.

설정이 있는데 오지 않으면 워커(`send_outgoing_mail`)가 떠 있는지 본다. 서버는 발송함에 적기만 한다.
워커가 떠 있으면 그 터미널에 `다시 시도 예정`이나 `버림`이 찍히는지, 관리자 화면의 "보낼 메일"에
어떤 오류가 적혀 있는지 본다. Gmail에서 `Username and Password not accepted`가 나오면
계정 비밀번호를 넣은 것이다. 앱 비밀번호를 넣어야 한다.

**Windows PowerShell 5.1에서 한글이 든 요청이 `400`으로 거부된다**

5.1의 `Invoke-RestMethod`는 문자열 본문을 UTF-8로 보내지 않아 한글이 깨져서 도착한다.
본문을 바이트로 바꿔 넘긴다. 성공 응답의 한글이 깨져 보이는 것은 5.1의 화면 표시 문제이고 서버 문제가 아니다.

```
$body = [System.Text.Encoding]::UTF8.GetBytes('{"nickname":"한글"}')
Invoke-RestMethod $url -Method Post -ContentType 'application/json' -Body $body
```
